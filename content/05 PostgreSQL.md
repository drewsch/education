## 1. Что такое PostgreSQL и архитектура процессов

PostgreSQL — реляционная база данных. Данные хранятся на диске в таблицах (строки и столбцы), таблицы связываются через ключи, запросы пишутся на SQL, транзакции соответствуют ACID.

Главные отличия от Redis:

|            | PostgreSQL                                  | Redis                          |
| ---------- | ------------------------------------------- | ------------------------------ |
| Хранение   | Диск + кэш страниц в памяти                 | Оперативная память             |
| Скорость   | Медленнее (сотни мкс – мс на запрос)        | Десятки мкс на команду         |
| Структура  | Строгая схема, таблицы                      | Ключ-значение, гибко           |
| Запросы    | SQL, JOIN, агрегации, оконные функции       | Простые операции с ключами     |
| Транзакции | ACID с полным rollback                      | MULTI/EXEC без rollback        |

### Модель «процесс на соединение»

Это первое, что надо понимать для нагрузочного тестирования, потому что отсюда вытекает половина проблем с соединениями.

```
Клиент 1 ──TCP──┐
Клиент 2 ──TCP──┼──> postmaster (главный процесс, слушает порт 5432)
Клиент 3 ──TCP──┘          │
                           │ fork() на каждое новое соединение
                           ▼
                 backend-процесс 1, backend-процесс 2, backend-процесс 3 ...

Фоновые процессы:
  checkpointer        — периодически сбрасывает грязные страницы на диск
  background writer   — понемногу пишет грязные страницы заранее
  walwriter           — сбрасывает WAL-буферы на диск
  autovacuum launcher — запускает autovacuum workers
  walsender           — отправляет WAL репликам (по одному на реплику)
  stats / logger / archiver
```

Аналогия с Java: в Tomcat один поток на запрос, а в PostgreSQL **один процесс ОС на соединение**. Процесс тяжелее потока:

- каждый backend занимает несколько МБ собственной памяти (плюс `work_mem` на каждую операцию сортировки/хэша);
- переключение между сотнями процессов — это context switches на уровне ядра;
- 1000 соединений = 1000 процессов, которые конкурируют за CPU и за общие блокировки (LWLock).

Поэтому у PostgreSQL обычно `max_connections` 100–500, а тысячи клиентских соединений «сжимают» через пулер (PgBouncer). Подробно — в разделе 20.

**Пример расчёта:** 800 соединений × 10 МБ собственной памяти процесса = ~8 ГБ только на процессы, ещё до `work_mem`. Если в каждом из 800 одновременно идёт сортировка с `work_mem = 64MB`, то в худшем случае ещё 800 × 64 МБ = 51 ГБ. Это и есть причина, по которой большой `work_mem` вместе с большим числом соединений приводит к OOM.

## 2. Как данные лежат на диске

### 2.1 Файлы

Каждая таблица и каждый индекс — это отдельный набор файлов в каталоге данных:

```
$PGDATA/base/<oid базы>/<relfilenode>        ← основной файл (main fork)
$PGDATA/base/<oid базы>/<relfilenode>.1      ← продолжение, если файл > 1 ГБ
$PGDATA/base/<oid базы>/<relfilenode>_fsm    ← Free Space Map: где есть свободное место
$PGDATA/base/<oid базы>/<relfilenode>_vm     ← Visibility Map: какие страницы «чистые»
```

```sql
-- Где физически лежит таблица
SELECT pg_relation_filepath('orders');
-- base/16384/24576

-- Сколько страниц и строк (оценка, обновляется VACUUM/ANALYZE)
SELECT relname, relpages, reltuples FROM pg_class WHERE relname = 'orders';
```

Файл разбит на сегменты по 1 ГБ, а каждый сегмент — на **страницы (блоки) по 8 КБ** (параметр сборки `BLCKSZ = 8192`).

### 2.2 Страница 8 КБ — главная единица ввода-вывода

PostgreSQL **никогда не читает с диска отдельную строку**. Он читает целую страницу 8 КБ, кладёт её в shared_buffers и уже там находит нужную строку. Даже `SELECT ... WHERE id = 1`, которому нужна одна строка в 60 байт, прочитает минимум одну страницу индекса (на практике 3–4 страницы — по уровням B-дерева) и одну страницу таблицы.

Устройство страницы:

```
 смещение 0                                                         8192
 ┌──────────────┬──────────────────────┬───────────────┬────────────────┬─────────┐
 │ PageHeader   │ Line pointers (ItemId)│  свободное    │   Кортежи      │ Special │
 │  24 байта    │  по 4 байта каждый    │  место        │  (строки)      │ (для    │
 │              │  растут ВПРАВО →      │               │  растут ← ВЛЕВО│ индексов)│
 └──────────────┴──────────────────────┴───────────────┴────────────────┴─────────┘
                                     ↑ pd_lower       ↑ pd_upper
```

**PageHeader (24 байта):**

| Поле                 | Размер | Смысл                                                         |
| -------------------- | ------ | ------------------------------------------------------------- |
| `pd_lsn`             | 8      | LSN последней записи WAL, изменившей страницу (для recovery)  |
| `pd_checksum`        | 2      | Контрольная сумма (если включены data checksums)              |
| `pd_flags`           | 2      | Флаги (например, «на странице есть свободные line pointers»)  |
| `pd_lower`           | 2      | Конец массива line pointers = начало свободного места         |
| `pd_upper`           | 2      | Начало области кортежей = конец свободного места              |
| `pd_special`         | 2      | Начало special-области (у таблиц пусто, у индексов — данные)  |
| `pd_pagesize_version`| 2      | Размер страницы и версия формата                              |
| `pd_prune_xid`       | 4      | Самый старый XID, который можно «подчистить» на странице      |

**Line pointer (ItemId, 4 байта)** — указатель «смещение + длина + статус» на кортеж внутри страницы. Статусы: `NORMAL`, `REDIRECT` (используется HOT, см. ниже), `DEAD`, `UNUSED`.

**Зачем указатели, а не прямые смещения?** Потому что внешние ссылки (из индекса) указывают на номер line pointer, а не на байтовое смещение. Тогда кортежи внутри страницы можно двигать при уплотнении, и индекс переписывать не надо.

### 2.3 Адрес строки — ctid

Физический адрес строки — `ctid = (номер страницы, номер line pointer)`.

```sql
SELECT ctid, id, status FROM orders LIMIT 3;
--  ctid  | id | status
-- (0,1)  |  1 | new
-- (0,2)  |  2 | new
-- (0,3)  |  3 | paid

UPDATE orders SET status = 'closed' WHERE id = 1;
SELECT ctid, id FROM orders WHERE id = 1;
-- (0,4)   ← новая версия строки получила НОВЫЙ ctid (MVCC, раздел 14)
```

Индекс хранит пары `ключ → ctid`. Index Scan = нашёл ключ в индексе → взял ctid → прочитал страницу таблицы по номеру → взял строку по номеру указателя.

### 2.4 Строка (кортеж) изнутри

```
┌────────────────────────── HeapTupleHeader (23 байта → выравнивается до 24) ─────────────────┐
│ t_xmin (4) │ t_xmax (4) │ t_cid (4) │ t_ctid (6) │ t_infomask2 (2) │ t_infomask (2) │ t_hoff (1)│
└─────────────────────────────────────────────────────────────────────────────────────────────┘
│ NULL-битмап (если есть NULL-ы, по 1 биту на колонку) │ данные колонок с выравниванием │
```

- `t_xmin` — XID транзакции, создавшей версию строки.
- `t_xmax` — XID транзакции, удалившей/обновившей версию (0 — строка жива).
- `t_ctid` — ссылка на следующую версию строки (цепочка версий после UPDATE).
- `t_infomask` — hint bits: «xmin закоммичен», «xmax откатился» и т.п. Нужны, чтобы не ходить каждый раз в журнал статусов транзакций (pg_xact).

**Выравнивание.** Колонки выравниваются по своему типу: `bigint`, `timestamp`, `double` — по 8 байт, `int` — по 4, `smallint` — по 2. Порядок колонок влияет на размер строки.

```
Плохой порядок:   smallint(2) + [6 пусто] + bigint(8) + smallint(2) + [6 пусто] + bigint(8) = 32 байта
Хороший порядок:  bigint(8) + bigint(8) + smallint(2) + smallint(2)                           = 20 байт
```

Экономия 12 байт на строку × 100 млн строк = 1,2 ГБ на диске и в кэше.

### 2.5 Пример расчёта: сколько строк влезает в страницу

Таблица `orders(id bigint, user_id bigint, amount numeric(12,2), status text, created_at timestamptz)`, средний `status` — 6 символов.

```
Заголовок кортежа:          24 байта (23 + выравнивание)
id bigint:                   8
user_id bigint:              8
amount numeric(12,2):       ~8  (numeric переменной длины: заголовок + цифры)
status text 'closed':        7  (1 байт короткого заголовка varlena + 6 символов)
выравнивание до 8 под ts:    1
created_at timestamptz:      8
───────────────────────────────
Кортеж:                     ~64 байта
Line pointer:                4
Итого на строку:            ~68 байт

Полезное место страницы: 8192 − 24 (заголовок) = 8168 байт
Строк на страницу:      8168 / 68 ≈ 120 строк
Страниц на 10 млн строк: 10 000 000 / 120 ≈ 83 334 страницы × 8 КБ ≈ 650 МБ
```

Это число — основа для оценки: Seq Scan этой таблицы прочитает ~83 тыс. страниц. С диска на скорости 500 МБ/с это ~1,3 с, из памяти — десятки–сотни мс.

### 2.6 Посмотреть страницу руками — pageinspect

```sql
CREATE EXTENSION pageinspect;

-- Заголовок страницы 0
SELECT * FROM page_header(get_raw_page('orders', 0));
--     lsn     | checksum | flags | lower | upper | special | pagesize | version | prune_xid
-- 0/1A2B3C40  |        0 |     0 |   508 |  1032 |    8192 |     8192 |       4 |         0
-- lower=508 → (508−24)/4 = 121 line pointer, upper−lower = 524 байта свободно

-- Кортежи страницы
SELECT lp, lp_off, lp_len, t_xmin, t_xmax, t_ctid
FROM heap_page_items(get_raw_page('orders', 0)) LIMIT 5;
```

### 2.7 TOAST — когда строка не помещается

Строка должна помещаться в страницу. Если кортеж больше ~2 КБ (порог `TOAST_TUPLE_THRESHOLD` ≈ 2032 байта, примерно 1/4 страницы), PostgreSQL:

1. пытается **сжать** длинные значения (pglz или lz4 с PG14: `ALTER TABLE t ALTER COLUMN data SET COMPRESSION lz4`);
2. если всё равно большое — **выносит** значение в отдельную TOAST-таблицу кусками по ~2 КБ, а в строке оставляет указатель 18 байт.

Стратегии колонки: `PLAIN` (нельзя ни сжимать, ни выносить), `MAIN` (сжимать, выносить в последнюю очередь), `EXTERNAL` (выносить без сжатия — быстрый `substring`), `EXTENDED` (по умолчанию: сжимать и выносить).

**Почему это важно для производительности:**

- `SELECT *` по таблице с большим `jsonb` вытаскивает и распаковывает TOAST, даже если поле не нужно. Выбирай конкретные колонки.
- Обновление строки с TOAST-значением, если TOAST-колонка не менялась, переиспользует старые TOAST-куски — это дёшево. Если `jsonb` меняется целиком (а в PostgreSQL `jsonb` всегда переписывается целиком при `jsonb_set`), каждый UPDATE пишет новый TOAST.
- В `EXPLAIN (ANALYZE, BUFFERS)` чтение TOAST видно как дополнительные buffers, а размер таблицы — через `pg_total_relation_size` (включает TOAST) против `pg_relation_size` (только основной файл).

```sql
SELECT pg_size_pretty(pg_relation_size('orders'))       AS heap,
       pg_size_pretty(pg_total_relation_size('orders')
                      - pg_relation_size('orders')
                      - pg_indexes_size('orders'))       AS toast,
       pg_size_pretty(pg_indexes_size('orders'))         AS indexes;
```

### 2.8 Fillfactor и HOT-обновления

**Fillfactor** — какой процент страницы заполнять при INSERT. Для таблиц по умолчанию 100 %, для B-tree индексов 90 %.

**HOT (Heap-Only Tuple) update** — оптимизация UPDATE:

```
Обычный UPDATE:
  1. новая версия строки пишется в любую страницу со свободным местом
  2. в КАЖДОМ индексе таблицы появляется новая запись → ctid новой версии
  → 5 индексов = 5 дополнительных записей + WAL на каждую

HOT UPDATE (условия: не изменилась ни одна индексируемая колонка
            И на той же странице есть свободное место):
  1. новая версия пишется на ТУ ЖЕ страницу
  2. старая версия получает ссылку t_ctid на новую
  3. индексы НЕ трогаются — они продолжают указывать на старый line pointer,
     а он через REDIRECT ведёт к новой версии
  → нет записей в индексы, меньше WAL, меньше bloat индексов
```

Чтобы на странице оставалось место для HOT, для часто обновляемых таблиц ставят fillfactor 70–90:

```sql
ALTER TABLE orders SET (fillfactor = 80);
-- применяется к новым страницам; для существующих — VACUUM FULL / pg_repack

-- Доля HOT-обновлений
SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct
FROM pg_stat_user_tables ORDER BY n_tup_upd DESC LIMIT 20;
-- hot_pct низкий на update-heavy таблице → либо обновляется индексированная колонка,
-- либо нет места на странице (снизить fillfactor)
```

Плюсы и минусы низкого fillfactor:

| Плюс                                                  | Минус                                              |
| ----------------------------------------------------- | -------------------------------------------------- |
| Больше HOT-обновлений → индексы не растут             | Таблица больше на диске (fillfactor 80 → +25 %)    |
| Строки остаются на своей странице → корреляция живёт  | Seq Scan читает больше страниц                     |
| Меньше WAL на UPDATE                                  | Меньше строк в одном буфере → ниже плотность кэша  |

### 2.9 Visibility Map и Free Space Map

**Visibility Map (VM)** — 2 бита на каждую страницу таблицы:

- `all-visible` — все строки на странице видимы всем транзакциям (нет мёртвых и незакоммиченных версий);
- `all-frozen` — все строки заморожены (не нужно трогать при борьбе с wraparound).

Зачем:

1. **Index Only Scan** может не ходить в таблицу только для страниц с `all-visible`. Для остальных он вынужден проверить видимость в heap — в плане это `Heap Fetches: N`. Если `Heap Fetches` близко к числу строк — Index Only Scan фактически стал обычным Index Scan. Лечится VACUUM (он выставляет биты).
2. VACUUM пропускает `all-visible` страницы, поэтому регулярный VACUUM дешёвый.

**Free Space Map (FSM)** — для каждой страницы примерно сколько там свободного места. INSERT и не-HOT UPDATE по ней ищут, куда положить строку.

## 3. Буферы и кэш

### 3.1 Два уровня кэша

```
Запрос → shared_buffers (кэш PostgreSQL)
             │ промах
             ▼
         read() системный вызов → page cache ОС (кэш ядра Linux)
             │ промах
             ▼
         диск (SSD/NVMe/HDD)
```

PostgreSQL работает через обычные `read()/write()`, а не через O_DIRECT. Поэтому одна и та же страница может лежать **дважды**: в shared_buffers и в page cache ОС (double buffering). Отсюда правило «shared_buffers ≈ 25 % RAM, остальное отдаём ОС под page cache»: page cache тоже работает на PostgreSQL, и `effective_cache_size` (≈75 % RAM) сообщает планировщику суммарный объём обоих кэшей.

**Важный нюанс для диагностики:** `shared read` в EXPLAIN и `blks_read` в статистике означают «не нашли в shared_buffers и попросили у ОС». Это **не обязательно диск** — страница могла прийти из page cache за ~5–20 мкс. Отличить можно только по времени:

```sql
SET track_io_timing = on;   -- накладные расходы малы на современном железе
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
--   Buffers: shared hit=120 read=4500
--   I/O Timings: shared read=3.2      ← 4500 страниц за 3,2 мс = из page cache
--   I/O Timings: shared read=2850.0   ← 4500 страниц за 2,8 с = с диска
```

Проверить утилитой `pg_test_timing`, что таймер дешёвый, перед включением на проде.

### 3.2 Устройство shared_buffers

```
shared_buffers = массив слотов по 8 КБ
  + массив Buffer Descriptors (на каждый слот: какая страница, pin count,
    usage_count, флаги dirty/valid, lock)
  + Buffer Mapping Table — хэш-таблица (relfilenode, fork, block) → номер слота,
    разбита на 128 партиций, каждая под своим LWLock
```

Как запрос получает страницу:

1. Считает хэш от адреса страницы, берёт LWLock партиции `BufferMapping`, ищет в хэш-таблице.
2. Нашёл — **hit**: увеличивает `pin count` (страница не может быть вытеснена, пока её используют), `usage_count++` (максимум 5).
3. Не нашёл — **miss**: нужен свободный слот → алгоритм вытеснения **clock-sweep**.

**Clock-sweep** (аналог «второго шанса»):

```
Стрелка «часов» идёт по кругу по всем слотам:
  слот закреплён (pin > 0)?      → пропустить
  usage_count > 0?               → usage_count−−, идти дальше
  usage_count == 0               → жертва найдена
     страница грязная (dirty)?   → сначала записать её на диск (это делает backend сам — плохо!)
     загрузить новую страницу в слот
```

Часто используемые страницы (корни и верхние уровни индексов) постоянно имеют высокий usage_count и почти никогда не вытесняются.

### 3.3 Кто пишет грязные страницы

| Кто                  | Когда                                        | Хорошо/плохо                                          |
| -------------------- | -------------------------------------------- | ----------------------------------------------------- |
| checkpointer         | на checkpoint — все грязные страницы         | нормально, это его работа                             |
| background writer    | заранее, понемногу, чтобы были чистые слоты  | нормально                                             |
| сам backend          | когда clock-sweep выбрал грязную жертву      | **плохо**: запрос пользователя ждёт записи на диск    |

```sql
-- PG 16+: подробная статистика I/O по типам процессов
SELECT backend_type, object, context, reads, writes, extends, evictions, fsyncs
FROM pg_stat_io WHERE writes > 0 OR reads > 0 ORDER BY writes DESC;
-- много writes у backend_type = 'client backend' в context = 'normal'
--   → backend-ы сами вытесняют грязные страницы → shared_buffers мал или bgwriter не успевает

-- До PG 17: pg_stat_bgwriter (buffers_backend, buffers_clean, buffers_checkpoint)
-- В PG 17 статистика checkpoint вынесена в pg_stat_checkpointer
```

Настройки bgwriter: `bgwriter_delay` (200 мс), `bgwriter_lru_maxpages` (100), `bgwriter_lru_multiplier` (2.0). Если backend-ы много пишут сами — увеличить `bgwriter_lru_maxpages` и `bgwriter_lru_multiplier`.

### 3.4 Ring buffers — защита кэша от больших сканов

Если бы Seq Scan таблицы на 100 ГБ проходил через общий кэш, он вытеснил бы всё полезное. Поэтому:

- Seq Scan таблицы больше 1/4 shared_buffers использует **кольцевой буфер 256 КБ** (32 страницы) — читает через маленькое кольцо и не засоряет кэш;
- VACUUM — своё кольцо (с PG16 размер задаётся `vacuum_buffer_usage_limit`);
- массовая запись (COPY, CREATE TABLE AS) — кольцо 16 МБ.

Следствие: после большого Seq Scan таблица **не оказывается в shared_buffers**, но вполне может осесть в page cache ОС. Повторный Seq Scan покажет `read`, но быстрый.

### 3.5 Что сейчас лежит в кэше — pg_buffercache

```sql
CREATE EXTENSION pg_buffercache;

SELECT c.relname,
       count(*)                                      AS buffers,
       pg_size_pretty(count(*) * 8192)               AS cached,
       round(100.0 * count(*) /
             (SELECT setting::int FROM pg_settings WHERE name = 'shared_buffers'), 1)
                                                     AS pct_of_cache,
       round(avg(b.usagecount), 2)                   AS avg_usage,
       sum(CASE WHEN b.isdirty THEN 1 ELSE 0 END)    AS dirty
FROM pg_buffercache b
JOIN pg_class c ON b.relfilenode = pg_relation_filenode(c.oid)
WHERE b.reldatabase = (SELECT oid FROM pg_database WHERE datname = current_database())
GROUP BY c.relname
ORDER BY buffers DESC LIMIT 20;
```

Как читать: если горячая таблица занимает 2 % кэша, а какая-то холодная архивная — 40 %, значит что-то (отчёт, выгрузка) регулярно вытесняет рабочие данные.

**Прогрев после рестарта:** `pg_prewarm('orders')` загружает таблицу в кэш; расширение с `pg_prewarm.autoprewarm = on` само сохраняет список страниц и восстанавливает его после рестарта. Для НТ важно: первый прогон после рестарта БД всегда хуже — либо прогревай, либо отбрасывай первые минуты.

### 3.6 Cache Hit Ratio

```sql
-- По базе целиком
SELECT datname,
       round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 2) AS hit_pct
FROM pg_stat_database WHERE datname = current_database();

-- По таблицам (heap и индексы отдельно)
SELECT relname,
       round(100.0 * heap_blks_hit / nullif(heap_blks_hit + heap_blks_read, 0), 2) AS heap_hit_pct,
       round(100.0 * idx_blks_hit  / nullif(idx_blks_hit  + idx_blks_read,  0), 2) AS idx_hit_pct
FROM pg_statio_user_tables
ORDER BY heap_blks_read DESC LIMIT 20;
```

**Норма для OLTP: 98–99 %+.** Ниже 95 % — рабочий набор не помещается в shared_buffers. Но смотри на это в паре с I/O timings (см. 3.1): 90 % hit ratio, где «промахи» обслуживает page cache ОС, может быть вполне нормальным.

**Сбросить статистику перед тестом**, иначе считаешь среднее за месяц: `SELECT pg_stat_reset();` (по базе) или сравнивай снимки «до» и «после» теста.

### 3.7 Остальная память

| Параметр                 | Что это                                                    | Сколько выделяется                       |
| ------------------------ | ---------------------------------------------------------- | ---------------------------------------- |
| `shared_buffers`         | общий кэш страниц                                          | один раз на сервер                       |
| `wal_buffers`            | буфер WAL до записи на диск (по умолчанию 1/32 shared_buffers, до 16 МБ) | один раз                   |
| `work_mem`               | на **одну** операцию Sort/Hash в одном запросе             | × операций × параллельных воркеров × соединений |
| `hash_mem_multiplier`    | хэш-операциям можно `work_mem × 2.0` (по умолчанию с PG15) | множитель                                |
| `maintenance_work_mem`   | VACUUM, CREATE INDEX, ALTER TABLE ADD FK                   | на операцию обслуживания                 |
| `autovacuum_work_mem`    | память autovacuum worker (−1 = брать maintenance_work_mem) | × autovacuum_max_workers                 |
| `temp_buffers`           | временные таблицы сессии                                   | на сессию                                |
| `effective_cache_size`   | **не выделяется**, только подсказка планировщику           | —                                        |

**huge_pages:** при shared_buffers в десятки ГБ таблица страниц процессов становится огромной (каждый из сотен backend-ов отображает весь shared_buffers страницами по 4 КБ). `huge_pages = on` (страницы 2 МБ) уменьшает расход памяти на page tables и промахи TLB. ## 4. Ключи

### PRIMARY KEY

* Уникальный идентификатор строки
* Не может быть NULL
* Автоматически создаёт уникальный B-tree индекс
* Обычно поле `id` типа `bigint GENERATED ALWAYS AS IDENTITY` (или `bigserial`) либо UUID

```sql
CREATE TABLE users (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name  varchar(100),
    email varchar(100)
);
```

### FOREIGN KEY

* Ссылка на PRIMARY KEY (или UNIQUE) другой таблицы
* Гарантирует ссылочную целостность
* **Не создаёт индекс автоматически** — нужно создавать вручную
* Может быть NULL

```sql
CREATE TABLE orders (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id bigint REFERENCES users(id),
    amount  numeric(12,2),
    status  varchar(50)
);
CREATE INDEX idx_orders_user_id ON orders(user_id);
```

**Почему индекс на FK обязателен под нагрузкой.** При `DELETE FROM users WHERE id = 5` PostgreSQL обязан проверить, что в `orders` нет строк с `user_id = 5`. Без индекса это Seq Scan всей `orders` на **каждое** удаление пользователя. Плюс JOIN `users ⋈ orders` по `user_id` без индекса не сможет использовать Nested Loop с Index Scan.

### В одной таблице может быть и PK, и FK

```sql
CREATE TABLE order_items (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id   bigint REFERENCES orders(id),
    product_id bigint REFERENCES products(id),
    quantity   int,
    price      numeric(12,2)
);
```

|              | PRIMARY KEY         | FOREIGN KEY             |
| ------------ | ------------------- | ----------------------- |
| Уникальность | Да                  | Нет                     |
| NOT NULL     | Да                  | Нет (может быть NULL)   |
| Индекс       | Автоматически       | Нужно создавать вручную |
| Ограничение  | Уникальность строки | Ссылочная целостность   |

### UUID vs bigint как ключ — влияние на производительность

| Тип ключа      | Размер | Порядок вставки           | Последствия                                                                 |
| -------------- | ------ | ------------------------- | --------------------------------------------------------------------------- |
| `bigint` identity | 8 байт | строго возрастающий     | вставка всегда в правый лист B-tree, горячая страница в кэше, корреляция ≈ 1 |
| UUIDv4 (случайный) | 16 байт | случайный               | вставка в случайный лист → page split, индекс на 30–50 % раздут, рабочий набор индекса = весь индекс, корреляция ≈ 0 |
| UUIDv7 (время + случайность) | 16 байт | почти возрастающий | поведение близко к bigint, при этом глобально уникален. Функция `uuidv7()` встроена с PostgreSQL 18 |

**Как это проявляется на НТ:** на таблице 100 млн строк с UUIDv4 PK каждая вставка трогает случайную страницу индекса. Если индекс 6 ГБ, а shared_buffers 4 ГБ — значительная часть вставок вызывает чтение с диска и вытеснение грязных страниц. С bigint/UUIDv7 вставки трогают одну «правую» страницу, которая всегда в кэше.

## 5. Индексы

### 5.1 Зачем и чем платим

Без индекса — **Seq Scan**: чтение всех страниц таблицы. С индексом — **Index Scan**: спуск по дереву к нужным ключам.

Цена индексов:

- каждый INSERT пишет во **все** индексы таблицы; каждый не-HOT UPDATE — тоже во все;
- каждая запись в индекс → WAL → больше нагрузки на диск и репликацию;
- индексы занимают место в shared_buffers, вытесняя данные;
- лишние индексы мешают HOT (если индексирована часто меняющаяся колонка).

**Правило:** 10 индексов на таблице с 5000 INSERT/с = 50 000 вставок в индексы в секунду.

### 5.2 Как устроен B-tree

```
                        [корень: 1000 | 5000]                        ← уровень 2
                 ┌──────────────┼──────────────────┐
         [100 | 500]        [2000 | 3500]        [7000 | 9000]       ← уровень 1 (внутренние)
        ┌───┼───┐           ┌───┼───┐            ┌───┼───┐
      [листья: ключ → ctid, связаны двусвязным списком ←→]           ← уровень 0
```

- Узел дерева = страница 8 КБ. В страницу помещаются сотни ключей (bigint-ключ + ctid ≈ 16 байт + 4 на указатель → ~400 ключей на страницу).
- Глубина дерева: 400³ = 64 млн, 400⁴ = 25 млрд. **Индекс на 100 млн строк — 4 уровня**, то есть поиск по ключу = 4 чтения страниц индекса + 1 страница таблицы.
- Листья связаны в список → диапазонный запрос `BETWEEN` спускается один раз и дальше идёт по листьям.
- Верхние уровни всегда в кэше (высокий usage_count), реально с диска читаются только листья.

**Дедупликация (PG13+):** повторяющиеся ключи хранятся один раз со списком ctid — индекс по `status` с 5 значениями на 100 млн строк в разы меньше, чем раньше.

**Page split:** если вставка попадает в полный лист, он делится пополам → индекс растёт, каждая страница заполнена на ~50 %. Отсюда раздутие индексов на случайных ключах (UUIDv4).

### 5.3 Виды индексов

**B-tree** — по умолчанию. Операторы: `=`, `<`, `>`, `<=`, `>=`, `BETWEEN`, `IN`, `= ANY(array)`, `IS NULL`, `LIKE 'abc%'` (при C-collation или с `text_pattern_ops`). Отдаёт данные в отсортированном порядке → может обслужить `ORDER BY` и `MIN/MAX` без сортировки.

```sql
CREATE INDEX idx_orders_status ON orders(status);
```

**Hash** — только `=`. С PG10 журналируется и безопасен. Меньше B-tree для длинных ключей (хранит 4-байтовый хэш), но не умеет диапазоны, сортировку, уникальность. Используется редко.

```sql
CREATE INDEX idx_users_email_hash ON users USING HASH (email);
```

**GIN (Generalized Inverted Index)** — «обратный» индекс: для каждого элемента (ключа JSON, элемента массива, лексемы) хранит список строк, где он встречается. Для `jsonb`, массивов, полнотекстового поиска, триграмм (`pg_trgm`).

- Плюс: быстрый поиск «содержит элемент».
- Минус: дорогая вставка (одна строка с 50 ключами JSON → 50 записей в индексе). Смягчается механизмом **fastupdate**: новые записи копятся в pending list и сливаются пачкой — но тогда запросы сканируют pending list, а слияние даёт пики latency. Размер списка — `gin_pending_list_limit` (4 МБ).

```sql
CREATE INDEX idx_orders_data ON orders USING GIN (data);
SELECT * FROM orders WHERE data @> '{"status": "active"}';
```

**GiST** — обобщённое дерево для геометрии, диапазонов (`tsrange`), ближайших соседей (`ORDER BY point <-> point`), exclusion constraints («бронирования не пересекаются»).

**SP-GiST** — для неравномерных пространств (префиксные деревья, IP-адреса, quadtree).

**BRIN (Block Range Index)** — для каждого диапазона из N страниц (по умолчанию 128) хранит только `min` и `max`. Индекс на 1 ТБ таблицу весит мегабайты. **Работает только при корреляции ≈ 1** (раздел 6): если `created_at` растёт вместе с физическим порядком строк, BRIN отсекает все диапазоны, где `max < нужной даты`. При корреляции ≈ 0 каждый диапазон содержит весь спектр дат → BRIN бесполезен.

```sql
CREATE INDEX idx_events_created ON events USING BRIN (created_at) WITH (pages_per_range = 32);
```

**Составной индекс** — на несколько колонок. Отсортирован по первой колонке, внутри неё по второй и т.д. (как телефонный справочник: фамилия, потом имя).

```sql
CREATE INDEX idx_orders_user_status ON orders(user_id, status);

-- Использует индекс эффективно (есть первая колонка):
SELECT * FROM orders WHERE user_id = 123 AND status = 'active';
SELECT * FROM orders WHERE user_id = 123;
SELECT * FROM orders WHERE user_id = 123 ORDER BY status;

-- Без первой колонки:
SELECT * FROM orders WHERE status = 'active';
-- до PG18: индекс по (user_id, status) практически не используется
-- PG18+: B-tree skip scan — индекс может использоваться, если у user_id мало
--        различных значений (планировщик «перепрыгивает» по значениям первой колонки).
--        При миллионе разных user_id выгоды не будет.
```

**Порядок колонок в составном индексе:**

1. Сначала колонки с условием равенства (`=`), потом колонка с диапазоном (`>`, `BETWEEN`) или сортировкой.
2. `WHERE user_id = 5 AND created_at > now() - interval '1 day'` → индекс `(user_id, created_at)`, а не `(created_at, user_id)`: во втором случае диапазон по `created_at` идёт первым, и `user_id` проверяется для каждой записи диапазона.

**Частичный индекс** — индексирует только строки, удовлетворяющие условию. Маленький, всегда в кэше.

```sql
CREATE INDEX idx_orders_pending ON orders(created_at) WHERE status = 'pending';
-- 100 млн заказов, из них 50 тыс. pending → индекс в 2000 раз меньше обычного
-- Используется ТОЛЬКО если WHERE запроса логически включает условие индекса:
SELECT * FROM orders WHERE status = 'pending' AND created_at < now() - interval '1 hour';  -- да
SELECT * FROM orders WHERE status = $1 AND ...;  -- generic plan: нет! (см. раздел 13)
```

**Покрывающий индекс (INCLUDE)** — дополнительные колонки хранятся только в листьях, не участвуют в поиске, но позволяют Index Only Scan.

```sql
CREATE INDEX idx_orders_user_cover ON orders(user_id) INCLUDE (status, amount);
SELECT status, amount FROM orders WHERE user_id = 123;  -- Index Only Scan
```

**Индекс по выражению** — индексирует результат функции.

```sql
CREATE INDEX idx_users_email_lower ON users (lower(email));
SELECT * FROM users WHERE lower(email) = 'a@b.ru';  -- использует
SELECT * FROM users WHERE email = 'a@b.ru';         -- НЕ использует этот индекс
```

Функция обязана быть `IMMUTABLE` (раздел 11.6). У индекса по выражению появляется своя статистика — после `ANALYZE` планировщик знает распределение `lower(email)`.

**Уникальный индекс** — `CREATE UNIQUE INDEX`, в том числе частичный: «один активный договор на клиента»:

```sql
CREATE UNIQUE INDEX one_active_contract ON contracts(client_id) WHERE status = 'active';
```

### 5.4 Операторные классы

Операторный класс определяет, какие операторы индекс поддерживает.

| Индекс / opclass           | Поддерживает                                  | Когда нужен                                  |
| -------------------------- | --------------------------------------------- | -------------------------------------------- |
| B-tree `text_ops` (default)| `=`, `<`, `>`, сортировка по collation        | обычно                                       |
| B-tree `text_pattern_ops`  | `LIKE 'abc%'`, `~ '^abc'` при не-C collation  | префиксный поиск в базе с ru_RU.UTF-8        |
| GIN `jsonb_ops` (default)  | `@>`, `?`, `?|`, `?&`, `@?`, `@@`             | нужны проверки «есть ли ключ»                |
| GIN `jsonb_path_ops`       | только `@>`, `@?`, `@@`                       | в 2–3 раза меньше и быстрее, если `?` не нужен |
| GIN `gin_trgm_ops` (pg_trgm)| `LIKE '%abc%'`, `ILIKE`, `~`, `similarity`   | поиск подстроки                              |
| GIN `array_ops`            | `@>`, `<@`, `&&`, `=` для массивов            | теги, списки id                              |

### 5.5 Когда что использовать

| Индекс        | Когда использовать                                              |
| ------------- | --------------------------------------------------------------- |
| B-tree        | Почти всегда — равенство, диапазоны, сортировка, MIN/MAX        |
| Hash          | Только точное равенство длинных ключей                          |
| GIN           | JSONB, массивы, полнотекстовый поиск, LIKE '%…%' (с pg_trgm)    |
| GiST          | Гео, диапазоны, ближайшие соседи, exclusion constraints         |
| BRIN          | Огромные append-only таблицы логов/событий по времени           |
| Составной     | Фильтр по нескольким колонкам, фильтр + сортировка              |
| Частичный     | Запросы всегда по малой доле строк (pending, active, not deleted)|
| INCLUDE       | Нужен Index Only Scan для частого запроса                       |
| По выражению  | WHERE с функцией: `lower()`, `(data->>'key')`, `date(ts)`       |

### 5.6 Практики

```sql
-- ВСЕГДА строить индекс на проде без блокировки записи
CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders(user_id);
-- Без CONCURRENTLY — SHARE lock: INSERT/UPDATE/DELETE ждут всё время построения.
-- CONCURRENTLY дольше (2 прохода) и не работает внутри транзакции.
-- Если упал — останется INVALID индекс, который не используется, но замедляет запись:
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
-- Удалить и создать заново: DROP INDEX CONCURRENTLY ...;

-- Пересоздать раздутый индекс без блокировки (PG12+)
REINDEX INDEX CONCURRENTLY idx_orders_user_id;

-- Неиспользуемые индексы (тормозят запись зря). Смотреть после ДОЛГОЙ работы
-- и на ВСЕХ репликах — на реплике индекс может использоваться для отчётов.
SELECT indexrelid::regclass AS index, relid::regclass AS table, idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0 AND indexrelid NOT IN (SELECT conindid FROM pg_constraint)
ORDER BY pg_relation_size(indexrelid) DESC;

-- Дубликаты: индекс (a) избыточен, если есть (a, b)
```

## 6. Корреляция: как проверить и как довести до 1

### 6.1 Что это

**Корреляция** — насколько порядок значений колонки совпадает с физическим порядком строк в файле таблицы. Значение от −1 до 1:

- **1** — строки лежат на диске ровно по возрастанию значения (вставлялись в порядке `created_at`);
- **−1** — строго по убыванию (тоже хорошо для индекса — просто читать в обратном направлении);
- **0** — значения разбросаны случайно (UUIDv4, после множества UPDATE).

```
Корреляция ≈ 1 (created_at при вставке по времени):
  Страница 0: 01.01 01.01 01.01 ...
  Страница 1: 01.01 02.01 02.01 ...
  Страница 2: 02.01 02.01 03.01 ...
  Запрос «за 2 января» → читает страницы 1–2 подряд

Корреляция ≈ 0 (user_id):
  Страница 0: user 51 user 9 user 77 ...
  Страница 1: user 3 user 51 user 12 ...
  Запрос «все заказы user 51» (500 строк) → до 500 РАЗНЫХ страниц в случайном порядке
```

### 6.2 Почему это влияет на план

Index Scan на каждую найденную строку идёт в таблицу по ctid. При корреляции 1 соседние ctid лежат на одной странице — 500 строк = ~5 страниц. При корреляции 0 — 500 строк ≈ 500 случайных чтений.

Планировщик учитывает это прямо в формуле стоимости Index Scan:

```
max_IO_cost = pages_fetched_при_случайном_доступе × random_page_cost
min_IO_cost = pages_нужные_при_идеальном_порядке × seq_page_cost  (первая random)

IO_cost = max_IO_cost + correlation² × (min_IO_cost − max_IO_cost)

correlation = 1   → correlation² = 1    → стоимость = min_IO_cost (дёшево)
correlation = 0.5 → correlation² = 0.25 → всего 25 % пути к дешёвому варианту
correlation = 0   → стоимость = max_IO_cost (дорого) → чаще выберет Bitmap или Seq Scan
```

Обрати внимание на квадрат: корреляция 0.7 даёт всего 0.49 — половину выгоды. Поэтому «почти упорядочено» ценится меньше, чем кажется.

**Bitmap Heap Scan** нивелирует плохую корреляцию: сначала собирает все ctid, сортирует их по номеру страницы и читает страницы по порядку, каждую один раз. Поэтому при корреляции ≈ 0 и средней селективности ты увидишь в плане Bitmap, а не Index Scan.

### 6.3 Как проверить

```sql
-- 1. Статистика планировщика (обновляется ANALYZE)
SELECT tablename, attname, correlation, n_distinct
FROM pg_stats
WHERE schemaname = 'public' AND tablename = 'orders'
ORDER BY abs(correlation) DESC;
--  tablename | attname    | correlation | n_distinct
--  orders    | id         |  0.9998     | -1          ← идеально
--  orders    | created_at |  0.9971     | -0.8
--  orders    | user_id    |  0.0123     |  95000      ← разбросано
--  orders    | status     |  0.31       |  5

-- 2. Проверить руками на конкретном диапазоне: сколько разных страниц
--    занимают строки одного пользователя
SELECT count(*)                                         AS rows,
       count(DISTINCT (ctid::text::point)[0])           AS distinct_pages
FROM orders WHERE user_id = 51;
-- rows = 500, distinct_pages = 497 → каждая строка на своей странице

-- 3. В плане: соотношение строк и прочитанных страниц
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 51;
--   rows=500 ... Buffers: shared hit=12 read=495
```

Важно: `correlation` в `pg_stats` считается **по выборке ANALYZE**, а не по всей таблице. После массовых изменений сначала `ANALYZE`, потом смотреть.

### 6.4 Почему корреляция падает

1. **Не-HOT UPDATE** — новая версия строки уходит на другую страницу (где есть место по FSM).
2. **DELETE + VACUUM + новые INSERT** — новые строки заполняют освободившиеся «дыры» в старых страницах вперемешку.
3. **Случайный ключ** — UUIDv4 никогда не будет коррелирован с порядком вставки.
4. **Вставка не по порядку** — загрузка данных пачками за разные дни в произвольном порядке.

### 6.5 Как довести корреляцию до ≈ 1

Сразу ограничение: **физический порядок один**, поэтому идеальная корреляция возможна только для одной колонки (и для колонок, которые с ней сами по себе связаны: `id` и `created_at` при вставке по времени). Выбирать колонку, по которой идут самые тяжёлые диапазонные запросы.

**Способ 1. CLUSTER — разовая физическая пересортировка**

```sql
CLUSTER orders USING idx_orders_user_id;
ANALYZE orders;
-- correlation(user_id) → 1.0
```

- Переписывает таблицу целиком в порядке индекса, заодно убирает bloat.
- Берёт **ACCESS EXCLUSIVE** блокировку — таблица недоступна даже на чтение всё время работы. Только в окно обслуживания.
- Нужно свободное место = размер таблицы + индексы.
- Порядок **не поддерживается** дальше: новые строки и UPDATE снова его размывают. Повторный `CLUSTER orders;` использует запомненный индекс.

**Способ 2. pg_repack — то же без долгой блокировки**

```bash
# Пересобрать таблицу, упорядочив по колонке
pg_repack -d mydb -t orders --order-by='user_id, created_at'
# или по индексу, который помечен для CLUSTER:
pg_repack -d mydb -t orders
```

Механизм: создаёт копию таблицы, триггером собирает изменения, которые идут во время копирования, применяет их, в конце на секунды берёт эксклюзивную блокировку для подмены. Требует расширение `pg_repack` и места под копию.

**Способ 3. Пересоздание таблицы в нужном порядке**

```sql
BEGIN;
CREATE TABLE orders_new (LIKE orders INCLUDING ALL);
INSERT INTO orders_new SELECT * FROM orders ORDER BY user_id, created_at;
ALTER TABLE orders RENAME TO orders_old;
ALTER TABLE orders_new RENAME TO orders;
COMMIT;
ANALYZE orders;
```

Подходит для подготовки стенда НТ: сгенерировал данные → залил в правильном порядке.

**Способ 4. Сохранять порядок при записи (самый правильный)**

- Ключи, растущие во времени: `bigint identity`, UUIDv7 вместо UUIDv4.
- Append-only модель для событий: только INSERT, без UPDATE — корреляция по времени держится сама.
- `fillfactor = 70–90` для часто обновляемых таблиц → обновления остаются HOT на той же странице → строки не «уезжают».
- Партиционирование по времени: внутри каждой партиции данные компактны, старые партиции не меняются.

**Способ 5. Если нужна «кластеризация» по колонке, которую нельзя сделать физическим порядком**

- **Покрывающий индекс** `(user_id) INCLUDE (...)` → Index Only Scan вообще не ходит в таблицу, корреляция становится не важна.
- Bitmap Scan (планировщик сам выберет) — читает страницы по порядку.

### 6.6 Проверка результата на примере

```
До CLUSTER:
  correlation(user_id) = 0.012
  EXPLAIN (ANALYZE, BUFFERS) ... WHERE user_id = 51
    Bitmap Heap Scan ... rows=500
      Buffers: shared hit=3 read=497        ← 497 страниц
    Execution Time: 41.2 ms

После CLUSTER orders USING idx_orders_user_id; ANALYZE orders;
  correlation(user_id) = 1.0
    Index Scan using idx_orders_user_id ... rows=500
      Buffers: shared hit=3 read=6          ← 6 страниц (500 строк / ~120 на страницу + индекс)
    Execution Time: 0.4 ms
```

## 7. Почему индекс есть, но не используется — полный список

Индекс — не гарантия. Планировщик выбирает план с минимальной **оценочной** стоимостью, а индекс иногда либо невыгоден, либо технически неприменим к выражению в запросе.

### 7.1 Индекс технически неприменим

| # | Причина | Пример | Как исправить |
|---|---------|--------|---------------|
| 1 | Функция или выражение над колонкой | `WHERE date(created_at) = '2024-01-01'`, `WHERE lower(email) = ...`, `WHERE amount * 1.2 > 100` | Переписать в диапазон: `created_at >= '2024-01-01' AND created_at < '2024-01-02'`; или индекс по выражению |
| 2 | Неявное приведение типа колонки | колонка `bigint`, параметр `numeric` → `WHERE id::numeric = 5` (колонка приводится, индекс не работает); колонка `varchar`, сравнение с `int` | Передавать параметр правильного типа (в JDBC — `setLong`, не `setBigDecimal`); смотреть в плане `Filter: ((id)::numeric = …)` |
| 3 | `LIKE '%abc'` / `'%abc%'` | B-tree умеет только префикс | GIN + `pg_trgm` |
| 4 | `LIKE 'abc%'` в базе с не-C collation | обычный B-tree не используется для LIKE | Индекс с `text_pattern_ops` / `varchar_pattern_ops` или `COLLATE "C"` |
| 5 | Нет ведущей колонки составного индекса | индекс `(a, b)`, запрос `WHERE b = 1` | Индекс по `b` или переставить; в PG18 skip scan помогает при малом числе значений `a` |
| 6 | Частичный индекс, предикат не совпадает | индекс `WHERE status='pending'`, запрос `WHERE status = $1` в generic плане | Литерал в запросе или обычный индекс |
| 7 | Не тот оператор для операторного класса | `jsonb_path_ops` + запрос `data ? 'key'` | `jsonb_ops` или переписать на `@>` |
| 8 | Collation запроса не совпадает с индексом | `ORDER BY name COLLATE "C"` при индексе в `ru_RU` | Индекс с нужной collation |
| 9 | Индекс INVALID | упал `CREATE INDEX CONCURRENTLY` | `pg_index.indisvalid` → пересоздать |
| 10 | `OR` по разным колонкам, одна без индекса | `WHERE a = 1 OR c = 2`, индекса на `c` нет | Индекс на обе (будет BitmapOr) или `UNION ALL` |
| 11 | Не тот порядок сортировки для составного индекса | индекс `(a ASC, b ASC)`, `ORDER BY a ASC, b DESC` | Индекс `(a, b DESC)` |
| 12 | `NOT IN (...)`, `<>`, `!=` | индекс ищет «равно», а не «не равно» | Обычно и не нужен: «не равно» возвращает почти всё |

### 7.2 Индекс применим, но планировщик считает его невыгодным

| # | Причина | Как понять | Что делать |
|---|---------|-----------|------------|
| 13 | Низкая селективность | запрос возвращает > 5–10 % строк | Это правильное решение — Seq Scan быстрее. Частичный индекс, если запрашивается редкое значение |
| 14 | Маленькая таблица | несколько страниц | Ничего, Seq Scan 3 страниц дешевле спуска по индексу |
| 15 | Устаревшая статистика | `rows=` в плане сильно отличается от `actual rows` | `ANALYZE table`; проверить `last_autoanalyze` |
| 16 | Неравномерное распределение, не хватает статистики | 1 значение = 90 % строк, остальные редкие | `ALTER TABLE ... ALTER COLUMN ... SET STATISTICS 1000; ANALYZE` |
| 17 | Коррелированные колонки | `WHERE city='Москва' AND region='Московская обл.'` → планировщик перемножает селективности и недооценивает | `CREATE STATISTICS s (dependencies, mcv) ON city, region FROM addr; ANALYZE` |
| 18 | Плохая корреляция | `correlation ≈ 0` | Раздел 6 |
| 19 | `random_page_cost = 4` на SSD | Index Scan переоценён | `random_page_cost = 1.1–1.5` |
| 20 | Маленький `effective_cache_size` | планировщик думает, что всё будет читаться с диска | 50–75 % RAM |
| 21 | `ORDER BY x LIMIT n` выбирает индекс по `x` | Index Scan по `created_at` + Filter, `Rows Removed by Filter` огромный | Составной индекс `(filter_col, x)`; это классическая ловушка «LIMIT выбрал не тот индекс» |
| 22 | Generic plan для prepared statement | первые 5 выполнений быстрые, потом медленные | `plan_cache_mode = force_custom_plan` для проблемного запроса (раздел 13) |
| 23 | Index Only Scan с плохой Visibility Map | `Heap Fetches` ≈ числу строк | VACUUM таблицы, тюнинг autovacuum |
| 24 | Включён `enable_indexscan = off` / хинт на сессию | `SHOW enable_indexscan` | Вернуть настройки |

### 7.3 Как проверить, может ли индекс вообще использоваться

```sql
-- 1. Запретить Seq Scan в текущей сессии и посмотреть план и стоимость
SET enable_seqscan = off;
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
RESET enable_seqscan;
-- Если индекс всё равно не используется → он ТЕХНИЧЕСКИ неприменим (п. 1–12).
-- Если используется и РЕАЛЬНО быстрее → ошибка в оценках (п. 15–22).
-- Если используется, но медленнее → планировщик был прав (п. 13, 14).

-- 2. Используется ли индекс в реальной нагрузке
SELECT relname, indexrelname, idx_scan, idx_tup_read, idx_tup_fetch
FROM pg_stat_user_indexes WHERE relname = 'orders';
```

## 8. Планировщик и EXPLAIN

### 8.1 Путь запроса

```
SQL → Parser (синтаксис) → Analyzer (какие таблицы/колонки/типы)
    → Rewriter (раскрывает VIEW, правила)
    → Planner (перебирает планы, считает стоимость, выбирает самый дешёвый)
    → Executor (выполняет дерево узлов)
```

**Planner — стоимостной оптимизатор.** Он не знает реальных данных, он знает **статистику** из `pg_statistic` (читаемая версия — `pg_stats`):

| Статистика           | Что это                                                       | Для чего                                         |
| -------------------- | ------------------------------------------------------------- | ------------------------------------------------ |
| `reltuples`, `relpages` | число строк и страниц таблицы                              | стоимость Seq Scan                               |
| `null_frac`          | доля NULL                                                     | селективность `IS NULL`                          |
| `n_distinct`         | число различных значений (отрицательное = доля от числа строк) | селективность `=`, оценка GROUP BY              |
| `most_common_vals` / `most_common_freqs` | самые частые значения и их доли          | точная селективность для частых значений         |
| `histogram_bounds`   | границы гистограммы (по умолчанию 100 корзин)                 | селективность диапазонов `<`, `>`, `BETWEEN`     |
| `correlation`        | физическая упорядоченность                                    | стоимость Index Scan                             |

Число корзин/MCV задаёт `default_statistics_target` (100) или `ALTER COLUMN ... SET STATISTICS N` (до 10000). ANALYZE берёт выборку 300 × target строк (по умолчанию 30 000 строк).

**Стоимость** — условные единицы, «цена чтения одной страницы последовательно = 1»:

| Параметр               | По умолчанию | Смысл                                      |
| ---------------------- | ------------ | ------------------------------------------ |
| `seq_page_cost`        | 1.0          | последовательное чтение страницы           |
| `random_page_cost`     | 4.0          | случайное чтение (для SSD ставить 1.1–1.5) |
| `cpu_tuple_cost`       | 0.01         | обработка строки                           |
| `cpu_index_tuple_cost` | 0.005        | обработка записи индекса                   |
| `cpu_operator_cost`    | 0.0025       | вычисление оператора/функции               |

**Пример: стоимость Seq Scan.** Таблица 83 334 страницы, 10 млн строк, условие `WHERE status = 'x'`:

```
cost = relpages × seq_page_cost + reltuples × (cpu_tuple_cost + cpu_operator_cost)
     = 83 334 × 1.0 + 10 000 000 × (0.01 + 0.0025)
     = 83 334 + 125 000 = 208 334
```

Именно это число ты увидишь в `cost=0.00..208334.00`.

### 8.2 Как читать EXPLAIN

```sql
EXPLAIN SELECT ...;                       -- только план, запрос НЕ выполняется
EXPLAIN ANALYZE SELECT ...;               -- выполняет и показывает реальные цифры
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS, WAL) SELECT ...;
-- BUFFERS  — страницы: hit / read / dirtied / written (в PG18 включено в ANALYZE по умолчанию)
-- VERBOSE  — выходные колонки каждого узла, схема
-- SETTINGS — изменённые параметры планировщика
-- WAL      — сколько WAL сгенерировал запрос (для INSERT/UPDATE)
-- FORMAT JSON — для визуализаторов (explain.dalibo.com, explain.depesz.com)
```

⚠️ `EXPLAIN ANALYZE` для `UPDATE/DELETE/INSERT` **реально меняет данные**. Оборачивать в `BEGIN; ... ROLLBACK;`.

```
Hash Join  (cost=1250.00..48500.00 rows=50000 width=64) (actual time=12.3..310.5 rows=48210 loops=1)
  Hash Cond: (o.user_id = u.id)
  Buffers: shared hit=4200 read=38000
  ->  Seq Scan on orders o  (cost=0.00..41000.00 rows=1000000 width=40) (actual time=0.01..150.2 rows=1000000 loops=1)
        Filter: (status = 'paid'::text)
        Rows Removed by Filter: 50000
  ->  Hash  (cost=1000.00..1000.00 rows=20000 width=24) (actual time=11.9..11.9 rows=20000 loops=1)
        Buckets: 32768  Batches: 1  Memory Usage: 1350kB
        ->  Seq Scan on users u  (...)
Planning Time: 0.4 ms
Execution Time: 318.2 ms
```

| Поле                | Что значит                                                                 |
| ------------------- | -------------------------------------------------------------------------- |
| `cost=A..B`         | A — стоимость до первой строки (startup), B — до последней                 |
| `rows=`             | **оценка** числа строк на выходе узла                                      |
| `width=`            | средний размер строки в байтах                                             |
| `actual time=A..B`  | реальное время в мс до первой и до последней строки, **на одну итерацию**  |
| `actual rows=`      | реальное число строк **на одну итерацию**                                  |
| `loops=`            | сколько раз выполнялся узел. Полное время = time × loops, строк = rows × loops |
| `Buffers`           | страницы: `hit` из shared_buffers, `read` от ОС, `dirtied`, `written`, `temp` — временные файлы на диске |

**Дерево читается снизу вверх и изнутри наружу**: листья (сканы таблиц) выполняются первыми, корень отдаёт результат.

### 8.3 Красные флаги в плане

| Признак                                          | Что означает                                               |
| ------------------------------------------------ | ---------------------------------------------------------- |
| `rows=10` vs `actual rows=500000` (разница ×10 и больше) | Ошибка оценки → почти наверняка не тот план. Главный флаг |
| `Rows Removed by Filter` ≫ `actual rows`         | Читаем много, отбрасываем почти всё → нужен (составной) индекс |
| `loops=50000` на внутреннем узле Nested Loop     | Внутренняя часть выполнена 50 000 раз                      |
| `Sort Method: external merge  Disk: 250000kB`    | Сортировка не влезла в work_mem → на диск                  |
| `Batches: 16` у Hash                             | Хэш-таблица не влезла → пошла на диск партиями             |
| `Buffers: temp read=... written=...`             | Временные файлы → work_mem мал                             |
| `Heap Fetches: N` у Index Only Scan, N ≈ rows    | Visibility Map не обновлена → VACUUM                       |
| `SubPlan` (не `hashed SubPlan`) под большим узлом| Подзапрос выполняется на каждую строку                     |
| `Workers Planned: 4, Workers Launched: 0`        | Не хватило `max_parallel_workers` — параллелизм не случился |
| `JIT: ... Timing: Total 180 ms` на быстром OLTP-запросе | JIT съедает больше, чем экономит → `jit = off` для OLTP |
| `Planning Time` ≫ `Execution Time`               | Сложный запрос/много партиций — prepared statements или упрощение |

## 9. Типы сканов

| Скан               | Когда выбирается                                  | Идёт в таблицу?                         | Порядок результата  |
| ------------------ | ------------------------------------------------- | --------------------------------------- | ------------------- |
| Seq Scan           | много строк / нет индекса / маленькая таблица     | читает её всю                           | физический          |
| Index Scan         | мало строк, хорошая корреляция, нужен порядок     | да, по ctid на каждую строку (random IO)| порядок индекса     |
| Index Only Scan    | все нужные колонки есть в индексе                 | только для страниц не all-visible       | порядок индекса     |
| Bitmap Index + Bitmap Heap Scan | средняя селективность, плохая корреляция, несколько индексов (AND/OR) | да, но страницы по порядку, каждая 1 раз | физический (без порядка индекса) |
| TID Scan           | `WHERE ctid = '(0,1)'`                            | прямо по адресу                         | —                   |
| Function Scan      | `FROM generate_series()`, `FROM jsonb_array_elements()` | —                                 | —                   |
| Values Scan        | `FROM (VALUES (1),(2))`                           | —                                       | —                   |
| CTE Scan           | материализованный CTE                             | —                                       | —                   |
| Subquery Scan      | подзапрос в FROM, который не удалось «развернуть» | —                                       | —                   |

### Seq Scan

Читает все страницы подряд. Последовательное чтение быстрое (диск и ОС делают read-ahead), а для таблиц > 1/4 shared_buffers используется ring buffer (раздел 3.4). Параллельная версия — `Parallel Seq Scan`: воркеры делят страницы между собой.

### Index Scan

```
Index Scan using idx_orders_user_id on orders  (cost=0.43..8.45 rows=50 width=40)
  Index Cond: (user_id = 12345)
```

Для каждой записи индекса — чтение страницы таблицы. Отдаёт строки в порядке индекса → может заменить сортировку для `ORDER BY` и остановиться рано при `LIMIT`.

### Index Only Scan

```sql
CREATE INDEX idx ON orders (user_id) INCLUDE (status, amount);
SELECT user_id, status, amount FROM orders WHERE user_id = 12345;
```

```
Index Only Scan using idx on orders  (actual rows=50)
  Index Cond: (user_id = 12345)
  Heap Fetches: 0          ← все страницы all-visible, в таблицу не ходили
```

### Bitmap Index Scan + Bitmap Heap Scan

Две фазы:

1. **Bitmap Index Scan** — проходит по индексу и строит битовую карту «какие страницы (и строки) нужны». Таблицу не трогает.
2. **Bitmap Heap Scan** — читает отмеченные страницы **в физическом порядке**, каждую один раз, и перепроверяет условие (`Recheck Cond`).

```
Bitmap Heap Scan on orders  (actual rows=12000)
  Recheck Cond: ((user_id = 5) OR (status = 'pending'))
  Heap Blocks: exact=3100 lossy=0
  ->  BitmapOr
        ->  Bitmap Index Scan on idx_orders_user_id    Index Cond: (user_id = 5)
        ->  Bitmap Index Scan on idx_orders_status     Index Cond: (status = 'pending')
```

- Умеет **комбинировать индексы**: `BitmapAnd` для `AND`, `BitmapOr` для `OR`.
- Превращает случайный I/O в почти последовательный.
- `Heap Blocks: lossy=N` — битовая карта не влезла в `work_mem`, перешла на гранулярность «страница целиком», и каждую строку на странице приходится перепроверять. Лечится увеличением work_mem.
- Минус: не сохраняет порядок индекса, поэтому для `ORDER BY ... LIMIT` не годится.

### Index Cond vs Filter — важнейшее различие

```
Index Scan using idx_orders_user_id on orders (actual rows=200)
  Index Cond: (user_id = 123)          ← применяется ВНУТРИ индекса — дёшево
  Filter: (status = 'active')          ← применяется ПОСЛЕ чтения строки из таблицы
  Rows Removed by Filter: 9800         ← прочитали 10 000 строк, нужны были 200
```

**Правило:** большой `Rows Removed by Filter` = условие нужно перенести в индекс:

```sql
CREATE INDEX idx_orders_user_status ON orders(user_id, status);
-- Index Cond: ((user_id = 123) AND (status = 'active'))
-- Rows Removed by Filter: 0
```

Ещё одна разновидность — `Index Filter` / проверки внутри индекса для составных индексов, когда условие на вторую колонку не диапазонное и проверяется по записи индекса без похода в таблицу. Всё равно лучше, чем Filter.

## 10. JOIN — логические виды и физические алгоритмы

Важно разделять два уровня:

- **Логический JOIN** — что ты написал в SQL (INNER, LEFT, SEMI через EXISTS...). Определяет **результат**.
- **Физический алгоритм** — как PostgreSQL это выполняет (Nested Loop, Hash Join, Merge Join). Определяет **скорость**. Один и тот же LEFT JOIN может выполниться любым из трёх алгоритмов.

### 10.1 Логические виды JOIN

Пример данных: `users` (1 Анна, 2 Борис, 3 Вера), `orders` (заказы user 1 ×2, user 2 ×1, user 99 ×1 — «сирота»).

| Вид | SQL | Результат | Узел в плане |
|-----|-----|-----------|--------------|
| INNER | `users u JOIN orders o ON o.user_id = u.id` | только пары, где есть совпадение: Анна×2, Борис×1 | `Hash Join`, `Nested Loop`, `Merge Join` |
| LEFT OUTER | `users u LEFT JOIN orders o ...` | все users + совпадения; Вера с NULL в колонках orders | `Hash Left Join`, `Nested Loop Left Join`, `Merge Left Join` (или `Hash Right Join` — когда хэш строится по левой таблице) |
| RIGHT OUTER | `users u RIGHT JOIN orders o ...` | все orders + совпадения; заказ user 99 с NULL | PostgreSQL переставляет стороны и выполняет как LEFT |
| FULL OUTER | `... FULL JOIN ...` | всё с обеих сторон, NULL где нет пары | только `Hash Full Join` или `Merge Full Join`; **Nested Loop не умеет FULL**; при неравенстве в условии FULL JOIN вообще не выполнится |
| CROSS | `users CROSS JOIN orders` | декартово произведение 3 × 4 = 12 строк | `Nested Loop` без условия. Опасно: 10 тыс. × 10 тыс. = 100 млн |
| SEMI | `WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id)` или `u.id IN (SELECT user_id FROM orders)` | users, у которых есть хотя бы один заказ, **каждый один раз**: Анна, Борис | `Hash Semi Join`, `Nested Loop Semi Join`, `Merge Semi Join`, иногда `Hash Join` + `HashAggregate` (дедупликация) |
| ANTI | `WHERE NOT EXISTS (...)` или `LEFT JOIN ... WHERE o.id IS NULL` | users без заказов: Вера | `Hash Anti Join`, `Nested Loop Anti Join`, `Merge Anti Join` |
| LATERAL | `FROM users u, LATERAL (SELECT ... WHERE o.user_id = u.id ORDER BY created_at DESC LIMIT 3) o` | для каждого user — его 3 последних заказа | `Nested Loop` (подзапрос выполняется на каждую строку слева) |
| Self join | `orders a JOIN orders b ON ...` | таблица с собой | любой алгоритм |

**SEMI vs INNER + DISTINCT:** `JOIN ... DISTINCT` сначала размножит строки (Анна × 2 заказа), потом схлопнет. SEMI JOIN останавливается на первом совпадении — дешевле, и это то, что ты хочешь, когда нужно «есть ли».

**ANTI JOIN и NOT IN** — главная ловушка: `NOT IN` при наличии NULL в подзапросе возвращает **пустой результат**, и планировщик не может превратить его в Anti Join. Подробно в разделе 11.3.

### 10.2 Nested Loop (вложенный цикл)

**Алгоритм:**

```
для каждой строки r из ВНЕШНЕЙ (outer) таблицы:
    найти во ВНУТРЕННЕЙ (inner) таблице строки, где inner.key = r.key
    вернуть пары
```

Аналогия с Java: двойной `for`. С индексом на внутренней таблице — `for` + `map.get()`.

```
Nested Loop  (actual time=0.05..1.2 rows=150 loops=1)
  ->  Index Scan using users_pkey on users u  (actual rows=50 loops=1)
        Index Cond: (id = ANY ('{1,2,...,50}'::bigint[]))
  ->  Index Scan using idx_orders_user_id on orders o  (actual rows=3 loops=50)
        Index Cond: (user_id = u.id)
```

Читаем: внешняя часть вернула 50 users; внутренний Index Scan выполнен 50 раз (`loops=50`), каждый раз в среднем 3 строки → итого 150.

**Сложность:** O(N × стоимость поиска во внутренней). С индексом — O(N × log M). Без индекса — O(N × M).

| Плюсы | Минусы |
|-------|--------|
| Нулевой startup — первая строка сразу. Отлично для `LIMIT` | Без индекса на внутренней таблице — катастрофа O(N×M) |
| Не нужна память (work_mem) | При большой внешней таблице миллионы случайных чтений индекса |
| Единственный алгоритм для **неравенств**: `ON a.ts BETWEEN b.start AND b.end`, `ON a.x < b.y`, `ON a.geom && b.geom` | Ошибка оценки внешней таблицы (думали 10, пришло 100 000) → резкая деградация |
| Работает с LATERAL и параметризованными подзапросами | Не умеет FULL JOIN |

**Когда выбирается:** внешняя часть маленькая (десятки–тысячи строк) и есть индекс на ключ соединения внутренней; или условие не равенство.

**Красный флаг:**

```
Nested Loop  (rows=10 оценка) (actual rows=4500000)
  ->  Seq Scan on a  (rows=10)  (actual rows=50000 loops=1)     ← оценка 10, реально 50 000
  ->  Seq Scan on b  (actual rows=90 loops=50000)                ← Seq Scan 50 000 раз!
```

Планировщик ошибся в оценке внешней стороны, выбрал Nested Loop, а внутри даже нет индекса. Лечение: индекс на ключ соединения, `ANALYZE`, расширенная статистика.

**Memoize (PG14+)** — кэш результатов внутренней стороны Nested Loop:

```
Nested Loop
  ->  Seq Scan on orders o           (rows=1 000 000)
  ->  Memoize
        Cache Key: o.product_id
        Hits: 999 000  Misses: 1 000  Evictions: 0  Memory Usage: 120kB
        ->  Index Scan using products_pkey on products p
              Index Cond: (id = o.product_id)
```

Если у миллиона заказов всего 1000 разных товаров, вместо миллиона Index Scan выполняется 1000, остальное — из кэша. Плохо работает, если много уникальных ключей (много Misses и Evictions). Отключение для диагностики: `SET enable_memoize = off`.

### 10.3 Hash Join

**Алгоритм:**

```
Фаза 1 (build):  прочитать МЕНЬШУЮ таблицу целиком
                 построить в памяти хэш-таблицу: hash(key) → строки
Фаза 2 (probe):  читать БОЛЬШУЮ таблицу строка за строкой
                 для каждой: hash(key) → посмотреть в хэш-таблицу → вернуть совпадения
```

Аналогия с Java: `Map<Key, List<Row>> map = small.stream().collect(groupingBy(...))`, потом `big.forEach(r -> map.get(r.key))`.

```
Hash Join  (actual time=12.3..310.5 rows=48210 loops=1)
  Hash Cond: (o.user_id = u.id)
  ->  Seq Scan on orders o  (actual rows=1000000)       ← probe (большая)
  ->  Hash  (actual rows=20000)                         ← build (меньшая)
        Buckets: 32768  Batches: 1  Memory Usage: 1350kB
        ->  Seq Scan on users u
```

**Сложность:** O(N + M) — каждая таблица читается один раз.

**Память:** хэш-таблица должна влезть в `work_mem × hash_mem_multiplier` (по умолчанию 4 МБ × 2 = 8 МБ на узел). Если не влезает:

```
Hash  Buckets: 65536  Batches: 16  Memory Usage: 8193kB
```

`Batches: 16` = обе таблицы разрезаны по хэшу на 16 частей и записаны во временные файлы; каждая пара частей соединяется отдельно. Это **гибридный hash join со сбросом на диск** — работает, но в разы медленнее. В `Buffers` появится `temp read/written`.

**Расчёт:** build-таблица 1 млн строк по ~100 байт + накладные расходы хэш-таблицы (~50 байт на запись) ≈ 150 МБ. При `work_mem = 64MB` и `hash_mem_multiplier = 2` лимит 128 МБ → не влезет → 2 batch. При `work_mem = 128MB` → 1 batch.

| Плюсы | Минусы |
|-------|--------|
| Линейная сложность — лучший выбор для больших таблиц без подходящих индексов | Нужна память; при нехватке — сброс на диск (Batches > 1) |
| Не нужен индекс и не нужна сортировка | Только равенство (`=`) в условии |
| Хорошо параллелится (`Parallel Hash Join` с общей хэш-таблицей, PG11+) | Большой startup: первая строка только после построения всей хэш-таблицы — плохо для `LIMIT 1` |
| Умеет все виды: INNER, LEFT, RIGHT, FULL, SEMI, ANTI | Если build-сторону недооценили (думали 1000, пришло 10 млн) — много batch |
|  | Перекос данных (одно значение ключа у 50 % строк) — один бакет огромный |

**Когда выбирается:** обе стороны большие, условие — равенство, нет удобных индексов или нужно много строк.

### 10.4 Merge Join

**Алгоритм:**

```
обе стороны ОТСОРТИРОВАНЫ по ключу соединения
два указателя идут по обеим сторонам одновременно (как слияние в merge sort):
  left.key < right.key → сдвинуть left
  left.key > right.key → сдвинуть right
  равны                → вернуть пару (с учётом дублей: «перемотка» правой стороны)
```

```
Merge Join  (actual rows=1000000)
  Merge Cond: (o.user_id = u.id)
  ->  Index Scan using idx_orders_user_id on orders o     ← уже отсортировано индексом
  ->  Index Scan using users_pkey on users u
```

Если сортированного источника нет, под Merge Join появятся узлы `Sort` — тогда это дороже Hash Join почти всегда.

**Сложность:** O(N + M), если данные уже отсортированы. С сортировкой — O(N log N + M log M).

| Плюсы | Минусы |
|-------|--------|
| Почти не нужна память, если вход уже отсортирован | Нужны отсортированные входы — либо индекс, либо дорогой Sort |
| Отдаёт результат в отсортированном порядке → может обслужить `ORDER BY` выше | Только равенство (merge-joinable операторы) |
| Хорош для двух очень больших таблиц, обе с индексом по ключу | Дубликаты ключей с обеих сторон → «перемотка» (Mark/Restore) |
| Умеет FULL JOIN | Если Sort не влез в work_mem — external merge на диске |

**Когда выбирается:** обе стороны большие и уже отсортированы по ключу (индексы), или результат нужен отсортированным по ключу соединения.

### 10.5 Сравнительная таблица

| | Nested Loop | Hash Join | Merge Join |
|---|---|---|---|
| Сложность | O(N × log M) с индексом, O(N × M) без | O(N + M) | O(N + M) + сортировки |
| Память | почти нет | work_mem × hash_mem_multiplier | почти нет (если не надо сортировать) |
| Startup | мгновенный | после построения хэша | после сортировки (или мгновенный с индексами) |
| Условия | любые, включая `<`, `BETWEEN`, `LIKE`, гео | только `=` | только `=` (сортируемые типы) |
| FULL JOIN | нет | да | да |
| Лучший случай | маленькая внешняя + индекс на внутренней, `LIMIT` | большие таблицы, нет индексов | большие таблицы с индексами по ключу, нужен порядок |
| Признак проблемы | `loops` огромный, Seq Scan внутри | `Batches > 1`, temp файлы | `Sort Method: external merge` |

### 10.6 Порядок соединений

При JOIN нескольких таблиц планировщик перебирает порядки. Число вариантов растёт факториально, поэтому:

- `join_collapse_limit = 8` — до 8 таблиц в явных JOIN перебираются все порядки; больше — порядок как написан в запросе;
- `from_collapse_limit = 8` — то же для подзапросов в FROM;
- `geqo_threshold = 12` — от 12 таблиц включается генетический оптимизатор (план недетерминированный — может «плавать» от запуска к запуску).

На НТ это проявляется так: запрос с 13 JOIN-ами иногда быстрый, иногда медленный — разные планы от GEQO. Решение: упростить запрос, разбить, поднять `geqo_threshold` для сессии.

### 10.7 Как повлиять на выбор алгоритма (для диагностики)

```sql
SET enable_nestloop  = off;   -- запретить Nested Loop
SET enable_hashjoin  = off;
SET enable_mergejoin = off;
SET enable_memoize   = off;
EXPLAIN (ANALYZE, BUFFERS) ...;
RESET ALL;
```

Это **инструмент диагностики**, а не решение для прода. Если с `enable_nestloop = off` запрос в 100 раз быстрее — значит, ошибка в оценке строк, и чинить нужно её (статистика, индекс, переписывание запроса). Хинты в PostgreSQL официально не поддерживаются; есть расширение `pg_hint_plan` как крайняя мера:

```sql
/*+ HashJoin(o u) SeqScan(o) */
SELECT ... FROM orders o JOIN users u ON u.id = o.user_id;
```

## 11. Сложные планы: ANY, IN, EXISTS, подзапросы, JSONB, функции

### 11.1 IN (список) и = ANY(массив)

```sql
SELECT * FROM orders WHERE id IN (1, 2, 3);
```

PostgreSQL сам переписывает это в `= ANY`:

```
Index Scan using orders_pkey on orders
  Index Cond: (id = ANY ('{1,2,3}'::bigint[]))
```

B-tree умеет искать сразу по массиву — один проход по индексу для всех значений (с PG17 это заметно эффективнее: значения из массива ищутся за меньшее число спусков, если они рядом в индексе).

**Параметр-массив — правильный способ передать переменный список:**

```sql
-- Плохо: под каждое число элементов — свой текст запроса
-- IN (?, ?)  IN (?, ?, ?)  IN (?, ?, ?, ?) ...
-- → кэш prepared statements засоряется, pg_stat_statements видит сотни «разных» запросов

-- Хорошо: один prepared statement на любое количество
SELECT * FROM orders WHERE id = ANY($1::bigint[]);
-- JDBC: ps.setArray(1, conn.createArrayOf("bigint", ids));
```

**Очень длинный список (десятки тысяч значений):**

- текст запроса огромный, парсинг и планирование дорогие (`Planning Time` растёт);
- оценка селективности становится неточной;
- альтернатива — `JOIN` с `VALUES` или с `unnest`, тогда планировщик может выбрать Hash Join:

```sql
SELECT o.* FROM orders o
JOIN unnest($1::bigint[]) AS ids(id) ON ids.id = o.id;
-- или временная таблица + ANALYZE, если список совсем большой (сотни тысяч)
```

**ANY с другими операторами:**

```sql
WHERE status = ANY('{new,paid}')          -- то же, что IN
WHERE name LIKE ANY('{abc%,def%}')        -- несколько шаблонов
WHERE amount > ANY(SELECT ...)            -- больше хотя бы одного
WHERE amount > ALL(SELECT ...)            -- больше всех
WHERE 'vip' = ANY(tags)                   -- значение содержится в колонке-массиве
-- ⚠️ последний вариант НЕ использует GIN-индекс по tags! Нужно:
WHERE tags @> ARRAY['vip']                -- использует GIN (array_ops)
```

### 11.2 IN (подзапрос) и EXISTS → Semi Join

```sql
SELECT * FROM users u
WHERE u.id IN (SELECT o.user_id FROM orders o WHERE o.amount > 1000);

SELECT * FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.amount > 1000);
```

Оба обычно превращаются в одинаковый план:

```
Hash Semi Join
  Hash Cond: (u.id = o.user_id)
  ->  Seq Scan on users u
  ->  Hash
        ->  Seq Scan on orders o
              Filter: (amount > 1000)
```

или (если пользователей мало, а у orders индекс):

```
Nested Loop Semi Join
  ->  Seq Scan on users u
  ->  Index Scan using idx_orders_user_id on orders o
        Index Cond: (user_id = u.id)
        Filter: (amount > 1000)
```

В современных версиях PostgreSQL разницы между `IN (подзапрос)` и `EXISTS` по скорости обычно нет — оба становятся Semi Join. Миф «EXISTS всегда быстрее IN» пришёл из старых СУБД.

### 11.3 NOT IN vs NOT EXISTS — главная ловушка

```sql
-- Пользователи без заказов
SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM orders);       -- ⚠️
SELECT * FROM users u WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);  -- ✓
```

**Проблема 1 — неправильный результат.** Если в `orders.user_id` есть хотя бы один NULL, `NOT IN` вернёт **пустой** результат. Логика трёхзначная: `5 NOT IN (1, 2, NULL)` = `5<>1 AND 5<>2 AND 5<>NULL` = `TRUE AND TRUE AND UNKNOWN` = `UNKNOWN` → строка не проходит.

**Проблема 2 — производительность.** Из-за семантики NULL планировщик не может превратить `NOT IN` в Anti Join. Получается:

```
Seq Scan on users
  Filter: (NOT (hashed SubPlan 1))     ← хорошо, если подзапрос влез в work_mem как хэш
  SubPlan 1
    ->  Seq Scan on orders
```

или, если результат подзапроса не влезает в work_mem:

```
Seq Scan on users
  Filter: (NOT (SubPlan 1))            ← подзапрос перебирается ДЛЯ КАЖДОЙ строки users
  SubPlan 1
    ->  Materialize
          ->  Seq Scan on orders
```

100 тыс. users × 10 млн orders = 10¹² сравнений → запрос «никогда не закончится».

`NOT EXISTS` даёт нормальный `Hash Anti Join` / `Nested Loop Anti Join` и правильно обрабатывает NULL. **Правило: всегда `NOT EXISTS`, никогда `NOT IN (подзапрос)`.** `NOT IN (1, 2, 3)` с литералами — безопасно.

### 11.4 SubPlan и InitPlan

**InitPlan** — подзапрос, не зависящий от внешней строки, выполняется **один раз**:

```sql
SELECT * FROM orders WHERE amount > (SELECT avg(amount) FROM orders);
```

```
Seq Scan on orders
  Filter: (amount > $0)
  InitPlan 1 (returns $0)
    ->  Aggregate
          ->  Seq Scan on orders orders_1
```

**SubPlan** — коррелированный подзапрос, выполняется **для каждой строки** внешнего запроса:

```sql
SELECT u.name,
       (SELECT count(*) FROM orders o WHERE o.user_id = u.id) AS cnt   -- скалярный подзапрос
FROM users u;
```

```
Seq Scan on users u  (actual rows=100000 loops=1)
  SubPlan 1
    ->  Aggregate  (actual rows=1 loops=100000)              ← 100 тыс. раз
          ->  Index Only Scan using idx_orders_user_id on orders o  (loops=100000)
```

С индексом это терпимо (100 тыс. × 4 чтения индекса), без индекса — 100 тыс. Seq Scan. Переписать в JOIN + GROUP BY:

```sql
SELECT u.name, coalesce(c.cnt, 0)
FROM users u
LEFT JOIN (SELECT user_id, count(*) cnt FROM orders GROUP BY user_id) c ON c.user_id = u.id;
-- Hash Left Join + HashAggregate — каждая таблица читается один раз
```

### 11.5 OR в условии

```sql
SELECT * FROM orders WHERE user_id = 5 OR status = 'pending';
```

- Оба поля индексированы → `BitmapOr` (раздел 9).
- Хотя бы одно не индексировано → Seq Scan.
- `OR` между разными таблицами в JOIN (`ON a.x = b.x OR a.y = b.y`) — только Nested Loop, обычно очень медленно. Переписать на `UNION`:

```sql
SELECT ... FROM a JOIN b ON a.x = b.x
UNION
SELECT ... FROM a JOIN b ON a.y = b.y;
```

### 11.6 Функции в запросах: волатильность и индексы

У каждой функции есть категория волатильности — это обещание планировщику, как функция себя ведёт:

| Категория   | Обещание | Примеры | Последствия для планов |
|-------------|----------|---------|------------------------|
| `IMMUTABLE` | одинаковые аргументы → всегда одинаковый результат, не читает БД | `lower()`, `abs()`, `md5()`, `int4pl` | Можно строить индекс по выражению; с константами вычисляется на этапе планирования |
| `STABLE`    | одинаковый результат **в пределах одного запроса** | `now()`, `current_date`, `to_char(timestamptz)`, функции, читающие таблицы | Можно использовать как значение для Index Cond (вычисляется один раз на сканирование); **нельзя** в индекс по выражению |
| `VOLATILE` (по умолчанию для пользовательских функций!) | может вернуть что угодно при каждом вызове | `random()`, `nextval()`, `clock_timestamp()`, функции с INSERT/UPDATE | Вызывается для **каждой строки**, не может быть условием индекса, мешает многим оптимизациям |

```sql
-- now() — STABLE → индекс используется
SELECT * FROM orders WHERE created_at > now() - interval '1 hour';
-- Index Cond: (created_at > (now() - '01:00:00'::interval))

-- clock_timestamp() — VOLATILE → индекс НЕ используется, Seq Scan + Filter
SELECT * FROM orders WHERE created_at > clock_timestamp() - interval '1 hour';
```

**Индекс по выражению требует IMMUTABLE.** Частая ошибка с датами:

```sql
CREATE INDEX ON orders (date_trunc('day', created_at));
-- ERROR: functions in index expression must be marked IMMUTABLE
-- Причина: created_at типа timestamptz, а результат date_trunc для timestamptz
-- зависит от параметра сессии TimeZone → функция STABLE.

-- Решение: зафиксировать часовой пояс
CREATE INDEX ON orders (date_trunc('day', created_at AT TIME ZONE 'UTC'));
SELECT ... WHERE date_trunc('day', created_at AT TIME ZONE 'UTC') = '2024-01-01';
-- Или лучше — диапазон без функции, индекс по самой колонке
```

**Своя функция в WHERE:**

```sql
CREATE FUNCTION is_vip(uid bigint) RETURNS boolean AS $$
  SELECT EXISTS (SELECT 1 FROM vip_users WHERE id = uid)
$$ LANGUAGE sql;          -- по умолчанию VOLATILE!

SELECT * FROM orders WHERE is_vip(user_id);
-- Seq Scan on orders, Filter: is_vip(user_id) — функция вызвана для каждой из 10 млн строк,
-- каждый вызов — отдельный запрос к vip_users.
```

Что знать о функциях:

- **PL/pgSQL-функция — чёрный ящик** для планировщика: он не видит, что внутри, и оценивает её стоимостью `COST 100` (×cpu_operator_cost) и, для set-returning, `ROWS 1000`.
- **SQL-функция** (`LANGUAGE sql`) из одного SELECT может быть **встроена (inlined)** — тогда планировщик видит её тело как часть запроса и может превратить в JOIN. Условия inlining: `LANGUAGE sql`, не `SECURITY DEFINER`, не `VOLATILE` (для табличных — не `STRICT` и т.п.).
- Ставь правильную волатильность и стоимость:

```sql
ALTER FUNCTION is_vip(bigint) STABLE;
ALTER FUNCTION heavy_calc(int) COST 10000;       -- планировщик будет вызывать её как можно позже/реже
ALTER FUNCTION get_items(int) ROWS 20;           -- для set-returning: ожидаемое число строк
```

- Время внутри функций видно через `track_functions = 'pl'` → `pg_stat_user_functions` (calls, total_time, self_time), а планы запросов внутри функций — через `auto_explain.log_nested_statements = on`.

### 11.7 JSONB

**Операторы:**

| Оператор | Что делает | Пример | Использует GIN? |
|----------|-----------|--------|-----------------|
| `->`  | получить поле как jsonb | `data->'address'` | нет |
| `->>` | получить поле как text | `data->>'status'` | нет (только индекс по выражению) |
| `#>` / `#>>` | путь | `data#>>'{address,city}'` | нет |
| `@>`  | содержит | `data @> '{"status":"active"}'` | да (`jsonb_ops`, `jsonb_path_ops`) |
| `<@`  | содержится в | | да (`jsonb_ops`) |
| `?`   | есть ключ (верхнего уровня) | `data ? 'discount'` | только `jsonb_ops` |
| `?|` / `?&` | есть любой / все ключи | `data ?| array['a','b']` | только `jsonb_ops` |
| `@?`  | jsonpath: есть ли элемент | `data @? '$.items[*] ? (@.price > 100)'` | да |
| `@@`  | jsonpath-предикат | `data @@ '$.amount > 100'` | да |

**Какой индекс для какого запроса:**

```sql
-- 1. Запросы «содержит»: GIN
CREATE INDEX idx_data_gin ON orders USING GIN (data jsonb_path_ops);
SELECT * FROM orders WHERE data @> '{"status": "active", "region": "msk"}';
-- Bitmap Heap Scan → Bitmap Index Scan on idx_data_gin
--   Index Cond: (data @> '{"status": "active", "region": "msk"}'::jsonb)

-- 2. Равенство/диапазон по конкретному полю: B-tree по выражению — компактнее и точнее
CREATE INDEX idx_data_status ON orders ((data->>'status'));
SELECT * FROM orders WHERE data->>'status' = 'active';          -- использует
SELECT * FROM orders WHERE data @> '{"status":"active"}';       -- НЕ использует этот индекс

-- Числовое поле: индекс и запрос с одинаковым приведением
CREATE INDEX idx_data_amount ON orders (((data->>'amount')::numeric));
SELECT * FROM orders WHERE (data->>'amount')::numeric > 1000;
```

**Почему по JSONB часто плохие планы — статистика.** Для колонки `jsonb` ANALYZE не собирает статистику по ключам внутри. Поэтому для `data @> '...'` планировщик фактически угадывает: использует небольшую фиксированную оценку селективности (порядка 0,1–1 % строк) — и для `"status":"active"` (90 % строк) ошибается в сотни раз:

```
Bitmap Heap Scan on orders  (rows=10000)  (actual rows=9000000)    ← оценка 10 тыс., реально 9 млн
```

Дальше по плану эта ошибка тянет за собой Nested Loop там, где нужен Hash Join. Решения:

1. **Индекс по выражению** `((data->>'status'))` — у него появляется собственная статистика (MCV, гистограмма), и запросы вида `data->>'status' = ...` оцениваются точно.
2. **Расширенная статистика по выражению (PG14+)** без индекса:
   ```sql
   CREATE STATISTICS st_orders_status ON ((data->>'status')) FROM orders;
   ANALYZE orders;
   ```
3. **Вынести часто фильтруемые поля в обычные колонки.** JSONB — для действительно произвольной структуры; поля, по которым фильтруют/джойнят — колонками. Это самое эффективное.

**Разворачивание массивов JSON:**

```sql
SELECT o.id, item->>'sku' AS sku, (item->>'qty')::int AS qty
FROM orders o, jsonb_array_elements(o.data->'items') AS item
WHERE o.created_at > now() - interval '1 day';
```

```
Nested Loop
  ->  Index Scan using idx_orders_created on orders o
  ->  Function Scan on jsonb_array_elements item  (rows=100)   ← оценка по умолчанию 100
```

Set-returning функции по умолчанию оцениваются в 100 строк, поэтому дальше по плану оценки могут уехать.

**Стоимость обновления JSONB:** `UPDATE ... SET data = jsonb_set(data, '{status}', '"paid"')` переписывает **весь** документ (и TOAST, если он большой), плюс все GIN-записи для изменившихся ключей. Документ 50 КБ → каждый UPDATE пишет 50 КБ + WAL. Частые обновления одного поля — признак того, что поле надо вынести в колонку.

### 11.8 Массивы

```sql
CREATE INDEX idx_tags ON articles USING GIN (tags);

WHERE tags @> ARRAY['postgres']           -- содержит все   → GIN
WHERE tags && ARRAY['pg','mysql']         -- пересекается   → GIN
WHERE tags <@ ARRAY['a','b','c']          -- содержится в   → GIN
WHERE 'postgres' = ANY(tags)              -- ⚠️ GIN не используется → Seq Scan
WHERE array_length(tags, 1) > 3           -- ⚠️ функция → Seq Scan
```

### 11.9 LIKE, ILIKE, регулярные выражения, полнотекстовый поиск

```sql
-- Префикс: B-tree с text_pattern_ops (или collation C)
CREATE INDEX idx_name_prefix ON users (name text_pattern_ops);
WHERE name LIKE 'Ив%'

-- Подстрока, регистронезависимо: триграммы
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_name_trgm ON users USING GIN (name gin_trgm_ops);
WHERE name ILIKE '%ван%'          -- Bitmap Index Scan on idx_name_trgm
-- Триграммный поиск плохо работает для шаблонов короче 3 символов

-- Полнотекстовый поиск
CREATE INDEX idx_fts ON docs USING GIN (to_tsvector('russian', body));
WHERE to_tsvector('russian', body) @@ plainto_tsquery('russian', 'налоговый мониторинг')
-- выражение в WHERE должно ТОЧНО совпадать с выражением индекса (включая 'russian')
-- лучше хранить tsvector в generated column
```

### 11.10 Неявные приведения типов — как найти в плане

```
Seq Scan on orders
  Filter: ((id)::numeric = '12345'::numeric)       ← колонка приведена к numeric → индекс не работает
```

```
Seq Scan on users
  Filter: ((phone)::text = '79001234567'::text)   ← phone типа bigint? char? проверить схему
```

Типичные источники: ORM передаёт `BigDecimal` для `bigint`; JDBC `setString` для числовой колонки с `stringtype=unspecified`; сравнение `varchar` с `uuid`; `timestamp` vs `timestamptz` (приводится, при этом индекс может не использоваться). Правило: смотреть в `Filter`/`Index Cond` на `::тип` вокруг **колонки**, а не вокруг константы.

## 12. Агрегация, сортировка, оконные функции, параллельность, JIT

### 12.1 Агрегация

| Узел | Как работает | Память | Когда |
|------|-------------|--------|-------|
| `Aggregate` (Plain) | один результат для всей выборки | O(1) | `SELECT count(*) FROM ...` |
| `HashAggregate` | хэш-таблица `группа → аккумулятор` | ~число групп × размер | групп не очень много, вход не отсортирован |
| `GroupAggregate` | вход отсортирован по ключу группировки, группы идут подряд | O(1) | есть индекс по ключу / уже отсортировано / групп очень много |
| `MixedAggregate` | GROUPING SETS / ROLLUP | | |
| `Partial` + `Finalize Aggregate` | параллельная агрегация: каждый воркер считает своё, лидер собирает | | большие таблицы |

С PG13 `HashAggregate` при нехватке памяти сбрасывается на диск: в плане `Disk Usage: 512000kB  Batches: 33`. Раньше он мог разрастись за пределы work_mem и привести к OOM.

**Почему COUNT(*) медленный.** Из-за MVCC у PostgreSQL нет «счётчика строк» — видимость каждой строки своя для каждой транзакции. `SELECT count(*) FROM big_table` = скан всей таблицы (или всего индекса через Index Only Scan, если VM актуальна). Для примерной оценки: `SELECT reltuples FROM pg_class WHERE relname = 'orders'`.

### 12.2 Сортировка

| Метод в плане | Что значит |
|---------------|------------|
| `Sort Method: quicksort  Memory: 25kB` | всё в памяти — хорошо |
| `Sort Method: top-N heapsort  Memory: 30kB` | `ORDER BY ... LIMIT N` — держит только N лучших строк |
| `Sort Method: external merge  Disk: 250000kB` | не влезло в work_mem — сортировка на диске |
| `Incremental Sort` (PG13+) | вход уже отсортирован по первой колонке, досортировываем по второй внутри групп |

```sql
-- Индекс убирает сортировку и позволяет остановиться после LIMIT
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at DESC);
SELECT * FROM orders WHERE user_id = 5 ORDER BY created_at DESC LIMIT 20;
-- Limit → Index Scan using idx_orders_user_created  (actual rows=20) — без Sort
```

**Пагинация OFFSET — ловушка:** `LIMIT 20 OFFSET 100000` читает и выбрасывает 100 000 строк. На последних страницах запрос становится всё медленнее. Решение — **keyset pagination**:

```sql
SELECT * FROM orders WHERE user_id = 5 AND created_at < $last_seen
ORDER BY created_at DESC LIMIT 20;
```

### 12.3 Оконные функции

Обычная агрегация `GROUP BY` сжимает строки в одну. Оконная функция считает агрегат, но **строки не сжимает** — каждая остаётся и получает вычисленное поле.

```sql
SELECT user_id, amount,
       SUM(amount)  OVER (PARTITION BY user_id) AS user_total,
       ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at) AS order_num
FROM orders;
-- user_id=1, amount=100, user_total=1500, order_num=1
-- user_id=1, amount=400, user_total=1500, order_num=2
-- user_id=2, amount=200, user_total=800,  order_num=1
```

Синтаксис: `функция() OVER (PARTITION BY колонка ORDER BY колонка [ROWS/RANGE frame])`.

```sql
ROW_NUMBER()  -- 1, 2, 3, 4
RANK()        -- 1, 2, 2, 4  (с пропусками при равенстве)
DENSE_RANK()  -- 1, 2, 2, 3  (без пропусков)
LAG(amount) OVER (PARTITION BY user_id ORDER BY created_at)   -- предыдущее значение
LEAD(...)                                                      -- следующее
SUM(amount) OVER (ORDER BY created_at)                         -- нарастающий итог
AVG(latency) OVER (ORDER BY ts ROWS BETWEEN 59 PRECEDING AND CURRENT ROW)  -- скользящее среднее

-- Последний заказ каждого пользователя
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
  FROM orders
) t WHERE rn = 1;
-- альтернатива, часто быстрее при индексе (user_id, created_at DESC):
SELECT DISTINCT ON (user_id) * FROM orders ORDER BY user_id, created_at DESC;
```

В плане это `WindowAgg` над `Sort` (по `PARTITION BY, ORDER BY`). Сортировка — главная стоимость; индекс по `(user_id, created_at)` её убирает. Строки текущей группы держатся в памяти (tuplestore в work_mem) — большая партиция окна уходит на диск.

### 12.4 Параллельные планы

```
Gather  (Workers Planned: 4, Workers Launched: 4)
  ->  Partial Aggregate
        ->  Parallel Seq Scan on orders
```

- `Gather` — лидер собирает строки от воркеров; `Gather Merge` — сохраняет порядок сортировки.
- Параметры: `max_worker_processes` (общий лимит фоновых процессов), `max_parallel_workers` (лимит параллельных воркеров на сервер), `max_parallel_workers_per_gather` (на один узел Gather), `min_parallel_table_scan_size` (8 МБ — меньше таблицы не параллелятся), `parallel_setup_cost`, `parallel_tuple_cost`.
- `Workers Launched` < `Workers Planned` — воркеров не хватило (все заняты другими запросами). Под нагрузкой это частая причина того, что запрос «то быстрый, то медленный».
- Для OLTP с высоким RPS параллельность часто вредна: каждый воркер — отдельный процесс, при 200 одновременных запросах × 4 воркера CPU захлёбывается. Для OLTP-нагрузки разумно `max_parallel_workers_per_gather = 0–2`.

### 12.5 JIT

С PG11 запросы с высокой оценённой стоимостью (`jit_above_cost = 100000`) компилируются через LLVM. Для аналитики это ускорение, для OLTP — часто **замедление**: компиляция занимает десятки–сотни мс, а запрос выполнился бы за 20 мс. Оценённая стоимость у OLTP-запроса бывает большой из-за неверной статистики.

```
JIT:
  Functions: 42
  Options: Inlining true, Optimization true, Expressions true, Deforming true
  Timing: Generation 5.1 ms, Inlining 60.2 ms, Optimization 110.3 ms, Emission 45.8 ms, Total 221.4 ms
Execution Time: 245.0 ms        ← 221 мс из 245 — это JIT
```

На OLTP-кластере обычно `jit = off` (или поднять `jit_above_cost`).

## 13. Prepared statements: custom и generic планы

### 13.1 Механизм

```sql
PREPARE q(text) AS SELECT * FROM orders WHERE status = $1;
EXECUTE q('pending');
```

- Первые **5 выполнений** PostgreSQL строит **custom plan** — план под конкретное значение параметра (знает, что `'pending'` = 0,1 % строк → Index Scan).
- После 5-го сравнивает среднюю стоимость custom-планов со стоимостью **generic plan** (план без знания значения, по средней селективности). Если generic не дороже — дальше использует его и **перестаёт планировать** (экономия Planning Time).
- Generic plan для `status = $1` оценивает селективность как «среднее значение» → если `'active'` = 90 % строк, а `'pending'` = 0,1 %, generic может выбрать Seq Scan для всех, или наоборот Index Scan для всех.

**Симптом на НТ:** первые секунды теста запрос быстрый, после ~5 выполнений в каждом соединении латентность прыгает. В `pg_stat_statements` среднее хорошее, но p99 плохой.

```sql
SET plan_cache_mode = force_custom_plan;   -- всегда планировать под значения
SET plan_cache_mode = force_generic_plan;  -- всегда generic (меньше CPU на планирование)
SET plan_cache_mode = auto;                -- по умолчанию

-- Посмотреть generic план без выполнения (PG16+)
EXPLAIN (GENERIC_PLAN) SELECT * FROM orders WHERE status = $1;
```

### 13.2 Prepared statements в Java и через PgBouncer

- **PgJDBC** переключает запрос на серверный prepared statement после `prepareThreshold = 5` выполнений одного `PreparedStatement` (по умолчанию). До этого — «безымянный» statement, планируется каждый раз.
- `prepareThreshold=0` — никогда не использовать серверные prepared statements.
- **PgBouncer в transaction mode**: серверные prepared statements привязаны к соединению с PostgreSQL, а PgBouncer в каждой транзакции может дать клиенту **другое** соединение → ошибка `prepared statement "S_1" does not exist`. С PgBouncer 1.21+ это решается параметром `max_prepared_statements` (PgBouncer сам отслеживает и пере-подготавливает statements). На старых версиях — `prepareThreshold=0` в JDBC.
- **Python psycopg3**: `prepare_threshold` (по умолчанию 5) — та же логика; asyncpg кэширует prepared statements агрессивно и тоже требует настройки при PgBouncer (`statement_cache_size=0`).

## 14. MVCC, VACUUM, bloat, wraparound

### 14.1 Зачем MVCC

Без MVCC писатель блокирует читателей, а читатели — писателей. На высоком RPS это узкое место.

MVCC (Multi-Version Concurrency Control) решает: **читатели не блокируют писателей и наоборот**. Каждая транзакция видит согласованный снимок данных.

### 14.2 Как работает

Каждая версия строки хранит `xmin` (кто создал) и `xmax` (кто удалил/обновил, 0 = жива) — см. раздел 2.4.

При UPDATE PostgreSQL **не меняет строку на месте**, а создаёт новую версию:

```
До UPDATE:   (0,1) xmin=100, xmax=0,   status='active'   ← живая
После UPDATE транзакцией 500:
             (0,1) xmin=100, xmax=500, status='active'   ← старая (мёртвая после COMMIT 500)
             (0,4) xmin=500, xmax=0,   status='closed'   ← новая
DELETE — просто проставляет xmax, строка физически остаётся
```

**Снимок (snapshot)** — `xmin` самой старой активной транзакции, `xmax` следующего XID и список активных транзакций. Версия видна, если создавшая её транзакция закоммичена до снимка, а удалившая — нет.

Поэтому `UPDATE` в PostgreSQL = `INSERT` новой версии + пометка старой. Следствия:

- UPDATE пишет столько же, сколько INSERT (плюс индексы, если не HOT);
- таблица с частыми UPDATE постоянно копит мёртвые версии;
- уборку делает VACUUM.

### 14.3 VACUUM и autovacuum

Задачи VACUUM:

1. удаляет мёртвые версии, которые не видны **ни одной** активной транзакции, и освобождает место для повторного использования (FSM);
2. удаляет ссылки на них из индексов;
3. обновляет Visibility Map (для Index Only Scan);
4. «замораживает» старые строки — защита от wraparound;
5. `ANALYZE` (отдельно или вместе) — обновляет статистику.

**Когда autovacuum запускается на таблице:**

```
порог_vacuum  = autovacuum_vacuum_threshold (50) + autovacuum_vacuum_scale_factor (0.2) × reltuples
порог_analyze = autovacuum_analyze_threshold (50) + autovacuum_analyze_scale_factor (0.1) × reltuples
порог_insert  (PG13+) = autovacuum_vacuum_insert_threshold (1000) + 0.2 × reltuples   — для append-only таблиц

Пример: таблица 100 млн строк
  порог_vacuum = 50 + 0.2 × 100 000 000 = 20 000 050 мёртвых строк
  → autovacuum придёт только когда накопится 20 млн мёртвых версий
  → к этому времени таблица и индексы раздуты, запросы читают лишнее
```

Поэтому для больших таблиц scale_factor уменьшают до 0.01–0.05 (раздел 14.5).

**Скорость autovacuum (throttling):** autovacuum специально медленный, чтобы не мешать нагрузке. Он «тратит» бюджет `autovacuum_vacuum_cost_limit` (по умолчанию = `vacuum_cost_limit` = 200) очков, потом спит `autovacuum_vacuum_cost_delay` (2 мс с PG12; было 20 мс). Цена: страница из кэша = 1, с диска = 2 (`vacuum_cost_page_miss`, с PG14), грязная страница = 20. На быстрых дисках бюджет 200 слишком мал — autovacuum не успевает за нагрузкой.

```sql
-- Мёртвые строки и когда последний раз приходил autovacuum
SELECT relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 2) AS dead_pct,
       last_autovacuum, last_autoanalyze, autovacuum_count
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 20;
-- dead_pct > 10–20 % — autovacuum не успевает

-- Что делает autovacuum прямо сейчас
SELECT pid, relid::regclass, phase, heap_blks_total, heap_blks_scanned, heap_blks_vacuumed,
       index_vacuum_count
FROM pg_stat_progress_vacuum;
```

### 14.4 Почему VACUUM не может убрать мёртвые строки — «горизонт»

VACUUM удаляет версию только если её не может увидеть **ни одна** транзакция. Самая старая из живых транзакций держит «горизонт»:

- **Долгая транзакция** (открыли транзакцию в отчёте на 2 часа, или `idle in transaction`) → все версии, удалённые за эти 2 часа во **всех** таблицах базы, нельзя удалить.
- **Слот репликации**, который никто не читает, (`pg_replication_slots` с `active = false`) — держит и WAL, и горизонт (если `hot_standby_feedback`).
- **Реплика с `hot_standby_feedback = on`**, на которой идёт долгий запрос.
- **Забытые prepared transactions** (`pg_prepared_xacts`).

```sql
-- Самые старые транзакции
SELECT pid, usename, state, now() - xact_start AS xact_age, backend_xmin, left(query, 80)
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY age(backend_xmin) DESC LIMIT 10;

-- Слоты репликации
SELECT slot_name, active, xmin, catalog_xmin,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
FROM pg_replication_slots;
```

В логе VACUUM (`log_autovacuum_min_duration = 0`) это видно как `tuples: 0 removed, 2000000 remain, 2000000 are dead but not yet removable`.

### 14.5 Тюнинг autovacuum под высокий RPS

Глобально:

```
autovacuum_max_workers = 5                 # по умолчанию 3 (с PG18 можно менять без рестарта
                                           #   в пределах autovacuum_worker_slots)
autovacuum_naptime = 15s                   # как часто проверять таблицы (по умолчанию 1 мин)
autovacuum_vacuum_scale_factor = 0.02      # 2 % вместо 20 %
autovacuum_analyze_scale_factor = 0.01
autovacuum_vacuum_cost_limit = 2000        # бюджет делится между всеми воркерами!
autovacuum_vacuum_cost_delay = 2ms
maintenance_work_mem / autovacuum_work_mem = 1GB   # память под список мёртвых ctid
log_autovacuum_min_duration = 1s           # логировать долгие проходы
```

Для конкретной горячей таблицы:

```sql
ALTER TABLE payments SET (
  autovacuum_vacuum_scale_factor = 0.01,
  autovacuum_vacuum_threshold    = 1000,
  autovacuum_vacuum_cost_delay   = 1,
  autovacuum_vacuum_cost_limit   = 1000,
  fillfactor = 85
);
```

### 14.6 VACUUM vs VACUUM FULL vs pg_repack

```
VACUUM orders
  — помечает место как свободное для повторного использования
  — файл НЕ уменьшается (кроме пустых страниц в самом конце)
  — НЕ блокирует чтение и запись (ShareUpdateExclusiveLock)

VACUUM FULL orders
  — физически переписывает таблицу и индексы, файл уменьшается
  — ACCESS EXCLUSIVE: блокирует ВСЁ, включая SELECT, на всё время работы
  — нужно место под полную копию
  — только в окно обслуживания

pg_repack -t orders
  — как VACUUM FULL, но таблица доступна почти всё время
  — эксклюзивная блокировка только на короткий момент подмены
  — для production
```

### 14.7 Bloat

**Bloat** — таблица/индекс физически больше, чем нужно для живых данных. Seq Scan читает 80 ГБ вместо 30, в кэш помещается меньше полезного.

Причины: autovacuum не успевает, горизонт держит долгая транзакция, массовый DELETE/UPDATE (место освобождено, но файл не уменьшится сам).

```sql
-- Быстрая оценка по статистике
SELECT relname,
       n_dead_tup * 100.0 / nullif(n_live_tup + n_dead_tup, 0) AS dead_ratio,
       pg_size_pretty(pg_total_relation_size(relid))            AS total_size
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC;

-- Точно (читает таблицу целиком — осторожно на проде)
CREATE EXTENSION pgstattuple;
SELECT * FROM pgstattuple('orders');          -- dead_tuple_percent, free_percent
SELECT * FROM pgstattuple_approx('orders');   -- быстрее, по Visibility Map
SELECT * FROM pgstatindex('idx_orders_user_id');  -- avg_leaf_density < 50 % → индекс раздут
```

### 14.8 Transaction ID Wraparound

XID — 32-битный счётчик, ~4,2 млрд значений, а сравнение «старше/младше» работает по кругу в окне ±2,1 млрд. Если не «заморозить» строки старше ~2 млрд транзакций, они внезапно станут «из будущего» и пропадут из видимости. Чтобы этого не случилось, autovacuum выполняет **заморозку** (`FREEZE`) — помечает строки как видимые всем навсегда.

- `autovacuum_freeze_max_age = 200 млн` — после этого возраста autovacuum придёт на таблицу **принудительно** (aggressive vacuum, читает все не-frozen страницы — тяжёлый, его нельзя отменить по `autovacuum` lock conflict обычным способом).
- Если возраст подходит к ~2 млрд — PostgreSQL перестаёт выдавать новые XID и требует ручной VACUUM. Это авария.

```sql
SELECT datname, age(datfrozenxid) AS xid_age FROM pg_database ORDER BY xid_age DESC;
SELECT relname, age(relfrozenxid) AS xid_age FROM pg_class WHERE relkind = 'r' ORDER BY 2 DESC LIMIT 10;
-- xid_age > 1,5 млрд — тревога; > 200 млн — идёт или скоро пойдёт aggressive vacuum
```

**На НТ:** высокий RPS записи (особенно короткие транзакции по одной строке) сжигает XID быстро. 5000 TPS × 86400 с = 432 млн XID в сутки → aggressive vacuum большой таблицы будет срабатывать примерно раз в 11 часов; в момент его работы может быть всплеск I/O и latency. Батчинг записей в одну транзакцию экономит XID.

## 15. Уровни изоляции и ACID

### 15.1 Аномалии

- **Dirty Read** — читаешь незакоммиченные данные другой транзакции; та откатилась — ты работал с несуществующими данными.
- **Non-repeatable Read** — читаешь одну строку дважды в одной транзакции, получаешь разные значения (другая транзакция изменила и закоммитила между чтениями).
- **Phantom Read** — одинаковый запрос дважды, во второй раз появились новые строки.
- **Lost Update** — две транзакции прочитали одно значение, обе записали своё, одно изменение потерялось.
- **Serialization anomaly (write skew)** — две транзакции читают пересекающиеся данные и пишут непересекающиеся, результат невозможен ни при каком последовательном порядке. Пример: два врача одновременно проверяют «на смене есть ещё кто-то» и оба уходят.

### 15.2 Уровни

| Уровень                      | Dirty Read | Non-repeatable | Phantom   | Serialization anomaly |
| ---------------------------- | ---------- | -------------- | --------- | --------------------- |
| READ UNCOMMITTED             | нет*       | возможен       | возможен  | возможна              |
| READ COMMITTED ← **default** | нет        | возможен       | возможен  | возможна              |
| REPEATABLE READ              | нет        | нет            | нет**     | возможна              |
| SERIALIZABLE                 | нет        | нет            | нет       | нет                   |

\* В PostgreSQL `READ UNCOMMITTED` ведёт себя как `READ COMMITTED` — грязного чтения нет вообще.
\** PostgreSQL защищает от фантомов уже на REPEATABLE READ благодаря снимку на всю транзакцию.

**READ COMMITTED** — снимок берётся на **каждый оператор**. Максимальный RPS, минимум конфликтов. Если UPDATE натыкается на строку, которую изменила и закоммитила параллельная транзакция, он перечитывает свежую версию и применяет условие заново.

**REPEATABLE READ** — снимок один на всю транзакцию. Для отчётов и аудита, где все SELECT-ы должны видеть одно состояние.

```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1; -- 1000
-- другая транзакция изменила на 500 и закоммитила
SELECT balance FROM accounts WHERE id = 1; -- всё равно 1000
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- ERROR: could not serialize access due to concurrent update  → нужен retry
COMMIT;
```

**SERIALIZABLE** (SSI — Serializable Snapshot Isolation) — результат как при последовательном выполнении. PostgreSQL отслеживает зависимости чтения/записи через предикатные блокировки (`SIReadLock` в `pg_locks`) и при опасной структуре откатывает одну транзакцию с ошибкой `40001 serialization_failure`.

### 15.3 Влияние на производительность

- READ COMMITTED → максимальный RPS.
- REPEATABLE READ → снимок держится всю транзакцию → длинные RR-транзакции держат горизонт VACUUM (раздел 14.4).
- SERIALIZABLE → накладные расходы на предикатные блокировки (память `max_pred_locks_per_transaction`), и главное — **retry**: при высокой конкуренции доля откатов растёт, и полезный RPS падает в разы. На НТ обязательно считать долю ошибок `40001` и проверять, что приложение умеет повторять транзакцию.

### 15.4 ACID

| Буква | Свойство                      | Что означает                                                 | Чем обеспечивается в PostgreSQL |
| ----- | ----------------------------- | ------------------------------------------------------------ | ------------------------------- |
| A     | Atomicity (атомарность)       | транзакция целиком или никак                                 | MVCC: незакоммиченные версии просто невидимы и потом вычищаются |
| C     | Consistency (согласованность) | все constraints соблюдены до и после                         | constraints, FK, триггеры        |
| I     | Isolation (изоляция)          | транзакции не мешают друг другу (по уровню изоляции)         | снимки MVCC, блокировки, SSI     |
| D     | Durability (долговечность)    | после COMMIT данные не потеряются при падении                | WAL + fsync                      |

## 16. WAL и checkpoint

### 16.1 Принцип

**Write-Ahead Log**: «сначала запиши в журнал, потом меняй данные». Изменение считается сохранённым, когда **запись WAL** надёжно на диске; сами страницы данных могут писаться позже.

```
UPDATE orders SET status='closed' WHERE id=123;  COMMIT;

1. Изменение страницы в shared_buffers (страница становится dirty), запись WAL-record в wal_buffers
2. COMMIT → WAL сбрасывается на диск (write + fsync) до этой точки
   → клиенту отвечаем OK
3. Позже checkpointer / bgwriter запишет грязную страницу в файл таблицы
```

Почему это быстрее: WAL пишется **последовательно** в конец файла (дёшево даже для HDD), а страницы данных — случайно по всему диску. Коммит ждёт только последовательной записи.

**Восстановление после падения:** берём последний checkpoint и проигрываем WAL от него вперёд — получаем все закоммиченные изменения.

### 16.2 Стоимость коммита — fsync

Каждый COMMIT ждёт `fsync` WAL. На SSD с конденсаторами (enterprise) это ~0,05–0,2 мс, на дешёвом SSD без защиты от потери питания — 1–5 мс, на сетевом диске (Ceph, облачный блочный том) — 1–10 мс. **Это нижняя граница latency любой пишущей транзакции.**

Расчёт: fsync = 2 мс, все транзакции идут последовательно → максимум 500 коммитов/с. На практике помогает **group commit**: пока идёт один fsync, другие транзакции копятся, и следующий fsync подтверждает их пачкой. Параметры `commit_delay` / `commit_siblings` позволяют специально подождать соседей.

```
synchronous_commit = on       # ждём fsync (по умолчанию)
synchronous_commit = off      # не ждём: ответ клиенту сразу, fsync позже (до 3 × wal_writer_delay ≈ 600 мс)
                              # при падении сервера теряются последние закоммиченные транзакции,
                              # но база НЕ повреждается. Можно ставить на сессию/транзакцию:
SET LOCAL synchronous_commit = off;   -- для некритичных записей (логи, метрики)
```

Метрика: в `pg_stat_activity` много сессий с `wait_event = 'WALWrite'` / `'WALSync'` → упираемся в диск WAL. Отдельный быстрый диск под `pg_wal` решает.

### 16.3 Checkpoint

Checkpoint — момент, когда все грязные страницы из shared_buffers записываются в файлы данных. После этого WAL до этой точки не нужен для восстановления и может быть удалён/переиспользован.

Когда происходит:

- по времени — `checkpoint_timeout` (5 мин по умолчанию);
- по объёму — накопилось `max_wal_size` WAL (1 ГБ по умолчанию);
- вручную `CHECKPOINT`, при остановке сервера.

**Почему checkpoint виден на НТ как всплеск latency:**

1. Запись большого количества грязных страниц нагружает диск — запросам, которым нужно читать с диска, приходится ждать в очереди.
2. **Full page writes:** после каждого checkpoint **первое** изменение каждой страницы пишет в WAL её **полную копию 8 КБ** (защита от «порванных» страниц при сбое). Сразу после checkpoint объём WAL резко растёт, потом снижается — «пила» на графике WAL.

```
checkpoint_timeout = 15min            # реже checkpoint → меньше full page writes, но дольше recovery
max_wal_size = 8GB                    # чтобы checkpoint шёл по времени, а не по объёму
checkpoint_completion_target = 0.9    # растянуть запись на 90 % интервала (по умолчанию 0.9 с PG14)
wal_compression = lz4                 # сжатие full page images (PG15+: lz4/zstd)
log_checkpoints = on                  # по умолчанию on с PG15
```

```sql
-- Сколько checkpoint-ов произошло по времени и по требованию (PG17+)
SELECT num_timed, num_requested, write_time, sync_time, buffers_written
FROM pg_stat_checkpointer;
-- До PG17: SELECT checkpoints_timed, checkpoints_req FROM pg_stat_bgwriter;
-- num_requested >> num_timed → max_wal_size мал, checkpoint-ы идут слишком часто
```

В логе при `log_checkpoints`: `checkpoints are occurring too frequently (12 seconds apart)` — явный признак маленького `max_wal_size`.

### 16.4 Репликация через WAL

Реплики получают поток WAL от мастера (`walsender` → `walreceiver`) и применяют те же изменения. Подробно — раздел 18.

## 17. Блокировки

### 17.1 MVCC и блокировки — два независимых механизма

- MVCC управляет **видимостью** версий для читателей.
- Блокировки управляют **доступом** писателей к одним и тем же строкам и объектам.
- Обычный SELECT никогда не блокирует UPDATE, UPDATE никогда не блокирует обычный SELECT.
- Два UPDATE одной строки — второй ждёт, пока первая транзакция закончится.

### 17.2 Уровни блокировок таблиц (самые важные)

| Блокировка | Кто берёт | С чем конфликтует |
|------------|-----------|-------------------|
| `ACCESS SHARE` | SELECT | только с ACCESS EXCLUSIVE |
| `ROW EXCLUSIVE` | INSERT, UPDATE, DELETE | SHARE и выше (CREATE INDEX без CONCURRENTLY) |
| `SHARE UPDATE EXCLUSIVE` | VACUUM, ANALYZE, CREATE INDEX CONCURRENTLY | сама с собой и выше |
| `SHARE` | CREATE INDEX | с записью |
| `ACCESS EXCLUSIVE` | DROP, TRUNCATE, VACUUM FULL, CLUSTER, большинство ALTER TABLE | **со всем, включая SELECT** |

**Очередь блокировок — классическая авария на проде:**

```
1. Долгий SELECT держит ACCESS SHARE на orders (отчёт на 10 минут)
2. Миграция: ALTER TABLE orders ADD COLUMN ... — хочет ACCESS EXCLUSIVE, встаёт в очередь
3. Все новые SELECT/INSERT по orders встают в очередь ЗА ALTER TABLE
   (иначе ALTER никогда бы не получил блокировку)
→ таблица фактически недоступна 10 минут, пулы соединений забиваются ожидающими
```

Защита: перед DDL `SET lock_timeout = '3s'` — если не получил блокировку за 3 с, отвалиться и повторить позже.

### 17.3 Блокировки строк

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;   -- строка заблокирована для изменений
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

Без `FOR UPDATE` — lost update: две транзакции прочитали 1000, обе записали 900 вместо 800. Альтернатива — атомарный UPDATE `SET balance = balance - 100` без предварительного SELECT.

| Режим | Смысл |
|-------|-------|
| `FOR UPDATE` | собираюсь изменить/удалить строку |
| `FOR NO KEY UPDATE` | собираюсь изменить, но не ключ (берёт UPDATE без смены ключа автоматически) |
| `FOR SHARE` | строку нельзя менять, пока я работаю |
| `FOR KEY SHARE` | нельзя менять ключ/удалять (берётся при проверке FK) |
| `NOWAIT` | не ждать — сразу ошибка |
| `SKIP LOCKED` | пропустить заблокированные строки |

**Очередь задач на PostgreSQL** (используется в джоб-шедулерах):

```sql
-- Каждый воркер берёт свою пачку, не мешая другим
UPDATE jobs SET status = 'running', worker = $1
WHERE id IN (
  SELECT id FROM jobs WHERE status = 'new'
  ORDER BY created_at LIMIT 10
  FOR UPDATE SKIP LOCKED
)
RETURNING *;
```

Блокировки строк хранятся **в самой строке** (поле xmax + infomask), а не в памяти — поэтому можно заблокировать хоть миллион строк. Но ожидание блокировки строки видно в `pg_locks` как ожидание транзакции (`locktype = 'transactionid'`).

### 17.4 Deadlock

```
Транзакция А: заблокировала id=1, хочет id=2
Транзакция Б: заблокировала id=2, хочет id=1  → взаимная блокировка
```

PostgreSQL через `deadlock_timeout` (1 с) запускает проверку графа ожиданий и откатывает одну транзакцию: `ERROR: deadlock detected`. Как избежать — блокировать ресурсы в одном порядке:

```sql
SELECT * FROM accounts WHERE id IN (1, 2) ORDER BY id FOR UPDATE;
```

`log_lock_waits = on` — в лог попадут все ожидания дольше deadlock_timeout. На НТ это самый быстрый способ увидеть lock contention.

### 17.5 Диагностика блокировок

```sql
-- Кто кого блокирует
SELECT blocked.pid                    AS blocked_pid,
       left(blocked.query, 60)        AS blocked_query,
       now() - blocked.query_start    AS blocked_for,
       blocking.pid                   AS blocking_pid,
       blocking.state                 AS blocking_state,
       left(blocking.query, 60)       AS blocking_query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking ON blocking.pid = ANY(pg_blocking_pids(blocked.pid));

-- idle in transaction — держит блокировки и соединение, держит горизонт VACUUM
SELECT pid, now() - state_change AS idle_for, left(query, 80)
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY idle_for DESC;

SELECT pg_cancel_backend(pid);     -- отменить текущий запрос
SELECT pg_terminate_backend(pid);  -- убить соединение

-- Системная защита
ALTER SYSTEM SET idle_in_transaction_session_timeout = '60s';
ALTER SYSTEM SET lock_timeout = '10s';           -- лучше на уровне роли приложения
ALTER SYSTEM SET statement_timeout = '30s';      -- лучше на уровне роли/сессии
-- PG17+: transaction_timeout — ограничение всей транзакции
```

### 17.6 Advisory Locks — пользовательские блокировки

Блокировки, смысл которых придумывает приложение. PostgreSQL не знает, что они защищают — это просто числа. Альтернатива Redis-блокировкам, когда всё приложение работает с одной БД.

```sql
-- Session-level — живёт, пока живёт соединение (или до unlock)
SELECT pg_advisory_lock(12345);          -- блокирующий, ждёт
SELECT pg_try_advisory_lock(12345);      -- неблокирующий: true/false
SELECT pg_advisory_unlock(12345);

-- Transaction-level — снимается автоматически при COMMIT/ROLLBACK
BEGIN;
SELECT pg_advisory_xact_lock(12345);
SELECT pg_try_advisory_xact_lock(12345);
COMMIT;

-- Ключ из строки или пары чисел
SELECT pg_advisory_lock(hashtext('nightly_report'));
SELECT pg_advisory_lock(1, 123);   -- 1 = тип операции, 123 = order_id
```

Сценарии:

```sql
-- Ночной отчёт — только один инстанс из пяти
SELECT pg_try_advisory_lock(hashtext('nightly_report'));
-- инстанс-1: true → делает отчёт; инстансы 2–5: false → пропускают

-- Обработка задачи ровно одним воркером
BEGIN;
SELECT pg_try_advisory_xact_lock(job_id);   -- false → другой воркер уже взял
UPDATE jobs SET status = 'done' WHERE id = job_id;
COMMIT;
```

⚠️ **Session-level advisory lock + PgBouncer в transaction mode = ошибка.** Блокировка привязана к серверному соединению, а PgBouncer отдаст его другому клиенту после транзакции — блокировка «уедет» к чужому клиенту. С PgBouncer в transaction mode — только `pg_advisory_xact_lock`.

|                              | Advisory Lock   | Redis Lock          |
| ---------------------------- | --------------- | ------------------- |
| Нужен Redis                  | нет             | да                  |
| Атомарно с транзакцией БД    | да (xact-вариант)| нет                |
| Несколько сервисов с разными БД | нет          | да                  |
| Автоснятие при разрыве       | да (соединение) | да (TTL)            |

```sql
SELECT pid, locktype, classid, objid, mode, granted
FROM pg_locks WHERE locktype = 'advisory';
-- granted = true — держит; false — ждёт
```

## 18. Репликация, Patroni, CAP

### 18.1 Физическая потоковая репликация

```
Мастер: backend пишет WAL → walsender читает WAL → TCP → walreceiver на реплике
        → пишет WAL на диск реплики → startup-процесс применяет (replay)
```

```
Мастер:   запись + чтение
Реплика:  только чтение (hot standby)
          INSERT → ERROR: cannot execute INSERT in a read-only transaction
```

**Асинхронная (по умолчанию):** мастер отвечает клиенту после локального fsync WAL, реплике отправляет «когда получится». Быстро; при падении мастера последние транзакции могут быть потеряны (RPO > 0).

**Синхронная:** `synchronous_standby_names = 'FIRST 1 (replica1, replica2)'` — COMMIT ждёт подтверждения реплики. Уровень ожидания задаёт `synchronous_commit`:

| `synchronous_commit` | Ответ клиенту после | Потеря при падении мастера | Цена |
|----------------------|--------------------|----------------------------|------|
| `off`                | без ожидания fsync | последние ~600 мс           | минимальная |
| `local`              | fsync на мастере   | что не дошло до реплики     | fsync |
| `remote_write`       | реплика получила и записала в ОС | только при одновременном падении ОС реплики | fsync + RTT |
| `on`                 | реплика сделала fsync | нет                      | fsync + RTT + fsync реплики |
| `remote_apply`       | реплика применила (видно в запросах к ней) | нет, + read-your-writes на реплике | максимальная |

**Влияние сети:** при синхронной репликации **каждый коммит ждёт сетевой RTT до реплики**. Реплика в соседнем ЦОДе с RTT 2 мс + её fsync 1 мс → +3 мс к каждой пишущей транзакции. Если реплика тормозит или сеть до неё перегружена — тормозят **все коммиты на мастере** (в `pg_stat_activity` — `wait_event = 'SyncRep'`). Если синхронная реплика недоступна, а другой нет — коммиты зависают совсем.

### 18.2 Replication lag

```sql
-- На мастере
SELECT application_name, client_addr, state, sync_state,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), sent_lsn))   AS not_sent,
       pg_size_pretty(pg_wal_lsn_diff(sent_lsn, flush_lsn))              AS not_flushed,
       pg_size_pretty(pg_wal_lsn_diff(flush_lsn, replay_lsn))            AS not_replayed,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;

-- На реплике
SELECT now() - pg_last_xact_replay_timestamp() AS replay_delay;
```

Где застряло — так и ищешь причину:

| Большой разрыв | Причина |
|----------------|---------|
| `not_sent` | мастер не успевает отправлять или **сеть** не тянет объём WAL (смотри трафик интерфейса: 200 МБ/с WAL при канале 1 Гбит/с = 125 МБ/с → лаг растёт бесконечно) |
| `not_flushed` | диск реплики медленный |
| `not_replayed` | replay однопоточный — реплика не успевает применять, или replay приостановлен конфликтом с долгим запросом на реплике (`max_standby_streaming_delay`) |

**Конфликты на реплике:** VACUUM на мастере удалил версии, которые читает долгий запрос на реплике. Реплика либо ждёт (`max_standby_streaming_delay = 30s`, лаг растёт), либо отменяет запрос: `ERROR: canceling statement due to conflict with recovery`. `hot_standby_feedback = on` убирает отмены, но реплика начинает держать горизонт VACUUM мастера → bloat на мастере.

### 18.3 Что можно читать с реплики

```
Можно (некритично к отставанию):     Только с мастера:
✓ справочники, каталоги              ✗ данные, которые этот пользователь только что записал
✓ аналитика и отчёты                 ✗ финансовые проверки «достаточно ли средств»
✓ исторические данные                ✗ всё, где важна актуальность прямо сейчас
```

**Read-your-writes:** пользователь записал на мастер и сразу читает с реплики — видит старые данные. Решения: критичное читать с мастера; после записи в течение N секунд направлять сессию на мастер; LSN tracking — запомнить LSN после записи (`pg_current_wal_lsn()`) и читать с реплики, только если `pg_last_wal_replay_lsn() >= этот LSN`.

### 18.4 Логическая репликация

|                   | Физическая                    | Логическая                        |
| ----------------- | ----------------------------- | --------------------------------- |
| Что передаёт      | байты WAL (изменения страниц) | строки: INSERT/UPDATE/DELETE      |
| Реплика           | точная копия, read-only       | обычная БД, можно писать          |
| Версии PostgreSQL | одинаковые major              | могут различаться                 |
| Отдельные таблицы | нельзя                        | можно                             |
| DDL               | реплицируется                 | **не реплицируется**              |
| Использование     | HA, масштабирование чтения    | миграции между версиями, выгрузка в другие системы, CDC (Debezium) |

```sql
CREATE PUBLICATION my_pub FOR TABLE orders, users;                                     -- на источнике
CREATE SUBSCRIPTION my_sub CONNECTION 'host=primary dbname=mydb' PUBLICATION my_pub;   -- на приёмнике
```

Требует `wal_level = logical` и **слот репликации**. Брошенный слот (подписчик умер) держит WAL бесконечно → диск мастера заканчивается. В PG13+ ограничивается `max_slot_wal_keep_size`.

### 18.5 Patroni — автоматический failover

PostgreSQL умеет репликацию, но **не умеет сам переключать мастер**. Без внешнего инструмента при падении мастера нужен администратор — простой 15–30 минут. С Patroni — 30–60 секунд.

```
etcd / Consul / ZooKeeper (DCS: хранит «кто лидер» с TTL-арендой)
    │
    ├── Patroni агент + PostgreSQL МАСТЕР    (узел 1)  — каждые loop_wait (10 с) продлевает аренду
    ├── Patroni агент + PostgreSQL реплика   (узел 2)
    └── Patroni агент + PostgreSQL реплика   (узел 3)
```

**Как происходит failover:**

1. Мастер перестал продлевать аренду лидера в DCS (упал сервер, сеть, процесс).
2. Агенты ждут истечения `ttl` (30 с по умолчанию).
3. Реплики сравнивают свои позиции WAL; кандидатом становится наиболее догнавшая (с учётом `maximum_lag_on_failover`).
4. Победитель захватывает ключ лидера в DCS и делает `pg_ctl promote`.
5. Остальные реплики переключаются на нового мастера.
6. Старый мастер, если вернётся, увидит, что лидер другой, и станет репликой (при необходимости через `pg_rewind`).

**Защита от split-brain:** если сам мастер потерял связь с DCS и не может продлить аренду — Patroni **понижает его до read-only**. Лучше недоступность записи, чем два мастера с разными данными.

```bash
patronictl -c /etc/patroni.yml list                      # состояние, роли, Lag in MB
patronictl -c /etc/patroni.yml switchover                # плановое переключение
patronictl -c /etc/patroni.yml failover                  # аварийное
patronictl -c /etc/patroni.yml restart <cluster> node2
patronictl -c /etc/patroni.yml edit-config               # изменить параметры PostgreSQL на всём кластере
```

`Lag in MB` в `patronictl list` — отставание реплики в мегабайтах WAL. Норма — 0 или около. Если растёт под нагрузкой — при failover потеряешь (асинхронная репликация) или реплика не будет выбрана кандидатом.

**Как приложение находит мастера:** HAProxy (или keepalived/VIP, или Kubernetes Service) опрашивает REST API Patroni:

```bash
curl -s -o /dev/null -w '%{http_code}' http://node1:8008/primary   # 200 = мастер, 503 = нет
curl -s -o /dev/null -w '%{http_code}' http://node1:8008/replica   # 200 = реплика
```

Альтернатива без балансировщика — **multi-host строка подключения** в драйвере: `jdbc:postgresql://node1,node2,node3/db?targetServerType=primary`.

**Тест отказоустойчивости на НТ:** под нагрузкой выполнить `patronictl switchover`/убить мастер и измерить: сколько секунд запросы падали, сколько ошибок, как быстро пул соединений приложения переподключился (пулы часто держат «мёртвые» соединения до таймаута — это ещё одна причина ставить TCP keepalive, раздел 21).

### 18.6 CAP-теорема

Распределённая система при сетевом разделении (P) должна выбрать: отвечать согласованно (C) или отвечать всегда (A).

- **C — Consistency** — все узлы видят одни данные.
- **A — Availability** — каждый запрос получает ответ.
- **P — Partition tolerance** — система работает при потере связи между узлами.

Сеть рвётся всегда, поэтому P обязательна, выбор — между C и A.

- **PostgreSQL + Patroni = CP.** При потере кворума DCS мастер понижается — лучше недоступность записи, чем split-brain. Правильно для финансов.
- **Redis Cluster = AP.** При разделении продолжает работать, может вернуть устаревшие данные или потерять записи. Приемлемо для кэша.

Ответ на собесе: «PostgreSQL с Patroni — CP: при потере кворума предпочтёт недоступность записи, а не split-brain. Redis Cluster — AP: продолжит отвечать, но может вернуть устаревшие данные; для кэша это нормально».

## 19. Партиционирование, materialized views, CTE, триггеры, процедуры

### 19.1 Партиционирование

Большая таблица разбивается на части; каждая партиция — отдельная физическая таблица со своими индексами.

**Типы:**

```sql
-- Range — по диапазону (самый частый: по дате)
CREATE TABLE events (id bigint, created_at timestamptz, payload jsonb)
  PARTITION BY RANGE (created_at);
CREATE TABLE events_2025_01 PARTITION OF events
  FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');

-- List — по конкретным значениям
CREATE TABLE orders_by_region (...) PARTITION BY LIST (region);
CREATE TABLE orders_msk PARTITION OF orders_by_region FOR VALUES IN ('msk', 'mo');

-- Hash — равномерное распределение
CREATE TABLE sessions (...) PARTITION BY HASH (user_id);
CREATE TABLE sessions_p0 PARTITION OF sessions FOR VALUES WITH (MODULUS 8, REMAINDER 0);
```

**Partition pruning** — планировщик пропускает партиции, которые не могут содержать нужные строки:

```sql
EXPLAIN SELECT * FROM events WHERE created_at >= '2025-03-01' AND created_at < '2025-03-08';
-- Append
--   ->  Index Scan on events_2025_03 ...   ← только одна партиция
```

- Pruning на этапе планирования — если значение известно (литерал, `now()`).
- Pruning на этапе выполнения (`Subplans Removed: 23`) — для параметров prepared statements и значений из JOIN.
- **Если в WHERE нет ключа партиционирования — читаются ВСЕ партиции**, это хуже, чем без партиционирования (N сканов индексов вместо одного).

**Плюсы:**

- удаление старых данных: `DROP TABLE events_2021_01` — мгновенно, без bloat, вместо многочасового DELETE;
- индексы каждой партиции меньше → верхние уровни и горячая партиция в кэше;
- VACUUM работает по партициям, старые неизменные партиции не трогает;
- можно держать старые партиции на медленном диске (tablespace).

**Минусы и подводные камни:**

- уникальный индекс/PK обязан включать ключ партиционирования;
- много партиций (тысячи) → растёт `Planning Time` и потребление памяти (lock на каждую партицию при планировании);
- запросы без partition key — медленнее;
- нужна автоматизация создания будущих партиций (`pg_partman` или cron) — иначе INSERT за новый месяц упадёт: `no partition of relation "events" found for row` (или уйдёт в `DEFAULT` партицию, которая потом мешает создавать новые).

**Когда НЕ нужно:** таблица меньше 10–50 ГБ, нет чёткого ключа, запросы не фильтруют по ключу.

### 19.2 Materialized Views

|                 | View                         | Materialized View         |
| --------------- | ---------------------------- | ------------------------- |
| Хранит данные   | нет (это сохранённый запрос) | да, на диске как таблица  |
| Скорость чтения | как исходный запрос          | как чтение таблицы        |
| Актуальность    | всегда свежие                | на момент последнего REFRESH |
| Индексы         | нельзя                       | можно                     |

```sql
CREATE MATERIALIZED VIEW user_stats AS
SELECT u.id, u.name, count(o.id) AS order_count, sum(o.amount) AS total
FROM users u LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id, u.name;

CREATE UNIQUE INDEX ON user_stats (id);
REFRESH MATERIALIZED VIEW CONCURRENTLY user_stats;
-- CONCURRENTLY: читатели не блокируются, но нужен UNIQUE индекс и работает дольше
-- без CONCURRENTLY: ACCESS EXCLUSIVE на время пересчёта
```

REFRESH всегда пересчитывает **весь** запрос (инкрементального обновления в ядре нет). Тяжёлый REFRESH во время НТ — источник всплесков I/O.

### 19.3 CTE (Common Table Expressions)

```sql
WITH active_orders AS (
  SELECT user_id, sum(amount) AS total
  FROM orders WHERE status = 'ACTIVE' GROUP BY user_id
)
SELECT u.name, ao.total FROM users u
JOIN active_orders ao ON ao.user_id = u.id WHERE ao.total > 1000;
```

- **До PG12** CTE всегда материализовался (optimization fence): планировщик не мог протолкнуть условия внутрь. Отсюда миф «CTE медленные».
- **С PG12** CTE без побочных эффектов, использованный **один раз**, встраивается в запрос как подзапрос.

```sql
WITH x AS NOT MATERIALIZED (...)   -- принудительно встроить
WITH x AS MATERIALIZED (...)       -- принудительно вычислить один раз (полезно, если CTE используется несколько раз
                                   -- или как «забор» против плохого плана)
```

**Рекурсивный CTE** — для иерархий:

```sql
WITH RECURSIVE tree AS (
  SELECT id, name, parent_id, 0 AS level FROM categories WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, c.name, c.parent_id, t.level + 1
  FROM categories c JOIN tree t ON t.id = c.parent_id
)
SELECT * FROM tree ORDER BY level, name;
-- нужен индекс на categories(parent_id); защититься от циклов (CYCLE clause с PG14)
```

### 19.4 Триггеры

```sql
CREATE FUNCTION log_changes() RETURNS trigger AS $$
BEGIN
  INSERT INTO audit_log VALUES (NEW.id, OLD.status, NEW.status, now());
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_order_change
  AFTER UPDATE OF status ON orders
  FOR EACH ROW EXECUTE FUNCTION log_changes();
```

```
BEFORE → до изменения: можно изменить NEW или отменить операцию (RETURN NULL)
AFTER  → после изменения: данные уже записаны
FOR EACH ROW       → UPDATE 1000 строк = 1000 вызовов
FOR EACH STATEMENT → один вызов на весь оператор (с transition tables NEW TABLE/OLD TABLE)
```

**Влияние на производительность:**

- `FOR EACH ROW` при массовых операциях = миллион вызовов PL/pgSQL;
- триггер выполняется **внутри транзакции** — всё, что он делает, удлиняет транзакцию и держит блокировки;
- **никогда не делать сетевые вызовы из триггера** (HTTP, dblink) — транзакция ждёт сеть, соединения копятся;
- триггеры не видны в `EXPLAIN` основного запроса, кроме строки `Trigger trg_order_change: time=850.2 calls=10000` в конце `EXPLAIN ANALYZE`.

**Transactional Outbox** — правильный паттерн «отправить событие при изменении»:

```sql
-- Триггер (или само приложение в той же транзакции) только пишет событие в таблицу
INSERT INTO outbox (aggregate_id, event_type, payload) VALUES (NEW.id, 'ORDER_PAID', ...);
-- Отдельный воркер читает outbox (FOR UPDATE SKIP LOCKED) и отправляет в Kafka/HTTP
-- Событие отправится, только если транзакция закоммичена — без двойной записи
```

### 19.5 Функции и процедуры

```sql
-- Функция: возвращает значение, вызывается в SELECT, не управляет транзакцией
CREATE OR REPLACE FUNCTION transfer(from_id bigint, to_id bigint, amount numeric)
RETURNS void AS $$
BEGIN
  IF (SELECT balance FROM accounts WHERE id = from_id FOR UPDATE) < amount THEN
    RAISE EXCEPTION 'Недостаточно средств';
  END IF;
  UPDATE accounts SET balance = balance - amount WHERE id = from_id;
  UPDATE accounts SET balance = balance + amount WHERE id = to_id;
END;
$$ LANGUAGE plpgsql;
SELECT transfer(1, 2, 500);

-- Процедура (PG11+): вызывается через CALL, может делать COMMIT внутри
CREATE OR REPLACE PROCEDURE close_old_orders_batched() AS $$
DECLARE n int;
BEGIN
  LOOP
    UPDATE orders SET status = 'closed'
    WHERE id IN (SELECT id FROM orders
                 WHERE status = 'active' AND created_at < now() - interval '30 days'
                 LIMIT 10000);
    GET DIAGNOSTICS n = ROW_COUNT;
    COMMIT;                 -- фиксируем каждую пачку: короткие транзакции, VACUUM успевает
    EXIT WHEN n = 0;
  END LOOP;
END;
$$ LANGUAGE plpgsql;
CALL close_old_orders_batched();
```

|            | Функция            | Процедура                       |
| ---------- | ------------------ | ------------------------------- |
| Вызов      | `SELECT f()`       | `CALL p()`                      |
| Возвращает | значение/таблицу   | ничего (или OUT-параметры)      |
| Транзакции | не управляет       | может `COMMIT`/`ROLLBACK` внутри |

Пример выше — **батчинг массовых изменений**: один UPDATE на 10 млн строк = одна огромная транзакция, гигантский всплеск WAL, лаг реплик, bloat и блокировки на всё время. Пачки по 10 тыс. с COMMIT — нагрузка размазана.

**Пример расчёта для 16 ГБ RAM, 8 CPU, SSD:**

```
shared_buffers        = 16 × 0.25 = 4GB
effective_cache_size  = 16 × 0.75 = 12GB
max_connections       = 200
work_mem              = (16384 − 4096) МБ / (200 × 3) ≈ 20 МБ → 16MB, точечно 256MB для отчётов
maintenance_work_mem  = 16 × 0.06 ≈ 1GB
random_page_cost      = 1.1  (SSD)
max_wal_size          = 8GB

PgBouncer:
default_pool_size     = 8 ядер × 2 = 16 → старт с 20, подбирать нагрузкой
max_client_conn       = 50 инстансов × 20 (пул HikariCP) = 1000
```

**Почему соединений к PostgreSQL должно быть мало.** Полезная работа ограничена ядрами CPU и параллелизмом диска. Формула из документации HikariCP как стартовая точка: `pool_size = (число ядер × 2) + число эффективных дисков`. На 8 ядрах ≈ 17–20 активных соединений дают максимальный throughput; при 500 активных растёт конкуренция за LWLock, context switches, кэш процессора — throughput **падает**, latency растёт. Это проверяется на НТ ступенчатым увеличением пула.

### 20.2 PgBouncer

**Режимы пулинга:**

| `pool_mode` | Серверное соединение отдаётся клиенту на | Можно использовать | Нельзя |
|-------------|------------------------------------------|--------------------|--------|
| `session`   | всю сессию клиента                       | всё                | экономии почти нет |
| `transaction` | одну транзакцию                         | обычный OLTP        | `SET` (без LOCAL), session advisory locks, `LISTEN`, temp tables между транзакциями, серверные prepared statements (до 1.21 / без `max_prepared_statements`) |
| `statement` | один запрос                              | автокоммит         | многооператорные транзакции |

```ini
[pgbouncer]
pool_mode = transaction
max_client_conn = 1000            ; сколько клиентов может подключиться
default_pool_size = 20            ; серверных соединений на пару (база, пользователь)
min_pool_size = 5
reserve_pool_size = 5             ; доп. соединения при пиках
reserve_pool_timeout = 3          ; через сколько секунд ожидания использовать резерв
max_db_connections = 50           ; потолок на базу (все пользователи)
max_prepared_statements = 200     ; PgBouncer 1.21+: поддержка prepared statements в transaction mode

query_wait_timeout = 10           ; клиент ждёт свободное серверное соединение не дольше 10 с → ошибка
query_timeout = 0                 ; убить запрос дольше N с (лучше statement_timeout в PostgreSQL)
idle_transaction_timeout = 60     ; клиент в idle in transaction
server_idle_timeout = 600
server_lifetime = 3600
server_connect_timeout = 5
server_check_query = select 1
tcp_keepalive = 1
```

**PgBouncer однопоточный.** Один процесс использует одно ядро. При ~30–50 тыс. запросов/с и TLS он сам становится узким местом (CPU процесса pgbouncer = 100 % одного ядра). Решение: несколько процессов на одном порту (`so_reuseport = 1`), или альтернатива — PgCat / Odyssey (многопоточные).

```sql
-- Консоль: psql -p 6432 -U pgbouncer pgbouncer
SHOW POOLS;
-- cl_active   — клиенты, у которых сейчас есть серверное соединение
-- cl_waiting  — клиенты, ЖДУЩИЕ серверное соединение  ← главная метрика
-- sv_active   — серверные соединения в работе
-- sv_idle     — свободные серверные соединения
-- maxwait     — сколько секунд ждёт самый старый клиент
SHOW STATS;      -- запросы/с, среднее время запроса и ожидания (avg_wait_time)
SHOW CLIENTS;  SHOW SERVERS;

## 21. Сеть и PostgreSQL

### 21.1 Цена сетевого round-trip

Каждый запрос — минимум один сетевой round-trip (RTT) между приложением и БД. В одном ЦОДе RTT ≈ 0,1–0,5 мс, между ЦОДами — 1–10 мс, через PgBouncer — плюс ещё один хоп.

**Пример — N+1 запросов:**

```
Экран «список заказов»: 1 запрос за 100 заказами + по 1 запросу за позициями каждого заказа
= 101 запрос
Время выполнения одного запроса в БД: 0,2 мс
RTT до БД: 0,5 мс (через PgBouncer)
Итого: 101 × (0,2 + 0,5) = 70,7 мс, из которых 50,5 мс — сеть
Если БД в соседнем ЦОДе (RTT 3 мс): 101 × 3,2 = 323 мс
```

Один JOIN или `WHERE order_id = ANY($1)` — это 1 round-trip вместо 101.

**Сетевые признаки в запросах:**

| Симптом | Что значит |
|---------|-----------|
| В `pg_stat_statements` запрос быстрый (0,2 мс), а в трейсе приложения — 5 мс | время уходит на сеть, пул соединений, сериализацию |
| `wait_event = ClientRead` у `active`/`idle in transaction` сессий | БД **ждёт клиента**: клиент не прислал следующую команду (приложение занято, медленная сеть, HTTP-вызов внутри транзакции) |
| `wait_event = ClientWrite` | БД **не может отдать результат**: клиент медленно читает (большой результат, медленная сеть, клиент перегружен по CPU/GC) |

### 21.2 Объём данных и пропускная способность

```
SELECT * FROM orders WHERE created_at > now() - interval '1 day'   → 2 млн строк × 500 байт = 1 ГБ
Канал 1 Гбит/с ≈ 110 МБ/с полезных → ~9 секунд только на передачу
Канал 10 Гбит/с → ~1 с, но тогда упрёмся в CPU десериализации на клиенте
```

- Выбирать только нужные колонки: `SELECT *` с большим `jsonb`/`text` гонит TOAST по сети.
- **JDBC `fetchSize`**: по умолчанию PgJDBC читает **весь результат в память** клиента. Для больших выборок `setFetchSize(1000)` **внутри транзакции** (autocommit = false) — драйвер читает курсором порциями.
- Большие выгрузки — `COPY ... TO STDOUT` (в разы быстрее построчного SELECT).
- Массовая вставка: `COPY FROM`, multi-row `INSERT ... VALUES (...), (...)`, в PgJDBC `reWriteBatchedInserts=true` (превращает batch в multi-row INSERT), `unnest` массивов.

```
Вставка 100 000 строк:
  по одному INSERT с autocommit:   100 000 × (RTT 0,5 мс + fsync 1 мс) ≈ 150 с
  batch по 1000 в одной транзакции: 100 × 0,5 мс + время записи ≈ 2–3 с
  COPY:                             < 1 с
```

### 21.3 TLS и установка соединения

Новое соединение к PostgreSQL дорогое:

```
TCP handshake (1 RTT) → SSLRequest (1 RTT) → TLS handshake (1–2 RTT) → startup + аутентификация
SCRAM-SHA-256 (2 RTT + вычисление 4096 итераций хэша на сервере, ~несколько мс CPU)
→ fork() backend-процесса на сервере (~1–3 мс)
Итого: 5–10 мс на соединение даже в одном ЦОДе
```

Поэтому:

- **никогда не открывать соединение на каждый запрос** — только пул;
- «шторм подключений» (рестарт 50 подов приложения одновременно, каждый открывает пул 20 соединений = 1000 подключений за секунду) нагружает postmaster и CPU на SCRAM — видно как всплеск `connections` и CPU system;
- если TLS обязателен, PgBouncer снимает стоимость: клиентские TLS-соединения к PgBouncer долгоживущие, а PgBouncer ↔ PostgreSQL — переиспользуемые.

### 21.4 Фаерволы, NAT и обрывы idle соединений

Между приложением и БД часто стоят фаервол, NAT, балансировщик (в Kubernetes — conntrack на каждой ноде). У них есть **таймаут простоя соединения** (часто 5–60 минут, у облачных NAT — 350 с и меньше). Если соединение в пуле простаивает дольше — промежуточное устройство молча удаляет запись о нём **без RST**.

```
Что видит приложение:
  берёт «живое» соединение из пула → отправляет запрос → пакеты уходят в никуда
  → ждёт TCP retransmit timeout (~15 мин по умолчанию в Linux, tcp_retries2 = 15)
  → или socketTimeout драйвера → ошибка «connection reset» / «I/O error»
```

Защита — держать трафик в соединении и находить мёртвые соединения быстрее:

| Где | Настройка |
|-----|-----------|
| PostgreSQL | `tcp_keepalives_idle = 60`, `tcp_keepalives_interval = 10`, `tcp_keepalives_count = 6` |
| PgJDBC | `tcpKeepAlive=true`, `socketTimeout=` (секунды, ограничение ожидания ответа), `connectTimeout=` |
| HikariCP | `keepalive-time` < idle-таймаута фаервола, `max-lifetime` < всех таймаутов на пути |
| PgBouncer | `tcp_keepalive = 1`, `tcp_keepidle`, `server_idle_timeout` |
| Linux | `net.ipv4.tcp_keepalive_time` (7200 с по умолчанию — слишком долго), `tcp_retries2` |

Порт PostgreSQL 5432 (PgBouncer часто 6432). В `pg_hba.conf` — разрешённые адреса и метод аутентификации; ошибка `no pg_hba.conf entry for host` — это не сеть, а правило доступа.

### 21.5 Пропускная способность репликации

WAL идёт по сети к каждой реплике. Объём WAL при НТ = прямая сетевая нагрузка:

```
Нагрузка пишет 80 МБ/с WAL (с full page writes после checkpoint — пики до 200 МБ/с)
2 реплики → 160–400 МБ/с исходящего трафика с мастера
Канал 1 Гбит/с (~115 МБ/с) → лаг реплик растёт бесконечно, при синхронной репликации тормозят коммиты
```

Смотреть: `pg_stat_wal` (wal_bytes), трафик интерфейса мастера, `pg_stat_replication`. Снижать: `wal_compression`, реже checkpoint, отдельная сеть под репликацию.

## 22. Поиск узких мест — методика

### 22.1 Порядок действий

```
1. Подтвердить, что узкое место в БД, а не до неё
   — время запроса в pg_stat_statements vs время в трейсе приложения

2. Ресурсы сервера БД (USE: Utilization, Saturation, Errors) — [[01 Linux — ядро, ресурсы, метрики]]
   CPU:   user vs system vs iowait, load average относительно ядер, PSI cpu
   Память: page cache, swap (должен быть 0), PSI memory
   Диск:  iostat: %util, r_await/w_await, aqu-sz; PSI io
   Сеть:  трафик интерфейса относительно канала, retransmits, drops

3. Что делают сессии — wait events (раздел 22.2)

4. Какие запросы потребляют ресурсы — pg_stat_statements (по total_exec_time, а не только по mean)

5. Почему запрос медленный — EXPLAIN (ANALYZE, BUFFERS) (разделы 8–13)

6. Фоновые процессы — autovacuum, checkpoint, репликация (разделы 14, 16, 18)

### 22.2 Wait events — что ждут сессии

Снимок `pg_stat_activity` каждые 1–5 секунд — это «профилировщик бедняка» для БД. Расширение `pg_wait_sampling` делает это автоматически и хранит историю.

```sql
SELECT wait_event_type, wait_event, state, count(*)
FROM pg_stat_activity
WHERE backend_type = 'client backend' AND state <> 'idle'
GROUP BY 1, 2, 3 ORDER BY 4 DESC;
```

| `wait_event_type` / `wait_event` | Что значит | Куда смотреть |
|----------------------------------|-----------|---------------|
| `NULL` (и state = active) | работает на CPU | pg_stat_statements по total_exec_time, CPU сервера |
| `IO / DataFileRead` | читает страницы с диска | cache hit, shared_buffers, индексы, iostat |
| `IO / WALWrite`, `IO / WALSync` | ждёт записи WAL | диск под pg_wal, fsync latency, батчинг коммитов |
| `IPC / SyncRep` | ждёт синхронную реплику | сеть до реплики, её диск |
| `Lock / transactionid`, `Lock / tuple` | ждёт блокировку строки | раздел 17.5: кто блокирует |
| `Lock / relation` | ждёт блокировку таблицы | DDL, VACUUM FULL, LOCK TABLE |
| `LWLock / BufferMapping` | конкуренция за хэш-таблицу буферов | рабочий набор не влезает в shared_buffers, частые вытеснения |
| `LWLock / WALInsert` | конкуренция за вставку в WAL | очень высокий темп записи |
| `LWLock / LockManager` | конкуренция в менеджере блокировок | много партиций/индексов в одном запросе при высоком RPS, fast-path исчерпан |
| `LWLock / buffer_content` | горячая страница (все пишут в одну) | счётчики в одной строке, вставки в последний лист индекса |
| `LWLock / SubtransSLRU`, `MultiXact*` | подтранзакции (SAVEPOINT, EXCEPTION в PL/pgSQL) / multixact | убрать SAVEPOINT в цикле, FK под сильной конкуренцией |
| `Client / ClientRead` | ждёт команду от клиента | приложение, сеть, idle in transaction |
| `Client / ClientWrite` | не может отдать результат клиенту | сеть, объём результата, клиент |
| `Timeout / PgSleep`, `VacuumDelay` | сон | обычно норма |

### 22.3 pg_stat_statements — главный инструмент

```sql
CREATE EXTENSION pg_stat_statements;   -- + shared_preload_libraries

-- Топ по суммарному времени — что реально грузит БД
SELECT left(query, 100) AS query, calls,
       round(total_exec_time::numeric, 0)                  AS total_ms,
       round(mean_exec_time::numeric, 2)                   AS mean_ms,
       round(stddev_exec_time::numeric, 2)                 AS stddev_ms,
       rows / nullif(calls, 0)                             AS rows_per_call,
       round(100.0 * shared_blks_hit / nullif(shared_blks_hit + shared_blks_read, 0), 1) AS hit_pct,
       temp_blks_written,
       round((shared_blk_read_time + shared_blk_write_time)::numeric, 0) AS io_ms   -- PG17 имена
FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 20;
```

- **total_exec_time** — что грузит БД сильнее всего (частый запрос по 2 мс важнее редкого по 2 с).
- **mean vs stddev** — большой stddev = нестабильный план или блокировки.
- **rows_per_call** большой при маленьком результате в приложении — выборка лишних данных.
- **temp_blks_written** > 0 — work_mem.
- Перед тестом: `SELECT pg_stat_statements_reset();`, после — снимок.

`auto_explain` логирует планы медленных запросов прямо под нагрузкой:

```
shared_preload_libraries = 'pg_stat_statements,auto_explain'
auto_explain.log_min_duration = '200ms'
auto_explain.log_analyze = on
auto_explain.log_buffers = on
auto_explain.log_timing = off          # снижает накладные расходы
auto_explain.sample_rate = 0.1         # логировать 10 % медленных
```

### 22.4 Метрики для Grafana (postgres_exporter)

| Метрика | Что смотреть |
|---------|--------------|
| `pg_stat_database_xact_commit` / `_rollback` (rate) | TPS и доля откатов |

       pg_size_pretty(pg_total_relation_size(oid)) AS total,
       pg_size_pretty(pg_relation_size(oid))       AS heap,
       pg_size_pretty(pg_indexes_size(oid))        AS indexes
FROM pg_class WHERE relkind = 'r' AND relnamespace = 'public'::regnamespace
ORDER BY pg_total_relation_size(oid) DESC LIMIT 20;

       seq_tup_read / nullif(seq_scan, 0) AS avg_rows_per_seq_scan
FROM pg_stat_user_tables
WHERE seq_scan > 0 ORDER BY seq_tup_read DESC LIMIT 20;

-- Лаг реплик
SELECT application_name, client_addr, state,

## 24. Индексы глубже: уроки «Use The Index, Luke»

> По мотивам книги-сайта Маркуса Винанда [use-the-index-luke.com](https://use-the-index-luke.com) — лучший бесплатный материал по индексам, общий для PostgreSQL, Oracle, MySQL, SQL Server. Здесь — то, что дополняет разделы 5–7 и 12.

### 24.1 Три шага поиска по индексу — почему «индекс есть, а медленно»

Любой Index Scan состоит из трёх шагов, и только первый гарантированно быстрый:

```
1. Спуск по дереву (tree traversal)     — ограничен глубиной дерева: 3–5 страниц, всегда быстро
2. Проход по цепочке листьев (leaf chain) — сколько записей индекса подходит под Index Cond
3. Обращение к таблице (table access)    — по одному ctid на каждую подходящую запись
```

Медленный индексный поиск — это почти всегда шаги 2 и 3: условие в индексе слишком широкое (много листьев), или каждая найденная запись ведёт на отдельную страницу таблицы (плохая корреляция, раздел 6). Миф «индекс выродился и его надо перестроить» почти всегда неверен — перестройка не меняет число подходящих записей.

### 24.2 Порядок колонок: сначала равенство, потом диапазон

```sql
WHERE date_of_birth BETWEEN '1971-01-01' AND '1971-01-09' AND subsidiary_id = 27
```

| Индекс | Что происходит в шаге 2 |
|--------|------------------------|
| `(date_of_birth, subsidiary_id)` | Index Cond по диапазону дат проходит **все** записи за 9 дней (всех подразделений), `subsidiary_id` проверяется внутри как фильтр |
| `(subsidiary_id, date_of_birth)` | спуск сразу к `subsidiary_id = 27`, внутри — только 9 дней этого подразделения |

Правило: **колонки с равенством — первыми, колонка с диапазоном — последней**. После первой колонки с диапазоном последующие колонки уже не сужают проход по листьям.

В плане PostgreSQL это видно так: у плохого варианта большие `Buffers` на индексном узле при маленьком числе строк.

### 24.3 «Обфусцированные» условия — индекс не работает, хотя колонка та же

| Условие | Почему мимо индекса | Как правильно |
|---------|--------------------|---------------|
| `WHERE date(created_at) = '2025-10-18'` | функция над колонкой | `created_at >= '2025-10-18' AND created_at < '2025-10-19'` |
| `WHERE to_char(created_at, 'YYYY') = '2025'` | функция | диапазон года |
| `WHERE numeric_str = 42` (колонка `text` с числами) | приведение колонки к числу | сравнивать с `'42'`, хранить числа числами |
| `WHERE a + b = 100`, `WHERE price * 1.2 > 1000` | арифметика над колонкой | `WHERE price > 1000 / 1.2` или индекс по выражению |
| `WHERE first_name \|\| ' ' \|\| last_name = 'Иван Петров'` | склейка колонок | условия по каждой колонке + составной индекс |
| `WHERE created_at + interval '1 day' > now()` | выражение над колонкой | `created_at > now() - interval '1 day'` |

Правило: **колонка должна стоять в условии «голой»**, все вычисления переносятся на сторону константы.

### 24.4 «Умная логика» — антипаттерн динамических фильтров

```sql
-- Одна «универсальная» форма поиска с необязательными фильтрами
SELECT * FROM orders
WHERE ($1::bigint IS NULL OR user_id = $1)
  AND ($2::text   IS NULL OR status  = $2)
  AND ($3::date   IS NULL OR created_at >= $3);
```

Выглядит элегантно, но для prepared statement с **generic-планом** (раздел 13) планировщик обязан построить план, корректный при **любых** значениях параметров, включая все NULL. Такой план — Seq Scan всей таблицы. Даже с custom-планом оптимизатору приходится упрощать условия на лету.

Правильно: собирать текст запроса динамически только из реально заданных фильтров (с параметрами, не конкатенацией значений!). Разное число условий → разные prepared statements → у каждого свой нормальный план.

### 24.5 Параметры запроса: зачем и когда они мешают

- Параметры (`$1`, `?`) защищают от SQL-инъекций и позволяют переиспользовать план.
- Цена — generic-план, который не знает конкретного значения. Для колонок с перекосом распределения (`status`: 95 % `done`, 0,1 % `pending`) один план не может быть хорош для всех значений → `plan_cache_mode` (раздел 13).
- **Никогда** не подставлять значения в текст запроса ради «лучшего плана» без экранирования — это SQL-инъекция.

### 24.6 NULL в индексах PostgreSQL

- B-tree PostgreSQL **индексирует NULL** (в отличие от Oracle, где запись из одних NULL в индекс не попадает): `WHERE col IS NULL` может использовать индекс.
- Порядок NULL: в B-tree по умолчанию `NULLS LAST` для `ASC` и `NULLS FIRST` для `DESC`. Запрос `ORDER BY created_at DESC NULLS LAST LIMIT 20` не сможет использовать индекс `(created_at)` без сортировки → индекс `(created_at DESC NULLS LAST)`.
- Частичный индекс `WHERE deleted_at IS NULL` — классика для «живых» строк при soft delete.

### 24.7 Индекс вместо сортировки: pipelined ORDER BY и top-N

Если индекс отдаёт строки уже в нужном порядке, PostgreSQL **не сортирует** и может **остановиться**, получив первые N строк:

```sql
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at DESC);

SELECT * FROM orders WHERE user_id = 5 ORDER BY created_at DESC LIMIT 20;
-- Limit → Index Scan  (actual rows=20)    ← прочитано 20 строк, а не все заказы пользователя
```

Условия: колонки `WHERE` с равенством + колонки `ORDER BY` в индексе в том же порядке и направлении. Если в `WHERE` диапазон по первой колонке, а сортировка по второй — индекс уже не отдаёт нужный порядок, появится `Sort` (или `Incremental Sort`).

Это главный инструмент для **постоянного** времени ответа лент и списков: без индекса время растёт с объёмом данных пользователя, с индексом — нет.

**Keyset-пагинация** (раздел 12.2) — продолжение той же идеи: `WHERE (created_at, id) < ($last_ts, $last_id) ORDER BY created_at DESC, id DESC LIMIT 20` с индексом `(created_at DESC, id DESC)` даёт одинаковое время для первой и для тысячной страницы. С `OFFSET 20000` — каждая следующая страница медленнее предыдущей.

### 24.8 GROUP BY через индекс

`GroupAggregate` может читать данные из индекса уже сгруппированными, без сортировки и без хэш-таблицы в памяти — и, что важно, **конвейерно**: первые группы готовы сразу. `HashAggregate` должен прочитать всё до первой строки результата. Для `GROUP BY ... LIMIT` индекс по колонкам группировки даёт тот же эффект, что и для `ORDER BY ... LIMIT`.

### 24.9 Цена индексов на запись

```
INSERT в таблицу с N индексами: 1 запись в heap + N записей в индексы (+ WAL на каждую)
Порядок величины по замерам Винанда: каждый дополнительный индекс заметно увеличивает время INSERT;
таблица с 5 индексами вставляет в несколько раз медленнее, чем без индексов.
DELETE: тоже трогает все индексы (точнее — оставляет мёртвые записи до VACUUM).
UPDATE: только индексы изменённых колонок — но в PostgreSQL без HOT это ВСЕ индексы (раздел 2.8).
```

Вывод для НТ: на сценариях интенсивной записи каждый «на всякий случай» созданный индекс — прямая потеря throughput. Проверять `pg_stat_user_indexes.idx_scan = 0` (раздел 5.6).

## 25. Практический чек-лист оптимизации

> По мотивам статьи Selectel «Оптимизация PostgreSQL: практические советы» (Хабр, 2025) и курса Postgres Pro QPT. Порядок — от дешёвого к дорогому.

### 25.1 Сначала собрать статистику запросов

Прежде чем оптимизировать конкретный запрос — понять, **какие запросы и откуда** нагружают базу (`pg_stat_statements` по `total_exec_time`, раздел 22.3). Часто самый большой выигрыш даёт не тюнинг SQL, а удаление лишних запросов: фронтенд дёргает один и тот же endpoint трижды, сервис перечитывает справочник на каждый запрос, ORM делает N+1.

### 25.2 Отдельный сервер для СУБД

Когда на одной машине живут PostgreSQL, приложение, Redis, брокер задач, nginx, агенты мониторинга и ночной бэкап — они конкурируют за CPU, память (page cache!) и диск. Вынос БД на отдельный сервер или в managed-сервис — базовый шаг, а не «оптимизация на потом». Для НТ: стенд, где на одной ВМ крутится всё, даёт результаты, не переносимые на прод.

### 25.3 ORM: знать, какой SQL он генерирует

- **N+1**: `orders = Order.objects.all(); for o in orders: o.user.name` → 1 + N запросов (раздел 21.1). В Django — `select_related`/`prefetch_related`, в JPA/Hibernate — `JOIN FETCH`, `@EntityGraph`, batch fetching.
- Даже «правильные» методы ORM могут генерировать неоптимальные JOIN-ы.
- Включить логирование SQL на стенде и смотреть реальные запросы и их число на одну бизнес-операцию.
- Сложные отчётные запросы — писать руками и проверять `EXPLAIN (ANALYZE, BUFFERS)`.

### 25.4 Не использовать SELECT *

Лишние колонки = лишние страницы TOAST (раздел 2.7), лишний трафик (раздел 21.2), лишняя память на клиенте, и **невозможность Index Only Scan**: покрывающий индекс бесполезен, если запрос просит все колонки.

### 25.5 Широкие таблицы

Таблицы на сотни колонок (часто в хранилищах данных и в «универсальных» сущностях) плохи для строкового хранения: строка длинная → мало строк на странице → кэш заполняется неиспользуемыми колонками.

- Разделить на «горячую» часть (часто читаемые колонки) и «холодную» (редкие), связать 1:1 по ключу.
- Аналитику по широким таблицам — в колоночное хранилище ([[06 ClickHouse]]) с синхронизацией через CDC/Kafka/ETL. ClickHouse дополняет PostgreSQL, а не заменяет его для OLTP.

### 25.6 Не бояться JOIN

Нормализованная схема с индексами на ключи соединения — нормальная и быстрая. Проблемы JOIN почти всегда — отсутствие индекса на FK и ошибки оценки строк (раздел 10), а не JOIN как таковой. Денормализация «чтобы не джойнить» создаёт аномалии обновления и раздувает таблицы.

### 25.7 Кластеризация таблицы

`CLUSTER` / `pg_repack --order-by` переупорядочивают строки по индексу → диапазонные запросы читают соседние страницы (подробно — раздел 6.5). Помнить: порядок не поддерживается автоматически, `CLUSTER` блокирует таблицу.

### 25.8 Статистика — причина значительной доли «странных» планов

Когда обновлять статистику вручную (`ANALYZE table`), не дожидаясь autovacuum:

- после массовой загрузки или удаления (ETL, миграция, восстановление из бэкапа — **после pg_restore статистики нет, план будет плохим до ANALYZE!**);
- после смены распределения значений (90 % строк перешли в `status = 'archived'`);
- новая таблица, сразу заполненная данными;
- после подготовки данных стенда НТ — обязательно `VACUUM ANALYZE` перед тестом.

```sql
-- Когда последний раз собиралась статистика
SELECT relname, n_live_tup, n_mod_since_analyze, last_analyze, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_mod_since_analyze DESC;
-- n_mod_since_analyze — сколько строк изменено с последнего ANALYZE
```

### 25.9 Порядок действий при медленном запросе

```
1. pg_stat_statements: действительно ли он важен (total_exec_time, calls)?
2. EXPLAIN (ANALYZE, BUFFERS): где расхождение оценок rows vs actual rows?
3. Статистика свежая? → ANALYZE
4. Индекс есть? Используется? Index Cond или Filter? (разделы 7, 9)
5. Условия «голые»? Нет функций и приведений над колонками? (24.3)
6. Порядок колонок в составном индексе: равенство → диапазон → сортировка (24.2, 24.7)
7. Хватает ли work_mem (Sort/Hash на диске)?
8. Подходит ли алгоритм JOIN (раздел 10)?
9. Только потом — настройки сервера и железо
```

## 26. Сжатие в PostgreSQL

### 26.1 Что сжимается в «ванильном» PostgreSQL

| Что | Механизм | Настройка |
|-----|----------|-----------|
| Длинные значения (`text`, `jsonb`, `bytea` > ~2 КБ) | TOAST: сжатие значения, при необходимости вынос в TOAST-таблицу (раздел 2.7) | `default_toast_compression = lz4` (PG14+, по умолчанию `pglz`), на колонку: `ALTER TABLE t ALTER COLUMN data SET COMPRESSION lz4` |
| Full page images в WAL | сжатие полных копий страниц после checkpoint (раздел 16.3) | `wal_compression = lz4` или `zstd` (PG15+; раньше только `on` = pglz) |
| Логические бэкапы | сжатие дампа | `pg_dump -Fc -Z zstd:5` (PG16+), `-Z 9` (gzip) |
| Физические бэкапы | сжатие на клиенте или сервере | `pg_basebackup --compress=server-zstd:5` (PG15+) |
| Сетевой трафик | — | в ядре PostgreSQL нет сжатия протокола; TLS-компрессия отключена из соображений безопасности |
| **Обычные страницы таблиц и индексов** | **не сжимаются** | — |

Важно: строки, которые меньше порога TOAST, не сжимаются вообще. Таблица из миллиарда коротких строк в ванильном PostgreSQL хранится как есть.

**pglz vs lz4 для TOAST:** lz4 сжимает и распаковывает в разы быстрее при сопоставимой степени сжатия. Смена `default_toast_compression` действует на **новые** значения; существующие не пережимаются даже при `VACUUM FULL` — только когда значение перезаписывается (UPDATE).

```sql
-- Каким алгоритмом сжато значение
SELECT pg_column_compression(data), count(*) FROM orders GROUP BY 1;
-- Размер значения до и после
SELECT pg_column_size(data) AS stored, octet_length(data::text) AS raw FROM orders LIMIT 5;
```

### 26.2 Варианты сжатия страниц целиком

1. **Файловая система со сжатием** (ZFS с `compression=lz4`/`zstd`, Btrfs): прозрачно для PostgreSQL; на ZFS популярно с `recordsize=8K–32K`. Цена — CPU, особенности ZFS (ARC вместо page cache, copy-on-write → фрагментация).
2. **Колоночные расширения** (Citus columnar, Hydra и др.) — для аналитических таблиц: сжатие в разы, но не для OLTP-обновлений.
3. **Встроенное сжатие страниц в форках PostgreSQL** — например, Tantor Postgres CSM.

### 26.3 Сжатие страниц в Tantor Postgres (CSM) — как устроено

> По статье Tantor Labs на Хабре (2026). Это функция коммерческого форка, не ванильного PostgreSQL, но идеи полезны для понимания компромиссов любого сжатия.

- Страницы **сжимаются только на диске**. В shared_buffers они остаются обычными 8 КБ → запросы работают как обычно; CPU тратится на распаковку при чтении с диска и на сжатие при записи грязной страницы (bgwriter, checkpointer, backend при вытеснении).
- **Фиксированный размер сжатой страницы** (4, 2 или 1 КБ — параметр хранения таблицы/индекса): адрес страницы по-прежнему вычисляется из номера блока, не нужна карта адресов. Страница, которая не ужалась до выбранного размера, уходит в отдельный **overflow-файл** — это лишний I/O, поэтому важно, чтобы таких страниц было мало.
- Альтернатива — страницы переменного размера (как в CFS): лучше степень сжатия, но нужна карта адресов, фрагментация при росте страниц и больше write amplification.

**Выбор алгоритма и размера:**

| Алгоритм | Степень | Скорость | Когда |
|----------|---------|----------|-------|
| lz4 | средняя | самый быстрый | активная запись, OLTP — 4 КБ страницы |
| zstd | лучшая | самый медленный (особенно распаковка) | редко меняемые/архивные данные — 2 КБ или 1 КБ |
| pglz | худшая | средний | почти всегда хуже lz4; на 1 КБ почти все страницы переполняются |

**Результаты из статьи (базы 1С):** ERP 645 ГБ → ~220 ГБ (≈2,9×) при zstd и страницах 2 КБ; на нагрузочном тесте 1С время отклика и APDEX практически не изменились, CPU +~2 %, пиковая память +~10 %. Нагрузка там не была дисковой, поэтому выигрыш — в основном место.

**Синтетика:** при холодном кэше lz4 ускорил чтение (меньше байт с диска), zstd — замедлил; при данных в page cache zstd дал заметное замедление из-за дорогой распаковки.

### 26.4 Выводы для НТ

- Сжатие — обмен **CPU на I/O и место**. Выигрыш по времени есть, только если система упирается в диск, а распаковка дешёвая (lz4).
- Если нагрузка CPU-bound — сжатие с zstd может ухудшить latency.
- Оценивать нужно не только среднюю степень, но и **долю «неужимаемых» страниц** (overflow) и write amplification.
- Тестировать на копии реальных данных: степень сжатия синтетики (повторяющиеся строки) обманчиво высокая.
- `wal_compression = lz4` — почти всегда выгодно на нагрузке записи: меньше WAL → меньше I/O и сетевого трафика репликации (раздел 21.5).

## 27. Bloom-фильтры в PostgreSQL

**Фильтр Блума** — вероятностная структура «битовый массив + K хэш-функций»: на вопрос «есть ли элемент» отвечает «точно нет» или «возможно есть». Ложноположительные ответы возможны (их отсеивает перепроверка), ложноотрицательные — нет. Занимает очень мало памяти.

### 27.1 Индекс bloom (contrib-расширение, ванильный PostgreSQL)

```sql
CREATE EXTENSION bloom;
CREATE INDEX idx_bloom ON events USING bloom (a, b, c, d, e, f)
       WITH (length = 80, col1 = 2, col2 = 2, col3 = 4);
-- length — длина сигнатуры в битах на строку (по умолчанию 80, до 4096)
-- colN — сколько бит выставляет значение N-й колонки (по умолчанию 2)

SELECT * FROM events WHERE c = 42 AND e = 'x';   -- любая комбинация колонок
-- Bitmap Heap Scan → Bitmap Index Scan on idx_bloom (Recheck Cond — проверка ложных срабатываний)
```

Как работает: для каждой строки хранится короткая битовая сигнатура всех колонок. Поиск — **последовательный проход по всему индексу** (он маленький) и сравнение сигнатур → кандидаты → перепроверка в таблице.

| Плюсы | Минусы |
|-------|--------|
| одна маленькая структура вместо десятков составных B-tree для произвольных комбинаций `=` по многим колонкам | только оператор `=`; только типы `int4` и `text` (без доп. классов) |
| размер индекса не зависит от числа колонок так сильно, как набор B-tree | весь индекс читается при каждом поиске → для одной колонки B-tree на порядки быстрее |
| | нет уникальности, нет диапазонов, нет сортировки, нет поиска `IS NULL` |
| | ложные срабатывания → лишние чтения heap |

**Когда уместен:** таблица с 10–20 колонками-атрибутами, пользователи фильтруют по любой комбинации равенств, строить B-tree на каждую комбинацию невозможно. В остальных случаях — B-tree.

### 27.2 Bloom-фильтр в Hash Join (Tantor Postgres)

> По статье Tantor Labs на Хабре (2026). Функция коммерческого форка; идея применяется во многих аналитических СУБД (runtime filters / semi-join reduction).

Идея: при Hash Join строится хэш-таблица по маленькой таблице (build-сторона, раздел 10.3). Параллельно по её ключам строится Bloom-фильтр, и он **проталкивается в сканирование большой таблицы**: строки, ключа которых точно нет в маленькой таблице, отбрасываются ещё при сканировании, до узла Hash Join.

```
Без фильтра:  Seq Scan orders (10 млн строк) → все 10 млн строк идут в Hash Join → 100 тыс. совпадений
С фильтром:   Seq Scan orders + Bloom filter → 99 % строк отброшены сразу → в Hash Join приходит ~100 тыс.
```

Результаты из статьи:

- **Селективный JOIN** (совпадает 1 % ключей): общее время уменьшилось примерно вдвое — сам Hash Join стал в десятки раз быстрее, хотя сканирование и построение хэша немного подорожали.
- **Неселективный JOIN** (совпадает 95 % ключей): фильтр почти ничего не отсеивает, но стоит построения → запрос медленнее на ~15 %; исполнитель адаптивно отключает фильтр, когда видит, что тот не окупается.
- На реальных отчётах 1С — ускорение тяжёлых запросов в 1,5–2,5 раза.

**Чему учит для чтения планов в ванильном PostgreSQL:** в Hash Join дорогая часть — не построение хэша, а прогон всей большой таблицы через probe. Если в плане `Hash Join` пропускает миллионы строк, а на выходе тысячи — ищи способ отфильтровать раньше: индекс, условие по ключу (`WHERE customer_id IN (...)` с подзапросом), предагрегацию.

## 29. Шпаргалка: симптом → причина → решение

| Симптом | Вероятная причина | Решение |
|---------|-------------------|---------|
| Seq Scan вместо Index Scan | статистика устарела / низкая селективность / функция или приведение типа над колонкой / плохая корреляция | ANALYZE; переписать условие; индекс по выражению; раздел 7 |
| `rows=` оценка ≠ `actual rows` в 10+ раз | статистика, коррелированные колонки, JSONB без статистики | ANALYZE, SET STATISTICS, CREATE STATISTICS, индекс по выражению |
| `Rows Removed by Filter` огромный | условие не в индексе | составной индекс |
| `Hash Batches > 1`, `external merge Disk` | work_mem мал | `SET work_mem` для запроса/роли |
| Nested Loop с `loops=50000` и Seq Scan внутри | нет индекса на ключ соединения, ошибка оценки | индекс, ANALYZE |
| `NOT IN (подзапрос)` очень медленный | SubPlan на каждую строку | `NOT EXISTS` |
| Index Only Scan с большим `Heap Fetches` | Visibility Map не обновлена | VACUUM, тюнинг autovacuum |
| Запрос быстрый первые 5 раз, потом медленный | generic plan prepared statement | `plan_cache_mode = force_custom_plan` |
| `JIT Timing` сотни мс на OLTP | JIT | `jit = off` |
| `dead_pct > 20 %` | autovacuum не успевает / долгая транзакция держит горизонт | тюнинг autovacuum, найти старые транзакции и слоты |
| Таблица 80 ГБ, данных 30 ГБ | bloat | pg_repack |
| Пилообразные всплески latency каждые N минут | checkpoint / full page writes | max_wal_size, checkpoint_timeout, completion_target |
| `wait_event = WALSync` массово | медленный fsync диска WAL | быстрый диск под pg_wal, батчинг коммитов, synchronous_commit off для некритичного |
| `wait_event = SyncRep` | синхронная реплика / сеть до неё | сеть, диск реплики, remote_write |
| `wait_event = ClientRead` в транзакциях | приложение держит транзакцию (HTTP внутри) | вынести внешние вызовы из транзакции, idle_in_transaction_session_timeout |
| `wait_event = LWLock BufferMapping` | рабочий набор > shared_buffers | shared_buffers, индексы, меньше Seq Scan |
| `idle in transaction` растёт | приложение не закрывает транзакции | try/finally, таймауты |
| HikariCP pending растёт | медленные запросы / пул мал | сначала EXPLAIN и usage_seconds, потом пул |
| PgBouncer `cl_waiting > 0` | default_pool_size мал или запросы долгие | pool_size, оптимизация запросов |
| CPU процесса pgbouncer 100 % | PgBouncer однопоточный | несколько процессов с so_reuseport, Odyssey/PgCat |
| `deadlock detected` | блокировки в разном порядке | один порядок блокирования |
| Лаг реплик растёт | сеть не тянет WAL / диск реплики / конфликты replay | смотреть sent/flush/replay разрывы |
| Partition pruning не работает | нет ключа партиционирования в WHERE | добавить условие по ключу |
| Индекс с UUIDv4 огромный, вставки медленные | случайные вставки, page split | bigint / UUIDv7 |
| Индекс по (дата, тип) медленный для `тип = X AND дата BETWEEN` | диапазон первой колонкой | индекс (тип, дата) — равенство первым |
| Поиск с необязательными фильтрами всегда Seq Scan | `($1 IS NULL OR col = $1)` | собирать запрос из заданных фильтров |
| После pg_restore / массовой загрузки всё медленно | нет статистики | `VACUUM ANALYZE` |
| Медленные чтения при свободном CPU и загруженном диске | данные не помещаются в кэш | сжатие (lz4), кластеризация, покрывающие индексы |
| «Connection reset» после простоя | фаервол/NAT убил idle соединение | keepalive, max-lifetime |
| Триггер тормозит INSERT | FOR EACH ROW на массовых операциях | FOR EACH STATEMENT, outbox |
