## 1. Go против JVM

| | Java (JVM) | Go |
|---|---|---|
| Компиляция | байткод → JIT во время работы (прогрев) | сразу в машинный код (AOT), прогрева нет |
| Рантайм | JVM — отдельный процесс-платформа | рантайм вкомпилирован в бинарник (планировщик, GC, сеть) |
| Потоки | платформенные потоки = потоки ОС; виртуальные (Java 21) | горутины (лёгкие, мультиплексируются на потоки ОС) |
| GC | поколенческие, компактирующие (G1, ZGC) | неполоколенческий, некомпактирующий, конкурентный mark-sweep |
| Настройка памяти | `-Xmx`, десятки флагов GC | `GOGC`, `GOMEMLIMIT` — по сути всё |
| Объекты | почти всё в куче, escape analysis JIT-а | компилятор решает «стек или куча» на этапе сборки |
| Старт | секунды (с прогревом JIT — минуты) | миллисекунды |
| Диагностика | jstack, jmap, JFR, async-profiler | pprof (встроен), `go tool trace`, `GODEBUG` |

Для НТ: у Go **нет фазы прогрева JIT** — производительность стабильна с первых секунд (но есть прогрев кэшей, пулов соединений, роста кучи).

## 2. Горутины

```go
go handleRequest(conn)   // запустить функцию в новой горутине
```

- **Горутина** — лёгкая единица выполнения, управляемая рантаймом Go, а не ядром.
- Начальный стек **2 КБ**, растёт и сжимается динамически (копированием). Поток ОС — обычно 1–8 МБ стека.
- Создание — сотни наносекунд. Миллион горутин = ~2–4 ГБ памяти и это работает; миллион потоков ОС — нет.
- Ядро не видит горутины: в `top -H` ты увидишь лишь десяток потоков процесса.

Аналогия с Java: горутина ≈ виртуальный поток Java 21 (`Thread.ofVirtual()`). Модель «одна горутина на соединение/запрос» — стандарт Go, как «один виртуальный поток на запрос» в новых Java-серверах.

**Утечка горутин** — главная болезнь: горутина, заблокированная навсегда (ждёт канал, который никто не закроет; ждёт ответа HTTP без таймаута), не освобождается никогда — вместе со своим стеком и всем, на что ссылается. Метрика `go_goroutines`, растущая под постоянной нагрузкой без возврата, — утечка.

## 3. Планировщик GMP

### 3.1 Три сущности

```
G — goroutine (задача): стек, указатель команды, состояние
M — machine: поток ОС, который реально выполняет код
P — processor: «право выполнять Go-код» + локальная очередь готовых G (до 256)
    число P = GOMAXPROCS

      P0 [G G G]        P1 [G G]         P2 [G]          ← локальные очереди
      │                 │                │
      M0 (поток ОС)     M1               M2              ← каждый M выполняет G, только держа P
                     Глобальная очередь [G G G ...]
```

- Чтобы выполнять Go-код, поток M должен держать P. Значит **одновременно выполняется не больше GOMAXPROCS горутин**.
- `GOMAXPROCS` по умолчанию = число доступных ядер.
- **Work stealing:** если у P пусто, он берёт половину очереди у соседнего P или из глобальной очереди. Нагрузка выравнивается без центрального узла.

### 3.2 Блокирующие операции

| Что делает горутина | Что делает рантайм |
|---------------------|-------------------|
| ждёт канал / мьютекс / `time.Sleep` | G паркуется, M берёт следующую G из очереди P — поток ОС не простаивает |
| сетевой ввод-вывод | сокет в неблокирующем режиме, G регистрируется в **netpoller** (epoll в Linux) и паркуется; когда данные готовы — G снова в очереди. Поток не блокируется |
| блокирующий системный вызов (чтение файла, cgo) | M блокируется в ядре вместе с G; рантайм **отбирает P** у этого M и отдаёт другому (новому) потоку, чтобы Go-код продолжал выполняться |

Отсюда метрика `go_threads` (потоков ОС): обычно ~GOMAXPROCS + несколько. Если сотни — много горутин висят в блокирующих syscalls (файловый I/O на медленном диске, cgo, DNS через cgo-резолвер).

### 3.3 Вытеснение

С Go 1.14 планировщик **асинхронно вытесняет** горутину, выполняющую долгий цикл без вызовов функций, сигналом (каждые ~10 мс). Раньше такой цикл мог блокировать P и даже остановку мира для GC.

### 3.4 Задержка планирования

Если готовых горутин много больше, чем P, горутина ждёт в очереди. Метрика (через `runtime/metrics`): `/sched/latencies:seconds` — гистограмма времени от «готова к выполнению» до «начала выполняться». В Prometheus-клиенте — `go_sched_latencies_seconds`. Рост — CPU-насыщение процесса (или throttling контейнера).

## 4. Синхронизация

```go
ch := make(chan Job, 100)      // буферизованный канал: отправка блокируется, когда 100 элементов
var mu sync.Mutex              // как ReentrantLock, но НЕ реентерабельный
var rw sync.RWMutex            // как ReentrantReadWriteLock
var wg sync.WaitGroup          // как CountDownLatch
var once sync.Once
atomic.AddInt64(&counter, 1)   // как AtomicLong
ctx, cancel := context.WithTimeout(parent, 2*time.Second)   // отмена и дедлайны по цепочке вызовов
```

**context.Context** — передаётся первым параметром во все вызовы, несёт дедлайн и сигнал отмены. HTTP-сервер отменяет контекст запроса, когда клиент отключился → БД-драйвер и HTTP-клиент прерывают работу. Если контекст не передавать — работа продолжается впустую после таймаута клиента.

**Contention:** один `sync.Mutex` вокруг общей карты/кэша при 16 ядрах и 50 000 RPS — горутины выстраиваются в очередь. Симптом: CPU не загружен, latency растёт, в профиле mutex (раздел 8) — горячая блокировка. Решения: шардирование (N мьютексов по хэшу ключа), `sync.RWMutex` для чтения, `sync.Map` для «записал один раз — читают многие», atomic.

**Неограниченный параллелизм** — частая ошибка: `for _, item := range items { go process(item) }` на 100 000 элементов → 100 000 одновременных запросов к БД. Ограничивать семафором (буферизованный канал, `golang.org/x/sync/semaphore`, `errgroup.SetLimit`).

## 5. Память: стек, куча, escape analysis

Компилятор Go сам решает, где разместить переменную:

- **на стеке** горутины — если она не «убегает» из функции. Освобождается бесплатно при возврате, GC её не видит;
- **в куче** — если на неё остаётся ссылка после возврата (вернули указатель, положили в глобальную карту, захватили в замыкание горутины, привели к интерфейсу).

```go
func newUser() *User {
    u := User{Name: "a"}
    return &u            // u убегает → куча
}
func sum(xs []int) int {
    s := 0               // на стеке
    for _, x := range xs { s += x }
    return s
}
```

```bash
go build -gcflags='-m' ./...
# ./user.go:5:2: moved to heap: u
# ./log.go:12:13: ... argument escapes to heap   ← частая причина: fmt.Sprintf, интерфейсы
```

Аналогия: escape analysis есть и в JIT C2 JVM ([[10 JVM]], раздел 5), но в Go он работает на этапе компиляции и его вывод можно посмотреть.

**Почему важно:** каждая аллокация в куче — работа для GC. **Скорость аллокаций** (байт/с) прямо определяет, как часто запускается GC и сколько CPU он съедает.

**Как снижают аллокации:**

- переиспользовать буферы: `sync.Pool` (пул объектов, очищается при GC), `bytes.Buffer` с `Reset()`;
- предвыделять слайсы: `make([]T, 0, n)` вместо роста с `append` (каждое увеличение — новая аллокация и копирование);
- избегать лишних преобразований `[]byte ↔ string`, `fmt.Sprintf` в горячем пути, `interface{}`/`any`;
- `encoding/json` работает через рефлексию и много аллоцирует → кодогенерация (easyjson), `json/v2` (новый пакет), `sonic`, `goccy/go-json`.

## 6. Сборщик мусора

### 6.1 Как работает

- **Конкурентный трёхцветный mark-sweep**: помечает живые объекты параллельно с работой программы; затем «выметает» (sweep) мёртвые постепенно.
- **Неполоколенческий** — нет разделения на Young/Old, каждый цикл обходит всю живую кучу.
- **Некомпактирующий** — объекты не перемещаются (поэтому фрагментация возможна, зато нет перемещения указателей).
- **STW-паузы очень короткие** (обычно десятки–сотни микросекунд): в начале (включить write barrier) и в конце маркировки.
- **Write barrier** во время маркировки — каждая запись указателя дороже.

Сравнение с Java: паузы как у ZGC (миллисекунды и меньше), но без поколений и компактирования. Платой за короткие паузы является CPU: GC по умолчанию использует **25 % от GOMAXPROCS** фоновыми воркерами во время маркировки.

### 6.2 GOGC — когда запускается GC

```
целевой размер кучи = живая куча после прошлого GC × (1 + GOGC/100)

GOGC=100 (по умолчанию): живых 500 МБ → следующий GC при 1000 МБ
GOGC=200:                живых 500 МБ → GC при 1500 МБ  (реже GC, больше памяти)
GOGC=50:                 живых 500 МБ → GC при 750 МБ   (чаще GC, меньше памяти)
GOGC=off:                GC не запускается по росту кучи (только по GOMEMLIMIT)
```

**Пример расчёта частоты GC:**

```
Скорость аллокаций: 400 МБ/с, живая куча 200 МБ, GOGC=100
Запас до следующего GC = 200 МБ → GC каждые 200 / 400 = 0,5 с → 2 цикла в секунду
Каждый цикл маркирует 200 МБ живой кучи

GOGC=400 → запас 800 МБ → GC каждые 2 с, пиковая куча ~1 ГБ, CPU на GC в ~4 раза меньше
```

### 6.3 GOMEMLIMIT (Go 1.19+)

Мягкий лимит памяти **всего рантайма** (куча + стеки + метаданные). При приближении к лимиту GC запускается чаще, независимо от GOGC.

```
Проблема без лимита в контейнере:
  limit 1 ГиБ, живых 600 МБ, GOGC=100 → цель 1,2 ГБ → OOMKilled до ближайшего GC

Решение:
  GOMEMLIMIT=900MiB (≈ 85–90 % лимита контейнера)
  GOGC оставить 100 или поднять/выключить для экономии CPU, лимит не даст вылезти
```

**Опасность — «спираль смерти»:** если живая куча сама по себе близка к GOMEMLIMIT, GC запускается непрерывно и съедает весь CPU. Рантайм ограничивает долю CPU на GC примерно 50 % (защита), но сервис всё равно сильно деградирует. Симптом: `go_gc_cycles` растёт лавинообразно, CPU 100 %, latency растёт, `heap_alloc` у самого лимита.

### 6.4 GC assist — почему GC бьёт по latency

Если программа аллоцирует быстрее, чем фоновые воркеры успевают маркировать, рантайм заставляет **аллоцирующую горутину саму помогать GC** (mark assist) прямо во время обработки запроса. Запрос, которому не повезло попасть на assist, получает лишние миллисекунды. Поэтому снижение аллокаций уменьшает **хвосты latency**, а не только CPU.

### 6.5 Новые разработки

В Go 1.25 появился экспериментальный сборщик **Green Tea** (`GOEXPERIMENT=greenteagc`) — маркировка, ориентированная на локальность памяти (обходит объекты страницами), уменьшает накладные расходы GC на многоядерных машинах. Проверять, какая версия Go у сервиса, и смотреть release notes.

### 6.6 Диагностика GC

```bash
GODEBUG=gctrace=1 ./service
# gc 152 @45.123s 4%: 0.031+2.1+0.045 ms clock, 0.25+1.2/4.1/8.0+0.36 ms cpu, 412->420->205 MB, 420 MB goal, 0 MB stacks, 0 MB globals, 8 P
#      │     │      │  └ STW начало + конкурентная маркировка + STW конец (реальное время)
#      │     │      └ 4 % CPU с начала работы ушло на GC
#      │     └ время с запуска
#      └ номер цикла
#   412->420->205 MB: куча в начале GC → в конце → живая после маркировки
#   420 MB goal: целевой размер
```

## 7. Метрики рантайма (Prometheus)

Клиент `prometheus/client_golang` по умолчанию экспортирует Go- и process-метрики.

| Метрика | Что значит | На что смотреть |
|---------|-----------|-----------------|
| `go_goroutines` | число горутин | растёт без возврата при стабильной нагрузке → утечка |
| `go_threads` | потоки ОС | ≫ GOMAXPROCS → блокирующие syscalls/cgo |
| `go_gc_duration_seconds` | паузы STW (сводка/квантили) | обычно < 1 мс |
| `go_memstats_alloc_bytes_total` (rate) | **скорость аллокаций**, байт/с | главная причина нагрузки на GC |
| `go_memstats_heap_alloc_bytes` | занято в куче (живые + ещё не собранные) | пила между GC |
| `go_memstats_heap_inuse_bytes` | память в используемых спанах кучи | |
| `go_memstats_heap_idle_bytes` / `_released_bytes` | свободная память кучи / возвращённая ОС | |
| `go_memstats_next_gc_bytes` | целевой размер кучи для следующего GC | |
| `go_memstats_sys_bytes` | вся память, взятая у ОС | сравнивать с лимитом контейнера |
| `go_gc_gogc_percent`, `go_gc_gomemlimit_bytes` | текущие настройки | |
| `go_sched_latencies_seconds` | задержка планирования горутин | рост → нехватка CPU |
| `go_gc_cycles_total_gc_cycles_total` (новые версии клиента) | число циклов GC | rate = частота GC |
| `process_cpu_seconds_total`, `process_resident_memory_bytes`, `process_open_fds` | процесс | |

```promql
rate(go_memstats_alloc_bytes_total[1m])                     # аллокации, байт/с
rate(go_gc_duration_seconds_count[1m])                      # циклов GC в секунду
go_memstats_heap_alloc_bytes / go_gc_gomemlimit_bytes       # близость к лимиту
rate(process_cpu_seconds_total[1m])                         # ядер CPU
```

## 8. Профилирование

### 8.1 pprof — встроенный профилировщик

```go
import _ "net/http/pprof"
go func() { log.Println(http.ListenAndServe("localhost:6060", nil)) }()
// отдельный порт, недоступный снаружи!
```

| Профиль | URL | Что показывает | Аналог в Java |
|---------|-----|----------------|---------------|
| CPU | `/debug/pprof/profile?seconds=30` | где тратится CPU (сэмплирование 100 Гц) | async-profiler cpu |
| heap | `/debug/pprof/heap` | что **живо** в куче (inuse) и что аллоцировалось (alloc) | heap dump / histo |
| allocs | `/debug/pprof/allocs` | все аллокации с начала работы | async-profiler alloc |
| goroutine | `/debug/pprof/goroutine?debug=2` | стеки **всех** горутин | **jstack** |
| block | `/debug/pprof/block` | где горутины ждут (каналы, мьютексы) | — |
| mutex | `/debug/pprof/mutex` | где ждут мьютексы (contention) | async-profiler lock |
| trace | `/debug/pprof/trace?seconds=5` | трассировка планировщика, GC, syscalls | JFR |

`block` и `mutex` по умолчанию выключены: `runtime.SetBlockProfileRate(1)`, `runtime.SetMutexProfileFraction(5)` (с накладными расходами — включать на время диагностики).

```bash
go tool pprof -http=:8080 http://svc:6060/debug/pprof/profile?seconds=30   # flame graph в браузере
go tool pprof -top http://svc:6060/debug/pprof/heap
go tool pprof -sample_index=alloc_space http://svc:6060/debug/pprof/heap  # кто больше всего аллоцирует
curl -s 'http://svc:6060/debug/pprof/goroutine?debug=1' | head -50        # группировка стеков горутин с количеством
```

**Поиск утечки горутин:** снять `goroutine?debug=1` дважды с интервалом — стек, у которого счётчик растёт (например, `12034 @ ... net/http.(*persistConn).readLoop` или `chan receive` в твоём коде), и есть утечка.

### 8.2 go tool trace

```bash
curl -o trace.out 'http://svc:6060/debug/pprof/trace?seconds=5'
go tool trace trace.out
```

Показывает по каждому P во времени: какие горутины выполнялись, где GC, STW, ожидание в syscall, задержки планирования. Отвечает на вопрос «почему этот запрос ждал, хотя CPU был свободен».

### 8.3 GODEBUG

```bash
GODEBUG=gctrace=1              # строка на каждый цикл GC
GODEBUG=schedtrace=1000        # раз в секунду: число горутин, потоков, длины очередей P
GODEBUG=schedtrace=1000,scheddetail=1
```

### 8.4 Continuous profiling

Pyroscope / Grafana Pyroscope, Parca — постоянно снимают pprof-профили со всех инстансов. На НТ это позволяет сравнить профиль «до деградации» и «во время».

## 9. HTTP-сервер и HTTP-клиент

### 9.1 Сервер — таймауты по умолчанию отсутствуют

```go
srv := &http.Server{
    Addr:              ":8080",
    Handler:           mux,
    ReadHeaderTimeout: 5 * time.Second,   // защита от медленных клиентов (Slowloris)
    ReadTimeout:       10 * time.Second,
    WriteTimeout:      30 * time.Second,
    IdleTimeout:       120 * time.Second, // keep-alive; БОЛЬШЕ idle timeout балансировщика перед сервисом
    MaxHeaderBytes:    1 << 20,
}
```

`http.ListenAndServe(":8080", mux)` без настройки = **все таймауты бесконечны**: каждое медленное или зависшее соединение навсегда держит горутину и FD.

Сервер создаёт **горутину на каждое соединение**; ограничения параллелизма нет — при перегрузке растут горутины и память, а не очередь. Нужен свой лимит (middleware-семафор, `netutil.LimitListener`) или защита на уровне балансировщика.

### 9.2 Клиент — две классические ловушки

```go
// Ловушка 1: http.DefaultClient без таймаута — запрос может висеть вечно
// Ловушка 2: MaxIdleConnsPerHost = 2 по умолчанию

transport := &http.Transport{
    MaxIdleConns:        1000,
    MaxIdleConnsPerHost: 200,             // по умолчанию 2 (!)
    MaxConnsPerHost:     0,               // 0 = без лимита
    IdleConnTimeout:     90 * time.Second,
    TLSHandshakeTimeout: 5 * time.Second,
    DialContext: (&net.Dialer{Timeout: 2 * time.Second, KeepAlive: 30 * time.Second}).DialContext,
    ForceAttemptHTTP2:   true,
}
client := &http.Client{Transport: transport, Timeout: 10 * time.Second}   // по умолчанию Timeout = 0 — бесконечно
```

**Что происходит с `MaxIdleConnsPerHost = 2` под нагрузкой:**

```
Сервис делает 500 параллельных запросов к одному хосту
→ открывает 500 соединений (MaxConnsPerHost не ограничен)
→ после ответа в пуле можно оставить только 2 → 498 соединений ЗАКРЫВАЮТСЯ
→ следующая волна снова открывает 498 новых
Результат: тысячи TIME_WAIT, CPU на TLS-рукопожатия, исчерпание эфемерных портов,
           «connect: cannot assign requested address»
```

**Ловушка 3: тело ответа.** Соединение возвращается в пул, только если тело **прочитано до конца и закрыто**:

```go
resp, err := client.Do(req)
if err != nil { return err }
defer resp.Body.Close()
io.Copy(io.Discard, resp.Body)   // дочитать, даже если тело не нужно
```

Без `Close()` — утечка соединения и горутин (`persistConn.readLoop`/`writeLoop`) и рост CLOSE_WAIT ([[02 Сеть — пропускная способность, фаерволы, узкие места]], раздел 5).

**DNS:** в стандартной библиотеке нет кэша DNS — каждое **новое** соединение разрешает имя. С хорошим пулом это редкость; без пула — нагрузка на DNS (особенно в Kubernetes с `ndots:5`).

## 10. database/sql и пулы соединений

`database/sql` — встроенный пул соединений (аналог HikariCP, но с другими дефолтами):

| Настройка | По умолчанию | Рекомендация |
|-----------|--------------|--------------|
| `SetMaxOpenConns` | **0 = без лимита** | ограничить (10–50 на инстанс), иначе под нагрузкой откроет сотни соединений к БД |
| `SetMaxIdleConns` | **2** | = MaxOpenConns, иначе лишние соединения закрываются и открываются снова (как у HTTP) |
| `SetConnMaxLifetime` | 0 (вечно) | 30 мин, меньше idle timeout фаерволов/PgBouncer |
| `SetConnMaxIdleTime` | 0 | 5–10 мин |

```go
s := db.Stats()
// s.OpenConnections, s.InUse, s.Idle
// s.WaitCount, s.WaitDuration       ← сколько раз и сколько суммарно ждали соединение (аналог Hikari pending)
// s.MaxIdleClosed, s.MaxLifetimeClosed ← сколько закрыто из-за лимитов (большой MaxIdleClosed = MaxIdleConns мал)
```

**`rows.Close()`** обязательно (`defer rows.Close()`): незакрытый результат держит соединение — пул «утекает», `WaitCount` растёт.

Для PostgreSQL часто используют **pgx** и его пул `pgxpool` (`MaxConns` по умолчанию = max(4, число CPU)) — быстрее `lib/pq`, поддерживает бинарный протокол, батчи и `COPY`.

## 11. Go в контейнере

- **GOMAXPROCS:** до Go 1.25 рантайм брал число ядер **ноды**, не учитывая CPU-лимит контейнера. Под с `limits.cpu: 2` на ноде с 64 ядрами получал GOMAXPROCS=64 → 64 потока жгут квоту за миллисекунды → жёсткий **CFS throttling** ([[01 Linux — ядро, ресурсы, метрики]], раздел 8). Лечилось библиотекой `go.uber.org/automaxprocs` или переменной `GOMAXPROCS`.
- **С Go 1.25** GOMAXPROCS по умолчанию учитывает CPU-лимит cgroup и обновляется при его изменении. Проверять версию Go сборки (`go version -m ./binary`) — старые сервисы всё ещё могут иметь проблему.
- **Память:** рантайм не знает о лимите контейнера → задавать `GOMEMLIMIT` (≈ 85–90 % лимита).

## 12. Сеть и Go

- **Netpoller** (epoll) обслуживает десятки тысяч соединений небольшим числом потоков — сетевой I/O в Go дешёвый, и упираются обычно не в «потоки», а в CPU обработки, GC и пулы.
- **TCP_NODELAY** включён по умолчанию для TCP-соединений в Go (Nagle отключён).
- **Keep-alive TCP** по умолчанию 15 с (`net.Dialer.KeepAlive`, с Go 1.23 настраивается детальнее `KeepAliveConfig`) — хорошо для обхода idle-таймаутов фаерволов.
- **HTTP/2** включается автоматически для TLS; одно соединение к хосту на HTTP/2 → проблема балансировки за L4 ([[03 Протоколы взаимодействия]], раздел 3.2). Для gRPC-клиентов — `round_robin` + headless Service.
- **Порты и TIME_WAIT** — см. ловушку `MaxIdleConnsPerHost` (раздел 9.2).
- **Таймауты** — через `context` и поля клиента/сервера; без них зависания сети превращаются в утечки горутин.
- **Большие ответы** — читать потоково (`io.Copy`, `json.Decoder`), а не `io.ReadAll` в память.

## 13. Типичные узкие места и как их найти

```
1. RED сервиса: RPS, ошибки, перцентили latency — где деградация
2. CPU процесса (process_cpu_seconds_total) относительно GOMAXPROCS / лимита:
   ≈ лимиту → CPU-bound → pprof CPU
   + throttling контейнера → GOMAXPROCS/лимит
3. GC: rate(alloc_bytes_total), частота GC, gctrace → pprof allocs
4. Горутины: go_goroutines растёт → goroutine profile, утечка
5. CPU низкий, latency высокая → ожидание:
   block/mutex profile → contention
   db.Stats WaitCount, HTTP-пул → пулы
   trace → где ждут горутины
6. Сеть: TIME_WAIT, CLOSE_WAIT, новые соединения/с (sar -n TCP) → пулы HTTP, Body.Close()
```

## 14. Шпаргалка: симптом → причина → решение

| Симптом | Причина | Решение |
|---------|---------|---------|
| `go_goroutines` растёт бесконечно | утечка: нет таймаутов, незакрытый Body, канал без читателя | goroutine profile, context с таймаутом, `Body.Close()` |
| Тысячи TIME_WAIT, `cannot assign requested address` | `MaxIdleConnsPerHost = 2` | увеличить до ожидаемой параллельности |
| Рост CLOSE_WAIT | не закрыт `resp.Body` | `defer resp.Body.Close()` + дочитать |
| Запросы к зависимости висят вечно | `http.Client` без Timeout | `Timeout`, context |
| Высокий CPU на GC, хвосты latency | высокая скорость аллокаций, GC assist | pprof allocs, sync.Pool, меньше аллокаций, GOGC выше |
| OOMKilled в контейнере | рантайм не знает лимит | `GOMEMLIMIT` |
| CPU 100 % при куче у лимита | спираль GC при GOMEMLIMIT | больше памяти, меньше живых данных |
| Throttling при низком среднем CPU | GOMAXPROCS = ядра ноды (Go < 1.25) | automaxprocs / GOMAXPROCS / новая версия Go |
| Сотни потоков ОС (`go_threads`) | блокирующие syscalls, cgo, файловый I/O | профиль, cgo DNS → pure Go резолвер |
| CPU низкий, latency высокая | mutex contention / ожидание пула | mutex/block profile, `db.Stats().WaitCount` |
| Сотни соединений к БД | `SetMaxOpenConns` не задан | ограничить пул |
| `encoding/json` в топе CPU | рефлексия | кодогенерация / быстрый JSON |
| Нагрузка ушла на один под | HTTP/2/gRPC за L4 | клиентская балансировка, L7 |
