## 1. Модель уровней

| Уровень (TCP/IP) | Что там | Адрес / единица | Примеры | Что может сломаться |
|------------------|---------|-----------------|---------|---------------------|
| Канальный (L2) | кадры в пределах сегмента | MAC, кадр (frame) | Ethernet, VLAN, ARP | дуплекс, ошибки кабеля, CRC, VLAN, MTU |
| Сетевой (L3) | маршрутизация между сетями | IP, пакет | IPv4, IPv6, ICMP | маршруты, асимметрия, MTU/фрагментация, потери |
| Транспортный (L4) | доставка между процессами | порт, сегмент/датаграмма | TCP, UDP, QUIC (поверх UDP) | ретрансмиссии, окна, backlog, порты, conntrack |
| Прикладной (L7) | смысл обмена | URL, метод, топик | HTTP, gRPC, PostgreSQL wire, Kafka protocol, Redis RESP | таймауты, пулы, keep-alive, сериализация |

TLS работает между L4 и L7. L4-балансировщик видит только IP и порты, L7 — содержимое HTTP (раздел 11).

## 2. Пропускная способность, задержка, BDP

### 2.1 Три разных понятия

- **Пропускная способность (bandwidth)** — сколько бит в секунду **может** пройти по каналу: 1 Гбит/с, 10 Гбит/с, 25 Гбит/с.
- **Пропускная способность фактическая (throughput)** — сколько **реально** проходит полезных данных.
- **Задержка (latency)** — время прохождения. **RTT (round-trip time)** — туда и обратно.

Аналогия: ширина трубы (bandwidth) и длина трубы (latency). Широкая длинная труба может пропускать много воды, но первая капля всё равно идёт долго.

### 2.2 Полезная скорость канала

```
1 Гбит/с = 1000 Мбит/с = 125 МБ/с «сырых» байт
Накладные расходы Ethernet + IP + TCP на пакет 1500 байт ≈ 5–6 %
→ полезный TCP-поток ≈ 112–118 МБ/с

10 Гбит/с → ~1,1–1,17 ГБ/с полезных
```

**Не путать биты и байты:** в мониторинге интерфейсов часто байты/с, в паспорте канала — биты/с. ×8.

### 2.3 Из чего складывается задержка

```
задержка = распространение (скорость света в оптике ≈ 200 км/мс → 5 мкс на км)
         + сериализация (размер пакета / скорость канала: 1500 байт на 1 Гбит/с = 12 мкс)
         + ожидание в очередях устройств (буферы коммутаторов, NIC, ядра) ← растёт при перегрузе
         + обработка (фаерволы, балансировщики, conntrack, TLS)
```

Типичные RTT:

| Путь | RTT |
|------|-----|
| loopback (127.0.0.1) | 0,01–0,05 мс |
| два пода на одной ноде K8s | 0,05–0,1 мс |
| два сервера в одной стойке | 0,05–0,2 мс |
| в пределах одного ЦОДа | 0,2–0,5 мс |
| соседние ЦОДы в одном городе | 1–3 мс |
| Москва — Санкт-Петербург | ~10–12 мс |
| Москва — Новосибирск | ~45–55 мс |
| Москва — Владивосток | ~110–130 мс |

### 2.4 BDP — почему быстрый канал не даёт скорость одному соединению

**BDP (Bandwidth-Delay Product)** — сколько данных «в полёте» нужно держать, чтобы загрузить канал:

```
BDP = пропускная способность × RTT

Пример 1: 1 Гбит/с, RTT 0,5 мс
  BDP = 125 МБ/с × 0,0005 с = 62,5 КБ   → буфера по умолчанию хватает

Пример 2: 10 Гбит/с, RTT 50 мс (межрегиональная репликация)
  BDP = 1,25 ГБ/с × 0,05 с = 62,5 МБ    → нужен буфер/окно 62,5 МБ!
```

TCP может отправить не больше, чем позволяет **окно** (меньшее из окна приёма получателя и окна перегрузки отправителя), а потом ждёт подтверждения. Максимальная скорость одного TCP-соединения:

```
throughput ≤ окно / RTT

Окно 4 МБ, RTT 50 мс → 4 МБ / 0,05 с = 80 МБ/с, хотя канал 10 Гбит/с (1250 МБ/с)
Окно 64 КБ (без window scaling), RTT 50 мс → 1,3 МБ/с
```

Отсюда:

- репликация БД, Kafka MirrorMaker, бэкапы между регионами упираются в **окно/буферы**, а не в канал → увеличить `net.core.rmem_max/wmem_max`, `tcp_rmem/tcp_wmem`, у Kafka — `socket.send.buffer.bytes`/`receive.buffer.bytes`, или использовать несколько параллельных соединений;
- `iperf3` с одним потоком на длинном канале покажет мало, с `-P 8` — больше.

### 2.5 Потери пакетов и скорость TCP

TCP при потере пакета уменьшает окно перегрузки. Грубая оценка (формула Матиса):

```
throughput ≈ (MSS / RTT) × (1,22 / √p),  где p — доля потерь

MSS 1460 байт, RTT 10 мс:
  p = 0,0001 (0,01 %) → 1460 / 0,01 × 1,22 / 0,01  = 17,8 МБ/с
  p = 0,01   (1 %)    → 1460 / 0,01 × 1,22 / 0,1   = 1,78 МБ/с
```

**1 % потерь режет скорость одного TCP-потока на порядок.** Поэтому доля ретрансмиссий — одна из главных сетевых метрик (норма в ЦОДе < 0,1 %).

### 2.6 Пакеты в секунду

Сетевое оборудование и ядро ограничены не только битами, но и **пакетами в секунду (pps)**. Обработка одного пакета стоит одинаково вне зависимости от размера. Маленькие пакеты (API-запросы по 200 байт, DNS, метрики UDP) упираются в CPU (softirq), фаерволы и балансировщики раньше, чем в канал. Облачные инстансы и виртуальные сети часто имеют явные лимиты pps.

### 2.7 Закон Литтла для сети и сервисов

```
одновременно в обработке (concurrency) = пропускная способность (RPS) × время ответа (latency)

5000 RPS × 0,04 с = 200 одновременных запросов
→ нужен пул соединений/потоков ≥ 200 на этом пути, иначе запросы встанут в очередь
→ если latency выросла до 0,4 с (медленная зависимость), при тех же 5000 RPS нужно уже 2000
```

Этот закон объясняет каскадные падения: латентность зависимости выросла → занятых соединений стало в 10 раз больше → пулы исчерпаны → очереди → ещё больше latency.

## 3. TCP: соединение, буферы, окна, контроль перегрузки

### 3.1 Что такое TCP-соединение

**TCP-соединение** — это состояние в ядре на обеих сторонах. У ядра это:

- запись в таблице соединений (TCB — Transmission Control Block), ключ — **4-кортеж** `(src IP, src port, dst IP, dst port)`;
- буферы отправки и приёма;
- таймеры: ретрансмиссии (RTO), keepalive, TIME_WAIT, delayed ACK;
- текущие номера последовательности, окна, оценка RTT.

В приложении это: объект сокета, поток/корутина/обработчик epoll, который его обслуживает, и **FD**.

Главные свойства TCP:

- **надёжность** — подтверждения (ACK), повторная отправка (retransmit);
- **поток байтов** — нет «сообщений»: две записи по 100 байт могут прийти одним чтением на 200 байт или тремя кусками. Границы сообщений определяет протокол сверху (HTTP Content-Length, длина в заголовке Kafka/PostgreSQL);
- **порядок** — байты приходят в порядке отправки. Потерянный сегмент задерживает все следующие (**head-of-line blocking**) — даже если они уже пришли;
- **управление потоком** — окно приёма (rwnd): получатель говорит, сколько ещё готов принять;
- **контроль перегрузки** — окно перегрузки (cwnd): отправитель сам ограничивает себя, чтобы не перегрузить сеть.

### 3.2 Буферы сокета

```
Приложение A                                          Приложение B
   write() → [send buffer A] → сеть → [receive buffer B] → read()
```

- **Send buffer полон** → `write()` блокируется (или возвращает EAGAIN в неблокирующем режиме). Причины: сеть медленная или **получатель не читает**.
- **Receive buffer полон** → получатель объявляет окно 0 (**zero window**) → отправитель останавливается. Причина: приложение-получатель не успевает читать (CPU, GC-пауза, блокировка).

```bash
ss -tmi dst 10.0.0.5
# skmem:(r0,rb131072,t0,tb87040,...)  — r/t: занято в буферах приёма/отправки
# Recv-Q / Send-Q в `ss -tan`:
#   для ESTABLISHED: Recv-Q — непрочитанные приложением байты, Send-Q — неподтверждённые байты
#   для LISTEN: Recv-Q — текущая длина accept queue, Send-Q — её максимум
```

**Диагностика «кто тормозит» по Recv-Q/Send-Q:**

- у сервера большой `Recv-Q` на соединениях → **сервер** не успевает читать;
- у отправителя большой `Send-Q` и у получателя `Recv-Q` пустой → тормозит **сеть**;
- у отправителя большой `Send-Q` и у получателя большой `Recv-Q` → тормозит **получатель**.

### 3.3 Контроль перегрузки

- **Slow start**: новое соединение начинает с маленького окна (initcwnd = 10 сегментов ≈ 14 КБ) и удваивает его каждый RTT, пока нет потерь. Следствие: **новое соединение не может сразу передавать быстро** — ещё одна причина держать соединения долгоживущими.
- **Congestion avoidance**: после порога окно растёт линейно.
- **Потеря** → окно уменьшается (у CUBIC — примерно на 30 %).
- **Алгоритмы:** `cubic` (по умолчанию в Linux) реагирует на потери; `bbr` оценивает пропускную способность и RTT, меньше страдает от случайных потерь и лучше на длинных каналах. `sysctl net.ipv4.tcp_congestion_control`.
- `tcp_slow_start_after_idle = 1` (по умолчанию) — после простоя соединения окно сбрасывается. Для keep-alive соединений с паузами это добавляет latency — на серверах часто ставят 0.

### 3.4 Nagle и delayed ACK — классическая ловушка 40 мс

- **Алгоритм Нейгла**: не отправлять маленький сегмент, пока предыдущий не подтверждён (копит данные).
- **Delayed ACK**: получатель не подтверждает сразу, а ждёт до ~40 мс (в Linux), чтобы отправить ACK вместе с ответом.

Вместе: клиент пишет запрос двумя `write()` (заголовок, потом тело). Первая часть ушла, вторая ждёт ACK по Нейглу, сервер ждёт полного запроса и не отвечает, ACK задержан на 40 мс → **каждый запрос +40 мс**.

Решение: `TCP_NODELAY` (отключить Нейгла) — большинство драйверов БД, HTTP-клиентов, Kafka, Redis-клиентов ставят его по умолчанию; либо собирать сообщение в один `write()`.

На графике latency ровно 40 мс (или кратные) у части запросов — почти всегда эта проблема.

### 3.5 Keepalive

- **TCP keepalive** — ядро шлёт пустые проверочные пакеты в простаивающем соединении. Linux по умолчанию: первая проверка через 7200 с (`tcp_keepalive_time`), потом 9 проверок раз в 75 с. Это слишком долго для обнаружения мёртвых соединений и для удержания записей в фаерволах/NAT — их idle-таймауты обычно 5–60 минут.
- **HTTP keep-alive** — совсем другое: переиспользование одного TCP-соединения для многих HTTP-запросов ([[03 Протоколы взаимодействия]]).

## 4. Handshake, очереди SYN и accept, backlog

### 4.1 Трёхстороннее рукопожатие

```
Клиент                          Сервер (LISTEN)
  │ ── SYN (seq=x) ──────────────> │   сервер создаёт запись в SYN queue (состояние SYN_RECV)
  │ <─ SYN-ACK (seq=y, ack=x+1) ── │
  │ ── ACK (ack=y+1) ────────────> │   запись переходит в ACCEPT queue (ESTABLISHED)
  │                                │   приложение вызывает accept() → забирает соединение
```

Установка соединения стоит **1 RTT** до того, как можно отправить первый байт данных (плюс TLS — ещё 1–2 RTT, [[03 Протоколы взаимодействия]]).

### 4.2 Две очереди на сервере

1. **SYN queue** — полуоткрытые соединения (`SYN_RECV`): сервер ответил SYN-ACK, ждёт финальный ACK. Размер — `net.ipv4.tcp_max_syn_backlog`.
2. **Accept queue** — полностью установленные соединения, которые ещё **не забрало приложение** через `accept()`. Размер = `min(backlog из listen(), net.core.somaxconn)`.

**Backlog в приложении:** Tomcat `acceptCount` (100), Netty `SO_BACKLOG`, nginx `listen ... backlog=`, Redis `tcp-backlog` (511), PostgreSQL — фиксированный внутри. Если приложение просит 100, а `somaxconn = 4096` — очередь будет 100.

**SYN cookies** (`net.ipv4.tcp_syncookies = 1`) — когда SYN queue полна, сервер не хранит состояние, а кодирует его в номер последовательности SYN-ACK. Защищает от SYN flood. В `dmesg`: `possible SYN flooding on port 8080. Sending cookies.` — на НТ это знак, что SYN queue мала для темпа новых соединений.

### 4.3 Что происходит при переполнении

```
Accept queue полна, пришёл финальный ACK:
  по умолчанию (tcp_abort_on_overflow = 0) — ACK игнорируется,
  клиент думает, что соединение установлено, и шлёт данные,
  сервер повторяет SYN-ACK, клиент получает ответ с задержкой или timeout
  → счётчики ListenOverflows и ListenDrops растут
  при tcp_abort_on_overflow = 1 — сервер сразу отвечает RST → клиент видит «connection reset»
```

**Симптомы заполненного backlog:**

- у клиентов `connect timeout`, иногда `connection refused`/`reset`;
- на сервере растут `ListenOverflows`, `ListenDrops`, `SYN_RECV`, ретраи SYN/SYN-ACK;
- `ss -ltn` у слушающего сокета `Recv-Q` близко к `Send-Q`.

```bash
ss -ltn                          # LISTEN: Recv-Q = текущая accept queue, Send-Q = её размер
sysctl net.ipv4.tcp_max_syn_backlog net.core.somaxconn
nstat -az TcpExtListenOverflows TcpExtListenDrops
```

**Главная причина переполнения accept queue — не маленький backlog, а то, что приложение медленно делает `accept()`**: все потоки заняты, GC-пауза, CPU 100 %, event loop заблокирован. Увеличение backlog только сглаживает пики.

## 5. Состояния TCP-соединения

```
         Активное открытие (клиент)            Пассивное открытие (сервер)
CLOSED ──SYN──> SYN_SENT                       LISTEN ──SYN получен──> SYN_RECV
SYN_SENT ──SYN-ACK получен, ACK──> ESTABLISHED  SYN_RECV ──ACK получен──> ESTABLISHED

         Активное закрытие (кто первым close)  Пассивное закрытие (кто получил FIN)
ESTABLISHED ──FIN──> FIN_WAIT_1                ESTABLISHED ──FIN получен──> CLOSE_WAIT
FIN_WAIT_1 ──ACK──> FIN_WAIT_2                 CLOSE_WAIT ──приложение close(), FIN──> LAST_ACK
FIN_WAIT_2 ──FIN получен, ACK──> TIME_WAIT     LAST_ACK ──ACK──> CLOSED
TIME_WAIT ──через 2×MSL (60 с в Linux)──> CLOSED
```

| Состояние | Где | Значит | Когда тревожно |
|-----------|-----|--------|----------------|
| `LISTEN` | сервер | ждёт подключений | — |
| `SYN_SENT` | клиент | отправил SYN, ждёт ответа | много → сервер/сеть не отвечает, фаервол молча режет (DROP) |
| `SYN_RECV` | сервер | получил SYN, ждёт ACK | много → SYN flood, потери ACK, перегруз |
| `ESTABLISHED` | обе | соединение работает | бесконечный рост → утечка соединений или слишком долгий keep-alive |
| `FIN_WAIT_1/2` | закрывший первым | ждёт подтверждения/FIN от другой стороны | много долгих FIN_WAIT_2 → другая сторона не закрывает |
| `CLOSE_WAIT` | получивший FIN | **удалённая сторона закрыла, а наше приложение ещё не вызвало close()** | **любой рост — почти всегда утечка сокетов в коде** |
| `LAST_ACK` | — | отправили свой FIN, ждём ACK | — |
| `TIME_WAIT` | закрывший первым | соединение закрыто, ждём 60 с | десятки тысяч → слишком много коротких соединений |

### TIME_WAIT подробно

**Зачем нужен:**

1. чтобы запоздавшие пакеты старого соединения не попали в новое с тем же 4-кортежем;
2. чтобы, если потерялся последний ACK, можно было ответить на повторный FIN.

**Почему проблема:** каждый TIME_WAIT держит 4-кортеж. Для **клиента** (генератора нагрузки, сервиса, вызывающего другой сервис) это означает занятый эфемерный порт на 60 с → при высоком темпе новых соединений порты заканчиваются ([[01 Linux — ядро, ресурсы, метрики]], раздел 10). Сам по себе TIME_WAIT дешёвый по памяти (~несколько сотен байт).

**Решения:** keep-alive и пулы соединений (главное!), HTTP/2, `tcp_tw_reuse = 1` (только для исходящих), расширение диапазона портов. Не использовать `tcp_tw_recycle` — удалён из ядра 4.12, ломал клиентов за NAT.

📌 **TIME_WAIT ≠ утечка. TIME_WAIT = churn соединений.**

### CLOSE_WAIT подробно

Ядро получило FIN, сообщило приложению (read вернул 0), но приложение не закрыло сокет. Типичные причины в коде:

- HTTP-клиент: не прочитали/не закрыли тело ответа (`response.close()`, в Go — `resp.Body.Close()`);
- соединение «вынули» из пула, вернуть забыли;
- исключение до `finally { close() }`.

CLOSE_WAIT не исчезает сам — висит, пока жив процесс. Следствие: рост FD → «Too many open files».

```bash
ss -tanp state close-wait | head      # какой процесс, к какому удалённому адресу
ss -tan | awk '{print $1}' | sort | uniq -c   # распределение по состояниям
```

## 6. Флаги TCP

| Флаг | Название | Что делает | Где видно / к чему ведёт |
|------|----------|-----------|--------------------------|
| **SYN** | Synchronize | открывает соединение, синхронизирует начальные номера последовательности | только в handshake. Проблемы → ListenDrops, TCPSynRetrans |
| **ACK** | Acknowledgment | «получил всё до байта N» | почти в каждом пакете после установки соединения; нет ACK → ретрансмиссии, AbortOnTimeout |
| **FIN** | Finish | «я больше не буду слать данные, но ещё могу принимать» | вежливое закрытие: FIN → ACK → FIN → ACK, данные доставлены |
| **RST** | Reset | «забудь это соединение» — аварийный разрыв | данные в буферах теряются, ошибка `Connection reset by peer`, растут `OutRsts`/`InRsts` |
| **PSH** | Push | подсказка «отдай данные приложению сразу» | на практике почти ни на что не влияет |
| **URG** | Urgent | в потоке есть срочные данные | исторический (Telnet), в проде почти не встречается |
| **ECE** | ECN Echo | «сеть пометила перегрузку (ECN), я это увидел» | при включённом ECN: мягкий сигнал перегрузки вместо потери пакета |
| **CWR** | Congestion Window Reduced | «я уменьшил окно в ответ на ECE» | пара к ECE |

**Когда отправляется RST:**

- пакет пришёл на порт, где никто не слушает → клиент получает `connection refused`;
- приложение закрыло сокет, в котором остались непрочитанные данные, или закрыло с `SO_LINGER=0` (так делают некоторые балансировщики и HTTP-клиенты, чтобы не копить TIME_WAIT);
- пришёл пакет для соединения, которого ядро не знает (сервер перезагрузился, conntrack/NAT забыл запись);
- переполнение accept queue при `tcp_abort_on_overflow = 1`;
- фаервол/балансировщик активно отвергает (`REJECT --reject-with tcp-reset`) или закрывает idle-соединение.

**Сценарии жизни соединения:**

```
Установка:          SYN → SYN+ACK → ACK
Передача:           данные с ACK (иногда PSH; ECE/CWR при перегрузке)
Нормальное закрытие: FIN → ACK → FIN → ACK  (активная сторона уходит в TIME_WAIT)
Аварийное:          RST — соединение мгновенно уничтожено
```

## 7. Ошибки TCP: что означает каждый счётчик

Источник — `nstat`/`netstat -s` или node_exporter (`node_netstat_TcpExt_*`, `node_netstat_Tcp_*`).

### 7.1 ListenOverflows — переполнилась accept queue

**Что это:** серверный сокет в LISTEN держит очередь **уже установленных** соединений (handshake прошёл), которые ждут `accept()`. Очередь полна — новое готовое соединение некуда положить.

**Причины:**

- приложение медленно делает `accept()`: зависло, мало потоков-акцепторов, GC stop-the-world, блокировки, CPU 100 %, заблокирован event loop;
- маленький `listen(backlog)` или `net.core.somaxconn`;
- шторм подключений: много клиентов, короткие соединения, reconnect-цикл, частые health-check-и.

**Следствия:** задержки и ошибки подключения у клиентов; вслед растут `ListenDrops`, `TCPSynRetrans`, `TCPAbortOnTimeout`.

### 7.2 ListenDrops — SYN к слушающему сокету отброшен

**Что это:** SYN пришёл, но ядро не смогло его обработать для LISTEN-сокета. Это уровень «клиент не может даже подключиться». Счётчик включает и случаи ListenOverflows.

**Причины:** переполнена SYN queue (`tcp_max_syn_backlog`) или accept queue; шторм SYN (атака, сканер, массовый реконнект); нехватка ресурсов ядра; conntrack/iptables под нагрузкой.

**Следствия:** клиенты повторяют SYN → растёт `TCPSynRetrans`; при долгих попытках — `TCPAbortOnTimeout` и connect timeout.

### 7.3 TCPSynRetrans — повторы SYN и SYN-ACK

**Что это:** TCP не получил ответ на этапе установки и повторяет: клиент — SYN (если нет SYN-ACK), сервер — SYN-ACK (если нет финального ACK). Интервалы повторов растут экспоненциально: 1 с, 2 с, 4 с, 8 с...

**Причины:** ListenDrops на сервере; потери/дропы в сети; фаервол молча отбрасывает (DROP) пакеты; асимметричная маршрутизация (ответ уходит другим путём через stateful-фаервол, который не видел SYN); перегруз сервера.

**Следствия:** у клиента «подключение висит» 1, 3, 7 секунд, потом `connect timeout`. Характерная картина в латентности — пики ровно около 1 с и 3 с: это первый и второй повтор SYN.

### 7.4 TCPAbortOnTimeout — соединение закрыто после исчерпания ретраев

**Что это:** TCP повторял важные сегменты, но так и не получил ACK за допустимое число попыток (`tcp_retries2 = 15` ≈ 15 минут для установленного соединения, `tcp_syn_retries = 6` ≈ 2 минуты для SYN) → ядро закрывает соединение как безнадёжное.

**Причины:** потери в сети; фаервол/балансировщик по пути удалил состояние соединения и молча отбрасывает пакеты; зависшее приложение на другой стороне; PMTU black hole (раздел 9); очень плохой канал.

**Следствия:** ошибки `timeout`, иногда `connection reset`. Это уже не деградация, а **реальные разрывы сессий**.

### 7.5 TCPSackRecoveryFail — не удалось восстановиться через SACK

**Что это:** SACK (Selective ACK) позволяет переслать только потерянные куски. Счётчик растёт, когда быстрое восстановление не удалось и TCP ушёл в таймаут ретрансмиссии (RTO).

**Причины:** потери пачками; переупорядочивание и дропы на сетевом оборудовании; переполненные очереди; плохой NIC или драйвер; изредка — проблемы offload-ов (TSO/GRO) в сочетании с фаерволом.

**Следствия:** рост latency, падение throughput; при длительной проблеме — `TCPAbortOnTimeout`.

### 7.6 Прочие счётчики

| Счётчик | Смысл |
|---------|-------|
| `Tcp_RetransSegs` / `Tcp_OutSegs` | доля ретрансмиссий — главный индикатор потерь |
| `Tcp_InErrs` | сегменты с ошибкой (контрольная сумма) |
| `Tcp_OutRsts` | отправленные RST |
| `Tcp_AttemptFails` | неудачные попытки соединения (в т.ч. получен RST на SYN) |
| `Tcp_EstabResets` | установленные соединения, закрытые RST |
| `TcpExt_TCPTimeouts` | срабатывания RTO |
| `TcpExt_TCPLossProbes` | проверки потерь в хвосте (TLP) |
| `TcpExt_TCPBacklogDrop` | пакет отброшен: сокет занят приложением, его backlog полон |
| `TcpExt_TCPRcvQDrop` | отброшен из-за нехватки памяти в буфере приёма |
| `TcpExt_TCPZeroWindowDrop` | получатель объявил нулевое окно — не успевает читать |
| `TcpExt_TCPMemoryPressures` | стек упёрся в `tcp_mem` |
| `TcpExt_TCPToZeroWindowAdv` | сколько раз мы сами объявили нулевое окно — **наше приложение не успевает читать** |

## 8. UDP

### 8.1 Свойства

UDP — датаграммы:

- нет соединения и handshake → нет 1 RTT на установку;
- нет гарантии доставки, нет повторов, нет порядка;
- границы сообщений сохраняются (одна отправка = одна датаграмма);
- нет контроля перегрузки — отправитель может «залить» сеть.

Используется: DNS, метрики (statsd), syslog, NTP, видео/голос, QUIC (HTTP/3 строит надёжность сам поверх UDP), WireGuard.

### 8.2 Ошибки и потери UDP — самое важное

| Счётчик (`node_netstat_Udp_*`) | Что это |
|--------------------------------|---------|
| `InDatagrams` / `OutDatagrams` | принято/отправлено |
| `RcvbufErrors` | **датаграмма пришла, но буфер приёма сокета полон — отброшена**. Приложение не успевает читать |
| `SndbufErrors` | не хватило буфера отправки |
| `NoPorts` | пришло на порт, где никто не слушает (отправителю уходит ICMP port unreachable) |
| `InErrors` | все ошибки приёма (включая RcvbufErrors и контрольную сумму) |

**Почему UDP «вроде работает», но данные пропадают:** потерянное в TCP было бы переотправлено, в UDP — исчезает без следа. Отправитель не узнает. «Пропали метрики/логи/ивенты» под нагрузкой — первым делом `RcvbufErrors`.

**Решения:** увеличить буфер сокета (`net.core.rmem_default`, `rmem_max` + `SO_RCVBUF` в приложении), ускорить обработчик (отдельный поток чтения + очередь), `netdev_max_backlog`, батчинг, переход на TCP/надёжный протокол.

## 9. MTU, фрагментация, PMTU black hole

**MTU (Maximum Transmission Unit)** — максимальный размер IP-пакета на канале: Ethernet 1500 байт, jumbo frames 9000. **MSS** = MTU − 40 байт (IP + TCP заголовки) = 1460.

Overlay-сети добавляют заголовки: VXLAN +50 байт, WireGuard +60–80, IPsec — больше. Поэтому в Kubernetes с VXLAN MTU пода обычно 1450.

**PMTU discovery:** отправитель ставит флаг «не фрагментировать» (DF); если пакет больше MTU какого-то участка, маршрутизатор отбрасывает его и присылает ICMP «Fragmentation needed» с допустимым размером.

**PMTU black hole:** где-то по пути фаервол **режет все ICMP**. Тогда:

```
маленькие пакеты (handshake, короткие запросы) проходят → соединение «работает»
большой ответ (страница, выборка из БД, TLS-сертификат) — пакеты 1500 байт исчезают
→ запрос с маленьким ответом успешен, с большим — висит до таймаута
```

Это классика: «ping работает, curl к API работает, но выгрузка зависает» или «TLS handshake висит» (сертификат большой). Проверка:

```bash
ping -M do -s 1472 10.0.0.5     # 1472 + 28 = 1500, запрет фрагментации; уменьшать до прохождения
tracepath 10.0.0.5              # покажет pmtu по пути
```

Решения: разрешить ICMP type 3 code 4 на фаерволах, MSS clamping (`iptables ... --clamp-mss-to-pmtu`), выровнять MTU, `net.ipv4.tcp_mtu_probing = 1`.

## 10. DNS

Перед первым соединением клиент разрешает имя в IP. Обычно это кэшируется, но:

- **JVM** кэширует успешные ответы на 30 с (без SecurityManager), отрицательные — 10 с (`networkaddress.cache.ttl`, `networkaddress.cache.negative.ttl`). В старых конфигурациях бывает «навсегда» → после переезда сервиса JVM ходит по старому IP.
- **Go** — свой резолвер или cgo-резолвер; кэша в стандартной библиотеке нет — каждое новое соединение делает запрос DNS (поэтому важны пулы соединений).
- **Python** — `getaddrinfo` через libc, кэша нет.
- **Kubernetes:** `ndots:5` в `/etc/resolv.conf` пода. Имя `api.example.com` (2 точки < 5) сначала пробуется с суффиксами `.ns.svc.cluster.local`, `.svc.cluster.local`, `.cluster.local`... → 4–5 лишних запросов (×2 для A и AAAA) на каждое разрешение. Под нагрузкой CoreDNS становится узким местом, а conntrack для UDP DNS — тоже (известная гонка с потерей пакетов DNS и задержками 5 с). Решения: FQDN с точкой в конце (`api.example.com.`), снизить `ndots`, NodeLocal DNSCache.

**Симптом DNS-проблем:** латентность новых соединений с хвостом ровно ~5 с (таймаут резолвера по умолчанию) или 2,5/10 с; ошибки `UnknownHostException` / `no such host` под нагрузкой.

## 11. Балансировщики L4 и L7

| | L4 (транспортный) | L7 (прикладной) |
|---|---|---|
| Что видит | IP, порты, TCP/UDP | HTTP: метод, URL, заголовки, cookie; gRPC-методы |
| Примеры | LVS/IPVS, kube-proxy, HAProxy в mode tcp, облачный NLB | nginx, HAProxy mode http, Envoy, Traefik, Ingress, API Gateway |
| Как работает | пересылает пакеты/соединение целиком на бэкенд | **завершает** TCP и TLS клиента, открывает свои соединения к бэкендам |
| Балансирует | **соединения** | **запросы** |
| Стоимость | минимальная | разбор HTTP, TLS, буферизация — CPU и latency (обычно 0,1–1 мс) |
| Возможности | — | маршрутизация по пути/заголовку, ретраи, таймауты, rate limit, кэш, аутентификация |

**Ловушка L4 + долгоживущие соединения:** L4-балансировщик распределяет **соединения**, а не запросы. HTTP/2, gRPC, пулы БД держат несколько долгоживущих соединений — и вся нагрузка клиента может уйти на один-два бэкенда. На НТ это выглядит как «у нас 6 подов, но 2 загружены на 90 %, а 4 простаивают». Решения: L7-балансировка (Envoy, service mesh), клиентская балансировка (gRPC client-side LB), периодическое пересоздание соединений (`max-connection-age`).

**Алгоритмы:** round robin, weighted, least connections, least request (лучше при разной сложности запросов), consistent hashing (липкость к бэкенду для кэшей), random of two (P2C).

**Таймауты по цепочке** должны уменьшаться от клиента к глубине: клиент 10 с → gateway 9 с → сервис 8 с → БД `statement_timeout` 5 с. Иначе внешний компонент сдаётся первым, а работа внутри продолжается впустую.

**Idle timeout балансировщика** (часто 60 с) меньше keep-alive timeout бэкенда → гонка: бэкенд закрывает соединение ровно в момент, когда балансировщик отправил в него запрос → редкие 502. Правило: keep-alive timeout сервера **больше**, чем idle timeout балансировщика перед ним.

## 12. NAT и conntrack

**conntrack** — подсистема ядра (netfilter), которая отслеживает каждое соединение (и даже UDP-«потоки»), чтобы работали stateful-фаервол (`-m state ESTABLISHED`) и NAT (подмена адресов). Используется: iptables с правилами состояния, Docker, Kubernetes (kube-proxy в режиме iptables/ipvs, Service = DNAT), NAT-шлюзы.

```bash
conntrack -S                             # статистика: insert_failed, drop, early_drop
conntrack -C                             # сколько записей
sysctl net.netfilter.nf_conntrack_max    # лимит
sysctl net.netfilter.nf_conntrack_tcp_timeout_established   # 432000 с = 5 суток!
sysctl net.netfilter.nf_conntrack_tcp_timeout_time_wait     # 120 с
```

**Проблемы под нагрузкой:**

1. **Таблица переполнена** → новые соединения **молча отбрасываются**: `nf_conntrack: table full, dropping packet` в `dmesg`. Для клиента — таймауты подключения (а не ошибка). Метрика: `node_nf_conntrack_entries / node_nf_conntrack_entries_limit`. Каждая запись ~300 байт; 1 млн записей ≈ 300 МБ.
2. **Много коротких соединений** — каждое занимает запись ещё 120 с в TIME_WAIT conntrack.
3. **Гонки при одновременном создании записей** (`insert_failed`) — известная проблема UDP DNS в Kubernetes.
4. **NAT и порты:** SNAT (например, исходящий трафик всех подов ноды через IP ноды или облачный NAT-шлюз) ограничен ~64 тыс. портов **на каждую пару (IP NAT, IP:порт назначения)**. Множество подов, бьющих в один внешний endpoint, исчерпывают порты NAT → ошибки соединения, которые не видны ни на клиенте, ни на сервере.

**Idle timeout на NAT/фаерволах:** запись удаляется после периода простоя (облачные NAT — 350 с и меньше, корпоративные фаерволы — часто 30–60 мин). Соединение в пуле, простоявшее дольше, становится «мёртвым» без RST. Защита: TCP keepalive < idle timeout, `max-lifetime` пулов, keepalive на уровне протокола ([[05 PostgreSQL]], раздел 21.4).

## 13. Фаерволы

### 13.1 Виды

| Вид | Где | Особенности |
|-----|-----|-------------|
| Хостовый: iptables / nftables / firewalld | на сервере | правила в ядре; stateful через conntrack |
| Kubernetes NetworkPolicy | реализует CNI (Calico, Cilium) | iptables/eBPF на нодах; по умолчанию всё разрешено, пока нет политики |
| Сетевые (аппаратные/NGFW) | между сегментами, ЦОДами | stateful, idle timeout, иногда DPI/инспекция TLS — заметная latency |
| Облачные security groups | виртуальная сеть | stateful, могут иметь лимиты отслеживаемых соединений |
| WAF | L7 перед веб-приложениями | разбор HTTP, правила по содержимому — CPU и latency |

### 13.2 DROP vs REJECT — как отличить по симптомам

| Действие | Что получает клиент | Как выглядит для приложения |
|----------|---------------------|-----------------------------|
| `ACCEPT` | соединение | работает |
| `REJECT` (`--reject-with tcp-reset` / ICMP) | RST или ICMP unreachable сразу | быстрый `connection refused` / `no route to host` |
| `DROP` | **ничего** | долгий `connect timeout`, ретраи SYN (1, 3, 7 с...), состояние `SYN_SENT` |

**Быстрая диагностика:**

```bash
nc -vz -w 3 10.0.0.5 5432           # открыт ли порт
# «succeeded»            → путь открыт
# «Connection refused»   → хост доступен, порт закрыт / REJECT
# timeout                → DROP где-то по пути или хост недоступен
curl -v --connect-timeout 3 https://api:443/health
traceroute -T -p 5432 10.0.0.5      # TCP-traceroute до конкретного порта
tcpdump -ni any host 10.0.0.5 and port 5432    # уходят SYN без ответа?
```

### 13.3 Влияние фаерволов на производительность

1. **Линейные правила iptables.** Пакет проходит цепочку правил по порядку. 10 000 правил (у kube-proxy в режиме iptables — по нескольку правил на каждый Service и endpoint) = заметный CPU на **каждый** новый пакет/соединение и медленное обновление правил. Решения: ipset, nftables (наборы, словари), kube-proxy в режиме IPVS или nftables, eBPF (Cilium).
2. **conntrack** — лимиты и таймауты (раздел 12).
3. **Stateful-фаервол + асимметричная маршрутизация** — ответ идёт другим путём, фаервол не видел SYN и отбрасывает пакеты как «INVALID».
4. **Idle timeout** — обрывы долгоживущих соединений пулов.
5. **Инспекция TLS/DPI** на NGFW — добавляет миллисекунды и может быть узким местом по пропускной способности (лицензионные лимиты на Гбит/с у межсетевых экранов!).
6. **Rate limiting / защита от DDoS** на периметре — нагрузочный тест с одного IP генератора может быть принят за атаку → ограничение скорости или блокировка. **Перед НТ согласовывать IP генераторов с сетевой безопасностью.**
7. **ICMP запрещён целиком** → PMTU black hole (раздел 9).

### 13.4 Как проверить, что тормозит фаервол

- latency между хостами в одном сегменте нормальная, а через фаервол — +1–5 мс → `mtr`/`hping3` до и после фаервола;
- iperf3 через фаервол даёт меньше канала → лимит устройства или его лицензии;
- `conntrack -S` с ростом `drop`/`insert_failed`;
- `iptables -L -v -n -x` — счётчики пакетов по правилам: какое правило срабатывает на трафик;
- `nft monitor trace` / `iptables -t raw -j TRACE` — трассировка пути пакета по правилам.

## 14. Связки метрик: как одно рождает другое

### Связка A: резкий рост новых соединений → backlog → ошибки

1. Спайк новых подключений (рестарт клиентов, нет пулов, reconnect-цикл).
2. Растут `SYN_RECV` и SYN queue.
3. Приложение медленно делает `accept()` → accept queue переполнена.
4. Клиенты получают таймауты/сбросы.
5. В ошибках TCP растут `ListenDrops`, `ListenOverflows`, `TCPSynRetrans`, RST.

На графиках: число соединений растёт, backlog растёт, ошибки TCP растут, latency клиента растёт (с характерными ступенями ~1 с и ~3 с).

### Связка B: короткие соединения → TIME_WAIT → порты → деградация

1. Клиенты не используют keep-alive/пулы.
2. Соединения закрываются пачками.
3. TIME_WAIT растёт до десятков тысяч.
4. На клиенте заканчиваются эфемерные порты, на NAT — порты трансляции, conntrack заполняется.
5. `connect` начинает тормозить или падает: `Cannot assign requested address`.

На графиках: TIME_WAIT высокий и стабильный, SYN_SENT подрастает, CPU system вырос (handshake и TLS на каждый запрос).

### Связка C: приложение не закрывает сокеты → CLOSE_WAIT → FD

1. Удалённая сторона закрывает соединение (FIN).
2. У нас — CLOSE_WAIT.
3. Приложение забыло `close()`.
4. FD копятся.
5. `Too many open files`, сервер перестаёт принимать соединения.

На графиках: CLOSE_WAIT растёт монотонно, `process_open_fds` растёт, число ESTABLISHED может выглядеть нормально.

### Связка D: UDP drops → «непонятные» потери данных

1. Поток UDP растёт.
2. Приложение не успевает читать.
3. Ядро отбрасывает датаграммы (`RcvbufErrors`).
4. «Пропали метрики/логи/ивенты».

На графиках: UDP In высокий, UDP errors растут, CPU softirq растёт.

### Связка E: ретрансмиссии → latency → очереди

1. Сеть или получатель не успевает.
2. Потери пакетов.
3. Ретрансмиссии растут, RTO срабатывают (минимум 200 мс в Linux!).
4. Latency растёт, throughput одного соединения падает.
5. По закону Литтла растёт число одновременных запросов → пулы и очереди забиваются → ещё хуже.

На графиках: доля ретрансмиссий > 0,1 %, хвосты latency кратны 200 мс, throughput может даже падать при росте нагрузки.

### Связка F: получатель не читает → zero window → отправитель стоит

1. Приложение-получатель на паузе (GC, CPU, блокировка) или медленно обрабатывает.
2. Буфер приёма полон → объявляется нулевое окно.
3. Отправитель останавливается, его send buffer заполняется, `write()` блокируется.
4. Задержка распространяется вверх по цепочке.

На графиках: `TCPToZeroWindowAdv` у получателя, большой `Recv-Q` у получателя и `Send-Q` у отправителя в `ss`.

## 15. Поиск сетевого узкого места — методика

```
Шаг 1. Где тратится время запроса?
  Трейс (OpenTelemetry): span клиента vs span сервера.
  Время клиента − время сервера = сеть + очереди + пулы + сериализация.
  Если разница большая — проблема между сервисами, а не в сервисе.

Шаг 2. Установка соединения или передача данных?
  curl -w для HTTP:
    curl -o /dev/null -s -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://api/health
  dns большой        → DNS (раздел 10)
  connect большой    → сеть/фаервол/backlog (разделы 4, 7, 13)
  tls большой        → TLS handshake, нет переиспользования соединений, CPU
  ttfb − tls большой → сервер долго думает (не сеть)
  total − ttfb большой → передача тела: пропускная способность, размер ответа

Шаг 3. Хватает ли канала?
  Трафик интерфейса (бит/с и pps) против скорости линка/лимита облака: > 70–80 % → насыщение
  iperf3 между хостами — реальная пропускная способность пути (в окно без нагрузки!)

Шаг 4. Есть ли потери?
  Доля ретрансмиссий, drops на интерфейсах, softnet dropped, conntrack drops
  mtr — на каком хопе начинаются потери (ICMP rate limit на маршрутизаторах даёт ложные потери
        на промежуточных хопах — смотреть, сохраняются ли потери до конечного узла)

Шаг 5. Очереди и окна
  ss -tmi: rtt, cwnd, retrans, Recv-Q/Send-Q, zero window → кто не успевает (раздел 3.2)

Шаг 6. Соединения
  ss -s: TIME_WAIT, CLOSE_WAIT, SYN_SENT/SYN_RECV
  ListenOverflows/ListenDrops, порты, conntrack, FD

Шаг 7. Захват трафика, если всё ещё непонятно
  tcpdump -i any -s 128 -w /tmp/cap.pcap host X and port Y → Wireshark:
  ретрансмиссии, дубли ACK, zero window, RST, время между запросом и ответом
```

**Как отличить «тормозит сеть» от «тормозит сервер»:**

| Признак | Сеть | Сервер/получатель |
|---------|------|-------------------|
| ретрансмиссии | растут | нет |
| RTT (`ss -ti`) | растёт | стабилен |
| `Recv-Q` у получателя | пустой | большой |
| zero window | нет | есть |
| время в span сервера | нормальное | большое |
| ping/mtr | потери, рост задержки | нормально |

## 16. Инструменты

| Инструмент | Для чего |
|------------|----------|
| `ss -s`, `ss -tanp`, `ss -ltn`, `ss -tmi` | сокеты, состояния, очереди, буферы, RTT, cwnd, ретрансмиссии по соединению |
| `nstat -az`, `netstat -s` | счётчики TCP/UDP/IP |
| `sar -n DEV,TCP,ETCP,SOCK 1` | трафик, новые соединения/с, ретрансмиссии/с |

| `ethtool eth0` | скорость, дуплекс; `ethtool -g` — ring buffers; `-l` — очереди; `-k` — offload |
| `ping`, `mtr`, `traceroute -T`, `tracepath` | задержка, потери по хопам, путь, PMTU |
| `iperf3 -c host -P 4 -t 30` | пропускная способность пути (TCP/UDP, несколько потоков) |
| `nc -vz host port`, `curl -v -w ...` | доступность порта, фазы HTTP-запроса |
| `tcpdump`, Wireshark | захват и разбор пакетов |
| `dig`, `nslookup`, `resolvectl` | DNS |
| `conntrack -S/-L/-C` | состояние conntrack |
| `iptables -L -v -n`, `nft list ruleset` | правила фаервола и их счётчики |

**netem для НТ** — отличный способ проверить поведение системы при деградации сети: добавить 50 мс задержки между сервисом и БД и посмотреть, как изменятся пулы (закон Литтла!) и таймауты.

## 17. Шпаргалка: симптом → причина → решение

| Симптом | Причина | Решение |
|---------|---------|---------|
| `connection refused` быстро | порт не слушается, REJECT | сервис, порт, правило фаервола |
| connect timeout, `SYN_SENT` | DROP на фаерволе / маршрут / переполнение backlog | `nc`, tcpdump, правила, ListenDrops на сервере |
| Ступени latency ~1 с / ~3 с | повторы SYN | backlog, accept, потери, conntrack |
| Хвост latency ровно ~40 мс | Nagle + delayed ACK | TCP_NODELAY, один write на сообщение |
| Хвост latency кратно 200 мс | RTO после потерь | потери, ретрансмиссии |
| Хвост ~5 с на новых соединениях | DNS таймаут | ndots, NodeLocal DNS, кэш, conntrack DNS |
| `Cannot assign requested address` | исчерпаны эфемерные порты | keep-alive, пулы, port range, tw_reuse |
| Тысячи TIME_WAIT | короткие соединения | keep-alive, пулы, HTTP/2 |
| Растёт CLOSE_WAIT | утечка сокетов в коде | закрывать ответы/соединения |
| `Connection reset by peer` после простоя | NAT/фаервол удалил idle-соединение | TCP keepalive, max-lifetime пула |
| Редкие 502 на балансировщике | keep-alive бэкенда < idle timeout LB | увеличить keep-alive timeout бэкенда |
| Малые запросы ок, большие ответы висят | PMTU black hole | ICMP frag-needed, MSS clamping, MTU |
| Один поток медленный на длинном канале | окно/буфер < BDP | tcp_rmem/wmem, параллельные потоки, BBR |
| Нагрузка ушла на 2 пода из 6 | L4-балансировка долгоживущих соединений | L7/клиентская балансировка, max-connection-age |
| `nf_conntrack: table full` | переполнение conntrack | nf_conntrack_max, таймауты, меньше коротких соединений |
| UDP-метрики пропадают | RcvbufErrors | буферы, скорость чтения |
| softirq 100 % на одном ядре | прерывания NIC на одно ядро | RSS/RPS, irqbalance |
| Ретрансмиссии > 1 % | потери в сети/на перегруженном оборудовании | mtr, drops на интерфейсах, QoS |
