## 1. Тест-планы и тест-стратегия

### Что такое тест-план

**Тест-план (Test Plan)** — документ, описывающий **что**, **как**, **когда**, **кто** и **зачем** тестирует. Составляется под конкретный релиз или спринт.

***

### Структура тест-плана (IEEE 829)

| #  | Раздел                | Содержание                                               |
| -- | --------------------- | -------------------------------------------------------- |
| 1  | Идентификатор         | Уникальное имя/номер документа                           |
| 2  | Введение              | Краткое описание продукта и целей тестирования           |
| 3  | Объект тестирования   | Что именно тестируем (модули, фичи, версия)              |
| 4  | IN SCOPE              | Функции, **подлежащие** тестированию                     |
| 5  | OUT OF SCOPE          | Функции, **не** подлежащие тестированию (с обоснованием) |
| 6  | Подход                | Виды тестирования, ручное/автоматическое                 |
| 7  | Критерии входа/выхода | Entry/Exit Criteria                                      |
| 8  | Критерии приостановки | Suspension/Resumption Criteria                           |
| 9  | Тестовые артефакты    | Тест-кейсы, отчёты, баги                                 |
| 10 | Задачи                | Breakdown по задачам и исполнителям                      |
| 11 | Окружение             | Стенды, ОС, браузеры, тестовые данные                    |
| 12 | Ответственности       | Матрица RACI                                             |
| 13 | Расписание            | Сроки по этапам                                          |
| 14 | Риски и митигация     | Что может пойти не так и как реагируем                   |

***

### Entry / Exit Criteria

**Entry Criteria (критерии входа):**

* Тестовое окружение развёрнуто и доступно
* Тестовая документация прошла ревью
* Билд стабилен (smoke-тесты прошли > 95%)
* Требования утверждены и не меняются

**Exit Criteria (критерии выхода):**

* Все тест-кейсы выполнены
* Покрытие требований >= 95%
* Нет открытых Critical/Blocker дефектов
* Регрессия пройдена
* Тест-отчёт согласован

> **Совет Senior QA:** если критерии выхода не выполнены, а дедлайн горит — фиксируем это в **Release Risk Report**, передаём PM и Stakeholders, получаем письменное согласие на выпуск с известными рисками. Никогда не выпускаем молча.

***

### Тест-план vs Тест-стратегия

|              | Тест-стратегия            | Тест-план                     |
| ------------ | ------------------------- | ----------------------------- |
| Уровень      | Организация / проект      | Конкретный релиз / Sprint     |
| Автор        | QA Lead / Test Manager    | QA Lead или Senior QA         |
| Горизонт     | Долгосрочный              | Краткосрочный                 |
| Содержание   | «Как мы тестируем вообще» | «Что тестируем в этом релизе» |
| Изменяемость | Меняется редко            | Под каждый релиз              |

***

### Матрица RACI в тестировании

RACI — инструмент распределения ответственностей:

|         | R (Responsible)              | A (Accountable)     | C (Consulted)            | I (Informed)          |
| ------- | ---------------------------- | ------------------- | ------------------------ | --------------------- |
| Кто это | Исполнитель                  | Владелец результата | Эксперт/советник         | Получатель информации |
| Пример  | QA Engineer пишет тест-кейсы | QA Lead подписывает | Архитектор консультирует | PM уведомляется       |

**Пример RACI для тест-плана:**

```
Задача                  | QA Lead | QA Engineer | Dev | PM
------------------------|---------|-------------|-----|----
Написать тест-план      |   A/R   |      C      |  C  |  I
Написать тест-кейсы     |    A    |      R      |  C  |  I
Выполнить тестирование  |    A    |      R      |  I  |  I
Создать баг-репорт      |    A    |      R      |  I  |  I
Финальный отчёт         |   R/A   |      C      |  I  |  I

```

## 2. Жизненный цикл ПО — SDLC

### Этапы SDLC и роль QA

| Этап                  | Описание                | Роль QA                                |
| --------------------- | ----------------------- | -------------------------------------- |
| **Планирование**      | Scope, бюджет, сроки    | Оценка трудозатрат на тестирование     |
| **Анализ требований** | BRD, SRS, User Stories  | Ревью требований, поиск противоречий   |
| **Проектирование**    | Архитектура, API, UI/UX | Ревью дизайна, тест-стратегия          |
| **Разработка**        | Написание кода          | Написание тест-кейсов, тестовые данные |
| **Тестирование**      | Проверка функционала    | Основная работа QA                     |
| **Развёртывание**     | Выпуск в production     | Smoke после деплоя                     |
| **Сопровождение**     | Патчи, новые фичи       | Регрессия на каждое изменение          |

***

### Модели SDLC

#### Waterfall

Последовательные этапы. Нельзя вернуться назад.

* ✅ Чёткая документация, понятный процесс
* ❌ Баги находятся поздно, дорого менять требования

#### V-Model

Каждому этапу разработки соответствует этап тестирования.

```
Требования  ←————→  Приёмочное тестирование (UAT)
  Дизайн    ←————→  Системное тестирование
  Модули    ←————→  Интеграционное тестирование
    Код     ←————→  Unit-тестирование

```

* ✅ Тестирование планируется с самого начала
* ❌ Негибкий, дорогой в изменениях

#### Agile / Scrum

Итерации (Sprints) по 1–4 недели. Постоянная обратная связь.

* ✅ Гибкость, быстрое обнаружение проблем
* ❌ Требует зрелой команды и дисциплины

#### Kanban

Непрерывный поток задач. Нет фиксированных итераций.

* ✅ Хорошо для support, hotfix, операционных команд
* ✅ Визуализация узких мест через метрики потока

#### SAFe (Scaled Agile Framework)

Масштабирование Agile на несколько команд и продуктов.

* PI Planning (Program Increment) — совместное планирование на 8–12 недель
* QA роль: участие в System Demo, IP Sprint (Innovation & Planning)

***

### Shift Left и Shift Right Testing

**Shift Left** — тестирование начинается как можно раньше:

* QA участвует в ревью требований с самого начала
* Acceptance Criteria пишутся совместно с Dev и BA
* Правило Бёма: цена исправления бага растёт экспоненциально

```
Этап:        Требования  Дизайн  Разработка  Тестирование  Прод
Стоимость:       x1        x5       x10          x50       x100+

```

**Shift Right** — тестирование в production:

* A/B-тестирование на реальных пользователях
* Feature Flags — постепенное раскрытие фичей
* Canary Releases — выкатка на 1–5% пользователей
* Chaos Engineering — намеренное введение сбоев (Netflix Chaos Monkey)
* Observability — мониторинг + логи + трейсинг в проде

> **Senior QA понимает:** хорошее тестирование — это не только «до деплоя», но и наблюдение за поведением системы в production.

## 3. Базовая теория тестирования

### Виды тестирования

#### По знанию системы

| Вид           | Суть                                            |
| ------------- | ----------------------------------------------- |
| **Black Box** | Тестируем без знания внутренней реализации      |
| **White Box** | Знаем код, тестируем конкретные пути выполнения |
| **Grey Box**  | Частичное знание (API, схема БД доступны)       |

#### По целям

| Вид                  | Описание                                             |
| -------------------- | ---------------------------------------------------- |
| **Функциональное**   | Проверяем «что делает система»                       |
| **Нефункциональное** | Производительность, безопасность, надёжность         |
| **Регрессионное**    | Убеждаемся, что старое не сломалось                  |
| **Smoke**            | «Жив ли вообще» продукт после нового билда           |
| **Sanity**           | Быстрая проверка конкретного исправления             |
| **Exploratory**      | Исследовательское без заранее написанных тест-кейсов |
| **Acceptance (UAT)** | Проверка соответствия бизнес-требованиям             |
| **Интеграционное**   | Проверка взаимодействия между модулями/сервисами     |
| **Системное**        | Проверка системы в целом                             |
| **End-to-End (E2E)** | Полный пользовательский сценарий от начала до конца  |

> **Smoke vs Sanity:**

> &#x20;Smoke — широкий поверхностный прогон **всего** приложения.

> &#x20;Sanity — узкая глубокая проверка **конкретной** фичи или фикса.

#### По уровням (Test Levels / Пирамида тестирования)

```
          /\
         /  \
        / E2E\          <- медленно, дорого, мало
       /------\
      /  Integr \       <- умеренно
     /------------\
    /   Unit Tests  \   <- быстро, дёшево, много
   /________________\

```

* **Unit** — тестирование отдельных функций/методов (пишут разработчики)
* **Integration** — тестирование взаимодействия компонентов
* **System / E2E** — полный пользовательский сценарий

> **Антипаттерн — Ice Cream Cone:**

> &#x20;Много E2E, мало unit-тестов. Дорого, медленно, нестабильно. QA Lead должен выстраивать правильную пирамиду.

***

### 7 принципов тестирования (ISTQB)

1. **Тестирование показывает наличие дефектов, но не их отсутствие**
2. **Исчерпывающее тестирование невозможно** → риск-ориентированный подход
3. **Раннее тестирование** → Shift Left, дешевле исправлять
4. **Скопление дефектов** → 80% багов в 20% модулей (правило Парето)
5. **Парадокс пестицида** → одни и те же тесты перестают находить новые баги
6. **Тестирование зависит от контекста** → банк ≠ игра ≠ медицинская система
7. **Заблуждение об отсутствии ошибок** → продукт без багов, но ненужный = провал

***

### Верификация vs Валидация

|        | Верификация (Verification)    | Валидация (Validation)     |
| ------ | ----------------------------- | -------------------------- |
| Вопрос | «Правильно ли мы строим?»     | «Правильное ли мы строим?» |
| Суть   | Соответствие спецификации     | Решает задачи пользователя |
| Метод  | Статическое: ревью, инспекции | Динамическое: запуск, UAT  |
| Кто    | QA, BA, разработчик           | QA, пользователи, BA       |

## 4. Техники тест-дизайна

### Классы эквивалентности (Equivalence Partitioning)

Делим входные данные на классы — внутри каждого система ведёт себя одинаково. Тестируем по одному представителю от каждого класса.

**Пример: поле «Возраст» (0–150):**

* Класс 1 (невалидный, < 0): `-1`
* Класс 2 (валидный): `25`
* Класс 3 (невалидный, > 150): `200`
* Класс 4 (невалидный, не число): `"abc"`

***

### Граничные значения (Boundary Value Analysis — BVA)

Тестируем значения на границах диапазона: min-1, min, min+1, max-1, max, max+1.

**Пример: поле «Скидка» (0–100%):**

```
+-----------+------------+--------------------------+
| Значение  |  Ожидание  |       Описание           |
+-----------+------------+--------------------------+
|    -1     |   Ошибка   | Ниже минимума            |
|     0     |   Успех    | Минимальное значение     |
|     1     |   Успех    | Минимум + 1              |
|    50     |   Успех    | Середина диапазона       |
|    99     |   Успех    | Максимум - 1             |
|   100     |   Успех    | Максимальное значение    |
|   101     |   Ошибка   | Выше максимума           |
|  "abc"    |   Ошибка   | Нечисловой ввод          |
|  пусто    |   Ошибка   | Пустое поле              |
+-----------+------------+--------------------------+

```

***

### Таблица решений (Decision Table)

Для систем с несколькими условиями, влияющими на результат.

**Пример: скидка на заказ**

```
Условия                   | C1  | C2  | C3  | C4
--------------------------|-----|-----|-----|----
Клиент Premium            |  Да |  Да | Нет | Нет
Сумма > 5000              |  Да | Нет |  Да | Нет
--------------------------|-----|-----|-----|----
Действия                  |     |     |     |
Скидка 20%                |  +  |  -  |  -  |  -
Скидка 10%                |  -  |  +  |  +  |  -
Скидка 0%                 |  -  |  -  |  -  |  +
Бесплатная доставка       |  +  |  +  |  -  |  -

```

***

### Попарное тестирование (Pairwise / Allpairs)

Тестируем каждую пару параметров хотя бы один раз. Резко сокращает количество тест-кейсов при большом числе комбинаций.

**Пример:** 3 параметра (ОС, Браузер, Язык) × 3 значения каждый = 27 комбинаций полностью, но Pairwise даёт \~9 тест-кейсов при том же покрытии пар.

***

### Тестирование состояний и переходов (State Transition Testing)

Моделируем систему как конечный автомат.

**Пример: аккаунт пользователя**

```
[Новый] --верификация email--> [Активный]
[Активный] --3 неверных пароля--> [Заблокирован]
[Заблокирован] --сброс пароля--> [Активный]
[Активный] --удаление--> [Удалён]

```

Покрытие переходов (transition coverage) — тест-кейсы для каждого перехода.

&#x20;Покрытие состояний (state coverage) — тест-кейсы для каждого состояния.

***

### Use Case Testing

Тестирование на основе сценариев использования. Проверяем:

* **Основной поток (Happy Path)** — всё идёт как ожидается
* **Альтернативные потоки** — допустимые отклонения
* **Исключительные потоки (Unhappy Path)** — ошибки, граничные случаи

***

### Исследовательское тестирование (Exploratory Testing)

Тестирование без заранее написанных тест-кейсов. Тестировщик одновременно проектирует и выполняет тесты.

**Техники структуризации Exploratory:**

* **Session-Based Testing** — тест-сессии фиксированной длины (60–90 мин) с конкретной целью
* **Charter (Устав сессии):** «Исследовать модуль оплаты с акцентом на граничные случаи суммы»
* **Мнемоники:** SFDIPOT (Structure, Function, Data, Interfaces, Platform, Operations, Time)

> **Senior QA** применяет Exploratory там, где сложно покрыть всё тест-кейсами: новые фичи, сложная бизнес-логика, поиск неочевидных багов.

### Тестирование API — Postman

**Что проверяем в API-ответе:**

* Статус-код (200, 201, 204, 400, 401, 403, 404, 422, 500)
* Тело ответа: структура, типы данных, значения полей
* Заголовки: Content-Type, Authorization, Cache-Control, CORS
* Время ответа (SLA требования)
* JSON Schema validation

**Пример тестов в Postman для POST /api/login:**

```
pm.test("Status 200", () => {
  pm.response.to.have.status(200);
});

pm.test("Получен access_token", () => {
  const json = pm.response.json();
  pm.expect(json).to.have.property("access_token");
  pm.expect(json.access_token).to.be.a("string").and.not.be.empty;
  pm.environment.set("auth_token", json.access_token);
});

pm.test("Время ответа < 500ms", () => {
  pm.expect(pm.response.responseTime).to.be.below(500);
});

pm.test("Content-Type JSON", () => {
  pm.response.to.have.header("Content-Type", /application\/json/);
});

// Негативный сценарий — отдельный запрос:
// POST /api/login + неверный пароль -> 401 Unauthorized
// POST /api/login + пустой email -> 422 Unprocessable Entity

```

### Работа с базой данных

```
-- Проверить, что запись создалась
SELECT * FROM users WHERE email = 'test@example.com';

-- Проверить количество
SELECT COUNT(*) FROM orders WHERE status = 'completed';

-- Проверить связанные данные (JOIN)
SELECT u.name, o.total
```

### Жизненный цикл дефекта

```
New -> Assigned -> In Progress -> Fixed -> Retest -> Closed
                       |                      |
                       v                      v
                   Rejected               Reopened
                   Duplicate
                   Won't Fix
                   Deferred

```

| Статус               | Описание                                  |
| -------------------- | ----------------------------------------- |
| **New / Open**       | Баг зарегистрирован QA                    |
| **Assigned**         | Назначен разработчику                     |
| **In Progress**      | Разработчик работает над исправлением     |
| **Fixed / Resolved** | Разработчик утверждает, что исправил      |
| **Retest**           | QA проверяет исправление                  |
| **Closed**           | Баг подтверждён исправленным              |
| **Rejected**         | Не является дефектом / не воспроизводится |
| **Duplicate**        | Уже зарегистрирован                       |
| **Deferred**         | Отложен на следующий релиз                |
| **Won't Fix**        | Осознанное решение не исправлять          |
| **Reopened**         | Исправление не помогло                    |

### Priority vs Severity

**Severity** — техническое влияние на **функциональность**:

| Уровень      | Пример                                       |
| ------------ | -------------------------------------------- |
| **Blocker**  | Приложение не запускается, белый экран       |
| **Critical** | Нельзя оформить заказ, потеря данных         |
| **Major**    | Основная функция сломана, есть обходной путь |
| **Minor**    | Некритичная функция сломана                  |
| **Trivial**  | Опечатка, косметика                          |

**Priority** — бизнес-срочность исправления:

| Уровень | Описание                     |
| ------- | ---------------------------- |
| **P1**  | Немедленно, блокирует работу |
| **P2**  | В текущем спринте            |
| **P3**  | В следующем спринте          |
| **P4**  | Когда-нибудь                 |

#### Важно: они могут не совпадать!

* **High Severity / Low Priority:** Ошибка расчёта для 0,001% пользователей
* **Low Severity / High Priority:** Опечатка в названии компании на главной

**Triage-встреча (Bug Triage):**

* Регулярная (обычно 1–2 раза в неделю) встреча QA + Dev + PM

## 7. Kanban: метрики, WIP, Flow — уровень Lead

### Что такое Kanban

**Kanban** — метод управления потоком работы, основанный на визуализации, ограничении незавершённой работы (WIP) и непрерывном улучшении.

Kanban не диктует роли и итерации. Это **система вытягивания (pull system):** новая задача берётся в работу только когда освобождается «слот» (WIP limit позволяет).

***

### Канбан-доска

Базовая структура:

```
+----------+----------+----------+----------+----------+
|  Backlog |  To Do   |  In      |  Review  |   Done   |
|          | (WIP: 5) |  Progress|  (WIP: 3)|          |
|          |          | (WIP: 3) |          |          |
+----------+----------+----------+----------+----------+
|  Story A |  Story B |  Story C |  Story D |  Story E |
|  Story F |  Story G |  Story H |          |  Story I |
|  ...     |          |          |          |  ...     |
+----------+----------+----------+----------+----------+

```

**Типичные колонки для QA-команды:**

```
Backlog -> Ready for Dev -> In Dev -> Ready for QA -> In QA -> Review -> Done

```

***

### WIP Limits (Ограничение незавершённой работы)

**WIP (Work In Progress)** — количество задач, находящихся в работе одновременно.

**Зачем ограничивать WIP:**

* Уменьшает переключение контекста
* Обнажает узкие места (bottleneck)
* Ускоряет прохождение задачи через систему
* Снижает стресс команды

**Правило:** если WIP limit достигнут — нельзя брать новую задачу. Нужно сначала завершить текущие или помочь коллеге.

**Пример:**

```
Колонка "In QA" с WIP = 3:

Ситуация 1: В работе 3 задачи -> QA не берёт новую, а помогает
            Dev ускорить прохождение существующих.

Ситуация 2: В работе 1 задача -> QA может взять ещё 2.

```

**Как выбрать WIP limit?** Правило большого пальца: WIP = количество людей в колонке × 1,5.

&#x20;Начинают с завышенного значения и постепенно снижают, наблюдая за метриками.

***

### Ключевые Kanban-метрики

#### 1. Lead Time (Время выполнения)

**Определение:** время от момента, когда задача была **запрошена** (появилась в backlog) до момента, когда она **доставлена** клиенту/заказчику.

```
Lead Time = дата завершения - дата создания задачи

Пример:
  Задача создана: 1 марта
  Задача завершена: 10 марта
  Lead Time = 9 дней

```

**Что показывает:** насколько быстро команда реагирует на запросы бизнеса. Это **метрика для заказчика**.

***

#### 2. Cycle Time (Время цикла)

**Определение:** время от момента, когда команда **начала работать** над задачей (взяла в работу), до момента её завершения.

```
Cycle Time = дата завершения - дата начала работы

Пример:
  Задача взята в работу: 5 марта
  Задача завершена: 10 марта
  Cycle Time = 5 дней

```

**Что показывает:** эффективность самого процесса. Это **внутренняя метрика команды**.

```
|---- Lead Time (9 дней) --------------------|
  |-- Ожидание (4 дня) --|-- Cycle Time (5 д) --|
  1 марта              5 марта              10 марта
  (создана)           (взята в работу)     (завершена)

```

**Разница Lead Time vs Cycle Time:**

* Если Lead Time >> Cycle Time — задачи долго лежат в очереди. Проблема в **приоритизации** или **входящем потоке**.
* Если Cycle Time большой — проблема в **процессе выполнения** (блокеры, зависимости, перегруз).

***

#### 3. Throughput (Пропускная способность)

**Определение:** количество задач, завершённых за единицу времени (день, неделю, спринт).

```
Throughput = количество завершённых задач / период

Пример:
  За неделю завершено 12 задач
  Throughput = 12 задач/неделю

```

**Что показывает:** производительность команды. Используется для прогнозирования: сколько задач команда выполнит за следующие N недель.

**Важно:** Throughput считается по **завершённым** задачам, а не по начатым. «Почти готово» не считается.

***

#### 4. Flow Efficiency (Эффективность потока)

**Определение:** соотношение активного времени работы над задачей к общему Lead Time.

```
Flow Efficiency = Время активной работы / Lead Time × 100%

Пример:
  Lead Time = 10 дней
  Активная работа (Cycle Time) = 2 дня
  Flow Efficiency = 2 / 10 × 100% = 20%

```

**Нормальные значения:** в большинстве команд Flow Efficiency = 15–40%. Значение > 40% — очень хороший результат.

**Что показывает:** сколько времени задача реально «в работе», а не «ждёт». Низкая эффективность → много ожидания и блокеров.

***

#### 5. WIP (Work In Progress)

**Формула Литтла (Little's Law):**

```
Lead Time = WIP / Throughput

или

WIP = Lead Time × Throughput

```

**Пример:**

* Throughput = 10 задач/неделю
* WIP = 20 задач
* Lead Time = 20 / 10 = 2 недели

**Вывод:** чтобы снизить Lead Time вдвое, нужно либо снизить WIP вдвое, либо удвоить Throughput.

> **Закон Литтла** — один из фундаментальных в теории очередей. Любой Kanban Lead должен его понимать и применять.

***

#### Сводная таблица метрик

| Метрика             | Что измеряет                                         | Для кого                    |
| ------------------- | ---------------------------------------------------- | --------------------------- |
| **Lead Time**       | Скорость реакции на запрос (от создания до доставки) | Заказчик, бизнес            |
| **Cycle Time**      | Эффективность процесса (от начала до конца работы)   | Команда                     |
| **Throughput**      | Производительность (задач/неделю)                    | Менеджмент, прогнозирование |
| **Flow Efficiency** | Доля активной работы от Lead Time                    | Команда, улучшение          |
| **WIP**             | Количество задач «в работе» прямо сейчас             | Команда, Kanban Master      |

***

### Cumulative Flow Diagram (CFD)

**CFD** — накопительная диаграмма потока. Показывает количество задач в каждой колонке со временем.

```
Задачи
  ^
40|..........Done (растёт плавно — хорошо)
  |.........
30|........
  |.....In QA (постоянная ширина — нет узкого места)
20|....
  |...In Dev (широкая полоса — bottleneck!)
10|..
  |.
  +-------------------------------------> Время

```

**Что читать на CFD:**

* Горизонтальные полосы расширяются → задачи накапливаются в колонке → **узкое место (bottleneck)**
* Плавный рост Done → стабильный поток, всё хорошо
* Резкий скачок Done → задачи разблокировались после длительного ожидания

***

### Cumulative Flow Diagram для QA

Пример интерпретации CFD в QA-контексте:

```
Ситуация: полоса "In QA" расширяется (много задач накапливается)

Возможные причины:
  1. В QA поступает больше, чем QA успевает обрабатывать
  2. Нехватка QA-ресурса
  3. Тест-окружение нестабильно
  4. Задачи блокируются зависимостями

Действия QA Lead:
  1. Снизить WIP в "In Dev" (меньше задач отправлять в QA)
  2. Подключить дополнительный ресурс
  3. Разобраться с блокерами окружения
  4. Поднять вопрос на ретроспективе

```

***

### Monte Carlo Forecasting

Продвинутый метод прогнозирования на основе исторических данных Throughput.

**Идея:** вместо детального планирования («когда закончим 50 задач?») запускаем тысячи симуляций на основе исторического Throughput и получаем вероятностный прогноз.

```
Пример:
  Исторический Throughput: 8–15 задач/неделю
  Осталось задач: 40

  Monte Carlo результат:
    50% вероятность — завершим через 3 недели
    85% вероятность — завершим через 5 недель
    95% вероятность — завершим через 7 недель

```

> **На практике:** используйте Throughput + Monte Carlo вместо story points для прогнозирования. Это более честно и основано на реальных данных.

***

### Kanban-практики для QA Lead

**1. Service Level Expectations (SLE)**

&#x20;Явное соглашение о Cycle Time для разных типов задач:

* Критический баг: <= 1 день
* Стандартная история: <= 5 дней
* Эпик: <= 20 дней

**2. Classes of Service (Классы сервиса)**

&#x20;Категории задач с разным приоритетом обработки:

| Класс          | Тип задач                                   | Приоритет                |
| -------------- | ------------------------------------------- | ------------------------ |
| **Expedite**   | Production-инциденты, критические баги      | Немедленно, нарушает WIP |
| **Fixed Date** | Задачи с дедлайном (юридические, маркетинг) | Высокий                  |
| **Standard**   | Обычные истории и задачи                    | Обычный                  |
| **Intangible** | Технический долг, улучшения                 | Низкий                   |

**3. Replenishment Meeting (Пополнение очереди)**

&#x20;Регулярная встреча (1–2 раза в неделю): какие задачи добавить в Ready for Work. Отдельно от ежедневного Standup.

**4. Kanban Review Meeting**

&#x20;Обзор метрик: CFD, Lead Time, Throughput. Ищем тренды и аномалии.

### Онбординг нового QA-инженера

```

  - Изучить продукт (как пользователь)

Месяц 3: Полная интеграция
  - Работать наравне с командой

```

### Управление рисками в тестировании

**Risk-Based Testing** — приоритизация тестирования на основе рисков.

**Формула риска:**

```
Риск = Вероятность дефекта × Влияние дефекта

Пример:
  Модуль оплаты: вероятность 3, влияние 5 -> Риск = 15 (высокий)
  Страница "О нас": вероятность 1, влияние 1 -> Риск = 1 (низкий)

```

**Матрица рисков:**

```
Влияние
  5 |  15  |  20  |  25  |
  4 |  12  |  16  |  20  |
  3 |   9  |  12  |  15  |
  2 |   6  |   8  |  10  |
  1 |   3  |   4  |   5  |
    +------+------+------+
         1      2      3   Вероятность

Красная зона (>= 15): тестируем в первую очередь
Жёлтая зона (8-14): тестируем во вторую очередь
Зелёная зона (<8): тестируем при наличии времени

```

### Процессы ретроспективы для QA Lead

**QA Retrospective** (отдельно от общей Sprint Retro) — анализ QA-процесса:

Темы для обсуждения:

1. Что пошло хорошо с точки зрения тестирования?
2. Что можно улучшить (окружение, инструменты, коммуникация)?
3. Какие метрики изменились? Почему?
4. Есть ли системные проблемы, требующие эскалации?

**Root Cause Analysis (RCA)** — для критических дефектов, прорвавшихся в прод:

```
5 Почему (5 Whys):
  Проблема: критический баг в проде

  Почему 1: Не было тест-кейса на этот сценарий
  Почему 2: Требование не было явно описано
  Почему 3: QA не участвовал в Refinement
  Почему 4: Не было процесса ревью требований с QA
  Почему 5: (Root Cause) Процесс Shift Left не внедрён

  Действие: внедрить обязательное участие QA в Refinement

```

## 10. Тест-стратегия на уровне организации

### Компоненты тест-стратегии

**Тест-стратегия** — высокоуровневый документ, описывающий подход к тестированию в масштабах проекта/организации.

Разделы тест-стратегии:

```
1. Цели тестирования
   Что считаем "достаточно протестированным"

2. Объём тестирования
   Какие виды тестирования применяем

3. Инструменты
   TMS, bug-tracker, автоматизация, мониторинг

4. Среды тестирования
   Dev / Stage / UAT / Pre-prod / Prod

5. Управление рисками
   Risk-based подход к приоритизации

6. Подход к автоматизации
   Пирамида тестирования, что автоматизируем

7. Критерии качества
   Метрики, пороговые значения

8. Процессы и роли
   Кто, что, когда делает

9. Reporting
   Кому, что, когда докладываем

```

***

### Тестовые среды (Test Environments)

| Среда                | Назначение                       | Кто использует        |
| -------------------- | -------------------------------- | --------------------- |
| **Dev**              | Локальная разработка             | Разработчики          |
| **Integration / CI** | Автотесты при каждом коммите     | CI/CD пайплайн        |
| **Stage / Staging**  | Ручное тестирование              | QA                    |
| **UAT**              | Приёмочное тестирование          | Заказчик / BA         |
| **Pre-prod**         | Финальная проверка перед деплоем | QA + Ops              |
| **Production**       | Prod monitoring, Canary          | Ops + QA (мониторинг) |

**Проблема "works on my machine":** использование одинаковых конфигов (Infrastructure as Code, Docker) для всех сред.

***

### Подход к автоматизации тестирования

**Что автоматизировать:**

* Регрессионные smoke/sanity сценарии
* Часто повторяемые тест-кейсы
* API-тесты (быстрее и стабильнее UI)
* Data-driven сценарии с множеством входных данных

**Что НЕ автоматизировать:**

* Одноразовые тест-кейсы
* Исследовательское тестирование
* Тест-кейсы с часто меняющимся UI
* То, что дешевле проверить вручную

**ROI автоматизации:**

```
ROI = (Время ручного теста × Количество прогонов - Время создания автотеста)
      / Время создания автотеста × 100%

Правило: автоматизировать выгодно, если тест будет прогоняться > 10 раз

```

***

### Test Debt (Технический долг в тестировании)

Аналог технического долга, но в тестировании:

* Устаревшие тест-кейсы, не отражающие реальное поведение
* Нулевое или низкое покрытие автотестами
* Ручные процессы, которые давно стоит автоматизировать
* Баги, отложенные в «Won't Fix» без реального обоснования

**Управление Test Debt:**

* Вести backlog технического долга QA
* Выделять 10–20% спринта на его погашение
* Регулярно пересматривать релевантность тест-кейсов

***

### Definition of Done (DoD) с точки зрения QA

**DoD** — соглашение команды о том, когда задача считается завершённой.

**Типичный DoD с QA-условиями:**

```
Задача считается Done, если:
  [ ] Код написан и прошёл code review
  [ ] Unit-тесты написаны, покрытие >= 80%
  [ ] Функциональные тест-кейсы выполнены
  [ ] Нет открытых Critical/Major дефектов
  [ ] API задокументировано (Swagger обновлён)
  [ ] Регрессионные тест-кейсы обновлены
  [ ] Smoke-тест в Stage прошёл
  [ ] PM/BA провели демо и приняли функционал

```

## 13. Нагрузочное тестирование: методология (уровень Senior/Lead)

### 13.1 Виды тестов производительности и их цели

| Вид | Профиль нагрузки | Вопрос, на который отвечает |
|-----|-----------------|-----------------------------|
| **Поиск максимальной производительности** (capacity / step test) | ступени: 25 %, 50 %, 75 %, 100 %, 125 %... от целевой, каждая 10–20 мин | при какой нагрузке система перестаёт выдерживать SLA и что упирается первым |
| **Подтверждение (load)** | целевая пиковая нагрузка 1–2 часа | выдерживаем ли SLA на ожидаемом пике |
| **Стабильность (soak / endurance)** | 70–100 % целевой 8–24 часа | утечки памяти/соединений/FD, рост таблиц, деградация со временем, отработка фоновых задач |
| **Стресс** | выше максимума до отказа | как система **отказывает** и **восстанавливается** (graceful degradation, без потери данных) |
| **Spike** | резкий скачок ×3–×10 на минуты | автомасштабирование, очереди, холодные кэши, пулы |
| **Объёмный (volume)** | нормальная нагрузка на большом объёме данных | планы запросов на реальных объёмах, индексы, партиции |
| **Отказоустойчивость** | целевая нагрузка + отказ компонента (убить под, failover БД, отключить зону) | время восстановления, число ошибок, поведение ретраев |
| **Масштабируемость** | одна нагрузка при 1, 2, 4, 8 репликах | линейно ли растёт throughput (закон Амдала / USL) |

### 13.2 Модель нагрузки

1. **Профиль операций** — из прод-логов/метрик: какие операции, в какой пропорции (например, 70 % чтение карточки, 20 % поиск, 8 % создание, 2 % отчёт).
2. **Интенсивность** — RPS на операцию в пиковый час; пик = средний × коэффициент (из истории).
3. **Объёмы данных** — как в проде (или с прогнозом на 1–2 года): размеры таблиц, распределение популярности ключей (кэши!).
4. **Модель пользователей:**
   - **закрытая** (N виртуальных пользователей, следующий запрос после ответа + think time) — RPS сам падает при замедлении системы → маскирует деградацию (coordinated omission);
   - **открытая** (фиксированный темп поступления запросов, как в реальности у публичного API) — честнее показывает очереди.
   - Закон Литтла для пересчёта: `N пользователей = RPS × (время ответа + think time)`.

### 13.3 Критерии успешности

- SLA/SLO на перцентили (p95/p99) по каждой операции, а не на среднее;
- допустимая доля ошибок (например, < 0,1 %);
- утилизация ресурсов на целевой нагрузке (CPU < 70 % — запас на пики и отказ одного узла);
- отсутствие трендов роста (память, lag, размер очередей) в тесте стабильности.

### 13.4 Соответствие стенда проду

Разница в любом из пунктов делает результат непереносимым:

- версии ПО, конфигурации (пулы, таймауты, JVM-флаги, параметры БД);
- requests/limits контейнеров, число реплик, отключённый HPA ([[13 Kubernetes, OpenShift, Docker]], раздел 11.6);
- объём и распределение данных;
- сетевая топология: те же балансировщики, фаерволы, mesh, задержки между зонами ([[02 Сеть — пропускная способность, фаерволы, узкие места]]);
- внешние зависимости — реальные или заглушки с реалистичной latency.

Если стенд меньше прода — **масштабный коэффициент** обосновывается тестом масштабируемости, а не делением.

### 13.5 Генератор нагрузки — тоже система

- CPU генератора < 70–80 % (иначе завышенные времена и недогруз) — [[12 Python]], раздел 11;
- сетевые лимиты генератора: порты, FD, conntrack, канал;
- генератор должен работать с соединениями как реальные клиенты (keep-alive, пулы, TLS-сессии) — [[03 Протоколы взаимодействия]], раздел 14;
- синхронизация времени (NTP) между генератором и системой — для корреляции метрик.

### 13.6 Общий алгоритм поиска узкого места

```
1. Зафиксировать симптом: на какой ступени, по каким операциям вырос p99 / появились ошибки
2. RED каждого сервиса по цепочке (трассировка): где первым выросло время
3. Разделить «работаю» и «жду»:
   работаю → CPU (и throttling!), профиль: [[10 JVM]] [[11 Go]] [[12 Python]]
   жду     → пулы (БД, HTTP), блокировки, зависимость, сеть
4. Ресурсы узлов по USE: [[01 Linux — ядро, ресурсы, метрики]]
5. Хранилища: [[05 PostgreSQL]] [[06 ClickHouse]] [[07 Redis]] [[08 Kafka]]
6. Сеть: [[02 Сеть — пропускная способность, фаерволы, узкие места]]
7. Гипотеза → одно изменение → повторный прогон → сравнение. Никогда не менять несколько параметров сразу.
```

**Главная ловушка:** первое найденное узкое место скрывает следующее. Расширил пул БД — упёрлись в CPU БД; увеличил CPU — упёрлись в сеть. Поиск максимума — итеративный.

### 13.7 Отчёт по НТ

Структура: цель и объект → конфигурация стенда (и отличия от прода) → модель нагрузки → результаты по каждому тесту (графики RPS, перцентилей, ошибок, ресурсов) → найденные узкие места с доказательствами (метрики, профили, планы запросов) → максимальная производительность и запас относительно целевой → рекомендации и риски.
