## 1. CPython: как выполняется код

```
исходник .py → компилятор → байткод (.pyc в __pycache__) → интерпретатор (цикл eval)
```

| | Java | CPython |
|---|---|---|
| Байткод | да | да |
| JIT | C1/C2, код становится машинным | исторически нет; с 3.13 экспериментальный JIT (выключен по умолчанию), выигрыш пока небольшой. Есть «специализирующий интерпретатор» (3.11+), ускоривший код в 1,25–1,6 раза |
| Объекты | примитивы `int`, `long` без объектов | **всё — объект**: `int` 28 байт, `float` 24 байта, вызов функции — создание кадра |
| Потоки | настоящий параллелизм | GIL: один поток исполняет байткод в момент времени |
| GC | трассирующий, поколенческий | **подсчёт ссылок** + сборщик циклов |

Отсюда порядки величин: «чистый» Python в CPU-задачах в 10–100 раз медленнее Java/Go. Быстрым его делают библиотеки на C/Rust (numpy, orjson, pydantic-core, uvloop), в которых тяжёлая работа идёт вне интерпретатора.

## 2. GIL

**GIL (Global Interpreter Lock)** — глобальная блокировка интерпретатора: в каждый момент времени байткод Python исполняет **только один поток** процесса.

Зачем: подсчёт ссылок и внутренние структуры CPython не потокобезопасны; GIL защищает их дёшево.

### 2.1 Что GIL блокирует, а что нет

| Работа | Держит GIL? | Масштабируется потоками? |
|--------|-------------|--------------------------|
| Python-код (циклы, разбор JSON встроенным `json` и т.п.) | да | **нет** — 8 потоков ≈ 1 ядро |
| Ожидание сети/диска (`socket.recv`, `requests.get` пока ждёт ответ, `time.sleep`) | **нет** — GIL отпускается | да |
| C-расширения, которые явно отпускают GIL (numpy, hashlib на больших данных, сжатие zlib) | нет | да |

**Переключение:** поток, держащий GIL, отпускает его каждые `sys.getswitchinterval()` = **5 мс** (если кто-то ждёт) или при блокирующем вызове.

```
Пример: 4 потока считают хэши на чистом Python на 8-ядерной машине
→ CPU процесса ≈ 100 % (одно ядро), а не 400 %
→ ещё хуже: потоки дерутся за GIL, накладные расходы на переключение

4 потока делают HTTP-запросы (ждут сеть 95 % времени)
→ отлично масштабируется: пока один ждёт, другой работает
```

**Признак упора в GIL на НТ:** процесс Python использует ~1 ядро (100 % в `top`), хотя потоков много и ядер свободно; latency растёт с нагрузкой.

### 2.2 Free-threaded Python

С Python 3.13 есть экспериментальная сборка **без GIL** (`python3.13t`), в 3.14 она получила статус официально поддерживаемой (но не по умолчанию). Потоки выполняются параллельно, но:

- однопоточный код медленнее (дополнительные атомарные операции);
- не все C-расширения совместимы;
- для продакшена пока редкость. Стоит знать, что это есть и куда движется.

## 3. Модели конкурентности

| Модель | Как | Параллелизм CPU | Для чего | Аналог в Java |
|--------|-----|-----------------|----------|---------------|
| `threading` | потоки ОС | нет (GIL) | блокирующий I/O | `ThreadPoolExecutor` |
| `multiprocessing` / `ProcessPoolExecutor` | отдельные процессы, свой интерпретатор и GIL | **да** | CPU-задачи | несколько JVM |
| `asyncio` | один поток, цикл событий, корутины `async/await` | нет | много I/O-соединений | CompletableFuture/Netty, виртуальные потоки |
| `gevent` (greenlets) | кооперативные «зелёные потоки», monkey-patch стандартной библиотеки | нет | много I/O в синхронном коде | виртуальные потоки |

### 3.1 asyncio — главное правило

```python
async def handler(request):
    user = await db.fetch_user(request.user_id)     # отдаёт управление циклу, пока ждёт БД
    data = await http.get(f"/profile/{user.id}")     # то же
    return render(user, data)
```

Цикл событий — **один поток**. Пока корутина выполняет код без `await`, **все остальные запросы стоят**.

```python
async def handler(request):
    time.sleep(0.5)                  # ✗ блокирует весь цикл на 500 мс для ВСЕХ запросов
    requests.get(url)                # ✗ синхронный HTTP-клиент блокирует цикл
    heavy_cpu_calculation()          # ✗ 200 мс CPU — все ждут
    await asyncio.sleep(0.5)         # ✓
    await client.get(url)            # ✓ (httpx.AsyncClient / aiohttp)
    await asyncio.to_thread(blocking_io)          # ✓ блокирующий код — в поток
    await loop.run_in_executor(process_pool, cpu) # ✓ CPU — в процесс
```

**Метрика «задержка цикла событий» (event loop lag):** периодическая задача замеряет, насколько позже запланированного она запустилась. Рост — кто-то блокирует цикл. `asyncio` debug mode (`PYTHONASYNCIODEBUG=1`) логирует корутины, работавшие дольше `slow_callback_duration` (100 мс).

`uvloop` — замена стандартного цикла на libuv: в 2–4 раза быстрее на сетевых нагрузках.

### 3.2 gevent

Monkey-patching подменяет `socket`, `time.sleep`, `ssl` и т.д. на кооперативные версии: синхронный с виду код становится асинхронным. **Locust построен на gevent** (раздел 11). Ловушка: C-библиотеки, которые делают I/O сами (не через пропатченный `socket`), например некоторые драйверы БД, — блокируют весь процесс.

## 4. Память

### 4.1 Подсчёт ссылок + сборщик циклов

- У каждого объекта счётчик ссылок; при обнулении объект **освобождается немедленно** (детерминированно, без пауз). Аналог в Java — нет, там только трассирующий GC.
- Циклические ссылки (`a.b = b; b.a = a`) подсчётом не собираются → **сборщик циклов** (модуль `gc`), поколенческий (поколения 0, 1, 2; пороги `gc.get_threshold()` = `(700, 10, 10)` — сборка поколения 0 после 700 новых контейнерных объектов сверх освобождённых). В новых версиях CPython сборщик циклов перерабатывается в сторону инкрементальной работы, чтобы уменьшить паузы на больших кучах.
- Сборка старшего поколения на куче с миллионами объектов — пауза в десятки–сотни мс. Метрика `python_gc_collections_total{generation="2"}`.

Приёмы: `gc.freeze()` после старта (перенести стартовые объекты в «вечное» поколение — уменьшает работу сборщика и copy-on-write в форкнутых воркерах gunicorn), `gc.disable()` в отдельных сервисах (Instagram так делал) — только понимая риски утечек циклов.

### 4.2 Почему RSS не уменьшается

CPython выделяет мелкие объекты через собственный аллокатор `pymalloc` блоками-аренами по 256 КБ (1 МБ в новых версиях). Арена возвращается ОС, только когда **все** объекты в ней освобождены. После пика нагрузки остаются «дырявые» арены → RSS остаётся высоким, хотя объекты удалены. Это **фрагментация, а не утечка**: при следующем пике память переиспользуется.

Отличить утечку: под **стабильной** нагрузкой RSS растёт бесконечно → утечка (глобальные кэши без лимита, списки «на всякий случай», замыкания, накопление в `lru_cache` без `maxsize`).

### 4.3 Размер объектов

```
int              28 байт
float            24 байта
пустой dict      64 байта (растёт)
dict на 10 ключей ~ 350 байт
объект класса    ~50 байт + __dict__ (~100+ байт); со __slots__ — меньше
список из 1 млн int: 8 МБ указателей + 28 МБ объектов int ≈ 36 МБ
тот же массив в numpy int64: 8 МБ
```

Для данных НТ (миллионы строк результатов) — pandas/numpy/polars вместо списков словарей.

## 5. Веб-серверы: WSGI, ASGI, воркеры

### 5.1 WSGI (синхронный) — gunicorn + Flask/Django

```
gunicorn app:app --workers 9 --worker-class sync --timeout 30 --backlog 2048
```

- **Мастер-процесс** форкает N **воркеров**; каждый воркер — отдельный процесс со своим интерпретатором и GIL → параллелизм по CPU есть.
- `sync`-воркер обрабатывает **один запрос за раз**. 9 воркеров = максимум 9 одновременных запросов. Остальные ждут в очереди сокета (`--backlog`).
- `gthread` — потоки внутри воркера (`--threads 4`): параллельность для I/O, но CPU всё равно один на воркер из-за GIL.
- Рекомендация по числу воркеров: `2 × ядра + 1` для sync (с поправкой на I/O).
- `--timeout 30` — воркер, не ответивший 30 с, убивается мастером (`WORKER TIMEOUT` в логе) — под НТ это видно как 502/обрывы.
- `--max-requests 1000 --max-requests-jitter 100` — перезапуск воркера после N запросов (лечение утечек, но рестарт = прогрев).

**Закон Литтла для gunicorn sync:**

```
9 воркеров, среднее время запроса 150 мс
максимальный throughput = 9 / 0,15 = 60 RPS
если зависимость замедлилась до 1,5 с → 6 RPS, остальное — очередь и таймауты
```

### 5.2 ASGI (асинхронный) — uvicorn + FastAPI/Starlette

```
uvicorn app:app --workers 4 --loop uvloop --http httptools
# или gunicorn -k uvicorn.workers.UvicornWorker -w 4
```

- Каждый воркер — один цикл событий, тысячи одновременных соединений.
- Число воркеров ≈ число ядер.
- Любой блокирующий вызов в `async def` останавливает весь воркер (раздел 3.1). FastAPI: обычный `def`-обработчик выполняется в пуле потоков (по умолчанию 40 потоков anyio) — пул тоже может стать узким местом.

### 5.3 Память воркеров

Каждый воркер — копия приложения в памяти. `--preload` загружает приложение в мастер до форка → страницы общие (copy-on-write), но подсчёт ссылок **пишет** в объекты при каждом обращении → страницы копируются, экономия тает. `gc.freeze()` перед форком частично помогает.

## 6. Метрики (Prometheus)

Библиотека `prometheus_client` по умолчанию отдаёт:

| Метрика | Что |
|---------|-----|
| `process_cpu_seconds_total` | CPU процесса; rate ≈ 1,0 → упор в одно ядро (GIL) |
| `process_resident_memory_bytes` | RSS |
| `process_open_fds` / `process_max_fds` | FD |
| `python_gc_objects_collected_total{generation}` | собрано объектов сборщиком циклов |
| `python_gc_collections_total{generation}` | число сборок по поколениям |
| `python_gc_objects_uncollectable_total` | неубираемые объекты (утечки в C-коде, `__del__` в циклах) |
| `python_info` | версия интерпретатора |

**Ловушка с gunicorn:** каждый воркер — отдельный процесс со своими счётчиками; scrape попадёт в случайный воркер. Нужен **multiprocess mode** (`PROMETHEUS_MULTIPROC_DIR`) — воркеры пишут метрики в файлы, endpoint их агрегирует.

Свои метрики, которые стоит добавить: длительность запросов (гистограмма), занятость воркеров/пула потоков, **event loop lag**, размер пулов соединений к БД и их ожидание.

## 7. Профилирование

| Инструмент | Как работает | Накладные расходы | Для чего | Аналог |
|------------|-------------|-------------------|----------|--------|
| **py-spy** | сэмплирует стек **снаружи** процесса (читает память), без перезапуска | минимальные | CPU-профиль и flame graph в проде, «что делают потоки сейчас» | async-profiler / jstack |
| `cProfile` | детерминированный: перехватывает каждый вызов | большие (×1,5–3) | локально, точное число вызовов | — |
| `scalene` | сэмплирующий: CPU (Python vs native), память, GPU | малые | понять, где Python, а где C | — |
| `memray` | трассирует все аллокации | средние | утечки и пики памяти, flame graph памяти | async-profiler alloc |
| `tracemalloc` (встроен) | снимки аллокаций с трассировкой | средние | сравнить снимки «до» и «после» | jmap -histo |
| `yappi` | профилирует потоки и корутины | средние | asyncio/многопоточный код | — |
| `faulthandler` / `py-spy dump` | дамп стеков всех потоков | — | зависание | jstack |

```bash
py-spy top --pid 12345                               # «top» по функциям в реальном времени
py-spy record -o profile.svg --pid 12345 --duration 30   # flame graph

# В контейнере нужны права: --cap-add SYS_PTRACE (или securityContext.capabilities)
```

```python
import tracemalloc
tracemalloc.start(25)
snap1 = tracemalloc.take_snapshot()
# ... нагрузка ...
snap2 = tracemalloc.take_snapshot()
for stat in snap2.compare_to(snap1, "lineno")[:10]:
    print(stat)    # какие строки кода больше всего нарастили память
```

## 8. HTTP-клиенты и пулы соединений

| Клиент | Пул по умолчанию | Таймаут по умолчанию | Заметки |
|--------|------------------|----------------------|---------|
| `requests.get(...)` (модульная функция) | **нет пула** — новое соединение каждый раз | **нет таймаута** — может висеть вечно | только для скриптов |
| `requests.Session()` | `HTTPAdapter(pool_connections=10, pool_maxsize=10)` | нет | при > 10 параллельных потоках лишние соединения создаются и **выбрасываются** (warning `Connection pool is full, discarding connection`) |
| `urllib3.PoolManager` | `maxsize=1` на хост (!) | нет | `block=False` → лишние соединения закрываются |
| `httpx.Client` / `AsyncClient` | `max_connections=100`, `max_keepalive_connections=20` | **5 с** | поддерживает HTTP/2 |
| `aiohttp.ClientSession` | `TCPConnector(limit=100, limit_per_host=0)` | 5 минут общий | создавать одну сессию на приложение, не на запрос |

```python
# requests: правильно
session = requests.Session()
adapter = requests.adapters.HTTPAdapter(pool_connections=20, pool_maxsize=100, max_retries=0)
session.mount("https://", adapter)
r = session.get(url, timeout=(2, 10))   # (connect, read) — ВСЕГДА задавать

# aiohttp: правильно — одна сессия на всё приложение
connector = aiohttp.TCPConnector(limit=200, limit_per_host=100, ttl_dns_cache=300)
session = aiohttp.ClientSession(connector=connector, timeout=aiohttp.ClientTimeout(total=10, connect=2))
```

**Антипаттерн** «новая `ClientSession`/`Session` на каждый запрос» = новое TCP+TLS соединение на каждый запрос → TIME_WAIT, CPU на TLS, исчерпание портов ([[02 Сеть — пропускная способность, фаерволы, узкие места]]).

**Сериализация:** встроенный `json` медленный; `orjson` в 3–10 раз быстрее (и возвращает bytes). В FastAPI — `ORJSONResponse`. Pydantic v2 (ядро на Rust) намного быстрее v1.

## 9. Работа с БД

| Драйвер | Тип | Заметки |
|---------|-----|---------|
| `psycopg2` | синхронный | блокирует GIL? — нет, ожидание сети отпускает GIL; с gevent нужен `psycogreen` |
| `psycopg` (3) | синхронный и async | pipeline mode, серверные prepared statements после `prepare_threshold=5` — с PgBouncer < 1.21 ставить `prepare_threshold=None` |
| `asyncpg` | async | очень быстрый, бинарный протокол; кэш prepared statements — с PgBouncer transaction mode `statement_cache_size=0` |
| `clickhouse-connect`, `clickhouse-driver` | HTTP / native | [[06 ClickHouse]] |

**SQLAlchemy пул:** `pool_size=5`, `max_overflow=10` по умолчанию → до 15 соединений **на процесс**.

```
gunicorn 9 воркеров × (5 + 10) = до 135 соединений с одного пода
× 10 подов = 1350 соединений к PostgreSQL → max_connections = 200 исчерпан
```

Считать соединения как `воркеры × пул × поды` и ставить PgBouncer ([[05 PostgreSQL]], раздел 20). `pool_pre_ping=True` — проверка соединения перед использованием (лишний RTT, но защищает от обрывов фаерволом); `pool_recycle=1800` — пересоздание старых соединений.

## 10. Python в контейнере

- `os.cpu_count()` возвращает **число ядер ноды**, а не CPU-лимит контейнера. `multiprocessing.cpu_count()`, `ProcessPoolExecutor()` без параметров, «auto»-режимы серверов используют его → под с лимитом 2 ядра на 64-ядерной ноде запускает 64 процесса/129 воркеров → память, конкуренция, жёсткий throttling ([[13 Kubernetes, OpenShift, Docker]]).
- `os.process_cpu_count()` (3.13+) учитывает CPU affinity, но **не** CFS-квоту.
- Решение: задавать число воркеров явно из переменной окружения (`WEB_CONCURRENCY`, `--workers`), вычислять из `cpu.max` cgroup при необходимости.
- Память: несколько воркеров × размер приложения; лимит контейнера считать на всех.

## 11. Locust: как устроен генератор и как его не сделать узким местом

### 11.1 Устройство

- Locust работает на **gevent**: каждый виртуальный пользователь — greenlet в одном процессе.
- **Один процесс Locust использует одно ядро** (GIL + один цикл gevent).
- Масштабирование — **master + workers**: `locust --master`, `locust --worker --master-host=...` или `locust --processes 8` (форк воркеров на одной машине).

### 11.2 Главное правило: генератор не должен быть узким местом

Locust пишет предупреждение `CPU usage above 90%! This may constrain your throughput and may even give inconsistent response time measurements!`. Когда процесс генератора загружен на 100 %:

- greenlet-ы не успевают отправлять запросы вовремя → **фактический RPS ниже заданного**;
- время ответа измеряется с задержкой (ответ пришёл, но greenlet ещё ждёт своей очереди) → **latency завышена**, хотя система отвечает быстро.

Контроль: CPU процессов-воркеров Locust < 70–80 %; при упоре — больше воркеров/машин.

### 11.3 HttpUser vs FastHttpUser

| | `HttpUser` | `FastHttpUser` |
|---|---|---|
| Клиент | `requests` (urllib3) | `geventhttpclient` |
| Производительность | ~в 4–6 раз меньше RPS на ядро | высокая (тысячи RPS на ядро) |
| Совместимость | полная с API requests | похожий API, есть отличия |
| Пул | `requests.Session` на пользователя | `concurrency` соединений на пользователя (по умолчанию 10) |

Для высоких нагрузок — `FastHttpUser`.

### 11.4 Соединения и порты генератора

- Каждый пользователь Locust держит свою сессию → своё соединение (keep-alive). 5000 пользователей = 5000+ соединений с машины генератора.
- Если сервис/балансировщик закрывает соединения (`Connection: close`, короткий keep-alive), генератор открывает новые → TIME_WAIT, исчерпание эфемерных портов → `Cannot assign requested address` ([[01 Linux — ядро, ресурсы, метрики]], раздел 10).
- Лимит FD на машине генератора: `ulimit -n` ≥ числа пользователей × 2.
- DNS: резолв имени при каждом новом соединении — при плохом keep-alive это лишняя нагрузка и латентность.

### 11.5 Модель нагрузки

- `wait_time = between(1, 2)` — закрытая модель: следующий запрос через 1–2 с **после ответа**. При замедлении системы RPS **сам падает** (coordinated omission — [[03 Протоколы взаимодействия]], раздел 14).
- `constant_throughput(1)` — каждый пользователь старается делать не больше 1 итерации/с; `constant_pacing(1)` — итерация раз в секунду с учётом времени выполнения. Ближе к открытой модели, но при сильном замедлении всё равно не досылает.
- Для точного RPS — достаточный запас пользователей + `constant_throughput`, или собственный shape (`LoadTestShape`).

### 11.6 Прочее

- Не делать тяжёлую работу в задачах (генерация больших данных, криптография на чистом Python) — съедает CPU генератора. Готовить данные заранее.
- Логин и токены — в `on_start`, с обновлением до истечения ([[04 Аутентификация и токены]], раздел 14).
- `name=` у запросов с параметрами в URL — иначе статистика разбивается на тысячи строк и раздувает память master-а.
- События `request` — для отправки метрик в Prometheus/VictoriaMetrics/ClickHouse.

## 12. Сеть и Python

- Таймауты по умолчанию часто **отсутствуют** (`requests`, `urllib3`, `socket`) — зависшая зависимость забирает потоки/воркеры навсегда. Всегда явные `connect` и `read`.
- Пулы соединений малы по умолчанию (`requests` — 10 на хост, `urllib3.PoolManager` — 1) → при параллельности выше пула — постоянное открытие/закрытие соединений.
- `aiohttp` и `httpx` кэшируют DNS (aiohttp — `ttl_dns_cache=10` с по умолчанию), `requests` — нет.
- `TCP_NODELAY`: `aiohttp` и большинство современных клиентов выставляют; при самописных сокетах — помнить про Nagle + delayed ACK ([[02 Сеть — пропускная способность, фаерволы, узкие места]], раздел 3.4).
- TLS в Python — через OpenSSL (C), рукопожатие отпускает GIL, но всё равно дорого при отсутствии keep-alive.
- Большие ответы читать потоково (`iter_content`, `stream=True`), а не целиком в память.

## 13. Типичные узкие места и методика

```
1. CPU процесса: rate(process_cpu_seconds_total) ≈ 1 на процесс → упор в GIL/одно ядро
   → py-spy record → что считает; больше процессов-воркеров; вынести CPU в C/Rust-библиотеки
2. Воркеры/пулы заняты: gunicorn sync — все воркеры заняты? очередь в backlog растёт?
   → py-spy dump: на чём стоят потоки (ожидание БД, HTTP, блокировки)
3. asyncio: event loop lag → блокирующий вызов в корутине
4. Память: RSS растёт при стабильной нагрузке → tracemalloc/memray
5. GC: python_gc_collections_total{generation="2"} растёт, паузы → gc.freeze, меньше объектов
6. Сеть/пулы: TIME_WAIT, «Connection pool is full», нет таймаутов
7. БД: соединения = воркеры × пул × поды
```

## 14. Шпаргалка: симптом → причина → решение

| Симптом | Причина | Решение |
|---------|---------|---------|
| Процесс упёрся в 100 % одного ядра, ядер много | GIL | больше процессов, multiprocessing, нативные библиотеки |
| Все запросы async-сервиса тормозят разом | блокирующий вызов в цикле событий | async-клиенты, `to_thread`, debug mode |
| `WORKER TIMEOUT` в gunicorn, 502 | медленные зависимости, sync-воркеров мало | таймауты к зависимостям, больше воркеров/gthread/async |
| `Connection pool is full, discarding connection` | пул requests 10 | `pool_maxsize` |
| Запросы висят бесконечно | нет таймаутов | `timeout=(connect, read)` |
| RSS не уменьшается после пика | фрагментация pymalloc | норма, если не растёт под стабильной нагрузкой |
| RSS растёт бесконечно | утечка (кэши, глобальные коллекции) | tracemalloc, memray |
| Метрики «скачут» под gunicorn | scrape случайного воркера | multiprocess mode |
| Слишком много процессов/воркеров в поде, throttling | `os.cpu_count()` = ядра ноды | явное число воркеров |
| Locust: RPS ниже заданного, latency выше реальной | генератор упёрся в CPU | больше воркеров Locust, FastHttpUser |
| Locust: `Cannot assign requested address` | порты генератора | keep-alive, port range, несколько IP |
| Сотни соединений к БД | пул × воркеры × поды | меньше пул, PgBouncer |
| `json` в топе профиля | медленная сериализация | orjson |
