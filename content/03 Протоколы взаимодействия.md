## 1. Карта протоколов

| Стиль | Протоколы | Когда |
|-------|-----------|-------|
| Синхронный запрос-ответ | HTTP/REST, gRPC unary, GraphQL, SOAP | нужен ответ сейчас: «получить заказ», «проверить баланс» |
| Потоковый (streaming) | gRPC streaming, WebSocket, SSE | обновления в реальном времени, большие потоки данных |
| Асинхронный через брокер | Kafka, AMQP (RabbitMQ), MQTT | события, развязка сервисов, буферизация пиков |
| Протоколы хранилищ | PostgreSQL wire, Redis RESP, ClickHouse native/HTTP | работа с БД и кэшем |

Ключевые вопросы к любому протоколу на НТ:

1. Сколько **RTT** до первого полезного байта (установка соединения + TLS)?
2. Переиспользуются ли **соединения**? Сколько одновременных запросов в одном соединении?
3. Каков **размер** сообщения на проводе (формат сериализации, сжатие, заголовки)?
4. Как распределяется нагрузка между **бэкендами** (соединения vs запросы)?
5. Что происходит при **ошибке/таймауте**: ретраи, идемпотентность?

## 2. HTTP/1.1

### 2.1 Запрос и ответ

```
GET /api/orders/42 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOi...
Accept: application/json
Connection: keep-alive

HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 128
Cache-Control: no-store

{"id":42,"status":"paid",...}
```

Текстовый протокол: заголовки — строки ASCII, повторяются в каждом запросе (часто 500 байт – 2 КБ, а с JWT ещё больше).

### 2.2 Keep-alive и пул соединений

В HTTP/1.0 каждое соединение закрывалось после ответа. В HTTP/1.1 соединение по умолчанию **переиспользуется** (keep-alive).

```
Без keep-alive (на каждый запрос):
  TCP handshake 1 RTT + TLS 1.3 1 RTT + запрос/ответ 1 RTT = 3 RTT
  + CPU на TLS-рукопожатие + TIME_WAIT на клиенте

С keep-alive (повторный запрос):
  запрос/ответ 1 RTT
```

**Но:** одно HTTP/1.1-соединение обслуживает **один запрос за раз**. Пока ответ не получен, следующий запрос в это соединение отправить нельзя (pipelining формально есть, но на практике выключен везде). Поэтому для параллельности нужен **пул соединений** к каждому хосту.

```
Нужно 200 одновременных запросов к сервису B (по закону Литтла: 5000 RPS × 40 мс)
→ пул HTTP/1.1-клиента должен иметь ≥ 200 соединений к B
Если пул 20 → 180 запросов ждут свободное соединение → latency растёт без нагрузки на B
```

**Дефолтные ограничения пулов — частая причина «непонятной» latency:**

| Клиент | Ограничение по умолчанию |
|--------|-------------------------|
| Apache HttpClient 4.x (`PoolingHttpClientConnectionManager`) | **2** соединения на маршрут, 20 всего |
| Apache HttpClient 5.x | 5 на маршрут, 25 всего |
| OkHttp | 5 простаивающих в пуле (активных не ограничено, но Dispatcher: 5 запросов на хост, 64 всего) |
| Java 11+ `HttpClient` | для HTTP/1.1 без явного лимита (`jdk.httpclient.connectionPoolSize`) |
| Go `net/http` | `MaxIdleConnsPerHost = 2` (лишние соединения закрываются → TIME_WAIT) — [[11 Go]] |
| Python `requests` (`HTTPAdapter`) | `pool_connections=10`, `pool_maxsize=10` — [[12 Python]] |
| Spring `RestTemplate` по умолчанию | `SimpleClientHttpRequestFactory` — без пула вообще |

### 2.3 Head-of-line blocking в HTTP/1.1

В одном соединении медленный ответ блокирует все следующие запросы в нём. Браузеры обходят это 6 соединениями на хост, серверы — пулами.

### 2.4 Заголовки, важные для производительности

| Заголовок | Влияние |
|-----------|---------|
| `Connection: keep-alive` / `close` | `close` от сервера/балансировщика = новое соединение на каждый запрос |
| `Keep-Alive: timeout=60, max=1000` | сколько держать idle-соединение и сколько запросов в нём |
| `Content-Encoding: gzip/br/zstd` | сжатие: −70–90 % байт JSON, но CPU на обеих сторонах |
| `Transfer-Encoding: chunked` | потоковая отдача без известной длины |
| `Cache-Control`, `ETag`, `If-None-Match` | кэширование, ответ `304 Not Modified` без тела |
| `Retry-After` | когда повторить (с `429`, `503`) |

### 2.5 Коды ответа, важные для НТ

| Код | Значит | Что смотреть |
|-----|--------|--------------|
| `200/201/204` | успех | — |
| `304` | не изменилось (кэш) | — |
| `400/422` | неверный запрос | ошибка в скрипте НТ или данных |
| `401/403` | нет/неверная аутентификация, нет прав | истёк токен в скрипте НТ — [[04 Аутентификация и токены]] |
| `404` | не найдено | тестовые данные |
| `408` | сервер не дождался запроса | медленный клиент |
| `409` | конфликт (версия, дубль) | конкуренция за данные, оптимистичные блокировки |
| `429` | rate limit | лимиты gateway — согласовать перед НТ |
| `499` (nginx) | клиент закрыл соединение, не дождавшись | таймаут клиента меньше времени ответа |
| `500` | ошибка сервера | логи приложения |
| `502` | балансировщик получил плохой ответ/обрыв от бэкенда | бэкенд упал, гонка keep-alive ([[02 Сеть — пропускная способность, фаерволы, узкие места]], раздел 11) |
| `503` | сервис недоступен | нет живых бэкендов, перегрузка, circuit breaker |
| `504` | таймаут балансировщика до бэкенда | бэкенд медленный, таймауты цепочки |

## 3. HTTP/2

### 3.1 Что изменилось

- **Бинарный** протокол: сообщения разбиты на кадры (frames).
- **Мультиплексирование:** в одном TCP-соединении много **потоков (streams)** одновременно. Запросы и ответы перемежаются кадрами — медленный ответ не блокирует остальные **на уровне HTTP**.
- **HPACK** — сжатие заголовков: таблица уже отправленных заголовков, повторяющийся заголовок передаётся индексом в 1–2 байта.
- **Flow control** на уровне потока и соединения (окна, как у TCP).
- Приоритеты потоков (на практике почти не используются).
- Server push — фактически заброшен.

```
HTTP/1.1: 100 параллельных запросов = 100 TCP-соединений (100 handshake, 100 TLS)
HTTP/2:   100 параллельных запросов = 1 соединение, 100 потоков
          SETTINGS_MAX_CONCURRENT_STREAMS — лимит потоков на соединение (часто 100–250)
```

### 3.2 Где HTTP/2 хуже

- **TCP head-of-line blocking остался:** все потоки в одном TCP. Потеря одного пакета задерживает **все** потоки, пока он не будет переотправлен. При потерях 1–2 % HTTP/2 может быть хуже нескольких соединений HTTP/1.1.
- **Балансировка:** одно долгоживущее соединение → L4-балансировщик отправляет весь трафик клиента на один бэкенд ([[02 Сеть — пропускная способность, фаерволы, узкие места]], раздел 11).
- **Лимит потоков:** если клиент держит одно соединение, а `MAX_CONCURRENT_STREAMS = 100`, 101-й запрос ждёт. Клиенты должны открывать дополнительные соединения.
- Больше CPU на кадрирование и HPACK, чем у простого HTTP/1.1, на очень мелких запросах.

### 3.3 h2 и h2c

- `h2` — HTTP/2 поверх TLS, согласуется через ALPN во время TLS-рукопожатия (браузеры поддерживают только его).
- `h2c` — HTTP/2 без TLS (cleartext), используется внутри кластера, в gRPC без TLS.

## 4. HTTP/3 и QUIC

**QUIC** — транспорт поверх **UDP**, реализованный в пространстве пользователя (не в ядре):

- шифрование TLS 1.3 встроено в транспорт: установка соединения + шифрование = **1 RTT**, при повторном подключении **0-RTT**;
- потоки независимы на уровне транспорта: потеря пакета одного потока **не блокирует** остальные (нет TCP HOL blocking);
- **миграция соединения**: идентификатор соединения не привязан к IP/порту — переход телефона с Wi-Fi на LTE не рвёт соединение;
- контроль перегрузки и ретрансмиссии — в библиотеке.

Минусы: больше CPU (нет аппаратных offload-ов, как для TCP), UDP режется некоторыми фаерволами (тогда откат на HTTP/2), сложнее отлаживать (всё зашифровано, tcpdump видит мало). Внутри ЦОДа между сервисами почти не используется — выгода в основном на мобильных и дальних сетях.

## 5. TLS

### 5.1 Рукопожатие

```
TLS 1.2 (полное): 2 RTT
  ClientHello → ServerHello + Certificate + ServerKeyExchange → ClientKeyExchange + Finished → Finished
TLS 1.3 (полное): 1 RTT
  ClientHello (+ key share) → ServerHello + Certificate + Finished → данные
TLS 1.3 resumption: 1 RTT без проверки сертификата; 0-RTT — данные сразу с первым пакетом
  (0-RTT уязвим к replay → только для идемпотентных запросов)
```

Плюс TCP handshake 1 RTT. Итого новое HTTPS-соединение = 2 RTT (TLS 1.3) или 3 RTT (TLS 1.2) до отправки запроса.

### 5.2 Стоимость

- **CPU на рукопожатие:** асимметричная криптография (ECDHE + подпись сертификата). RSA-2048 подпись дорогая (~1–2 мс CPU), ECDSA P-256 — в разы дешевле. Одно ядро — от сотен до нескольких тысяч полных рукопожатий в секунду.
- **CPU на шифрование трафика:** AES-GCM с аппаратной поддержкой AES-NI — гигабайты в секунду на ядро, почти бесплатно.
- **Вывод:** дорого не шифрование, а **рукопожатие**. Новое TLS-соединение на каждый запрос → CPU сервера уходит в криптографию.

**Пример:** 3000 RPS без keep-alive → 3000 рукопожатий/с × 1,5 мс CPU (RSA) = 4,5 ядра только на TLS. С keep-alive и 100 соединениями — рукопожатия только при открытии.

### 5.3 Session resumption

Сервер выдаёт клиенту **session ticket** (или session ID в TLS 1.2). При переподключении клиент предъявляет его — сокращённое рукопожатие без дорогих операций с сертификатом. Важно для НТ: если генератор нагрузки не переиспользует TLS-сессии, он создаёт нагрузку тяжелее, чем реальные клиенты.

### 5.4 Где завершается TLS (termination)

```
Клиент ──TLS──> Балансировщик/Ingress ──HTTP──> сервис           (TLS termination)
Клиент ──TLS──> Балансировщик ──TLS (новый)──> сервис           (re-encryption)
Клиент ──TLS──────────────────────────────────> сервис           (passthrough, L4)
Сервис A ──mTLS──> sidecar ──> сервис B                          (service mesh)
```

Каждая точка завершения TLS — CPU и ещё одно рукопожатие на новые соединения.

### 5.5 mTLS

Обе стороны предъявляют сертификаты — сервер проверяет клиента. Используется между микросервисами (service mesh Istio/Linkerd делают это прозрачно через sidecar), для доступа к Kafka, PostgreSQL. Подробнее — [[04 Аутентификация и токены]].

### 5.6 Диагностика

```bash
openssl s_client -connect api:443 -servername api -tls1_3 </dev/null
# версия, шифр, цепочка сертификатов, время

curl -w 'connect=%{time_connect} tls=%{time_appconnect}\n' -o /dev/null -s https://api/
# tls − connect = время TLS-рукопожатия
```

Проблемы: устаревшая цепочка сертификатов, недоверенный CA (`PKIX path building failed` в Java), проверка отзыва (OCSP) с запросом во внешнюю сеть на каждое соединение, большой сертификат + PMTU black hole.

## 6. REST

**REST** — архитектурный стиль поверх HTTP: ресурсы (существительные в URL), методы HTTP как действия, коды ответа как результат, без состояния сессии на сервере.

| Метод | Смысл | Безопасный (не меняет данные) | Идемпотентный |
|-------|-------|------------------------------|---------------|
| `GET` | получить | да | да |
| `HEAD` | только заголовки | да | да |
| `POST` | создать / выполнить действие | нет | **нет** |
| `PUT` | заменить целиком | нет | да |
| `PATCH` | изменить частично | нет | не обязательно |
| `DELETE` | удалить | нет | да |

**Идемпотентность** — повторный вызов даёт тот же результат, что и одиночный. Это определяет, можно ли **безопасно повторить** запрос при таймауте (раздел 13). POST делают идемпотентным через заголовок `Idempotency-Key`.

**Пагинация:** offset (`?page=1000&size=50` → БД пропускает 50 000 строк, медленно) vs курсорная (`?after=<id>` → индекс, постоянное время) — [[05 PostgreSQL]], раздел 12.2.

**Типичные проблемы производительности REST:**

- **chatty API** — много мелких вызовов на одну операцию (N+1 по HTTP): экран делает 30 запросов → 30 × RTT;
- **over-fetching** — ответ на 200 КБ, из которого клиенту нужно 3 поля;
- сериализация JSON больших ответов — CPU (в Java Jackson часто входит в топ профиля).

## 7. gRPC

### 7.1 Что это

- RPC-фреймворк поверх **HTTP/2**, контракт описывается в `.proto`, сообщения — **Protocol Buffers** (бинарный компактный формат).
- Генерирует клиентский и серверный код для разных языков.

```protobuf
service OrderService {
  rpc GetOrder (GetOrderRequest) returns (Order);                       // unary
  rpc ListOrders (ListRequest) returns (stream Order);                  // server streaming
  rpc UploadEvents (stream Event) returns (Summary);                    // client streaming
  rpc Chat (stream Message) returns (stream Message);                   // bidirectional
}
```

### 7.2 Сильные стороны

- компактные сообщения (Protobuf в 3–10 раз меньше JSON), быстрая (де)сериализация;
- строгий контракт, кодогенерация;
- стриминг в обе стороны;
- **deadlines** — клиент передаёт абсолютный срок, и он распространяется по цепочке вызовов: если срок истёк, сервер может не начинать работу;
- статусы: `OK`, `DEADLINE_EXCEEDED`, `UNAVAILABLE` (можно ретраить), `RESOURCE_EXHAUSTED` (перегрузка/лимит — так отвечает Zeebe при backpressure, [[09 Camunda Zeebe]]), `INVALID_ARGUMENT`, `UNAUTHENTICATED`, `PERMISSION_DENIED`, `INTERNAL`.

### 7.3 Подводные камни

- **Балансировка:** клиент держит одно долгоживущее HTTP/2-соединение → L4-балансировщик (Kubernetes Service/kube-proxy) отправит весь трафик клиента на **один под**. Решения: клиентская балансировка (`round_robin` + headless Service, DNS возвращает IP всех подов), L7-прокси (Envoy, service mesh), на сервере `MaxConnectionAge` — периодически закрывать соединение, чтобы клиент переподключился и перераспределился.
- **Лимит потоков** на соединение (обычно 100) → при большой параллельности нужны несколько каналов.
- **Keepalive gRPC:** клиентские пинги слишком часто → сервер закрывает соединение с `GOAWAY ENHANCE_YOUR_CALM` (защита от пинг-флуда). Параметры keepalive согласовывать на клиенте и сервере.
- Размер сообщения по умолчанию ограничен **4 МБ** на приём (`max_receive_message_length`).
- Браузеры не умеют gRPC напрямую → gRPC-Web через прокси.
- Отладка сложнее: бинарный формат; инструменты — `grpcurl`, `ghz` (нагрузка).

## 8. GraphQL, SOAP

**GraphQL** — один endpoint, клиент сам описывает, какие поля нужны. Решает over/under-fetching. Проблемы для производительности:

- **N+1 в резолверах**: запрос «заказы и их товары» → резолвер товаров вызывается для каждого заказа → решается DataLoader (батчинг);
- **дорогие запросы**: глубоко вложенный запрос может положить сервер → лимиты глубины и «стоимости» запроса;
- кэширование HTTP почти не работает (всё через POST на один URL).

**SOAP** — XML-конверты, WSDL-контракт, часто WS-Security. Тяжёлый: XML в 5–10 раз больше JSON, разбор XML — CPU. Встречается в госинтеграциях и банках. На НТ — профилировать (де)сериализацию и проверку подписей XML.

## 9. WebSocket, SSE, long polling

| | Long polling | SSE (Server-Sent Events) | WebSocket |
|---|---|---|---|
| Направление | сервер → клиент (эмуляция) | сервер → клиент | двунаправленное |
| Транспорт | обычные HTTP-запросы, висящие до события | одно долгое HTTP-соединение, `text/event-stream` | HTTP Upgrade → свой протокол кадров поверх TCP |
| Переподключение | каждый ответ — новый запрос | встроенное (`Last-Event-ID`) | вручную |
| Нагрузка на сервер | высокая (постоянные запросы) | одно соединение на клиента | одно соединение на клиента |

**WebSocket handshake:**

```
GET /ws HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: ...
→ HTTP/1.1 101 Switching Protocols
```

**Нагрузочная специфика долгоживущих соединений:**

- метрика — не RPS, а **число одновременных соединений** и **сообщений в секунду**;
- на каждое соединение: FD, буферы сокета (десятки КБ), объект сессии, иногда поток → 100 тыс. соединений = гигабайты памяти и лимиты FD ([[01 Linux — ядро, ресурсы, метрики]]);
- балансировщики должны поддерживать Upgrade и иметь большой idle timeout (иначе разрывы каждые 60 с), нужен ping/pong для удержания;
- деплой/рестарт пода рвёт все его соединения → **шторм переподключений** на оставшиеся поды;
- генератор нагрузки упирается в эфемерные порты: 28 тыс. портов на целевой IP:порт → для 100 тыс. соединений нужно несколько IP генератора.

## 10. Брокерные протоколы

| | Kafka | AMQP 0-9-1 (RabbitMQ) | MQTT |
|---|---|---|---|
| Модель | распределённый лог: партиции, offset, consumer groups | очереди и exchange-маршрутизация, push консьюмерам | publish/subscribe по топикам, лёгкий |
| Доставка | consumer сам читает (pull), хранится по retention | брокер толкает (push) с prefetch, удаляется после ack | QoS 0 / 1 / 2 |
| Порядок | внутри партиции | внутри очереди (при одном консьюмере) | по топику |
| Протокол | бинарный поверх TCP, батчи | бинарный поверх TCP, каналы в соединении | бинарный, очень компактный |
| Типичный узкий место | диск, сеть, число партиций, consumer lag | память брокера, prefetch, ack | число соединений устройств |
| Подробно | [[08 Kafka]] | — | — |

**AMQP (RabbitMQ) — важное для НТ:**

- одно TCP-соединение, внутри — **каналы** (как потоки HTTP/2); открывать соединение на каждое сообщение — антипаттерн;
- **prefetch (basic.qos)** — сколько неподтверждённых сообщений брокер отдаёт консьюмеру. Малый prefetch (1) при большом RTT → консьюмер простаивает, ожидая следующее сообщение; большой → один консьюмер забирает всё, остальные простаивают;
- **publisher confirms** — подтверждение записи брокером (аналог `acks` в Kafka);
- при нехватке памяти/диска брокер включает **flow control / блокирует публикацию** — продюсеры зависают.

**MQTT QoS:** 0 — не более одного раза, 1 — хотя бы один (дубли), 2 — ровно один (4 сообщения на доставку). Используется в IoT.

## 11. Протоколы баз данных

### 11.1 PostgreSQL wire protocol

- **Simple query** — текст запроса целиком, ответ текстом. 1 RTT.
- **Extended query** — Parse → Bind → Describe → Execute → Sync; поддерживает параметры (защита от SQL-инъекций), prepared statements, бинарный формат. Драйверы отправляют сообщения пачкой — 1 RTT на выполнение.
- **Pipeline mode** (libpq 14+, psycopg3, PgJDBC batch) — отправить много запросов, не дожидаясь ответов: N запросов за ~1 RTT.
- Подробно о сетевых аспектах — [[05 PostgreSQL]], раздел 21.

### 11.2 Redis RESP

Простой текстовый протокол: `*3\r\n$3\r\nSET\r\n$3\r\nkey\r\n$5\r\nvalue\r\n`. Команда выполняется за микросекунды, поэтому время запроса почти целиком = **RTT**. Pipeline (много команд без ожидания ответов) — главная оптимизация: [[07 Redis]].

### 11.3 ClickHouse

Native-протокол (TCP, порт 9000, бинарные колоночные блоки, сжатие) и HTTP (порт 8123). Native эффективнее для больших объёмов вставки и выборки. Подробно — [[06 ClickHouse]].

## 12. Форматы сериализации

| Формат | Тип | Размер (условно) | Скорость | Схема | Где |
|--------|-----|------------------|----------|-------|-----|
| JSON | текст | 100 % | медленно (разбор текста, числа как строки) | нет (JSON Schema опционально) | REST, логи |
| XML | текст | 150–300 % | медленнее JSON | XSD | SOAP |
| Protobuf | бинарный | 20–40 % | быстро | обязательна (`.proto`), имена полей не передаются — только номера | gRPC, Kafka |
| Avro | бинарный | 20–40 % | быстро | обязательна, хранится в Schema Registry, хорошо поддерживает эволюцию | Kafka, Hadoop |
| MessagePack | бинарный | 50–80 % | быстро | нет | кэши, RPC |

**Эволюция схемы:** Protobuf — новые поля с новыми номерами, удалённые номера не переиспользовать; Avro — совместимость (backward/forward) проверяется Schema Registry.

**Сжатие:** gzip даёт хорошую степень, но дорог по CPU; zstd и lz4 — быстрее. Для API сжатие ответов выгодно, когда сеть узкая или ответы большие; в ЦОДе на маленьких ответах только тратит CPU.

**На НТ:** (де)сериализация — частый лидер CPU-профиля. Jackson в Java, `json` в Python (медленный — `orjson` в разы быстрее), `encoding/json` в Go (рефлексия — медленный).

## 13. Надёжность взаимодействия

### 13.1 Таймауты — всегда явные

| Таймаут | Что ограничивает | Если не задан |
|---------|------------------|---------------|
| connect timeout | установку TCP-соединения | ждём до 2 мин (ретраи SYN ядра) |
| TLS handshake timeout | рукопожатие | — |
| read/socket timeout | ожидание данных от сервера | **бесконечно** в многих клиентах — поток/соединение зависает навсегда |
| request/total timeout | весь запрос целиком | — |
| pool acquire timeout | ожидание свободного соединения из пула | бесконечно / 30 с |

Таймауты по цепочке **уменьшаются** вглубь (gateway 10 с → сервис 8 с → БД 5 с).

### 13.2 Ретраи

- повторять можно только **идемпотентные** операции (или с `Idempotency-Key`);
- **экспоненциальная задержка с джиттером**: 100 мс, 200, 400, 800 + случайная добавка — без джиттера все клиенты ретраят одновременно волнами;
- **ограничить число** ретраев и использовать **retry budget** (не более 10 % дополнительных запросов);
- **retry storm:** сервис C начал тормозить → B ретраит 3 раза → A ретраит B 3 раза → C получает 9× нагрузку как раз когда ему плохо. Ретраи на одном уровне, а не на каждом.

### 13.3 Идемпотентность

```
Клиент → POST /payments {amount: 100}   → сервер провёл платёж → ответ потерялся по таймауту
Клиент повторяет POST → второй платёж!

С ключом: POST /payments, Idempotency-Key: 7f3a...
Сервер сохраняет ключ и результат; повтор с тем же ключом → возвращает сохранённый результат
```

### 13.4 Circuit breaker, bulkhead, rate limiting

- **Circuit breaker** — после N ошибок/таймаутов перестать вызывать зависимость на время (fail fast), потом пробовать по одному (half-open). Resilience4j в Java.
- **Bulkhead** — отдельный пул потоков/соединений на каждую зависимость, чтобы медленная зависимость не забрала все ресурсы.
- **Rate limiting** — token bucket / leaky bucket; ответ `429` + `Retry-After`.
- **Backpressure** — сервер сообщает «я перегружен» (gRPC `RESOURCE_EXHAUSTED`, HTTP 503, zero window TCP, Kafka quota throttling), клиент снижает темп.

Подробнее паттерны устойчивости — [[15 Микросервисы и системный дизайн]].

## 14. Нагрузочное тестирование разных протоколов

| Протокол | Что важно в генераторе нагрузки |
|----------|--------------------------------|
| HTTP/1.1 | keep-alive включён? размер пула соединений? переиспользование TLS-сессий? В Locust `FastHttpUser` (geventhttpclient) в разы эффективнее `HttpUser` (requests) — [[12 Python]] |
| HTTP/2 | сколько соединений открывает генератор (одно соединение = один бэкенд за L4) |
| gRPC | `ghz`, k6 (grpc модуль), Locust с grpcio + gevent-патчи; число каналов; deadline |
| WebSocket | метрика — одновременные соединения и сообщения/с; порты и FD генератора |
| Kafka | `kafka-producer-perf-test`, собственные продюсеры; размер батча, acks, сжатие |
| БД напрямую | `pgbench`, свои сценарии; реалистичный пул соединений |

**Правило:** генератор должен вести себя как реальные клиенты. Если реальные клиенты — 50 сервисов с пулами по 20 keep-alive соединений, а генератор открывает новое соединение на каждый запрос, ты тестируешь TLS-рукопожатия и TIME_WAIT, а не систему. И наоборот: если реальные клиенты — миллион мобильных устройств с короткими сессиями, тест на 100 долгоживущих соединениях не покажет проблем с рукопожатиями.

**Coordinated omission:** генератор с закрытой моделью (N виртуальных пользователей, следующий запрос после ответа) при замедлении системы **сам снижает нагрузку** и не учитывает время, которое запросы «должны были» ждать. Перцентили выглядят лучше реальности. Открытая модель (фиксированный темп прибытия запросов) — честнее.

## 15. Узкие места протоколов

| Протокол | Типичное узкое место | Признак |
|----------|---------------------|---------|
| HTTP/1.1 | маленький пул соединений клиента | latency растёт, сервер недогружен, на клиенте ожидание пула |
| HTTP/1.1 | нет keep-alive | TIME_WAIT, CPU на TLS, SYN-ы в каждом запросе |
| HTTP/2 / gRPC | одно соединение → один бэкенд | перекос нагрузки на поды |
| HTTP/2 | лимит MAX_CONCURRENT_STREAMS | запросы ждут свободный поток |
| HTTP/2 | потери пакетов | все потоки соединения тормозят разом |
| TLS | рукопожатия | CPU сервера в криптографии (профиль: `ECDSA`, `RSA`, `BigInteger` в Java) |
| JSON/XML | сериализация | CPU user, в профиле Jackson/json |
| WebSocket | число соединений | FD, память, порты генератора, idle timeout LB |
| Брокеры | prefetch / батчи / acks | простои консьюмеров, lag |
| Любой | нет таймаутов | зависшие потоки, исчерпание пулов при деградации зависимости |
| Любой | ретраи без джиттера/бюджета | лавинообразный рост нагрузки при сбое |

## 16. Шпаргалка

```
Новое HTTPS-соединение = TCP 1 RTT + TLS1.3 1 RTT (TLS1.2 — 2 RTT) + запрос 1 RTT
Keep-alive убирает первые два слагаемых и CPU рукопожатия
HTTP/1.1: 1 запрос на соединение за раз → нужен пул ≥ concurrency (закон Литтла)
HTTP/2: много потоков в 1 соединении → проблема балансировки и TCP HOL
HTTP/3: QUIC/UDP, нет TCP HOL, 0-RTT, но больше CPU
gRPC: Protobuf + HTTP/2, deadlines, клиентская балансировка, 4 МБ лимит сообщения
Идемпотентные: GET PUT DELETE HEAD; POST — нет (Idempotency-Key)
Ретраи: только идемпотентные, экспонента + джиттер, бюджет, на одном уровне
Таймауты: всегда явные, уменьшаются вглубь цепочки
```
