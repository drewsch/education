# Redis — полный конспект

> Связанные темы: [[02 Сеть — пропускная способность, фаерволы, узкие места]] · [[01 Linux — ядро, ресурсы, метрики]] (fork, THP, память) · [[04 Аутентификация и токены]] (сессии) · [[15 Микросервисы и системный дизайн]] (кэширование)

## Что такое Redis

Redis — in-memory хранилище данных. Хранит всё в оперативной памяти, поэтому работает в 100–1000 раз быстрее PostgreSQL который читает с диска.

Основные сценарии использования:

* **Кэширование** — снизить нагрузку на PostgreSQL
* **Сессии** — хранить пользовательские сессии с TTL
* **Rate limiting** — ограничение запросов через атомарный INCR
* **Distributed locks** — блокировки между инстансами (Redlock)
* **Pub/Sub** — уведомления между сервисами в реальном времени
* **Очереди** — через List (RPUSH/LPOP)

***

## Типы данных

| Тип            | Когда использовать                 | Пример                       |
| -------------- | ---------------------------------- | ---------------------------- |
| **String**     | Один ключ-значение, счётчики       | `SET user:1 "Андрей"`        |
| **Hash**       | Объект с полями (юзер, продукт)    | `HSET user:1 имя "Андрей"`   |
| **List**       | Очередь задач, лог событий         | `RPUSH задачи "email"`       |
| **Set**        | Уникальные значения, теги, email-ы | `SADD emails "a@mail.ru"`    |
| **Sorted Set** | Рейтинги, топы с очками            | `ZADD рейтинг 1500 "Андрей"` |
| **Stream**     | События, аналог Kafka-лайт         | `XADD events * key value`    |

## Базовые команды

```
# String
SET ключ "значение"
GET ключ
DEL ключ
EXISTS ключ          # 1 = есть, 0 = нет

# TTL
SET сессия "данные" EX 300    # истечёт через 300 сек
EXPIRE ключ 120               # поставить TTL на существующий
TTL ключ                      # сколько секунд осталось (-1 = без TTL, -2 = нет ключа)

# Счётчики (атомарно)
INCR счётчик
INCRBY счётчик 5

# Hash
HSET user:1 имя "Андрей" email "a@mail.ru"
HGET user:1 имя
HGETALL user:1

# List
RPUSH задачи "отправить email"
LPOP задачи

# Set
SADD emails "a@mail.ru"
SISMEMBER emails "a@mail.ru"   # проверить наличие — O(1)
SMEMBERS emails

# Sorted Set
ZADD рейтинг 1500 "Андрей"
ZREVRANGE рейтинг 0 9 WITHSCORES   # топ-10
ZREVRANK рейтинг "Андрей"          # позиция

```

## Атомарность

Атомарная операция — выполняется целиком или не выполняется вообще. Нельзя прервать на середине.

Redis **однопоточный** по обработке команд — команды выполняются строго по очереди, никто не влезет между шагами. Это даёт атомарность без дополнительных механизмов.

```
INCR лайки   # читает + прибавляет + записывает — одна неделимая операция
             # 1000 клиентов одновременно — счётчик не сломается

```

***

## Pipeline

Отправить много команд одним пакетом вместо по одной. Экономит время на сетевых round-trip.

**Без pipeline:** 1000 команд × (сеть + выполнение) = медленно

**С pipeline:** 1 пакет → все команды → 1 ответ = в 10–50 раз быстрее

```
# В redis-cli
echo -e "SET user:1 Андрей\nSET user:2 Иван\nSET user:3 Мария" | redis-cli --pipe

```

```
// В Java (Jedis)
Pipeline pipeline = jedis.pipelined();
pipeline.set("user:1", "Андрей");
pipeline.set("user:2", "Иван");
pipeline.incr("счётчик");
pipeline.sync(); // отправить всё разом

```

> ⚠️ Pipeline ≠ транзакция. Другие клиенты могут влезть между командами. Оптимальный батч — 100–1000 команд.

***

## Транзакции MULTI/EXEC

Атомарно выполнить несколько команд подряд. Никто не влезет между ними.

```
MULTI                        # начать транзакцию
SET баланс:андрей 500
SET баланс:иван 1500
INCR счётчик_переводов
EXEC                         # выполнить всё разом

DISCARD                      # отменить транзакцию

```

> ⚠️ Отличие от PostgreSQL: если одна команда упала с ошибкой — остальные всё равно выполнятся. Redis не делает rollback.

### WATCH — оптимистичная блокировка

```
WATCH баланс:андрей          # следить за ключом
GET баланс:андрей            # прочитали значение

MULTI
SET баланс:андрей 500
EXEC
# Если баланс:андрей изменился после WATCH — EXEC вернёт nil
# Нужно начать заново

```

> Для перформанса: много конфликтов WATCH при высоком concurrency = contention, видно по росту latency.

## Pub/Sub

Паттерн издатель/подписчик. Как радиостанция — вещает всем кто слушает.

```
# Подписчик (терминал 1)
SUBSCRIBE новости

# Издатель (терминал 2)
PUBLISH новости "Redis это просто"
# Вернёт: (integer) 1 — количество получателей

# Подписка по паттерну
PSUBSCRIBE заявки:*          # заявки:создана, заявки:закрыта — всё придёт

```

**Ограничения:**

* Сообщения не хранятся — подписчик отключился = сообщения потеряны
* Это не Kafka — нет гарантии доставки, нет истории

**Типичный сценарий:** инвалидация локального кэша между несколькими инстансами приложения в Kubernetes.

## Persistence — сохранение на диск

### RDB (снапшот)

```
# redis.conf
save 900 1      # сохранить если за 900 сек изменился 1 ключ
save 300 10     # или за 300 сек изменились 10 ключей

# Отключить для чистого кэша
save ""

```

Делает `fork()` процесса — копия пишет на диск. В момент fork возможен **latency spike** (copy-on-write overhead).

### AOF (журнал команд)

```
appendonly yes
appendfsync everysec    # компромисс: flush раз в секунду, теряет макс 1 сек данных
# appendfsync always    # безопасно но медленно
# appendfsync no        # быстро но риск потери данных

```

> Для чистого кэша оба отключают: `save ""` + `appendonly no`

## Архитектурные режимы

### Standalone

Один мастер + опциональные реплики. Реплики только читают. Нет автоматического failover.

### Sentinel

3+ процесса-сторожа следят за мастером. При падении мастера голосуют (кворум) и повышают реплику. Failover \~30 секунд — во время теста запросы будут падать.

### Cluster

Горизонтальный шардинг. 16384 слотов, ключ → `CRC16(key) mod 16384` → нужный шард.

&#x20;⚠️ Multi-key операции (`MGET`, `MSET`) работают только если все ключи в одном слоте.

## Eviction — политики вытеснения

Когда `maxmemory` заполнен, Redis удаляет ключи по политике:

| Политика          | Что удаляет                                     |
| ----------------- | ----------------------------------------------- |
| `allkeys-lru`     | Наименее недавно использованный из всех ключей  |
| `allkeys-lfu`     | Наименее часто используемый из всех ключей      |
| `allkeys-random`  | Случайный из всех ключей                        |
| `volatile-lru`    | LRU только среди ключей с TTL                   |
| `volatile-lfu`    | LFU только среди ключей с TTL                   |
| `volatile-random` | Случайный только среди ключей с TTL             |
| `volatile-ttl`    | Ближайший к истечению TTL                       |
| `noeviction`      | Ничего не удалять, возвращать ошибку при записи |

**Для кэша:**`allkeys-lru` — самый типичный выбор.

***

## Ключевые настройки

```
# redis.conf

maxmemory 2gb                    # ОБЯЗАТЕЛЬНО — без лимита Redis съест всю RAM
maxmemory-policy allkeys-lru     # политика вытеснения

requirepass мойпароль            # пароль

hz 10                            # частота фоновых задач (10–100)
lazyfree-lazy-eviction yes       # удаление в фоне, не блокирует event loop

tcp-backlog 511                  # очередь входящих соединений

# Отключить persistence для кэша
save ""
appendonly no

```

## Мониторинг и диагностика

### INFO — главная команда

```
redis-cli INFO all           # всё сразу
redis-cli INFO memory        # память
redis-cli INFO stats         # hit/miss, команды
redis-cli INFO clients       # подключения
redis-cli INFO replication   # репликация
redis-cli INFO keyspace      # количество ключей
redis-cli INFO persistence   # состояние BGSAVE/AOF

```

### Память

```
redis-cli INFO memory

```

| Метрика                      | Норма   | Проблема                                  |
| ---------------------------- | ------- | ----------------------------------------- |
| `mem_fragmentation_ratio`    | 1.0–1.5 | >1.5 фрагментация, <1.0 swap — катастрофа |
| `evicted_keys`               | 0       | Растёт = памяти не хватает                |
| `used_memory` vs `maxmemory` | <80%    | Близко к лимиту = скоро eviction          |

### Hit Rate — главная метрика кэша

```
redis-cli INFO stats | grep -E "keyspace_hits|keyspace_misses"
# hit_rate = hits / (hits + misses) × 100%

```

**Норма:** >90%. Если 40–50% — кэш почти не помогает. Причины: TTL слишком короткий, память кончается, запросы идут по уникальным ключам.

### Подключения

```
redis-cli INFO clients

```

* `connected_clients` — текущее количество
* `blocked_clients` — ждут блокирующих команд (BLPOP и др.)
* `rejected_connections` — отклонённые подключения (>0 = проблема)

### Latency

```
redis-cli --latency              # живая latency
redis-cli --latency -i 1         # обновлять каждую секунду
redis-cli LATENCY LATEST         # последние спайки
redis-cli LATENCY HISTORY event  # история по событию

```

**Норма в локальной сети:** десятые доли миллисекунды. Спайки 10–100мс — ищи причину: BGSAVE, фрагментация, тяжёлая команда.

### SLOWLOG — медленные команды

```
redis-cli CONFIG SET slowlog-log-slower-than 10000   # порог 10мс (в микросекундах)
redis-cli SLOWLOG GET 25         # последние 25 медленных команд
redis-cli SLOWLOG LEN            # количество записей
redis-cli SLOWLOG RESET          # очистить

```

### BGSAVE — фоновое сохранение

```
redis-cli INFO persistence | grep rdb_bgsave_in_progress
# 1 = идёт прямо сейчас → возможен latency spike

```

Периодические спайки с интервалом во время теста = первым делом проверь BGSAVE.

### MONITOR — все команды в реальном времени

```
redis-cli MONITOR

```

> ⚠️ Снижает производительность на 50%+. Только для кратковременной диагностики, никогда под нагрузкой.

## Опасные команды

| Команда                   | Проблема                             | Замена                             |
| ------------------------- | ------------------------------------ | ---------------------------------- |
| `KEYS *`                  | Блокирует Redis, O(N) по всем ключам | `SCAN 0 MATCH * COUNT 100`         |
| `FLUSHALL` / `FLUSHDB`    | Удаляет всё мгновенно                | Блокировать через `rename-command` |
| `SMEMBERS` на большом Set | O(N), возвращает всё                 | `SSCAN`                            |
| `HGETALL` на большом Hash | O(N)                                 | `HSCAN`                            |
| `DEBUG SLEEP 10`          | Усыпляет Redis на N секунд           | Никогда в production               |

```
# SCAN — безопасная альтернатива KEYS *
SCAN 0 MATCH user:* COUNT 100
# Возвращает курсор + пачку ключей
# Вызываешь снова пока курсор не вернёт 0

```

## Distributed Locks (Redlock) — для Zeebe

Когда несколько инстансов Zeebe обрабатывают задачи параллельно — нужна распределённая блокировка.

```
# Простая блокировка через один инстанс
SET lock:job_123 worker_id NX PX 30000
# NX = только если не существует
# PX 30000 = TTL 30 секунд (автоматически снимется если воркер упал)

```

**Redlock** — для нескольких инстансов Redis (обычно 5). Блокировка считается полученной если >N/2 инстансов ответили успехом. Добавляет latency — учитывай в нагрузочной модели.

## Ответ на собесе — диагностика Redis под нагрузкой

> "Начинаю с `INFO memory` — смотрю `evicted_keys` и `fragmentation_ratio`. Затем `INFO stats` — считаю hit rate. Если hit rate низкий — анализирую TTL и паттерн нагрузки. Параллельно запускаю `--latency` чтобы видеть задержки в реальном времени. Если есть периодические спайки — проверяю `rdb_bgsave_in_progress` на совпадение по времени. Смотрю `SLOWLOG` на тяжёлые команды. Если есть rejected\_connections — проверяю `maxclients` и `tcp-backlog`."

## Модель выполнения: почему Redis быстрый и где его предел

- Команды выполняются **в одном потоке** (event loop на epoll). Отсюда атомарность и отсутствие блокировок, но и предел: одна «тяжёлая» команда (O(N) на большом ключе, `KEYS *`, Lua-скрипт на 200 мс) **останавливает всех клиентов**.
- С Redis 6 есть **I/O threads** (`io-threads 4`, `io-threads-do-reads yes`): чтение из сокетов и разбор протокола/запись ответов — параллельно, выполнение команд — по-прежнему в одном потоке. Помогает, когда упираемся в сетевую обработку (много клиентов, большие ответы), а не в сами команды.
- Фоновые потоки: ленивое удаление (`lazyfree-*`, `UNLINK` вместо `DEL` для больших ключей), fsync AOF.
- Предел одного инстанса — обычно **100–200 тыс. простых операций/с на ядро** главного потока; дальше — pipeline, шардирование (Cluster) или I/O threads.

**Признак упора:** процесс `redis-server` грузит **одно ядро на ~100 %**, latency растёт, при этом остальные ядра свободны.

## Сеть и Redis

### Время запроса почти целиком — сеть

```
GET выполняется на сервере за ~1–5 мкс
RTT в одном ЦОДе ≈ 200–500 мкс
→ 99 % времени запроса — сеть

Последовательно 1000 GET: 1000 × 0,3 мс = 300 мс
Pipeline из 1000 GET:     ~1 RTT + 1000 × 3 мкс ≈ 3–4 мс   (в ~80 раз быстрее)
MGET 1000 ключей:          то же, одной командой
```

Поэтому для Redis главные оптимизации — **pipeline, MGET/MSET, Lua-скрипты** (несколько операций за один RTT), а Redis на другом конце медленной сети (другой ЦОД, RTT 3 мс) теряет большую часть смысла.

### Соединения

- `maxclients` (10 000) — при превышении новые клиенты получают ошибку `max number of clients reached`; лимит FD процесса должен быть больше.
- Пул соединений на клиенте (Jedis `JedisPool` — `maxTotal` 8 по умолчанию!, Lettuce — одно мультиплексированное соединение на всех, redis-py — `ConnectionPool(max_connections=...)`).
- Jedis с `maxTotal=8` при 200 потоках приложения → 192 потока ждут соединение из пула; в метриках Redis всё прекрасно, а latency приложения высокая.
- `timeout 0` (сервер не закрывает idle-соединения) + фаервол/NAT с idle timeout → мёртвые соединения в пуле клиента. `tcp-keepalive 300` (с Redis 3.2.1) — сервер шлёт keepalive; на клиенте — проверка соединения перед использованием (`testOnBorrow`) или keepalive.
- `tcp-backlog 511` ограничен `net.core.somaxconn` ([[02 Сеть — пропускная способность, фаерволы, узкие места]], раздел 4).

### Буферы клиентов

У каждого клиента есть выходной буфер на сервере. Медленный клиент (подписчик Pub/Sub, который не успевает читать; большой ответ `HGETALL` на миллион полей) накапливает буфер в памяти Redis:

```
client-output-buffer-limit normal 0 0 0
client-output-buffer-limit replica 256mb 64mb 60
client-output-buffer-limit pubsub 32mb 8mb 60
# pubsub-клиент, накопивший 32 МБ (или 8 МБ дольше 60 с), отключается
```

`CLIENT LIST` → поля `omem` (память выходного буфера), `qbuf` (входной), `age`, `idle`, `cmd`.

### Пропускная способность

Большие значения (100 КБ JSON в одном ключе) × высокий RPS упираются в сеть: 10 000 GET/с × 100 КБ = 1 ГБ/с ≈ 8 Гбит/с. Метрики: `instantaneous_input_kbps`, `instantaneous_output_kbps` в `INFO stats`. Решения: сжатие на клиенте, хранение только нужных полей (Hash), локальный кэш в приложении для самых горячих ключей.

### Redis Cluster и сеть

- Клиент должен знать топологию: при обращении не к тому узлу приходит `-MOVED 3999 10.0.0.5:6379` → лишний RTT. «Умные» клиенты (Lettuce, JedisCluster, redis-py-cluster) кэшируют карту слотов.
- Порты: `6379` клиентский и **`16379`** (порт + 10000) — шина кластера (cluster bus) для обмена состоянием между узлами. Закрытый фаерволом 16379 → узлы считают друг друга недоступными, failover-ы.
- Sentinel: порт 26379; клиент спрашивает у Sentinel адрес мастера.

## Большие и горячие ключи

```bash
redis-cli --bigkeys          # самые большие ключи каждого типа (сканирует SCAN-ом, безопасно)
redis-cli --memkeys          # по памяти
redis-cli --hotkeys          # самые частые (нужна политика maxmemory-policy *-lfu)
redis-cli MEMORY USAGE user:42
redis-cli OBJECT ENCODING user:42   # listpack/hashtable — компактная или полная кодировка
```

- **Большой ключ** (Hash на 5 млн полей, List на 10 млн): `DEL` блокирует сервер на секунды (использовать `UNLINK`), `HGETALL` — огромный ответ, миграция слота в Cluster зависает, репликация — всплески.
- **Горячий ключ**: в Cluster все запросы к нему идут на один узел → он упирается в CPU, остальные простаивают. Решения: локальный кэш, копии ключа с суффиксами (`key:{1..N}`), шардирование значения.

## Метрики (redis_exporter) и что они значат

| Метрика | Норма / тревога |
|---------|-----------------|
| `redis_commands_processed_total` (rate) | ops/s |
| `redis_commands_duration_seconds_total` / `_calls_total` по командам | средняя длительность команды: какие команды тяжёлые |
| `redis_connected_clients`, `redis_rejected_connections_total` | rejected > 0 — лимиты |
| `redis_blocked_clients` | клиенты в BLPOP и т.п. |
| `redis_memory_used_bytes` vs `redis_memory_max_bytes` | > 80–90 % — скоро eviction |
| `redis_mem_fragmentation_ratio` | 1,0–1,5 норма; < 1 — swap |
| `redis_evicted_keys_total`, `redis_expired_keys_total` | вытеснение под нагрузкой |
| `redis_keyspace_hits_total` / `_misses_total` | hit rate > 90 % для кэша |
| `redis_rdb_bgsave_in_progress`, `redis_aof_rewrite_in_progress` | совпадают ли со всплесками latency |
| `redis_latest_fork_usec` | длительность fork: десятки–сотни мс на больших инстансах |
| `redis_connected_slaves`, `redis_master_repl_offset` vs offset реплик | лаг репликации |
| `redis_cpu_sys_seconds_total`, `redis_cpu_user_seconds_total` | rate ≈ 1 → главный поток упёрся |
| `redis_net_input_bytes_total`, `redis_net_output_bytes_total` | сеть |

## Поиск узких мест в Redis — методика

```
1. Где latency: в Redis или до него?
   redis-cli --latency с хоста приложения vs с самого сервера Redis → разница = сеть
   LATENCY LATEST / LATENCY DOCTOR → внутренние события (fork, aof, команды)
   Клиент: ожидание соединения из пула (Jedis maxTotal!)
2. Главный поток: CPU redis-server ≈ 100 % одного ядра? → тяжёлые команды (SLOWLOG, commandstats)
   INFO commandstats → usec_per_call по командам
3. Память: used vs maxmemory, eviction, фрагментация, большие ключи
4. Персистентность: совпадение всплесков с BGSAVE/AOF rewrite (fork), THP включён?
5. Сеть: instantaneous_*_kbps vs канал, число клиентов, буферы клиентов (CLIENT LIST omem)
6. Cluster: перекос нагрузки по узлам (горячие ключи/слоты), MOVED-редиректы
```

## Шпаргалка: симптом → причина → решение

| Симптом | Причина | Решение |
|---------|---------|---------|
| redis-server 100 % одного ядра | тяжёлые команды / предел одного потока | SLOWLOG, commandstats, pipeline, Cluster, io-threads |
| Периодические всплески latency | fork для BGSAVE/AOF rewrite, THP | отключить persistence на кэше, THP never, реплика для бэкапов |
| В Redis быстро, в приложении медленно | пул соединений клиента мал / сеть | maxTotal пула, pipeline, близость по сети |
| `max number of clients reached` | maxclients / утечка соединений | пулы, лимиты FD |
| Hit rate низкий | TTL короткий, eviction, уникальные ключи в тесте | TTL, maxmemory, реалистичные данные НТ |
| `evicted_keys` растёт | не хватает памяти | maxmemory, меньше данных, политика |
| Один узел Cluster перегружен | горячий ключ/слот | локальный кэш, разнести ключ |
| `DEL` блокирует сервер | большой ключ | `UNLINK`, lazyfree |
| Pub/Sub клиенты отключаются | client-output-buffer-limit | быстрее читать, Streams вместо Pub/Sub |
| Узлы Cluster «теряют» друг друга | закрыт порт cluster bus (+10000) | правила фаервола |
