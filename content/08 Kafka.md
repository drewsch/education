# Apache Kafka — Полная теория

> Связанные темы: [[02 Сеть — пропускная способность, фаерволы, узкие места]] · [[01 Linux — ядро, ресурсы, метрики]] (page cache, диск) · [[15 Микросервисы и системный дизайн]] (event-driven, outbox, saga) · [[06 ClickHouse]] · [[09 Camunda Zeebe]]

## 1. Что такое Kafka и зачем она нужна

Apache Kafka — это распределённая платформа потоковой передачи событий (event streaming platform). Первоначально создана в LinkedIn, затем передана в Apache Software Foundation.

**Kafka решает три задачи:**

* **Publish / Subscribe** — как очередь сообщений, но масштабируемее
* **Хранение** — надёжное хранение потоков данных с репликацией
* **Обработка** — потоковая обработка событий в реальном времени

**Где применяется:**

* Межсервисная коммуникация в микросервисной архитектуре
* Сбор и агрегация логов и метрик
* Event Sourcing и CQRS паттерны
* CDC (Change Data Capture) — захват изменений из БД
* Потоковая аналитика в реальном времени
* Буфер между быстрым producer и медленным consumer

***

## 2. Ключевые свойства Kafka

| Свойство                           | Описание                                                                |
| ---------------------------------- | ----------------------------------------------------------------------- |
| **Распределённость**               | Данные и нагрузка распределяются по нескольким брокерам и нодам         |
| **Отказоустойчивость**             | Репликация данных гарантирует работу при падении узлов                  |
| **Высокая доступность**            | Кластер продолжает работать при выходе из строя отдельных брокеров      |
| **Надёжность и согласованность**   | Гарантии доставки (acks), ISR, механизм выбора лидера                   |
| **Высокая пропускная способность** | Батчинг, компрессия, sequential disk I/O, zero-copy transfer            |
| **Горизонтальное масштабирование** | Добавление брокеров и партиций без остановки кластера                   |
| **Интегрированность**              | Kafka Connect, Kafka Streams, Flink, Spark Streaming, сотни коннекторов |

## 3. Архитектура кластера

```
┌──────────────────────────────────────────────────────────────────┐
│                         Kafka Cluster                            │
│                                                                  │
│  ┌────────────┐      ┌────────────┐      ┌────────────┐         │
│  │  Broker 1  │      │  Broker 2  │      │  Broker 3  │         │
│  │            │      │            │      │            │         │
│  │ P0 Leader  │      │ P1 Leader  │      │ P2 Leader  │         │
│  │ P1 Follow  │      │ P2 Follow  │      │ P0 Follow  │         │
│  │ P2 Follow  │      │ P0 Follow  │      │ P1 Follow  │         │
│  └────────────┘      └────────────┘      └────────────┘         │
│         │                  │                   │                 │
│  ┌──────┴──────────────────┴───────────────────┴──────┐         │
│  │          ZooKeeper / KRaft Controller               │         │
│  │   (метаданные, состояние, адресная книга кластера)  │         │
│  └─────────────────────────────────────────────────────┘         │
└──────────────────────────────────────────────────────────────────┘

Producers ──────────────────────────────────────> Consumers

```

### 3.1 Брокер (Broker)

Брокер — отдельный сервер (нода) в кластере Kafka.

**Функции брокера:**

* **Приём сообщений** — получает данные от Producer-ов
* **Хранение сообщений** — сохраняет данные на диск в виде сегментированных логов
* **Выдача сообщений** — отдаёт данные Consumer-ам по запросу

Множество брокеров образуют **Kafka Cluster**. Брокеры обеспечивают масштабирование и репликацию.

### 3.2 ZooKeeper

> ⚠️ KRaft готов к production с Kafka 3.3, ZooKeeper объявлен устаревшим в 3.5 и **полностью удалён в Kafka 4.0** (2025). Новые кластеры — только KRaft; ZooKeeper встречается в старых инсталляциях.

Исторически ZooKeeper выполнял роль координатора:

* Хранит **состояние кластера** (какие брокеры живы, кто является лидером)
* Хранит **конфигурацию** топиков, партиций, ACL
* Является **адресной книгой** — продюсеры и консьюмеры обращаются к нему первым
* Fetch метаданных — **блокирующая операция**, может занять до 60 секунд при проблемах

### 3.3 KRaft (Kafka Raft) — новый режим без ZooKeeper

KRaft встроен прямо в брокеры. Один из брокеров становится активным контроллером через Raft-алгоритм консенсуса. Преимущества:

* Меньше компонентов в инфраструктуре
* Быстрее восстановление после сбоев
* Более предсказуемая топология

### 3.4 Kafka Controller

* Один из брокеров кластера, берущий на себя роль контроллера
* **Обеспечивает консистентность данных**
* Следит за состоянием партиций и реплик
* При падении лидера — назначает нового из ISR-кандидатов

## 4. Kafka Message (Сообщение)

Сообщение — базовая единица данных, key-value пара.

| Поле          | Тип      | Описание                                                                        |
| ------------- | -------- | ------------------------------------------------------------------------------- |
| **Key**       | `byte[]` | Ключ для маршрутизации по партициям. Одинаковый ключ → всегда одна партиция     |
| **Value**     | `byte[]` | Содержимое сообщения — любой формат: JSON, Avro, Protobuf и т.д.                |
| **Timestamp** | `long`   | Время сообщения. Устанавливается при отправке или при обработке внутри кластера |
| **Headers**   | `[]KV`   | Набор key-value пар с пользовательскими атрибутами (трейсинг, тип события)      |
| **Offset**    | `long`   | Порядковый номер внутри партиции. Устанавливается брокером, неизменяем          |

> **Важно:** Key и Value могут быть `null`. Если ключ `null` — партиция выбирается по round-robin (sticky partitioner в новых версиях).

***

## 5. Kafka Topic

**Topic** — именованный поток данных (логическая категория сообщений).

```
Topic "orders":
─────────────────────────────────────────────────────────>  время

Partition 0:  [msg0][msg1][msg2][msg3][msg4]...
                                              ↑ Producer пишет сюда

Partition 1:  [msg0][msg1][msg2]...
                              ↑ Consumer читает отсюда

Partition 2:  [msg0][msg1][msg2][msg3]...

```

**Ключевые свойства топика:**

* Продюсер пишет в топик, консьюмер читает из топика
* Внутри каждой партиции — строгий порядок (**FIFO**)
* Между партициями — порядок **не гарантируется**
* Данные **не удаляются явно** — только по TTL или по размеру
* Топик можно читать любое количество раз независимыми консьюмерами

***

## 6. Партиции (Partitions)

**Партиция** — логическая единица хранения внутри топика. Топик разбивается на партиции для параллельной обработки.

```
Topic "payments" → 3 партиции → 3 брокера

 Broker 1          Broker 2          Broker 3
──────────         ──────────        ──────────
 payments-0 (L)    payments-1 (L)    payments-2 (L)
 payments-1 (F)    payments-2 (F)    payments-0 (F)
 payments-2 (F)    payments-0 (F)    payments-1 (F)

(L) = Leader, (F) = Follower

```

### Зачем нужны партиции?

* **Параллельная запись** — продюсеры пишут в разные партиции одновременно
* **Параллельное чтение** — каждый консьюмер в группе читает свои партиции
* **Горизонтальное масштабирование** — партиции распределяются по брокерам

### Выбор партиции продюсером

```
1. Явно указана партиция в коде → используется она
        ↓
2. Указан ключ → hash(key) % num_partitions
        ↓
3. Ключ null → Sticky Partitioner (батч в одну партицию, потом следующая)

```

> ⚠️ При изменении числа партиций — маршрутизация по ключу нарушается. Число партиций планируй на старте, менять потом болезненно.

### Сколько партиций создавать?

| Ситуация                       | Рекомендация                                                          |
| ------------------------------ | --------------------------------------------------------------------- |
| Старт / неизвестная нагрузка   | 3–6 партиций                                                          |
| Высокая пропускная способность | 1 партиция на каждый Consumer в группе                                |
| Очень высокая нагрузка         | Количество партиций = пиковый throughput / throughput одного consumer |
| Максимум на брокер             | \~2000–4000 партиций на брокер                                        |

## 7. Хранение данных (Storage)

### Структура на диске

```
/kafka-logs/
├── orders-0/                        ← партиция 0 топика "orders"
│   ├── 00000000000000000000.log      ← сегмент, начинается с offset 0
│   ├── 00000000000000000000.index
│   ├── 00000000000000000000.timeindex
│   ├── 00000000000000000067.log      ← новый сегмент с offset 67
│   ├── 00000000000000000067.index
│   └── 00000000000000000067.timeindex
├── orders-1/
└── orders-2/

```

### Три файла в каждом сегменте

**`.log`****&#x20;— само сообщение**

| Offset | Position (bytes) | Timestamp     | Message                 |
| ------ | ---------------- | ------------- | ----------------------- |
| 0      | 0                | 1616418669000 | `{"id":1,"amount":500}` |
| 1      | 67               | 1616332232900 | `{"id":2,"amount":200}` |
| 2      | 134              | 1616445432100 | `{"id":3,"amount":750}` |

**`.index`****&#x20;— индекс по offset → быстрый поиск по номеру**

| Offset | Position |
| ------ | -------- |
| 0      | 0        |
| 1      | 67       |
| 2      | 134      |

**`.timeindex`****&#x20;— индекс по timestamp → быстрый поиск по времени**

| Timestamp     | Offset |
| ------------- | ------ |
| 1616418669000 | 0      |
| 1616332232900 | 1      |

### Жизненный цикл сегментов

```
Активный сегмент (запись идёт сюда)
        ↓  достигнут log.segment.bytes (1 GB) или log.roll.ms
Сегмент закрыт → становится "старым"
        ↓  прошло log.retention.ms (168 ч) или превышен log.retention.bytes
Сегмент удаляется целиком

```

> ⚠️ Если сегменты не удаляются — проверь **timestamp из будущего**. Kafka не удалит сегмент, пока его timestamp "ещё не истёк". Фикс: `log.message.timestamp.type=LogAppendTime` — тогда timestamp ставит брокер, а не продюсер.

## 8. Удаление данных (Data Retention)

> Операция явного удаления отдельного сообщения **не поддерживается!**

### Политики очистки

| Политика             | Параметр                                   | Описание                                                   |
| -------------------- | ------------------------------------------ | ---------------------------------------------------------- |
| **По времени (TTL)** | `log.retention.ms` / `log.retention.hours` | Удалять сегменты старше N часов (по умолч. 168 ч = 7 дней) |
| **По размеру**       | `log.retention.bytes`                      | Удалять старые сегменты при превышении N байт на партицию  |
| **Compaction**       | `log.cleanup.policy=compact`               | Хранить только последнее сообщение для каждого ключа       |
| **Оба сразу**        | `delete,compact`                           | Сначала compaction, потом удаление по TTL                  |

**Log Compaction** — специальный режим для хранения "последнего состояния":

```
До compaction:
  key=user1 → "Alice"
  key=user2 → "Bob"
  key=user1 → "Alicia"   ← обновление
  key=user1 → "Alex"     ← ещё одно обновление

После compaction:
  key=user2 → "Bob"
  key=user1 → "Alex"     ← только последнее значение

```

Используется для: таблиц состояний, кешей, event sourcing снапшотов.

## 9. Репликация (Replication)

Репликация — создание копий партиций на разных брокерах для отказоустойчивости.

```
Topic "orders", Partition 0, replication.factor=3

 Broker 1           Broker 2           Broker 3
──────────          ──────────         ──────────
 P0 [LEADER]        P0 [FOLLOWER]      P0 [FOLLOWER]
    ↑                    ↑                  ↑
 Read/Write          Pull from L        Pull from L

Producer → ВСЕГДА пишет в Leader
Consumer → ВСЕГДА читает из Leader (по умолчанию)

```

### In-Sync Replicas (ISR)

**ISR** — набор реплик, которые синхронизированы с лидером.

```
Leader  ──write──>  Follower 1  ✓ в ISR (отставание < replica.lag.time.max.ms)
                    Follower 2  ✓ в ISR
                    Follower 3  ✗ не в ISR (отстаёт или недоступен)

```

* Фолловеры **пуллят** данные у лидера периодически (не push, а pull!)
* Если фолловер отстаёт дольше `replica.lag.time.max.ms` (по умолч. 30 сек) — выбывает из ISR
* **ISR-реплика** = единственный кандидат на лидера при падении текущего лидера
* Не-ISR реплика может стать лидером только при `unclean.leader.election.enable=true` → **потеря данных**

### min.insync.replicas

```
replication.factor = 3
min.insync.replicas = 2   ← минимум 2 реплики должны подтвердить запись

Если ISR < min.insync.replicas → Producer получает NotEnoughReplicasException
→ запись невозможна, пока не восстановится хотя бы 1 реплика

```

**Рекомендация:**`min.insync.replicas = replication.factor - 1`

## 10. Master-Slave (Leader / Follower)

* В каждой партиции один брокер — **Leader**, остальные — **Follower**
* **Все операции чтения и записи** идут только через **Leader**
* **Kafka Controller** назначает и переназначает лидеров

```
Нормальная ситуация:          После падения Broker 1:

Broker 1: P0(L) P1(F) P2(F)  Broker 2: P0(L) P1(L) P2(F)  ← перераспределение
Broker 2: P0(F) P1(L) P2(F)  Broker 3: P0(F) P1(F) P2(L)
Broker 3: P0(F) P1(F) P2(L)

```

> ⚠️ Если вся нагрузка идёт на один брокер — значит, все лидеры находятся на нём. Нужна перебалансировка: `kafka-preferred-replica-election.sh` или `auto.leader.rebalance.enable=true`.

***

## 11. Producer (Продюсер)

Продюсер — высокопроизводительный отправитель сообщений. Пишет **только в Leader-реплику**.

### Жизненный цикл отправки

```
Producer.send(record)
    │
    ├─ 1. Fetch metadata (Bootstrap Brokers → кто лидер, где партиции)
    │       ⚠️ Блокирующая операция! Не создавай нового продюсера на каждое сообщение!
    │
    ├─ 2. Serialize (key + value → bytes через Serializer)
    │
    ├─ 3. Partition selection
    │       a) Явно указана → берём её
    │       b) Есть ключ → hash(key) % num_partitions
    │       c) Null ключ → Sticky Partitioner
    │
    ├─ 4. Compress batch (gzip / snappy / lz4 / zstd)
    │
    ├─ 5. Accumulate batch
    │       ← ждём batch.size байт ИЛИ linger.ms миллисекунд (что наступит раньше)
    │
    └─ 6. Send → Leader Broker → ждём acks

```

### Гарантии доставки (acks)

| acks         | Режим           | Что происходит                          | Риск                                          |
| ------------ | --------------- | --------------------------------------- | --------------------------------------------- |
| `0`          | Fire and forget | Не ждёт подтверждения вообще            | Сообщения теряются при любой ошибке           |
| `1`          | Leader ack      | Ждёт подтверждения только от Leader     | Потеря если Leader упал до репликации         |
| `-1` / `all` | Full ack        | Ждёт подтверждения от всех ISR + Leader | Максимальная надёжность, минимальная скорость |

### Ключевые параметры продюсера

| Параметр                                | По умолчанию       | Описание                                              |
| --------------------------------------- | ------------------ | ----------------------------------------------------- |
| `acks`                                  | `all`              | Гарантии подтверждения                                |
| `batch.size`                            | `16384` (16 KB)    | Максимальный размер батча в байтах                    |
| `linger.ms`                             | `0`                | Время ожидания перед отправкой батча                  |
| `compression.type`                      | `none`             | Тип компрессии: none, gzip, snappy, lz4, zstd         |
| `enable.idempotence`                    | `true` (≥ 3.0)     | Идемпотентная отправка (without duplicate)            |
| `retries`                               | `2147483647`       | Число повторных попыток                               |
| `max.in.flight.requests.per.connection` | `5`                | Незавершённых запросов (при idempotence=true → max 5) |
| `buffer.memory`                         | `33554432` (32 MB) | Память под буфер записи                               |
| `max.block.ms`                          | `60000`            | Время блокировки send() если буфер полон              |

## 12. Consumer (Консьюмер)

Консьюмер — высокопроизводительный получатель сообщений. Читает **из Leader-реплик** (по умолчанию).

### Как работает чтение

```
Consumer.poll(timeout)
    │
    ├─ 1. Fetch metadata (где лидер каждой партиции)
    │
    ├─ 2. Send FetchRequest к Leader брокерам
    │       (max.poll.records штук за раз, не по одному!)
    │
    ├─ 3. Deserialize (bytes → объекты через Deserializer)
    │
    ├─ 4. Process records
    │
    └─ 5. Commit offset (авто или вручную)

```

### Consumer Group

```
Topic "orders" (4 партиции):   P0   P1   P2   P3

Consumer Group "order-service":
  Consumer 1 ──────────────────> P0   P1
  Consumer 2 ──────────────────> P2   P3

Consumer Group "analytics":
  Consumer A ──────────────────> P0   P1   P2   P3   (читает всё независимо)

```

**Правила Consumer Group:**

* Каждая партиция читается **только одним** консьюмером из группы
* Один консьюмер может читать **несколько** партиций
* Если консьюмеров > партиций — лишние консьюмеры **простаивают**
* Разные группы читают **независимо**, имеют свои offsets
* При падении консьюмера — происходит **Rebalance**, партиции перераспределяются

### Rebalance (Перебалансировка)

Rebalance срабатывает при:

* Добавлении/удалении консьюмера в группе
* Изменении числа партиций
* Превышении `session.timeout.ms` (консьюмер считается мёртвым)
* Превышении `max.poll.interval.ms` (консьюмер не делает poll слишком долго)

> ⚠️ Во время Rebalance чтение **полностью останавливается** — это Stop-The-World для группы. Частые Rebalance — признак проблемы.

### Ключевые параметры консьюмера

| Параметр                  | По умолчанию | Описание                                         |
| ------------------------- | ------------ | ------------------------------------------------ |
| `max.poll.records`        | `500`        | Максимум записей за один poll()                  |
| `max.poll.interval.ms`    | `300000`     | Максимальное время обработки между poll()        |
| `session.timeout.ms`      | `45000`      | Таймаут сессии (heartbeat должен приходить чаще) |
| `heartbeat.interval.ms`   | `3000`       | Частота heartbeat к Group Coordinator            |
| `auto.offset.reset`       | `latest`     | earliest / latest / none                         |
| `enable.auto.commit`      | `true`       | Автокоммит offset                                |
| `auto.commit.interval.ms` | `5000`       | Интервал автокоммита                             |
| `fetch.min.bytes`         | `1`          | Минимум байт для возврата fetch                  |
| `fetch.max.wait.ms`       | `500`        | Ждать fetch.min.bytes этого времени              |

## 13. Offset (Смещение)

**Offset** — порядковый номер последнего обработанного сообщения в партиции для конкретной Consumer Group.

```
Топик __consumer_offsets (внутренний топик Kafka):

 Group           | Partition | Offset committed
─────────────────|───────────|─────────────────
 order-service   | orders/0  | 42
 order-service   | orders/1  | 37
 analytics       | orders/0  | 15

```

### Сценарий отказа консьюмера

```
Consumer 1 обрабатывает P0:  [0][1][2][3]✓[4]← тут упал (offset закоммичен = 3)
                                                  ↓
Rebalance → Consumer 2 берёт P0
                                                  ↓
Consumer 2 читает __consumer_offsets → видит committed = 3
Consumer 2 начинает с offset 4 → нет потерь, нет дублей (при manual commit)

```

### Типы коммитов

| Тип                       | Параметр                       | Семантика     | Риск                                          |
| ------------------------- | ------------------------------ | ------------- | --------------------------------------------- |
| **Auto commit**           | `enable.auto.commit=true`      | At least once (при синхронной обработке в цикле poll) / At most once (если обработка асинхронная) | offset коммитится при следующем poll по таймеру: упали после обработки, до коммита → дубли; обработка ушла в другой поток и упала после коммита → потеря |
| **Manual sync commit**    | `commitSync()` после обработки | At least once | Дубли при падении после обработки, до коммита |
| **Manual async commit**   | `commitAsync()`                | At least once | Дубли + нет retry при ошибке                  |
| **Custom offset storage** | Своя БД / транзакции           | Exactly once  | Сложная реализация                            |

### Устаревание офсетов

Если Consumer Group не читает партицию **> 7 дней** → offset удаляется.

Параметр: `offsets.retention.minutes` (по умолч. 10080 мин = 7 дней)

**При отсутствии сохранённого offset:**

| `auto.offset.reset` | Поведение                                    |
| ------------------- | -------------------------------------------- |
| `earliest`          | Начать с самого первого доступного сообщения |
| `latest`            | Начать с самого последнего (новые сообщения) |
| `none`              | Выбросить исключение                         |

## 14. Семантика доставки — подробный разбор

Семантика доставки — это **гарантия того, сколько раз сообщение будет обработано**.

```
Три уровня гарантий:

At most once   → 0 или 1 раз    (можем потерять, но не дублировать)
At least once  → 1 или более раз (можем дублировать, но не потерять)
Exactly once   → ровно 1 раз    (ни потерь, ни дублей)

```

### 14.1 At Most Once (не более одного раза)

**Когда возникает:** коммит offset **до** обработки сообщения.

```
Consumer получает batch [msg4, msg5, msg6]
    │
    ├─ Commit offset = 6   ← сохранили позицию
    │
    ├─ Начали обработку msg4...
    │   ↓
    ×   CRASH!             ← упали во время обработки
    
При перезапуске: читаем с offset 7 → msg4, msg5, msg6 потеряны навсегда

```

**Где применять:** метрики, статистика, логи — где потеря нескольких событий допустима, но скорость важна.

**Как настроить:**

```
# Продюсер
acks=0

# Консьюмер
enable.auto.commit=true
auto.commit.interval.ms=100   # коммитим часто, до обработки

```

***

### 14.2 At Least Once (хотя бы один раз)

**Когда возникает:** коммит offset **после** обработки, но без транзакционных гарантий.

```
Consumer получает batch [msg4, msg5, msg6]
    │
    ├─ Обработали msg4 ✓
    ├─ Обработали msg5 ✓
    ├─ Обработали msg6 ✓
    │
    ├─ Commit offset = 6...
    │   ↓
    ×   CRASH!             ← упали во время коммита
    
При перезапуске: читаем с offset 4 (последний успешный коммит)
→ msg4, msg5, msg6 обрабатываются СНОВА → дубли!

```

**Где применять:** большинство бизнес-сценариев — если сторона-получатель **идемпотентна** (т.е. повторная обработка не вредит). Например: обновление статуса заказа (повторное обновление на тот же статус — ОК).

**Как настроить:**

```
# Продюсер
acks=all
enable.idempotence=true
retries=Integer.MAX_VALUE

# Консьюмер
enable.auto.commit=false
# После обработки:
consumer.commitSync()

```

**Как бороться с дублями (идемпотентность):**

* Хранить `message_id` / `offset` в БД и проверять перед обработкой
* Делать операции идемпотентными (UPDATE вместо INSERT, UPSERT)
* Использовать уникальные ключи в БД

***

### 14.3 Exactly Once (ровно один раз)

**Когда возникает:** транзакционная запись + атомарный коммит offset.

```
Схема Kafka → Kafka (Kafka Streams / транзакции):

BEGIN TRANSACTION
    │
    ├─ Читаем msg из input-topic (P0, offset=4)
    │
    ├─ Трансформируем данные
    │
    ├─ Записываем результат в output-topic
    │
    ├─ Коммитим offset в __consumer_offsets
    │
COMMIT (атомарно!)
    │
Если падение ДО COMMIT → всё откатывается, msg обработается снова
Если падение ПОСЛЕ COMMIT → всё уже сохранено, msg не обработается повторно

```

**Exactly Once в Kafka делится на два уровня:**

**Уровень 1: Idempotent Producer** (защита от дублей при retries)

```
enable.idempotence=true
# Kafka присваивает каждому сообщению PID + sequence number
# Брокер отклоняет дубли автоматически

```

**Уровень 2: Transactional Producer** (атомарная запись в несколько партиций)

```
// Java пример
Properties props = new Properties();
props.put("transactional.id", "my-transactional-id");
props.put("enable.idempotence", "true");

KafkaProducer<String, String> producer = new KafkaProducer<>(props);
producer.initTransactions();

try {
    producer.beginTransaction();
    
    producer.send(new ProducerRecord<>("output-topic", key, value));
    producer.send(new ProducerRecord<>("output-topic-2", key, value));
    
    // Атомарный коммит offset + записанных сообщений
    producer.sendOffsetsToTransaction(offsets, consumerGroupMetadata);
    
    producer.commitTransaction();
} catch (ProducerFencedException e) {
    producer.close();
} catch (KafkaException e) {
    producer.abortTransaction();
}

```

**Уровень 3: Exactly Once в Kafka Streams**

```
// Самый простой способ — Kafka Streams делает всё сам
Properties props = new Properties();
props.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, 
          StreamsConfig.EXACTLY_ONCE_V2); // Kafka 2.5+

```

**Где применять:** финансовые транзакции, списание средств, уникальные заказы, любая операция где дубль = критическая ошибка.

**Ограничения Exactly Once:**

* Работает только внутри Kafka (Kafka → Kafka)
* Если результат идёт во внешнюю систему (БД, REST API) — нужна идемпотентность на стороне получателя
* Снижает throughput примерно на 20–30%
* Требует `transactional.id` — уникальный per producer instance

### Сравнительная таблица семантик

|                        | At Most Once  | At Least Once      | Exactly Once        |
| ---------------------- | ------------- | ------------------ | ------------------- |
| **Потеря данных**      | Возможна      | Невозможна         | Невозможна          |
| **Дубли**              | Невозможны    | Возможны           | Невозможны          |
| **Производительность** | Максимальная  | Высокая            | Умеренная (-20-30%) |
| **Сложность**          | Минимальная   | Средняя            | Высокая             |
| **acks**               | 0             | all                | all                 |
| **enable.idempotence** | false         | true               | true                |
| **Транзакции**         | Нет           | Нет                | Да                  |
| **Применение**         | Метрики, логи | Большинство кейсов | Финансы, платежи    |

## 15. Consumer Lag (Задержка потребителя)

**Consumer Lag** — разница между последним записанным offset (Log End Offset) и последним прочитанным offset (Consumer Committed Offset).

```
Partition P0:

  [msg0][msg1][msg2][msg3][msg4][msg5][msg6][msg7]
                          ↑                      ↑
                   committed offset=4      Log End Offset=7

  Consumer Lag = 7 - 4 = 3 сообщения

```

**Причины высокого lag:**

* Consumer слишком медленно обрабатывает сообщения
* Слишком мало инстансов Consumer в группе
* GC паузы на стороне Consumer
* Внешние зависимости (медленная БД, сторонний API)
* Резкий всплеск нагрузки у Producer

**Как мониторить:**

```
# Проверить lag через CLI
kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --group my-consumer-group \
  --describe

# Вывод:
# GROUP          TOPIC    PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
# my-group       orders   0          42              47              5
# my-group       orders   1          38              38              0

```

**Решения при высоком lag:**

1. Увеличить число партиций + Consumer инстансов
2. Оптимизировать логику обработки в Consumer
3. Увеличить `max.poll.records` (обрабатывать больше за раз)
4. Использовать асинхронную обработку внутри Consumer
5. Вертикальное масштабирование Consumer (больше RAM/CPU)

## 17. Оптимизация производительности

### 17.1 Оптимизация Producer

**Батчинг и linger.ms — главные рычаги throughput**

```
# Дефолт: linger.ms=0 → каждое сообщение отдельным запросом
Producer: [msg] → [msg] → [msg] → [msg]   (4 запроса)

# С батчингом: linger.ms=10 → ждём 10мс, собираем батч
Producer: [msg, msg, msg, msg] → broker   (1 запрос)

```

| Параметр           | Для throughput              | Для latency   |
| ------------------ | --------------------------- | ------------- |
| `linger.ms`        | 10–50 мс                    | 0–5 мс        |
| `batch.size`       | 65536–262144 (64-256 KB)    | 16384 (16 KB) |
| `compression.type` | `lz4` или `snappy`          | `none`        |
| `acks`             | `1` (если допустима потеря) | `all`         |
| `buffer.memory`    | 64–128 MB                   | по умолчанию  |

**Компрессия — бесплатный буст для throughput:**

| Алгоритм | Скорость сжатия | Степень сжатия | Скорость декомпрессии | Применение                             |
| -------- | --------------- | -------------- | --------------------- | -------------------------------------- |
| `none`   | —               | —              | —                     | Маленькие сообщения, уже сжатые данные |
| `gzip`   | Медленная       | Высокая        | Средняя               | Когда диск/сеть важнее CPU             |
| `snappy` | Высокая         | Средняя        | Высокая               | **Хороший баланс, рекомендуется**      |
| `lz4`    | Очень высокая   | Средняя        | Очень высокая         | **Лучший выбор для low-latency**       |
| `zstd`   | Высокая         | Очень высокая  | Высокая               | **Лучший выбор для high-throughput**   |

> Компрессия применяется на уровне **батча**, а не отдельного сообщения. Чем больше батч → тем лучше сжатие.

**Идемпотентный продюсер — производительность без потерь надёжности:**

```
enable.idempotence=true
max.in.flight.requests.per.connection=5   (не более 5 при idempotence)
retries=Integer.MAX_VALUE
acks=all

```

***

### 17.2 Оптимизация Consumer

**max.poll.records — сколько брать за раз**

```
# Маленькое значение → больше round-trips к брокеру
max.poll.records=50   (50 записей → частые запросы)

# Большое значение → меньше запросов, больше данных за раз
max.poll.records=1000  (1000 записей → редкие, но большие запросы)

⚠️ Баланс: если обработка 1000 записей займёт > max.poll.interval.ms → Rebalance!

```

**fetch.min.bytes + fetch.max.wait.ms — long polling**

```
fetch.min.bytes=65536         # ждать хотя бы 64 KB данных
fetch.max.wait.ms=500         # или 500мс — что наступит раньше

Результат: меньше пустых запросов, меньше нагрузка на брокер

```

**Параллельная обработка внутри Consumer:**

```
// ❌ Плохо: sequential обработка
for (ConsumerRecord<K,V> record : records) {
    processRecord(record);  // блокирующий вызов
}

// ✓ Хорошо: параллельная обработка с ручным коммитом
ExecutorService executor = Executors.newFixedThreadPool(8);
List<Future<?>> futures = new ArrayList<>();

for (ConsumerRecord<K,V> record : records) {
    futures.add(executor.submit(() -> processRecord(record)));
}

// Дождаться всех, потом коммит
for (Future<?> f : futures) f.get();
consumer.commitSync();

```

***

### 17.3 Оптимизация брокера

**Дисковая подсистема — самое важное для Kafka:**

```
✓ Использовать SSD или NVMe вместо HDD (в 10-100 раз быстрее)
✓ RAID 10 для баланса надёжности и скорости
✓ Отдельные диски для Kafka и OS
✓ XFS или ext4 с noatime
✓ Монтировать с опцией noatime (отключить запись времени доступа)

```

**Операционная система:**

```
# Увеличить лимиты файловых дескрипторов
ulimit -n 100000

# vm.swappiness — минимизировать своп
vm.swappiness=1

# Увеличить грязные страницы (dirty pages) для буферизации
vm.dirty_background_ratio=5
vm.dirty_ratio=60

# Сетевые буферы
net.core.rmem_max=134217728
net.core.wmem_max=134217728
net.ipv4.tcp_rmem=4096 65536 134217728
net.ipv4.tcp_wmem=4096 65536 134217728

```

**JVM настройки для брокера:**

```
# Оптимальные настройки для Kafka broker
KAFKA_HEAP_OPTS="-Xmx6g -Xms6g"
KAFKA_JVM_PERFORMANCE_OPTS="-XX:+UseG1GC 
  -XX:MaxGCPauseMillis=20 
  -XX:InitiatingHeapOccupancyPercent=35 
  -XX:+ExplicitGCInvokesConcurrent"

# G1GC → предсказуемые паузы
# MaxGCPauseMillis=20 → цель: не более 20мс на GC
# Heap не более 6-8 GB → остальное идёт на Page Cache

```

**Page Cache — секрет скорости Kafka:**

```
Kafka активно использует OS Page Cache для чтения.
Consumer часто читает то, что только что записал Producer
→ данные ещё в Page Cache → нет обращения к диску!

Рекомендация: оставлять 50-60% RAM под Page Cache.
На сервере с 32 GB RAM:
  JVM Heap: 6 GB
  OS + Kafka threads: 2 GB
  Page Cache: ~24 GB  ← как можно больше!

```

**Zero-Copy — механизм быстрой передачи:**

```
Без Zero-Copy:
  Диск → OS Buffer → JVM Heap → Socket Buffer → Сеть
  (4 копирования данных)

С Zero-Copy (sendfile syscall):
  Диск → OS Buffer ──────────────────────> Сеть
  (1-2 копирования)

Kafka использует FileChannel.transferTo() → ускорение в 2-4x для Consumer!

```

### 17.4 Оптимизация топиков и партиций

**Оптимальное число партиций:**

```
Формула:
  num_partitions = max(throughput_target / throughput_per_consumer,
                       throughput_target / throughput_per_producer)

Пример:
  Target throughput: 1 GB/s
  Consumer throughput: 50 MB/s per instance
  → num_partitions = 1000 / 50 = 20 партиций минимум

```

**Репликация и надёжность:**

```
Продакшн конфигурация:
  replication.factor=3
  min.insync.replicas=2
  unclean.leader.election.enable=false   ← никогда не выбирать не-ISR лидера
  
Для некритичных данных (логи, метрики):
  replication.factor=2
  min.insync.replicas=1

```

**Retention — баланс между надёжностью и расходом диска:**

```
# Временное хранение (стандарт)
log.retention.hours=168     # 7 дней
log.retention.bytes=-1      # без лимита по размеру

# Компактное хранение (таблицы состояний)
log.cleanup.policy=compact
log.min.cleanable.dirty.ratio=0.1
log.segment.ms=3600000      # компактируем каждый час

# Комбо: компакция + TTL
log.cleanup.policy=compact,delete
log.retention.ms=604800000  # 7 дней

```

| **Потеря сообщений**            | Данные пропали                  | Проверить `acks`, `min.insync.replicas`, `retries`       |

## 19. Валидация, Dead Letter Queue, бизнес-ошибки, API vs Kafka

### 19.1 Продюсинг и консьюминг — полный путь сообщения

```
Клиент ──HTTP──> API (валидация №1) ──> Producer ──> Kafka topic ──> Consumer (валидация №2)
                                                                     │
                                                         ┌───────────┼─────────────────┐
                                                         ▼           ▼                 ▼
                                                     успех     техническая ошибка   невалидно /
                                                     commit    (БД недоступна)      нарушение бизнес-правил
                                                               → retry               → DLQ / отклонение
```

### 19.2 Валидация payload-ов: на каком уровне что проверять

| Уровень | Что проверяет | Что делать при ошибке |
|---------|--------------|-----------------------|
| **API** (до отправки в Kafka) | формат JSON, обязательные поля, типы, длины, enum-значения, схема (JSON Schema / OpenAPI), права клиента | сразу вернуть клиенту `400` / `422` — **в Kafka не отправлять**. Клиент может исправить и повторить |
| **Схема в брокере** (Schema Registry + Avro/Protobuf) | совместимость структуры сообщения со схемой топика | продюсер получает ошибку сериализации — сообщение не уходит |
| **Консьюмер: десериализация** | можно ли вообще прочитать сообщение | «ядовитое сообщение» (poison pill) → DLQ, иначе консьюмер будет падать на нём бесконечно |
| **Консьюмер: бизнес-валидация** | существует ли клиент, достаточно ли лимита, допустим ли переход статуса | зависит от вида ошибки (раздел 19.4) |

**Почему валидация нужна и в API, и в консьюмере:**

- в топик пишут не только через ваш API (другие продюсеры, ручные выгрузки, старые версии сервиса);
- бизнес-правила проверяются на **момент обработки**, а не на момент приёма (лимит мог исчерпаться, пока сообщение лежало в очереди);
- консьюмер не должен доверять входу — иначе одно кривое сообщение роняет обработку партиции.

**Poison pill — главная опасность без DLQ:**

```
Консьюмер читает offset 1000 → ошибка десериализации → исключение → offset не закоммичен
→ рестарт/повтор poll → снова offset 1000 → снова ошибка → ...
Партиция ЗАСТРЯЛА: все сообщения после 1000 не обрабатываются, lag растёт бесконечно
(в Spring Kafka без ErrorHandlingDeserializer — бесконечный цикл ошибок в логе)
```

### 19.3 Dead Letter Queue (DLQ)

**DLQ** — отдельный топик (например, `orders.events.DLT`), куда отправляются сообщения, которые не удалось обработать, чтобы **не блокировать** обработку остальных.

```
orders.events ──> Consumer ──ошибка──> retry (N раз с задержкой) ──всё ещё ошибка──> orders.events.DLT
                                                                                     │
                                                       алерт + разбор человеком / автоматический
                                                       повтор после исправления (replay из DLT)
```

**Что класть в сообщение DLQ** (обычно в заголовки):

- исходный топик, партиция, offset, ключ, timestamp;
- класс и текст исключения, стектрейс (кратко);
- число попыток, время первой и последней попытки;
- идентификатор консьюмер-группы и версии сервиса.

**Схемы повторов:**

| Схема | Как | Плюсы | Минусы |
|-------|-----|-------|--------|
| Блокирующий retry в консьюмере | повторить N раз с паузой, не двигаясь дальше | простота, порядок сохраняется | партиция стоит всё время повторов; долгие паузы → превышение `max.poll.interval.ms` → rebalance |
| **Retry-топики** (non-blocking) | `orders.retry.10s` → `orders.retry.1m` → `orders.retry.10m` → `orders.DLT` | основной поток не блокируется | **порядок по ключу нарушается**: следующее сообщение того же заказа может обработаться раньше повторяемого |
| Сразу в DLQ | без повторов | для заведомо неисправимых ошибок (невалидный формат) | — |

В Spring Kafka: `DefaultErrorHandler` + `DeadLetterPublishingRecoverer` (блокирующие ретраи + DLT), `@RetryableTopic` (неблокирующие retry-топики).

**Метрики и алерты:** скорость записи в DLT (> 0 — алерт), размер DLT, возраст самого старого сообщения в DLT. DLQ без мониторинга = «чёрная дыра», куда молча уходят данные.

### 19.4 Поведение системы при нарушении бизнес-логики

Ключевое — **различать типы ошибок**: от этого зависит, повторять или нет.

| Тип ошибки | Пример | Повтор поможет? | Что делать |
|------------|--------|-----------------|-----------|
| **Транзиентная техническая** | БД недоступна, таймаут HTTP, `RESOURCE_EXHAUSTED`, rebalance | **да** | retry с экспонентой; если долго — остановить консьюмер (pause), а не сливать всё в DLQ |
| **Невалидный формат** | не парсится JSON, нет обязательного поля, неизвестная версия схемы | нет | сразу DLQ + алерт (ошибка продюсера) |
| **Нарушение бизнес-правила** | лимит превышен, клиент заблокирован, недопустимый переход статуса «закрыт → оплачен» | нет | это **ожидаемый бизнес-исход**, а не сбой: опубликовать событие отказа (`PaymentRejected`), записать статус, уведомить; **не DLQ** |
| **Нарушение порядка/зависимости** | пришёл `OrderPaid` раньше `OrderCreated` (другая партиция, ретраи) | возможно, позже | отложить (retry-топик с задержкой), «parking lot», или хранить и применить при появлении предка |
| **Дубликат** | сообщение уже обработано (at-least-once) | — | идемпотентность: пропустить (inbox, уникальный ключ) |
| **Баг в коде консьюмера** | NPE на определённых данных | после фикса — да | DLQ + replay после исправления |

**Антипаттерны:**

- отправлять **всё** в DLQ: при недоступности БД за минуту в DLQ уедут миллионы нормальных сообщений, и разбор превратится в аварию;
- бесконечный retry невалидного сообщения — партиция стоит;
- бизнес-отказ как исключение → ретраи → DLQ: отказ по лимиту — нормальный результат, его надо обработать бизнес-логикой;
- игнорировать ошибку и коммитить offset — молчаливая потеря данных.

**При массовой технической ошибке** (упала БД) правильнее **приостановить** потребление (`consumer.pause(partitions)` / остановить контейнер), чтобы lag копился в Kafka, а после восстановления — продолжить. Kafka для этого и нужна: она хранит сообщения по retention.

**Сага и компенсации.** Если бизнес-ошибка возникла на середине многошагового процесса (деньги списаны, товара нет), обработчик публикует событие, запускающее **компенсации** в предыдущих сервисах — [[15 Микросервисы и системный дизайн]], разделы 8–10.

### 19.5 Запись напрямую через API vs через Kafka

```
Вариант A (синхронно):   Клиент ──> API ──> БД ──> ответ 200/201 (данные записаны)
Вариант B (через Kafka): Клиент ──> API ──> Kafka ──> ответ 202 Accepted
                                              └──> Consumer ──> БД (позже)
```

| Критерий | Напрямую через API в БД | Через Kafka |
|----------|-------------------------|-------------|
| Latency ответа клиенту | время записи в БД (fsync, индексы, блокировки) | время записи в Kafka (`acks=all` — до ISR реплик), обычно меньше и стабильнее |
| Что знает клиент в ответе | данные **точно записаны** и валидны по бизнес-правилам | данные **приняты**, но ещё не обработаны (`202 Accepted`) |
| Согласованность | сразу (read-your-writes) | **eventual**: чтение сразу после записи может не найти данные |
| Пиковая нагрузка | БД должна выдержать пик напрямую; при перегрузке — таймауты и ошибки клиентам | Kafka **буферизует** пик; консьюмеры обрабатывают с постоянной скоростью; растёт lag, а не ошибки |
| Отказ БД | API отвечает ошибками, клиент должен ретраить | приём продолжается, данные копятся в Kafka и дозаписываются после восстановления |
| Бизнес-валидация | синхронно — клиент сразу получает отказ | асинхронно — отказ приходит позже (событие, callback, статус по `GET`) |
| Порядок операций | в рамках транзакций | только внутри партиции (ключ = ID сущности) |
| Дубли | транзакции, уникальные ключи | at-least-once → идемпотентный консьюмер обязателен |
| Сложность | ниже | выше: схемы, DLQ, мониторинг lag, статусы обработки |
| Несколько потребителей одних данных | каждый должен быть вызван/опрашивать | новые консьюмер-группы читают тот же топик независимо |
| Наблюдаемость | трейс одного запроса | трейс через брокер (заголовки `traceparent`), lag, end-to-end latency |

**Когда что выбирать:**

- **Напрямую**: клиенту нужен немедленный и окончательный результат (проверка баланса и списание, бронирование «последнего места»), низкая нагрузка, простота важнее.
- **Через Kafka**: высокие и неравномерные пики, данные нужны нескольким системам, допустима задержка обработки, важно не терять приём при сбоях хранилища (приём заявок, телеметрия, события аудита, интеграции).
- **Гибрид**: синхронная проверка формата и базовых правил в API (быстрый `422`), запись заявки в БД + outbox (гарантированное принятие), дальнейшая обработка асинхронно.

**Как это сравнить на НТ:**

```
Метрики варианта A: RPS, p95/p99 ответа API, ошибки под пиком, CPU/IO БД, пулы соединений
Метрики варианта B:
  — p99 ответа API (до 202) — обычно ниже и стабильнее
  — producer: request-latency, record-error-rate, buffer-exhausted-rate
  — consumer lag и его динамика: стабилизируется ли после пика? за сколько разгребается?
  — END-TO-END latency: от приёма в API до записи в БД (timestamp в сообщении → метрика в консьюмере)
  — скорость записи в DLT, доля бизнес-отказов
  — пропускная способность консьюмеров = максимальная устойчивая нагрузка (выше неё lag растёт бесконечно)

Профиль «ступенька с пиком»: базовая нагрузка → пик ×3 на 10 минут → базовая
  A: видно, где БД перестаёт справляться (рост latency и ошибок)
  B: видно, сколько копится lag и за сколько минут он рассасывается после пика
```

## 20. Сеть и Kafka

### 20.1 Порты и подключение

| Порт | Назначение |
|------|-----------|
| 9092 | клиентский (PLAINTEXT) |
| 9093 | часто — TLS/SASL или контроллеры KRaft |
| 9094+ | дополнительные listeners (внешний доступ) |
| JMX (9999 / свой) | метрики |

**advertised.listeners — самая частая сетевая ошибка.** Клиент подключается к bootstrap-серверу, получает **метаданные** со списком брокеров в виде `advertised.listeners` и дальше подключается **напрямую к каждому брокеру-лидеру** по этим адресам. Если брокер объявил внутренний адрес (`kafka-0.kafka-headless.svc:9092`), а клиент снаружи кластера — bootstrap проходит, но все последующие подключения падают. Для внешних клиентов нужны отдельные listeners с внешними адресами.

Следствие для фаерволов: клиенту нужен доступ **ко всем брокерам**, а не только к bootstrap-адресу.

### 20.2 Пропускная способность

```
Входящий поток продюсеров: 100 МБ/с
replication.factor = 3 → каждый байт уходит ещё на 2 фолловера: +200 МБ/с трафика между брокерами
3 консьюмер-группы читают всё → 300 МБ/с исходящего к консьюмерам
Итого через сеть кластера: 100 + 200 + 300 = 600 МБ/с ≈ 5 Гбит/с
На брокер (3 брокера, лидеры равномерно): ~200 МБ/с ≈ 1,6 Гбит/с → канал 1 Гбит/с НЕ хватит
```

Сеть — частый первый предел Kafka-кластера, раньше диска и CPU. Метрики: `BytesInPerSec`, `BytesOutPerSec`, `ReplicationBytesInPerSec` и трафик интерфейсов ([[01 Linux — ядро, ресурсы, метрики]], раздел 6).

**Сжатие на продюсере** (lz4/zstd) уменьшает и сетевой трафик, и диск: батч сжимается один раз продюсером и хранится/передаётся сжатым.

### 20.3 Задержки и окна

- Межрегиональная репликация (MirrorMaker 2) на длинном канале упирается в BDP: увеличить `socket.send.buffer.bytes`/`socket.receive.buffer.bytes` (−1 = автоподстройка ОС) и число задач ([[02 Сеть — пропускная способность, фаерволы, узкие места]], раздел 2.4).
- `linger.ms` и `batch.size` уменьшают число запросов → меньше влияние RTT.
- Консьюмер в другом ЦОДе: каждый fetch = RTT; `fetch.min.bytes` + `fetch.max.wait.ms` и `max.partition.fetch.bytes` (1 МБ) определяют, сколько данных приходит за один RTT. Для «чтения с ближайшей реплики» — rack awareness (`client.rack`, `replica.selector.class`).

### 20.4 Соединения и таймауты

- Каждый клиент держит TCP-соединение к каждому брокеру, с которым работает. 500 подов × 3 брокера = 1500 соединений на брокер — норма, но тысячи коротких соединений (новый продюсер на каждое сообщение) убьют брокер (`connection-creation-rate`, CPU на SASL/TLS-рукопожатия).
- `connections.max.idle.ms` (брокер 10 мин, клиент 9 мин) — idle-соединения закрываются; фаерволы с меньшим idle timeout рвут их раньше — ошибки `Disconnected` на клиенте.
- `request.timeout.ms` (30 с), `delivery.timeout.ms` (120 с) у продюсера — общее время с ретраями.
- TLS между клиентами и брокерами: zero-copy (`sendfile`) **не работает** с TLS — данные приходится шифровать в пространстве пользователя → CPU брокера заметно растёт на чтении.

## 21. Поиск узких мест в Kafka — методика

```
1. Где растёт задержка: продюсер, брокер или консьюмер?
   Продюсер: request-latency-avg, record-queue-time-avg (ждёт в буфере), buffer-exhausted-rate
   Брокер:   RequestQueueTimeMs, LocalTimeMs, RemoteTimeMs, ResponseSendTimeMs (разбивка времени запроса)
   Консьюмер: records-lag-max, время обработки poll-пачки, join-rate (rebalance)

2. Брокер:
   RequestHandlerAvgIdlePercent < 30 % → потоки обработки заняты (num.io.threads)
   NetworkProcessorAvgIdlePercent < 30 % → сетевые потоки (num.network.threads)
   RemoteTimeMs большой у Produce → ждём фолловеров (acks=all) → сеть/диск фолловеров
   UnderReplicatedPartitions > 0 → фолловеры не успевают
   Диск: iostat — запись сегментов, чтение консьюмеров, отстающих от хвоста (не из page cache!)
   Сеть: BytesIn/Out против канала

3. Консьюмер:
   lag растёт → время обработки × записей > возможностей → больше партиций/консьюмеров,
     быстрее обработка (батч-запись в БД), параллельная обработка внутри
   частые rebalance → max.poll.interval.ms / GC-паузы / долгая обработка пачки
   DLT растёт → ошибки обработки (раздел 19)

4. Перекос: одна партиция горячая (плохой ключ) → lag только на ней
```

**Ключевое про page cache:** консьюмер, читающий «хвост» (свежие данные), читает из page cache без диска. Консьюмер, догоняющий большой lag (читает старые данные), идёт на диск и вытесняет page cache у остальных — после пика с большим lag латентность **всех** консьюмеров может вырасти ([[01 Linux — ядро, ресурсы, метрики]], раздел 3.3).
