# Zeebe / Camunda — полный конспект

> Связанные темы: [[15 Микросервисы и системный дизайн]] (оркестрация, saga) · [[03 Протоколы взаимодействия]] (gRPC) · [[05 PostgreSQL]] (Camunda 7) · [[10 JVM]]

## BPM и зачем нужен Zeebe

**BPM (Business Process Management)** — управление бизнес-процессами. Последовательность шагов с условиями, таймаутами, параллельными ветками.

**Проблема без движка:** логика разбросана по коду, таймауты сложно отслеживать, при падении сервиса непонятно на каком шаге остановились.

**Zeebe** — движок оркестрации процессов. Хранит состояние каждого экземпляра, управляет переходами, обрабатывает таймауты и ошибки централизованно.

***

## Camunda 7 vs Camunda 8 (Zeebe)

|                              | Camunda 7                         | Camunda 8 (Zeebe)               |
| ---------------------------- | --------------------------------- | ------------------------------- |
| Тип                          | Java библиотека внутри приложения | Отдельный кластер               |
| Хранилище активных процессов | PostgreSQL                        | RocksDB (встроенная БД брокера) |
| История процессов            | PostgreSQL (ACT\_HI\_\*)          | Elasticsearch                   |
| Исполнитель задач            | Job Executor внутри               | Worker снаружи через gRPC       |
| Обработка                    | Синхронная                        | Асинхронная                     |
| Узкое место                  | PostgreSQL под нагрузкой          | Диск брокера, Elasticsearch     |

## BPMN — язык описания процессов

```
○  — Start Event (начало)
□  — Task (задача)
◇  — Gateway (развилка если/иначе)
⊕  — Parallel Gateway (параллельное выполнение)
●  — End Event (конец)
⏱  — Timer Event (таймаут)

```

Zeebe читает BPMN файл и выполняет процесс по нему.

## Архитектура Zeebe

```
┌─────────────────────────────────────┐
│           Zeebe Cluster             │
│  Broker 0  │  Broker 1  │  Broker 2 │
│  (лидер P0)│  (лидер P1)│  (лидер P2│
└─────────────────────────────────────┘
         │                │
         ▼                ▼
  Zeebe Gateway      Elasticsearch
  (точка входа,      (история процессов)
   stateless)
         │
    ┌────┴────┐
    ▼         ▼
Worker A   Worker B

```

**Broker** — ядро. Хранит состояние процессов через RocksDB, журнал событий. StatefulSet в Kubernetes — каждый брокер имеет свой диск.

**Gateway** — точка входа для клиентов. Stateless — масштабируется горизонтально.

**Worker** — приложение которое выполняет задачи. Подключается к Gateway, берёт jobs, обрабатывает, возвращает результат.

***

## Как работает выполнение задачи

```
1. Zeebe дошёл до Task в процессе
2. Создал Job типа "check-documents"
3. Worker подписан на "check-documents"
4. Worker забирает Job (activate)
5. Worker выполняет логику
6. Worker возвращает результат:
   complete → процесс идёт дальше
   fail     → retry или error path
   error    → BPMN error boundary event

```

Если Worker упал — Job возвращается в очередь через **job timeout**.

## Партиционирование Zeebe

Zeebe использует партиции как Kafka. Репликация через Raft протокол.

```
zeebe:
  broker:
    cluster:
      partitionsCount: 3      # количество партиций
      replicationFactor: 3    # копии каждой партиции
      clusterSize: 3          # количество брокеров

```

**Правило:**`partitionsCount = clusterSize × 3` для равномерного распределения.

Process Instance назначается в партицию по ключу. Все события одного инстанса → одна партиция → порядок гарантирован.

## Настройки Zeebe (Camunda 8)

### Брокер

```
zeebe:
  broker:
    threads:
      cpuThreadCount: 2       # потоки для CPU задач
      ioThreadCount: 2        # потоки для IO задач

# JVM — heap фиксированный
JAVA_OPTS: "-Xms4g -Xmx4g"

```

### Backpressure

```
zeebe:
  broker:
    backpressure:
      enabled: true
      algorithm: vegas        # TCP Vegas, или: fixed, aimd

```

Когда брокер перегружен → клиент получает `RESOURCE_EXHAUSTED` → retry с exponential backoff.

### Worker настройки

```
client.newWorker()
    .jobType("check-documents")
    .handler(handler)
    .timeout(Duration.ofMinutes(5))       // job timeout
    .pollInterval(Duration.ofMillis(100)) // как часто опрашивать
    .maxJobsActive(32)                    // максимум активных jobs
    .open();

```

**maxJobsActive** — важная настройка. Если worker берёт слишком много jobs и не успевает → jobs возвращаются по timeout → повторная обработка → дубликаты.

## Настройки Camunda 7

### Job Executor — пул потоков для задач

```
jobExecutor.corePoolSize=3           # минимум потоков
jobExecutor.maxPoolSize=10           # максимум потоков
jobExecutor.queueSize=3              # размер очереди задач
jobExecutor.waitTimeInMillis=5000    # пауза между опросами БД
jobExecutor.lockTimeInMillis=300000  # job lock timeout (5 минут)
jobExecutor.maxJobsPerAcquisition=3  # сколько jobs брать за раз

```

Если `queueSize` заполнен → новые задачи ждут → latency растёт.

### История процессов — главная нагрузка на PostgreSQL

```
# Уровень детализации — главная настройка для перформанса
camunda.bpm.history-level=none      # не писать историю — максимальный RPS
camunda.bpm.history-level=activity  # только шаги — баланс
camunda.bpm.history-level=audit     # + переменные
camunda.bpm.history-level=full      # всё — максимальная нагрузка на БД

```

`history-level=full` на высоком RPS убивает PostgreSQL. Первое что проверяешь при деградации.

### Таблицы истории которые растут

```
ACT_HI_PROCINST   -- исторические process instances
ACT_HI_ACTINST    -- каждый шаг каждого процесса (самая тяжёлая!)
ACT_HI_TASKINST   -- исторические задачи
ACT_HI_VARINST    -- исторические переменные
ACT_HI_DETAIL     -- детальная история изменений

```

### Очистка истории

```
camunda.bpm.history-time-to-live=P30D           # хранить 30 дней
historyCleanupBatchSize=500                      # удалять 500 записей за раз
historyCleanupBatchThreshold=10                  # запускать если > 10 записей

```

Без очистки таблицы `ACT_HI_*` растут до десятков ГБ → все запросы тормозят.

## Производительность — что нагружает систему

### Zeebe (Camunda 8)

```
1. Диск брокера — каждое событие пишется в журнал
   SSD обязателен! HDD → деградация в разы
   Метрика: zeebe_broker_disk_available

2. Количество партиций — параллелизм обработки
   Мало партиций → брокеры простаивают

3. Worker throughput
   Jobs накапливаются если worker медленный
   Метрика: zeebe_job_activated - zeebe_job_completed = очередь

4. Job timeout
   Worker не успел → Job возвращается → повторная обработка
   Дубликаты если worker не idempotent

5. Backpressure
   Метрика: zeebe_broker_backpressure_requests_total > 0 → брокер перегружен

```

### Camunda 7

```
1. PostgreSQL — основное узкое место
   ACT_HI_ACTINST растёт быстро
   Смотришь: pg_stat_statements для медленных запросов

2. Job Executor очередь
   Не должна быть полной
   
3. Индексы на ACT_RU_JOB
   По dueDate, processInstanceId — без них опрос очереди медленный

```

## Нагрузочное тестирование Zeebe — специфика

Процессы имеют время жизни — нельзя просто гнать RPS:

```
Профиль нагрузки:
  N = 100 процессов/сек (старт)
  L = 60 секунд (время жизни процесса)

Активных инстансов в любой момент:
  active = N × L = 100 × 60 = 6000 process instances

Все 6000 хранятся в памяти/диске брокера

```

**Что проверять под нагрузкой:**

```
1. Throughput: process instances/sec — растёт ли?
2. Активные инстансы — не переполняют ли память брокера
3. Job очередь — нет ли накопления незавершённых jobs
4. Backpressure — не включается ли при целевой нагрузке
5. Диск брокера — хватает ли места под журнал событий
6. Worker latency — время выполнения каждого шага
7. Elasticsearch lag — история успевает индексироваться

```

## Связь компонентов в проекте

```
Система заявок клиента:
  Приложение → PostgreSQL (бизнес-данные)
             → Redis (кэш, сессии, distributed locks)
             → Kafka (асинхронные события)

Zeebe сервисный:
  BPMN процессы → Zeebe Broker (RocksDB)
  Workers → PostgreSQL (бизнес-данные шагов)
           → Redis (locks между воркерами)
           → Kafka (события между процессами)
  История → Elasticsearch

```

## Шпаргалка для собеса

| Симптом                         | Причина                                        | Решение                                        |
| ------------------------------- | ---------------------------------------------- | ---------------------------------------------- |
| Zeebe backpressure              | Брокер перегружен                              | Увеличь partitionsCount / масштабируй          |
| Jobs накапливаются              | Worker медленный / мало workers                | Увеличь maxJobsActive / добавь workers         |
| Job дубликаты                   | Job timeout меньше времени обработки           | Увеличь job timeout / сделай worker idempotent |
| Диск брокера растёт             | Много активных инстансов / маленький retention | Настрой data retention в Zeebe                 |
| Camunda 7 PostgreSQL деградация | history-level=full                             | Снизить до activity или none                   |
| ACT\_HI\_\* таблицы огромные    | Нет очистки истории                            | Настроить historyCleanup / TTL                 |
| Job Executor очередь полная     | maxPoolSize мал / задачи долгие                | Увеличь maxPoolSize / оптимизируй задачи       |

## Уточнения к разделам выше

- **Число партиций.** Правило «partitionsCount = clusterSize × 3» — не официальная формула, а распространённая эвристика. Смысл: партиций должно быть не меньше, чем брокеров (иначе часть брокеров без лидеров), и столько, чтобы лидеры распределились равномерно; число партиций **нельзя уменьшить** после создания кластера и долго нельзя было увеличить (в новых версиях добавляется поддержка масштабирования партиций). Подбирать нагрузочным тестом: throughput растёт с числом партиций, пока не упрётся в CPU/диск брокеров.
- **Версии Camunda 8 сильно меняются** (8.6 → 8.7 → 8.8: REST API Orchestration Cluster, объединённые компоненты, изменения в хранении вторичных данных). Метрики и параметры проверять по документации своей версии.
- **Elasticsearch/OpenSearch** — это вторичное хранилище для Operate/Tasklist (история, поиск). Брокер пишет туда через **экспортеры**; если экспорт отстаёт, брокер не может удалять старые сегменты журнала → растёт диск брокера.

## Сеть и Zeebe / Camunda

### Порты

| Порт | Назначение |
|------|-----------|
| 26500 | gRPC-API Gateway для клиентов и воркеров |
| 26501 | Command API брокеров (gateway → брокер) |
| 26502 | внутренний кластерный трафик (Raft-репликация, gossip/SWIM членство) |
| 8080 / 8088 | REST API (новые версии) / веб-приложения |
| 9600 | management: health, `/actuator/prometheus` метрики |

Фаервол или NetworkPolicy, закрывающие 26502 между брокерами, ломают репликацию и выборы лидеров партиций.

### gRPC и балансировка

- Клиенты и воркеры работают с Gateway по **gRPC (HTTP/2)** — одно долгоживущее соединение ([[03 Протоколы взаимодействия]], раздел 7).
- Gateway stateless и масштабируется горизонтально, **но** за L4-балансировщиком (Kubernetes Service) воркеры будут «прилипать» к одному экземпляру Gateway → перекос нагрузки между Gateway. Решения: клиентская балансировка, L7 (Ingress с gRPC), или больше соединений.
- Через Ingress/L7 нужно поддерживать HTTP/2 и **долгие таймауты** — активация задач использует long polling (запрос висит до появления задач или `requestTimeout`).

### Как воркер получает задачи

- **Long polling** `ActivateJobs`: воркер отправляет запрос «дай до N задач типа X», Gateway опрашивает партиции; если задач нет — держит запрос открытым до `requestTimeout`. Пустые опросы на каждом воркере = нагрузка на Gateway и брокеры.
- **Job streaming** (новые версии, `StreamActivatedJobs`): воркер открывает поток, брокер **сам толкает** задачи по мере появления — меньше latency и холостой нагрузки. Включается в клиенте (`streamEnabled(true)` в Java-клиенте).
- Каждый шаг процесса = минимум два сетевых обмена: активация задачи и `CompleteJob`. Процесс из 10 сервисных задач — 20+ gRPC-вызовов плюс внутренняя репликация каждого события через Raft на реплики партиции.

### Задержки шага процесса

```
latency одного шага ≈ активация (long poll / stream) + обработка в воркере
                    + CompleteJob (gRPC до Gateway → брокер-лидер)
                    + запись в журнал и репликация Raft на кворум (сеть между брокерами + fsync)
                    + переход к следующему элементу BPMN
```

Высокий RTT между брокерами (брокеры в разных зонах доступности) или медленный fsync диска напрямую увеличивают latency каждого шага и снижают throughput партиции.

### Backpressure

`RESOURCE_EXHAUSTED` — брокер отклоняет новые команды, потому что очередь необработанных запросов партиции превысила адаптивный лимит. Это **защита**, а не ошибка: клиент обязан ретраить с экспоненциальной задержкой. На НТ:

- доля отклонённых запросов = индикатор, что достигнут предел;
- без ретраев в клиенте НТ backpressure превращается в «потерянные» старты процессов;
- агрессивные ретраи без задержки усиливают перегрузку.

## Camunda 7: узкие места, о которых спрашивают

- **Job Executor опрашивает БД** (`SELECT ... FROM ACT_RU_JOB WHERE ... LOCK_EXP_TIME_ < now ... FOR UPDATE`-подобные запросы) каждые `waitTimeInMillis`; много узлов кластера = много параллельных опросов одной таблицы.
- **OptimisticLockingException** — несколько потоков/узлов меняют один экземпляр процесса (параллельные ветки, сообщения в один процесс) → откат и ретрай. Под нагрузкой доля ретраев растёт, throughput падает. Решения: `asyncBefore/asyncAfter` и `exclusive=true` на задачах одного экземпляра.
- **Транзакционные границы:** без async-точек весь путь процесса до ожидания выполняется в одной транзакции БД и в потоке вызывающего (например, HTTP-запроса) → долгие транзакции, блокировки, нагрузка на пул соединений приложения ([[05 PostgreSQL]], раздел 20).
- **Индексы ACT_RU_*, ACT_HI_*** и очистка истории — разделы выше.

## Метрики Zeebe (Prometheus, порт 9600)

Названия зависят от версии; ключевые семейства:

| Метрика | Что смотреть |
|---------|-------------|
| `zeebe_element_instance_events_total{type="PROCESS", action="activated/completed"}` | старты и завершения процессов |
| `zeebe_job_events_total{action="created/activated/completed/failed/timed out"}` | поток задач; `timed out` > 0 — воркеры не успевают за job timeout |
| `zeebe_dropped_request_count_total`, `zeebe_received_request_count_total` | доля отклонённых (backpressure) |
| `zeebe_backpressure_requests_limit`, `zeebe_backpressure_inflight_requests_count` | лимит и текущая загрузка очереди |
| `zeebe_stream_processor_latency_bucket` / `zeebe_process_instance_execution_time_bucket` | время обработки команд и процессов |
| `zeebe_exporter_events_total`, разница позиций экспорта и записи | **отставание экспортера** → рост диска |
| `zeebe_log_appender_*`, `atomix_*` (Raft) | запись журнала, репликация, выборы лидеров |
| `zeebe_snapshot_*` | снапшоты RocksDB |
| JVM-метрики брокера и Gateway | [[10 JVM]], раздел 15 |

## Поиск узких мест — методика

```
1. Растёт ли backpressure (доля RESOURCE_EXHAUSTED)? Если да — предел брокеров/партиций
   → CPU брокеров, диск (fsync), число партиций, распределение лидеров
2. Накапливаются ли jobs (created − completed растёт)? → воркеры медленные или их мало
   → время обработки задачи в воркере, maxJobsActive, число воркеров, их зависимости (БД, HTTP)
3. Job timed out > 0 → воркер не успевает за timeout → дубли обработки
4. Отставание экспортера → Elasticsearch не успевает индексировать → диск брокеров растёт
5. Активные экземпляры = старты/с × время жизни (закон Литтла) → память/диск RocksDB
6. Сеть: перекос Gateway (gRPC за L4), RTT между брокерами, закрытые порты 26501/26502
```
