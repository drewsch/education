## 1. Базовая модель

### 1.1 Ядро и пространство пользователя

```
┌──────────────────────── user space ────────────────────────┐
│  java, postgres, python, go-бинарь, locust                 │
│  работают с ВИРТУАЛЬНОЙ памятью, не могут трогать железо    │
└───────────────┬────────────────────────────────────────────┘
                │ системный вызов (syscall): read, write, epoll_wait, futex, mmap, fsync...
┌───────────────▼──────────────── kernel space ───────────────┐
│  планировщик CPU, менеджер памяти, page cache, VFS,          │
│  блочный уровень, TCP/IP стек, драйверы, cgroups, netfilter  │
└───────────────┬────────────────────────────────────────────┘
                ▼
          CPU, RAM, диски, сетевые карты
```

Каждый системный вызов — переход из user mode в kernel mode. Это стоит сотни наносекунд – единицы микросекунд. Отсюда:

- время CPU делится на **user** (код приложения) и **system** (работа ядра по просьбе приложения);
- много маленьких `read()/write()` по 1 байту = много переходов = высокий `system`; буферизация и батчинг его снижают;
- `strace -c -p <pid>` показывает, какие системные вызовы делает процесс и сколько времени они занимают (под нагрузкой strace сам сильно тормозит процесс — только кратковременно).

### 1.2 Процессы и потоки

- **Процесс** — изолированное адресное пространство + ресурсы (файловые дескрипторы, сигналы).
- **Поток** — единица планирования внутри процесса; потоки делят память процесса.
- Для ядра Linux поток и процесс — одна сущность `task`; у потока свой TID, у процесса PID = TID главного потока.

Аналогия с Java: JVM — один процесс; каждый `java.lang.Thread` (платформенный) = отдельный поток ядра со своим TID — его видно в `top -H -p <pid>`. Виртуальные потоки Java 21 и горутины Go ядро **не видит** — они мультиплексируются рантаймом на небольшое число потоков ядра.

## 2. CPU

### 2.1 Режимы времени CPU

`node_cpu_seconds_total{mode=...}` — счётчик секунд, которые каждое ядро провело в режиме:

| mode      | Что это | На что указывает высокое значение |
|-----------|---------|----------------------------------|
| `user`    | код приложений | приложение считает: бизнес-логика, сериализация JSON, GC, сжатие, TLS |
| `nice`    | user-код процессов с пониженным приоритетом | фоновые задачи |
| `system`  | код ядра по системным вызовам | много syscalls (мелкие read/write), сеть, создание процессов, page faults, блокировки (futex) |
| `idle`    | простой | — |
| `iowait`  | простой, **при этом есть незавершённый дисковый I/O** | ожидание диска. ⚠️ Это **не** занятость CPU, а idle с пометкой: ядро свободно, но кто-то ждёт диск |
| `irq`     | обработка аппаратных прерываний | сетевая карта / диск генерируют много прерываний |
| `softirq` | отложенная обработка прерываний | **сеть**: приём/отправка пакетов, особенно много маленьких пакетов; выше при iptables/conntrack |
| `steal`   | гипервизор отдал ядро другой виртуалке | шумный сосед на гипервизоре; в облаке — исчерпан CPU-кредит |
| `guest`   | время, отданное гостевой ВМ | на гипервизоре |

```
Загрузка CPU, % = 100 − idle% − iowait%    (iowait — тоже «свободен», но смотреть его отдельно)
```

**Как читать типичные картины:**

- `user` 85 %, `system` 5 % → приложение упирается в вычисления → профилировать (async-profiler, pprof, py-spy).
- `user` 30 %, `system` 50 % → ядро работает больше приложения: сеть с мелкими пакетами, огромное число syscalls, lock contention через futex, page faults.
- `softirq` 30 % на одном ядре, остальные свободны → все прерывания сетевой карты приходят на одно ядро → нужны RSS/RPS (раздел 6.3).
- `iowait` 40 %, `user` низкий → система ждёт диск → раздел 4.
- `steal` > 5–10 % → у виртуалки отнимают CPU — результаты НТ на этом стенде нестабильны.

```bash
mpstat -P ALL 1        # по каждому ядру: %usr %sys %iowait %irq %soft %steal %idle
top / htop             # в top нажать 1 — по ядрам
pidstat -u 1           # CPU по процессам
pidstat -t -u -p <pid> 1   # по потокам процесса
```

### 2.2 Load Average — что это на самом деле

`node_load1`, `node_load5`, `node_load15` — экспоненциально сглаженное среднее за 1, 5, 15 минут числа задач:

- в состоянии **R** (выполняются или ждут CPU в очереди),
- **плюс** в состоянии **D** (непрерываемый сон — обычно ждут диск или NFS).

```
8 ядер, load1 = 4    → в среднем 4 задачи хотят CPU, ядер хватает
8 ядер, load1 = 8    → полная загрузка
8 ядер, load1 = 24   → в среднем 16 задач стоят в очереди → насыщение (saturation)
```

**Ловушка:** load 30 при CPU 10 % — это **не CPU**, а много процессов в состоянии D (ждут диск, зависший NFS). Проверка: `vmstat 1` → колонка `r` (ждут CPU) против `b` (blocked, состояние D).

Load average нормируется на число ядер: `node_load1 / count(node_cpu_seconds_total{mode="idle"}) by (instance)`.

### 2.3 Планировщик

Планировщик решает, какой поток выполняется на каком ядре и сколько. С ядра 6.6 основной планировщик — **EEVDF** (Earliest Eligible Virtual Deadline First), до этого — **CFS** (Completely Fair Scheduler). Идея обоих: каждому потоку «справедливая» доля CPU пропорционально весу.

**Вес и nice.** `nice` от −20 (высокий приоритет) до +19 (низкий). Вес nice 0 = 1024; каждый шаг nice меняет вес примерно в 1,25 раза:

```
nice  0 → вес 1024
nice  5 → вес  335
nice 10 → вес  110
nice −5 → вес 3121

Два потока, nice 0 и nice 5, оба хотят 100 % одного ядра:
  доля первого = 1024 / (1024 + 335) = 75 %
  доля второго =  335 / (1024 + 335) = 25 %
```

Что важно для НТ:

- **Run queue** — очередь потоков, готовых к работе. Метрика ожидания в очереди: `node_schedstat_waiting_seconds_total` (время, которое задачи провели в ожидании CPU) рядом с `node_schedstat_running_seconds_total`. Рост waiting при CPU < 100 % на отдельных ядрах — перекос нагрузки.
- **Переключения между ядрами** (миграции) ломают кэши CPU. Для latency-критичных процессов используют CPU pinning (`taskset`, в K8s — static CPU manager policy).
- **NUMA** — на многосокетных серверах память «своего» сокета быстрее чужой в 1,5–2 раза. `numactl --hardware`, `numastat`. Большие БД и JVM иногда страдают от удалённых обращений к памяти.

### 2.4 Context switches

`node_context_switches_total` — сколько раз CPU переключался с одного потока на другой.

- **Добровольные (voluntary)** — поток сам отдал CPU: ждёт I/O, блокировку, сон. Много добровольных = потоки много ждут.
- **Принудительные (involuntary)** — у потока отобрали CPU (кончился квант, пришёл более приоритетный). Много принудительных = потоков больше, чем ядер, конкуренция за CPU.

```bash
vmstat 1                       # cs — переключений в секунду, in — прерываний в секунду
pidstat -w 1                   # cswch/s (добровольные), nvcswch/s (принудительные) по процессам
cat /proc/<pid>/status | grep ctxt
```

**Как читать:**

- плавный рост вместе с нагрузкой — норма;
- пилообразно и резко — lock contention, «шторм» пробуждений;
- очень много при **низком CPU** → приложение в основном ждёт: блокировки, БД, сеть;
- 1000 потоков в пуле Tomcat при 8 ядрах → огромное число принудительных переключений, каждое стоит единицы микросекунд + потерю кэша CPU.

**Пример расчёта:** 200 000 переключений/с × ~3 мкс = 0,6 с CPU в секунду = 60 % одного ядра уходит только на переключения.

### 2.5 Прерывания и softirq

`node_intr_total` — аппаратные прерывания. Сетевая карта при приёме пакета генерирует прерывание; чтобы не обрабатывать каждый пакет отдельно, драйвер использует NAPI: после первого прерывания отключает их и опрашивает карту пачками в контексте **softirq** (`NET_RX`).

```bash
cat /proc/interrupts          # прерывания по ядрам и устройствам — видно, на какие ядра идут очереди NIC
cat /proc/softirqs            # NET_RX, NET_TX, TIMER, BLOCK по ядрам
mpstat -I SUM 1
```

Если в `/proc/interrupts` все прерывания `eth0` идут на CPU0, а он загружен на 100 % softirq — сеть упирается в одно ядро, хотя остальные свободны.

## 3. Память

### 3.1 Виртуальная память и страницы

Каждый процесс видит своё **виртуальное** адресное пространство. Ядро отображает виртуальные адреса на физическую память **страницами по 4 КБ** через таблицы страниц (page tables). Процессор кэширует отображения в TLB.

- **Demand paging** — память выделяется физически только при первом обращении. `malloc(1 ГБ)` или `-Xms8g` без `AlwaysPreTouch` сразу почти ничего не тратят.
- **Minor page fault** — страница в памяти есть (например, в page cache), её нужно только отобразить. Дёшево (~мкс).
- **Major page fault** — страницы нет, нужно читать с диска (из файла или swap). Дорого (~мс). Метрика `node_vmstat_pgmajfault` — рост под нагрузкой = нехватка памяти.

### 3.2 Как посчитана «занятая» память — /proc/meminfo

| Поле (`node_memory_..._bytes`) | Что это |
|--------------------------------|---------|
| `MemTotal` | вся RAM |
| `MemFree` | совсем не используется — обычно **маленькое, и это нормально** |
| `MemAvailable` | сколько можно отдать приложениям без свопинга (свободная + легко освобождаемый кэш). **Главная метрика «сколько памяти реально есть»** |
| `Buffers` | метаданные блочных устройств |
| `Cached` | page cache — содержимое файлов (данные PostgreSQL, сегменты Kafka, логи) |
| `Dirty` | изменённые страницы кэша, ещё не записанные на диск |
| `Writeback` | страницы, которые пишутся на диск прямо сейчас |
| `AnonPages` | анонимная память процессов (heap, стеки) — не связана с файлами |
| `Shmem` | общая память (shared_buffers PostgreSQL, tmpfs) — учитывается в Cached! |
| `Slab` / `SReclaimable` | кэши ядра (inode, dentry, буферы сокетов) |
| `SwapTotal` / `SwapFree` | своп |
| `HugePages_Total` / `HugePages_Free` | заранее выделенные huge pages |

```
Используемая приложениями память ≈ MemTotal − MemAvailable
```

**Ошибка новичка:** «`free` показывает 200 МБ free — сервер сейчас упадёт». Нет: Linux заполняет свободную память page cache-ем, и при нужде мгновенно его вытесняет. Смотреть на `available`.

```bash
free -m
#               total   used   free  shared  buff/cache  available
# Mem:          32000  12000    300    4200      19700       19000   ← реально доступно 19 ГБ
vmstat 1             # si/so — swap in/out; должны быть 0
cat /proc/meminfo
```

### 3.3 Page cache — почему он так важен для НТ

Все чтения и записи файлов идут через page cache:

- **чтение** — если страница файла уже в кэше, диск не трогается (Kafka-консьюмер, читающий только что записанное, PostgreSQL при промахе shared_buffers);
- **запись** — `write()` кладёт данные в кэш и помечает страницы грязными, возврат мгновенный; на диск их позже сбрасывают потоки writeback.

Параметры сброса грязных страниц:

```
vm.dirty_background_ratio = 10   # при 10 % грязных от доступной памяти — фоновый сброс
vm.dirty_ratio = 20              # при 20 % — процессы, которые пишут, БЛОКИРУЮТСЯ, пока не сбросится
vm.dirty_expire_centisecs = 3000 # грязная страница старше 30 с — пишется
```

На сервере с 256 ГБ RAM 20 % = 51 ГБ грязных данных. Когда начинается принудительный сброс, диск занят десятки секунд, а пишущие процессы стоят → всплески latency. Для серверов с большой памятью используют абсолютные значения `vm.dirty_background_bytes` / `vm.dirty_bytes` (например, 256 МБ / 1 ГБ).

**Для НТ:** второй прогон теста всегда быстрее первого, потому что данные уже в page cache. Перед честным сравнением либо прогревать, либо сбрасывать (`sync; echo 3 > /proc/sys/vm/drop_caches` — только на стенде!).

### 3.4 Память процесса: VSZ, RSS, PSS

| Метрика | Что это |
|---------|---------|
| VSZ / VIRT | весь виртуальный размер (зарезервированное, отображённые файлы) — почти бесполезен |
| RSS / RES | физическая память процесса, включая общие страницы (библиотеки, shared memory) |
| PSS | RSS, где общие страницы поделены между процессами — честная доля |
| USS | только уникальная память процесса |

Ловушка с PostgreSQL: каждый backend показывает в RSS прочитанные им страницы shared_buffers. 200 процессов × «2 ГБ RSS» ≠ 400 ГБ — это одни и те же общие 4 ГБ. Смотреть PSS (`smem`) или cgroup-метрики.

Метрики процесса в Prometheus: `process_resident_memory_bytes` (RSS), `process_virtual_memory_bytes`. В контейнерах — `container_memory_working_set_bytes` (именно по ней срабатывает OOM).

### 3.5 Swap и swappiness

Swap — выгрузка анонимных страниц на диск. Для БД и JVM swap означает многосекундные паузы: GC, проходящий по heap, будет поднимать страницы с диска.

```
vm.swappiness = 1–10   # на серверах БД/JVM: минимально предпочитать своп
                        # (0 на новых ядрах практически отключает своп анонимной памяти до крайности)
```

Метрики: `node_memory_SwapFree_bytes`, `node_vmstat_pswpin` / `pswpout` (rate > 0 под нагрузкой — плохо).

### 3.6 OOM killer

Когда память закончилась и освободить нечего, ядро выбирает процесс-жертву по `oom_score` (0–1000), который в основном пропорционален доле памяти процесса, плюс поправка `oom_score_adj` (−1000…+1000):

```
oom_score ≈ (RSS + swap + page tables процесса) / (вся доступная память) × 1000 + oom_score_adj

Пример: сервер 16 ГБ, JVM занимает 12 ГБ, oom_score_adj = 0
  oom_score ≈ 12 / 16 × 1000 = 750 → будет убита первой
С oom_score_adj = −500 → 250
С oom_score_adj = −1000 → никогда (так защищают sshd, kubelet)
```

```bash
cat /proc/<pid>/oom_score /proc/<pid>/oom_score_adj
dmesg -T | grep -i -E 'killed process|out of memory'
journalctl -k | grep -i oom
```

Метрика: `node_vmstat_oom_kill` (рост = кого-то убили). В Kubernetes — `OOMKilled`, exit code 137 (= 128 + сигнал 9 SIGKILL).

### 3.7 Huge pages и Transparent Huge Pages

- **Huge pages** (2 МБ или 1 ГБ вместо 4 КБ) — меньше записей в таблицах страниц и промахов TLB. Выгодно для больших shared_buffers PostgreSQL и больших JVM heap. Выделяются заранее (`vm.nr_hugepages`), `huge_pages = on` в PostgreSQL, `-XX:+UseLargePages` в JVM.
- **Transparent Huge Pages (THP)** — ядро само склеивает страницы в 2 МБ. Фоновый процесс `khugepaged` и дефрагментация памяти дают **непредсказуемые паузы latency**. Для PostgreSQL, Redis, MongoDB рекомендуется `never` (или `madvise` — только для тех, кто попросил).

```bash
cat /sys/kernel/mm/transparent_hugepage/enabled    # [always] madvise never
```

Redis при старте пишет предупреждение в лог, если THP включён.

## 4. Диск

### 4.1 Четыре характеристики

| Характеристика | Единица | Пример NVMe | Пример SATA SSD | Пример HDD |
|----------------|---------|-------------|-----------------|-----------|
| IOPS (операций/с) | оп/с | 500 000+ | 50 000–90 000 | 100–200 |
| Пропускная способность | МБ/с | 3000–7000 | 500 | 150–250 (последовательно) |
| Latency одной операции | мс | 0,02–0,1 | 0,1–0,5 | 5–10 |
| Глубина очереди, при которой достигается максимум | шт | 32–256 | 32 | 1–4 |

Связь между ними — закон Литтла:

```
средняя глубина очереди (aqu-sz) = IOPS × средняя latency (await, в секундах)

Пример: 5000 IOPS × 0,004 с = 20 запросов в среднем в очереди
```

И пропускная способность = IOPS × размер операции: 5000 IOPS × 8 КБ (страница PostgreSQL) = 40 МБ/с, а 5000 × 1 МБ (Kafka) = 5 ГБ/с — то есть упираемся в разные ограничения.

### 4.2 iostat -x — как читать

```bash
iostat -xz 1
# Device  r/s    w/s   rkB/s   wkB/s  r_await w_await aqu-sz  rareq-sz wareq-sz  %util
# nvme0n1 1200   3500  9600    56000    0.15    0.40    1.6     8.0      16.0    45.0
# sda      150    80   1200     640    12.50   25.00    3.9     8.0       8.0    99.8
```

| Колонка | Смысл | Тревожно |
|---------|-------|----------|
| `r/s`, `w/s` | IOPS чтения/записи | близко к паспортным пределам |
| `rkB/s`, `wkB/s` | пропускная способность | близко к пределу диска или **сетевого** канала (у сетевых томов) |
| `r_await`, `w_await` | среднее время операции **включая ожидание в очереди**, мс | SSD > 1–2 мс, HDD > 20 мс |
| `aqu-sz` | средняя длина очереди | растёт вместе с await → насыщение |
| `rareq-sz` / `wareq-sz` | средний размер запроса, КБ | маленький (4–8) = случайный I/O |
| `%util` | доля времени, когда была хотя бы одна операция | для HDD 100 % = насыщение; **для SSD/NVMe почти бесполезно** — они обрабатывают десятки операций параллельно, 100 % util не значит предел |

**Признак насыщения диска** — не `%util`, а **рост await и aqu-sz** при не растущих IOPS, плюс `PSI io` (раздел 7).

### 4.3 Метрики node_exporter для диска

```
node_disk_reads_completed_total, node_disk_writes_completed_total    — операции
node_disk_read_bytes_total, node_disk_written_bytes_total             — байты
node_disk_read_time_seconds_total, node_disk_write_time_seconds_total — суммарное время операций
node_disk_io_time_seconds_total                                       — время «занятости» (%util)
node_disk_io_time_weighted_seconds_total                              — взвешенное время (→ средняя очередь)
node_filesystem_avail_bytes, node_filesystem_files_free               — место и inode
```

```promql
# IOPS
rate(node_disk_reads_completed_total[1m]) + rate(node_disk_writes_completed_total[1m])
# Средняя latency чтения, мс (аналог r_await)
1000 * rate(node_disk_read_time_seconds_total[1m]) / rate(node_disk_reads_completed_total[1m])
# Средняя глубина очереди (аналог aqu-sz)
rate(node_disk_io_time_weighted_seconds_total[1m])
# Утилизация
rate(node_disk_io_time_seconds_total[1m])
```

### 4.4 fsync — главная цена надёжной записи

`write()` попадает в page cache и возвращается сразу. `fsync()` ждёт, пока данные физически окажутся на носителе. Именно fsync определяет latency коммита в PostgreSQL ([[05 PostgreSQL]], раздел 16), AOF в Redis, `flush` в Kafka (если включён).

```bash
# Измерить latency fsync на диске (как это делает PostgreSQL)
pg_test_fsync
# Или fio с fsync после каждой записи
fio --name=fsync --rw=write --bs=8k --size=256m --fsync=1 --filename=/data/test
```

Сетевые тома (Ceph RBD, облачные блочные диски, NFS) имеют latency fsync в разы выше локальных NVMe, потому что запись подтверждается через сеть и репликацию хранилища.

### 4.5 Планировщики I/O и файловая система

- Для NVMe/SSD — `none` или `mq-deadline` (`cat /sys/block/nvme0n1/queue/scheduler`); `bfq` — для десктопов.
- Монтировать данные с `noatime` — иначе каждое чтение файла пишет время доступа.
- `ext4` и `xfs` — стандарт для БД и Kafka.
- Место и inode: `df -h`, `df -i`. Закончившиеся inode (миллионы мелких файлов) дают «No space left on device» при свободных гигабайтах.

```bash
iotop -o                 # какие процессы пишут/читают
pidstat -d 1             # I/O по процессам
biolatency (bcc/bpftrace) # гистограмма latency блочного I/O — видно хвосты, а не среднее
```

## 5. Процессы, состояния, файловые дескрипторы

### 5.1 Состояния процессов

| Состояние | Значит | В load average? |
|-----------|--------|-----------------|
| `R` | выполняется или готов и ждёт CPU | да |
| `S` | прерываемый сон (ждёт событие: сеть, таймер, блокировку) | нет |
| `D` | **непрерываемый** сон (ждёт диск/NFS, нельзя убить даже `kill -9`) | **да** |
| `Z` | зомби: завершился, родитель не забрал код возврата | нет |
| `T` | остановлен (SIGSTOP, отладчик) | нет |

Метрики: `node_procs_running` (R), `node_procs_blocked` (D). Растущий `procs_blocked` = очереди к диску.

### 5.2 Файловые дескрипторы (FD)

В Linux «всё — файл»: файлы, сокеты, pipe, eventfd, epoll. **FD** — целое число, которое процесс получает при `open()`, `socket()`, `accept()`.

Каждое TCP-соединение = 1 FD у процесса. Ещё FD тратятся на: файлы логов, соединения к БД/Kafka/Redis, JAR-файлы JVM, сегменты Kafka (по 3 файла на сегмент!), pipe между процессами.

**Лимиты:**

| Уровень | Где | По умолчанию |
|---------|-----|--------------|
| на процесс (soft/hard) | `ulimit -n`, `/etc/security/limits.conf`, systemd `LimitNOFILE=` | часто 1024 (soft) — **мало для сервера** |
| на систему | `fs.file-max`, `fs.nr_open` | обычно миллионы |
| контейнер | наследует от runtime (containerd/docker) | обычно 1 048 576 |

```bash
cat /proc/<pid>/limits | grep 'open files'
ls /proc/<pid>/fd | wc -l           # сколько открыто сейчас
lsof -p <pid> | awk '{print $5}' | sort | uniq -c   # по типам: REG, IPv4, sock...
cat /proc/sys/fs/file-nr            # открыто в системе / свободно / максимум
```

Метрики: `process_open_fds`, `process_max_fds` (из клиентских библиотек Prometheus), `node_filefd_allocated`, `node_filefd_maximum`.

**Симптом исчерпания:** `Too many open files` (EMFILE), сервер перестаёт принимать соединения (`accept()` падает), начинают ломаться запись логов и открытие файлов.

**Почему FD растут:**

- утечка — сокет/файл не закрыт (часто видно по росту `CLOSE_WAIT`, см. [[02 Сеть — пропускная способность, фаерволы, узкие места]]);
- нет пулов и keep-alive — новое соединение на каждый запрос;
- нормальный рост с числом клиентов — тогда просто поднимать лимит.

Важно не путать: сокет в `TIME_WAIT` — это запись в ядре, **FD у процесса для него уже закрыт**. Многие дашборды смешивают «сокеты в ядре» (`node_sockstat_*`) и «FD процесса» (`process_open_fds`).

## 6. Сетевой стек глазами ядра и метрики node_exporter для сети

Теория TCP/UDP, состояния соединений, флаги, backlog, пропускная способность, фаерволы — в [[02 Сеть — пропускная способность, фаерволы, узкие места]]. Здесь — как путь пакета через ядро отражается в метриках.

### 6.1 Путь входящего пакета

```
Сетевая карта (NIC) → кольцевой буфер RX в памяти (ring buffer, ethtool -g)
  → прерывание → softirq NET_RX (NAPI опрос пачками)
  → очередь backlog ядра (net.core.netdev_max_backlog)
  → netfilter (iptables/nftables, conntrack) — PREROUTING, INPUT
  → TCP/UDP стек → буфер приёма сокета (rmem)
  → приложение делает read()/recv()
```

Пакет может быть потерян на каждом шаге — и для каждого шага своя метрика:

| Где потерялся | Метрика / команда |
|---------------|-------------------|
| ring buffer карты переполнен | `ethtool -S eth0 \| grep -i -E 'drop\|miss\|fifo'`, `node_network_receive_fifo_total`, `rx_missed_errors` |
| ядро не успело (backlog) | `/proc/net/softnet_stat` (2-я колонка — dropped), `node_softnet_dropped_total` |
| ядро отбросило на интерфейсе | `node_network_receive_drop_total` |
| ошибки кадров/CRC | `node_network_receive_errs_total` (часто — проблема кабеля/порта/дуплекса) |
| conntrack-таблица полна | `dmesg: nf_conntrack: table full, dropping packet`, `node_nf_conntrack_entries` vs `node_nf_conntrack_entries_limit` |
| буфер сокета UDP полон | `node_netstat_Udp_RcvbufErrors` |
| accept queue переполнена | `node_netstat_TcpExt_ListenOverflows`, `ListenDrops` |

### 6.2 Метрики интерфейсов

```promql
# Входящий/исходящий трафик, бит/с (сравнивать со скоростью линка!)
rate(node_network_receive_bytes_total{device="eth0"}[1m]) * 8
rate(node_network_transmit_bytes_total{device="eth0"}[1m]) * 8
node_network_speed_bytes{device="eth0"} * 8        # скорость линка (не у всех виртуальных интерфейсов)

# Пакеты/с — важно для маленьких пакетов: упираются в pps, а не в биты
rate(node_network_receive_packets_total[1m])

# Дропы и ошибки — должны быть 0
rate(node_network_receive_drop_total[1m])
rate(node_network_transmit_drop_total[1m])
rate(node_network_receive_errs_total[1m])
```

**Пропускная способность упирается не только в Гбит/с, но и в пакеты/с.** 10 Гбит/с при пакетах 1500 байт ≈ 820 тыс. pps, а при 64 байтах — 14,8 млн pps; обработать такой поток пакетов на одном ядре невозможно. Поэтому для API с маленькими запросами пределом часто становится CPU softirq, а не канал.

### 6.3 Распределение обработки сети по ядрам

- **RSS (Receive Side Scaling)** — у карты несколько аппаратных очередей, каждая со своим прерыванием на своё ядро. `ethtool -l eth0` — число очередей.
- **RPS/RFS** — программное распределение, если очередей мало (часто у виртуальных NIC).
- **irqbalance** — демон, раскидывающий прерывания по ядрам.

Симптом: `mpstat -P ALL` показывает 100 % `%soft` на одном-двух ядрах при свободных остальных.

### 6.4 Метрики TCP-стека (node_netstat_*, node_sockstat_*)

Эти метрики node_exporter берёт из `/proc/net/snmp`, `/proc/net/netstat` и `/proc/net/sockstat`. Подробная расшифровка причин — в файле про сеть, здесь — сводка.

**Ошибки TCP (`node_netstat_TcpExt_*`, `node_netstat_Tcp_*`):**

| Метрика | Что значит | Ведёт к |
|---------|-----------|---------|
| `TcpExt_ListenOverflows` | переполнилась accept queue — приложение не успевает делать `accept()` | ListenDrops, ретраи SYN, таймауты подключения |
| `TcpExt_ListenDrops` | SYN к слушающему сокету отброшен (любая причина, включает Overflows) | клиент «не может подключиться» |
| `TcpExt_TCPSynRetrans` | повторы SYN / SYN-ACK | долгий connect, connect timeout |
| `Tcp_RetransSegs` | все повторно отправленные сегменты | рост latency, падение throughput |
| `TcpExt_TCPAbortOnTimeout` | соединение закрыто после исчерпания ретраев | реальные разрывы сессий |
| `TcpExt_TCPSackRecoveryFail` | не удалось восстановиться после потерь через SACK | тяжёлые потери в сети |
| `Tcp_InErrs` | принятые сегменты с ошибкой (контрольная сумма и т.п.) | проблема в сети/NIC |
| `Tcp_OutRsts` | отправлено сегментов с флагом RST | аварийные закрытия: порт закрыт, приложение упало, переполнения |
| `TcpExt_TCPTimeouts` | срабатывания таймера ретрансмиссии (RTO) | потери, перегруз |
| `TcpExt_TCPMemoryPressures` | TCP-стек упёрся в лимит памяти `net.ipv4.tcp_mem` | урезание буферов, дропы |

**Доля ретрансмиссий** — один из лучших индикаторов здоровья сети:

```promql
rate(node_netstat_Tcp_RetransSegs[1m]) / rate(node_netstat_Tcp_OutSegs[1m])
# < 0,1 % — норма в ЦОДе; 1 % и выше — серьёзная проблема, throughput одного TCP-потока падает в разы
```

**Сокеты (`node_sockstat_*`):**

| Метрика | Что это | Норма / тревога |
|---------|---------|-----------------|
| `TCP_alloc` | все выделенные TCP-структуры в ядре (все состояния) | растёт и падает вместе с нагрузкой; монотонный рост = утечка или неуспевающее закрытие |
| `TCP_inuse` | TCP-сокеты в использовании (≈ ESTABLISHED + LISTEN + в обработке) | плато под стабильной нагрузкой — норма; рост без падения = соединения не освобождаются |
| `TCP_orphan` | сокеты, у которых процесс уже закрыл FD, а ядро ещё «дожёвывает» закрытие | 0–10 норма, 50+ тревога, сотни = abrupt close / проблемы закрытия |
| `TCP_tw` | сокеты в TIME_WAIT | растёт с RPS при коротких соединениях; тысячи-десятки тысяч = churn соединений (нет keep-alive/пулов) |
| `TCP_mem` | память TCP-буферов в страницах | сравнивать с `net.ipv4.tcp_mem` |
| `UDP_inuse` / `UDP_mem` | UDP-сокеты и их память | для TCP-проблем неважно |
| `sockets_used` | все сокеты всех типов | — |

📌 **TIME_WAIT ≠ утечка.** TIME_WAIT = много открытий/закрытий соединений. Утечка — это `CLOSE_WAIT` и рост `process_open_fds`.

```bash
ss -s                      # сводка: сколько сокетов в каких состояниях
ss -tan state time-wait | wc -l
ss -tanp state close-wait  # кто держит CLOSE_WAIT (с процессом)
nstat -az | grep -i -E 'listen|retrans|abort'   # счётчики TcpExt
netstat -s | grep -i -E 'listen|overflow|retrans'
```

## 7. PSI — Pressure Stall Information

Самый честный ответ на вопрос «хватает ли ресурса». Доступно с ядра 4.20 в `/proc/pressure/{cpu,memory,io}` и в cgroups v2 (`cpu.pressure`, `memory.pressure`, `io.pressure`).

**Что измеряет:** долю времени, когда задачи **не могли выполняться из-за нехватки ресурса**.

```bash
cat /proc/pressure/io
# some avg10=12.50 avg60=8.30 avg300=4.10 total=123456789
# full avg10=5.20  avg60=3.10 avg300=1.50 total=45678901
```

- `some` — хотя бы одна задача ждала ресурс. `avg10=12.5` = 12,5 % последних 10 секунд кто-то стоял в ожидании.
- `full` — **все** незанятые простоем задачи одновременно ждали ресурс — ни одна не продвигалась. Это прямая потеря полезной работы.
- `avg10/60/300` — скользящие средние; `total` — суммарные микросекунды (из него Prometheus считает rate).

**Чем лучше привычных метрик:**

- CPU 100 % — это ещё не проблема, если никто не ждёт; PSI cpu `some` > 0 — уже кто-то ждёт.
- `iowait` бывает нулевым при реальном ожидании диска (если ядра заняты другими задачами); PSI io показывает ожидание всегда.
- Память: PSI memory растёт **раньше** OOM — когда ядро начинает активно вытеснять page cache и подтягивать страницы с диска (thrashing).

**Как читать:**

| Сигнал | Значит |
|--------|-------|
| `cpu some` > 10–20 % стабильно | очередь за CPU, latency растёт |
| `memory some` > 0 заметно | вытеснение страниц, риск thrashing и OOM |
| `memory full` > 0 | система «толчёт» память — всё стоит |
| `io some` > 10 % | диск — узкое место |
| `io full` > 0 | все ждут диск |

Метрики node_exporter: `node_pressure_cpu_waiting_seconds_total`, `node_pressure_memory_waiting_seconds_total`, `node_pressure_memory_stalled_seconds_total` (full), `node_pressure_io_waiting_seconds_total`, `node_pressure_io_stalled_seconds_total`.

```promql
rate(node_pressure_io_waiting_seconds_total[1m])     # доля времени (0..1), когда кто-то ждал I/O
rate(node_pressure_memory_stalled_seconds_total[1m]) # «full» по памяти
```

## 8. Контейнеры: cgroups v2, throttling, лимиты памяти

Контейнер — это обычный процесс Linux, ограниченный **namespaces** (что он видит: PID, сеть, файловая система) и **cgroups** (сколько ресурсов может потратить). Подробнее про Kubernetes — [[13 Kubernetes, OpenShift, Docker]].

### 8.1 CPU-лимит = квота CFS

```
cpu.max = "200000 100000"     # квота 200 мс CPU на каждый период 100 мс = 2 ядра
(в Kubernetes: limits.cpu: "2")
```

Внутри **каждого** периода 100 мс все потоки контейнера вместе могут потратить 200 мс процессорного времени. Если потратили раньше — **все потоки замораживаются до конца периода** (throttling).

**Почему throttling бьёт по latency, даже когда средний CPU низкий:**

```
Лимит: 2 ядра (200 мс на 100 мс). JVM с 16 потоками на ноде с 16 ядрами.
GC запускает 16 параллельных потоков → за 12,5 мс реального времени тратится 16 × 12,5 = 200 мс CPU
→ квота исчерпана за 12,5 мс → контейнер стоит оставшиеся 87,5 мс
→ запрос, пришедший в этот момент, получает +87,5 мс latency
Средний CPU за минуту при этом может быть 30 %.
```

Метрики: `container_cpu_cfs_throttled_periods_total` / `container_cpu_cfs_periods_total` (доля периодов с throttling), `container_cpu_cfs_throttled_seconds_total`. В cgroup v2 файл `cpu.stat`: `nr_periods`, `nr_throttled`, `throttled_usec`.

```promql
rate(container_cpu_cfs_throttled_periods_total[5m]) / rate(container_cpu_cfs_periods_total[5m])
# > 5–10 % — throttling заметно влияет на хвосты latency
```

Подробный разбор «почему под простаивает, а его всё равно троттлят», метрики и способы борьбы — [[13 Kubernetes, OpenShift, Docker]], раздел 11.

Рантаймы должны знать о лимите: JVM (с 10-й версии) видит cgroup-лимит и подбирает число GC-потоков; Go с 1.25 сам ставит `GOMAXPROCS` по CPU-лимиту (раньше — `automaxprocs`); Python-пулы (`os.cpu_count()`) лимит **не учитывают** — см. [[10 JVM]], [[11 Go]], [[12 Python]].

### 8.2 Лимит памяти

```
memory.max  — жёсткий лимит; превышение → OOM killer внутри cgroup → контейнер убит (exit 137)
memory.high — мягкий лимит: при превышении ядро агрессивно вытесняет память и тормозит процессы
memory.current, memory.stat — текущее потребление по типам (anon, file, ...)
```

Что учитывается в лимите: анонимная память процесса (heap, стеки, off-heap, native) **и page cache файлов, которые читал/писал контейнер**. Page cache при давлении вытесняется, поэтому для OOM важна `container_memory_working_set_bytes` (≈ usage − неактивный file cache), а не `container_memory_usage_bytes`.

**Классическая ошибка с JVM:** `limits.memory = 4Gi`, `-Xmx4g` → heap занимает весь лимит, а ещё нужны Metaspace, стеки потоков, Code Cache, direct buffers, память GC → OOMKilled. Правило: heap ≈ 60–75 % лимита (`-XX:MaxRAMPercentage=70`).

## 9. Методика: USE и «60 секунд анализа»

### 9.1 Метод USE (Brendan Gregg)

Для **каждого ресурса** проверить три вещи:

- **U — Utilization** — какую долю времени ресурс занят;
- **S — Saturation** — есть ли очередь работы, которую ресурс не успевает;
- **E — Errors** — есть ли ошибки.

| Ресурс | Utilization | Saturation | Errors |
|--------|-------------|------------|--------|
| CPU | `100 − idle` по ядрам (mpstat) | load average > ядер, `vmstat r` > ядер, PSI cpu, throttling в контейнере | — |
| Память | `MemTotal − MemAvailable` | swap in/out, major page faults, PSI memory | OOM kills (`dmesg`, `node_vmstat_oom_kill`) |
| Диск | `%util` (для HDD), IOPS и МБ/с к пределу | `aqu-sz`, рост `await`, PSI io, `procs_blocked` | ошибки в `dmesg`, SMART |
| Сеть | бит/с и pps к пределу линка | drops, `softnet` dropped, ретрансмиссии, ListenOverflows | `rx_errors`, `InErrs`, RST |
| FD | `process_open_fds / process_max_fds` | — | EMFILE «Too many open files» |
| Пулы приложения | активные / максимум | ожидающие потоки (Hikari pending) | таймауты получения |

Для сервисов — дополнительно метод **RED**: Rate (RPS), Errors (доля ошибок), Duration (перцентили latency).

### 9.2 Первые 60 секунд на сервере

```bash
uptime                    # load average: растёт или падает?
dmesg -T | tail -50       # OOM kill, ошибки диска, conntrack table full, «possible SYN flooding»
vmstat 1 5                # r (очередь CPU), b (D-состояние), si/so (swap), us/sy/wa/st, cs/in
mpstat -P ALL 1 3         # перекос по ядрам, softirq, steal
pidstat 1 3               # кто ест CPU
iostat -xz 1 3            # диски: await, aqu-sz, util
free -m                   # available, swap
sar -n DEV 1 3            # трафик интерфейсов: rxkB/s, txkB/s, pps
sar -n TCP,ETCP 1 3       # active/s (исходящие connect), passive/s (входящие accept), retrans/s
ss -s                     # сколько сокетов в каких состояниях
cat /proc/pressure/*      # PSI
top                       # общая картина
```

### 9.4 Карта утилит по подсистемам (по мотивам схемы Брендана Грегга)

Идея: при инциденте не гуглить, а идти **по подсистемам сверху вниз** — от приложения к железу — и для каждой знать 2–3 команды и что искать в выводе. Подборка дополняет статью на Хабре «Шпаргалка по поиску узких мест в Linux: топ утилит на все случаи жизни» (RUVDS, 2026) и схему Linux Performance Observability Tools Брендана Грегга. Утилиты с пометкой **(bcc)** — из пакета `bcc-tools` (eBPF), требуют root и ядро 4.x+.

**1. Приложение и системные библиотеки**

| Команда | Что ищем |
|---------|----------|
| `strace -c -p <PID>` (несколько секунд, потом Ctrl+C) | какие системные вызовы и сколько времени в ядре: много `futex` — блокировки, `epoll_wait` — ждёт событий, `read`/`write` мелкими порциями — нет буферизации |
| `ltrace -c -p <PID>` | вызовы библиотек, если strace ничего не показал |
| `gethostlatency` (bcc) | задержки DNS-резолва по процессам — «сеть тормозит», а на деле DNS |
| `execsnoop` (bcc) | короткоживущие процессы, которые не успевает показать `top` (скрипты, health-check-и, форки) |
| `journalctl -u <сервис> -n 200 --no-pager` | логи сервиса systemd; `dmesg -T` — только ядро |
| `lsof -p <PID>`, `ls /proc/<PID>/fd \| wc -l` | утечки FD и сокетов |

**2. Интерфейс системных вызовов и ядро**

| Команда | Что ищем |
|---------|----------|
| `perf stat -a -- sleep 5` | общие счётчики: context switches, migrations, page faults, IPC (instructions per cycle) |
| `perf top -g -p <PID>` | горячие функции процесса, включая ядро |
| `perf record -F 99 -g -p <PID> -- sleep 30` → FlameGraph | flame graph CPU |
| `trace-cmd record -e syscalls:sys_enter_read ...` (ftrace) | трассировка событий ядра с меньшим оверхедом, чем strace |
| `offcputime` (bcc) | где потоки **не на CPU** (ждут I/O, блокировки) — главный инструмент для «CPU низкий, latency высокая» |
| `profile` (bcc) | сэмплирующий профиль всей системы |
| `runqlen`, `runqlat` (bcc) | длина очереди планировщика и время ожидания CPU — насыщение CPU при неполной утилизации |

**3. Файловая система и VFS**

| Команда | Что ищем |
|---------|----------|
| `lsof +D /path`, `lsof \| grep deleted` | кто держит файлы; удалённые логи, которые всё ещё занимают место |
| `opensnoop` (bcc) | кто и какие файлы открывает (лавина open/close) |
| `filelife` (bcc) | короткоживущие файлы (временные файлы на каждый запрос) |
| `ext4slower 10`, `xfsslower 10`, `ext4dist` (bcc) | операции ФС дольше 10 мс, распределение latency |
| `slabtop` | рост кэшей dentry/inode (миллионы мелких файлов) |
| `pcstat <файл>` | какая доля файла лежит в page cache |
| `df -h`, `df -i` | место и inode |

Мысль: нагрузку на VFS часто создаёт **способ работы с файлами** (миллионы мелких файлов, открытие на каждый запрос), а не сам диск — `iostat` при этом выглядит нормально.

**4. Блочные устройства**

| Команда | Что ищем |
|---------|----------|
| `lsblk -f` | топология: какие диски, LVM, RAID, файловые системы |
| `iostat -xz 1` | `r_await/w_await`, `aqu-sz`, IOPS и МБ/с (раздел 4.2) |
| `iotop -o`, `pidstat -d 1` | какой процесс делает I/O |
| `biolatency` (bcc) | гистограмма latency блочного I/O — видны хвосты, а не среднее |
| `biosnoop` (bcc), `biotop` (bcc) | каждая операция с PID, размером и временем |
| `nvme smart-log /dev/nvme0n1`, `smartctl -a /dev/sda` | здоровье диска: ошибки, износ, температура |

**5. Сетевой стек** (подробно — [[02 Сеть — пропускная способность, фаерволы, узкие места]])

| Команда | Что ищем |
|---------|----------|
| `ss -tunap`, `ss -s`, `ss -ltn` | соединения, состояния, accept queue у слушающих сокетов |
| `ip -s link`, `ip route show` | ошибки и дропы интерфейсов, маршруты |
| `ethtool -S eth0` | аппаратные счётчики NIC: `rx_missed`, `rx_fifo_errors` |
| `nicstat 1`, `sar -n DEV 1` | пакеты/с, Мбит/с, средний размер пакета |
| `nstat -az` | счётчики TCP/UDP ядра (ретрансмиссии, ListenOverflows) |
| `dropwatch -l kas` | **где именно** ядро отбрасывает пакеты (драйвер, стек, фильтр) |
| `tcpretrans` (bcc) | каждая ретрансмиссия с адресами — к какому хосту теряются пакеты |
| `tcplife` (bcc) | длительность и объём каждого TCP-соединения — короткие соединения без keep-alive |
| `tcpconnlat` (bcc), `solisten` (bcc) | время установки исходящих соединений; слушающие сокеты и их backlog |
| `lldptool -t -i eth0 -V portDesc` | в какой порт коммутатора включён сервер (для разговора с сетевиками) |

**6. Планировщик и CPU**

| Команда | Что ищем |
|---------|----------|
| `mpstat -P ALL 1` | перекос по ядрам; `%soft`, `%irq`, `%steal` |
| `pidstat -u 1`, `pidstat -t -p <PID> 1` | процессы и потоки по CPU |
| `top`/`htop`/`atop`/`btop` | общая картина; `atop` пишет историю — можно посмотреть «что было ночью» |
| `runqlen 1` (bcc) | очередь за CPU, когда load высокий, а CPU не 100 % |
| `perf stat -e cycles,instructions,cache-misses -p <PID> -- sleep 5` | IPC < 1 и много cache-misses → упираемся в память, а не в вычисления |
| `softirqs`, `hardirqs` (bcc) | время в обработке прерываний (шторм прерываний сети) |
| `turbostat 1`, `cpupower frequency-info` | частота, C-states, троттлинг по температуре/питанию — CPU «загружен», но работает на пониженной частоте |

**7. Память**

| Команда | Что ищем |
|---------|----------|
| `free -h`, `vmstat 1` | available, swap, `si/so` ≠ 0 — свопинг |
| `sar -r 1`, `sar -W 1`, `sar -B 1` | тренд памяти, своп, page faults (`majflt/s`) |
| `ps aux --sort=-rss \| head` | топ процессов по RSS |
| `numastat -p <PID>` | память процесса на «чужом» NUMA-узле |
| `slabtop` | память ядра (кэши сокетов, dentry) |
| `memleak -p <PID>` (bcc) | невозвращённые аллокации со стеками |
| `oomkill` (bcc), `dmesg -T \| grep -i oom` | кого убил OOM killer |
| `swapin` (bcc) | какие процессы ждут подкачки из swap |

**8. Железо**

| Команда | Что ищем |
|---------|----------|
| `perf stat` (IPC, cache-misses) | аппаратные ограничения |
| `sensors`, `ipmitool sensor` | температура, питание, вентиляторы — термотроттлинг |
| `smartctl`, `nvme smart-log` | деградация дисков |
| `dmidecode`, `lshw -short`, `lscpu` | что за железо, сколько сокетов/NUMA, частоты |
| `dstat -tcmnd` (или `dool`) | сводка CPU/память/сеть/диск в одной строке — удобно «на глаз» во время теста |

**Готовые системы, которые собирают это сами:** node_exporter + Grafana (то, что у нас), Netdata (тысячи метрик с секундной детализацией из коробки), Parca / Pyroscope (непрерывное профилирование), Inspektor Gadget (eBPF-диагностика в Kubernetes: те же `tcpretrans`, `opensnoop`, `profile` по подам), atop (история состояния системы).

## 10. sysctl и лимиты для нагрузочного стенда

Нагрузочный генератор (Locust, k6, JMeter) открывает тысячи исходящих соединений, сервер — принимает тысячи входящих. Дефолты Linux для этого малы.

| Параметр | По умолчанию | Для НТ | Зачем |
|----------|--------------|--------|-------|
| `ulimit -n` / `LimitNOFILE` | 1024 | 1 000 000 | FD на соединения |
| `fs.file-max` | зависит от RAM | 2 000 000 | системный лимит FD |
| `net.core.somaxconn` | 4096 (с ядра 5.4; раньше 128) | 4096–65535 | максимум accept queue (приложение ещё должно запросить большой backlog в `listen()`) |
| `net.ipv4.tcp_max_syn_backlog` | 128–1024+ | 8192+ | очередь полуоткрытых соединений |
| `net.ipv4.ip_local_port_range` | `32768 60999` (~28 тыс. портов) | `1024 65535` | исходящие порты генератора нагрузки |
| `net.ipv4.tcp_tw_reuse` | 2 (только loopback) | 1 | переиспользовать TIME_WAIT порты для исходящих соединений |
| `net.ipv4.tcp_fin_timeout` | 60 | 15–30 | время в FIN_WAIT2 |
| `net.netfilter.nf_conntrack_max` | зависит от RAM | 1 000 000+ | размер таблицы conntrack (если есть iptables/NAT/K8s) |
| `net.core.netdev_max_backlog` | 1000 | 10000–30000 | очередь пакетов перед стеком |
| `net.core.rmem_max` / `wmem_max` | ~208 КБ | 16–128 МБ | максимум буферов сокетов (для каналов с большим BDP) |
| `net.ipv4.tcp_rmem` / `tcp_wmem` | `4096 131072 6291456` | до `... 16777216` | автоподстройка TCP-буферов |
| `net.ipv4.tcp_keepalive_time` | 7200 | 60–300 | быстрее находить мёртвые соединения |
| `net.ipv4.tcp_slow_start_after_idle` | 1 | 0 | не сбрасывать окно перегрузки после простоя keep-alive соединения |
| `vm.swappiness` | 60 | 1–10 | серверы БД/JVM |

**Расчёт исчерпания портов на генераторе:**

```
Порты: 32768–60999 = 28 232 штуки на пару (src IP → dst IP:port)
TIME_WAIT держится 60 с
Если генератор открывает новое соединение на каждый запрос:
  максимум ≈ 28 232 / 60 ≈ 470 соединений/с на один целевой IP:порт
→ на 1000 RPS без keep-alive генератор упрётся в порты: «Cannot assign requested address» (EADDRNOTAVAIL)
Решения: keep-alive/пул соединений, расширить диапазон (~64 тыс. → ~1000/с), tcp_tw_reuse, несколько IP генератора
```

## 11. PromQL-шпаргалка для node_exporter

```promql
# CPU, % занятости по инстансу
100 * (1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[1m])))

sum by (mode) (rate(node_cpu_seconds_total{instance="$i"}[1m]))

# Major page faults/с
rate(node_vmstat_pgmajfault[1m])
# OOM kills
increase(node_vmstat_oom_kill[1h])

# Диск: latency записи, мс
1000 * rate(node_disk_write_time_seconds_total[1m]) / rate(node_disk_writes_completed_total[1m])
# Место: прогноз заполнения через 4 часа
predict_linear(node_filesystem_avail_bytes{mountpoint="/data"}[1h], 4*3600) < 0

# Сеть, Мбит/с
rate(node_network_transmit_bytes_total{device!~"lo|veth.*"}[1m]) * 8 / 1e6

rate(node_netstat_TcpExt_ListenOverflows[1m])

# Context switches и прерывания
rate(node_context_switches_total[1m])
rate(node_intr_total[1m])

# FD системы
node_filefd_allocated / node_filefd_maximum

# PSI
rate(node_pressure_cpu_waiting_seconds_total[1m])
rate(node_pressure_io_stalled_seconds_total[1m])
```

## 12. Шпаргалка: симптом → причина → решение

| Симптом | Вероятная причина | Что проверить / сделать |
|---------|-------------------|-------------------------|
| Load высокий, CPU низкий | процессы в D-состоянии (диск, NFS) | `vmstat b`, `iostat`, `ps -eo state,cmd \| grep ^D` |
| `system` CPU > `user` | много syscalls, сеть с мелкими пакетами, lock contention | `perf top`, `strace -c`, батчинг |
| `softirq` на одном ядре 100 % | прерывания NIC на одном ядре | RSS/RPS, irqbalance, число очередей NIC |
| `steal` > 10 % | шумные соседи на гипервизоре | другой хост, выделенные ядра |
| Много context switches при низком CPU | потоки ждут блокировки/I/O | thread dump / профилирование off-CPU |
| `free` мало, `available` много | page cache — норма | ничего |
| Swap in/out > 0 | нехватка памяти | лимиты, swappiness, утечки |
| PSI memory растёт | давление памяти, thrashing | работающий набор не помещается |
| OOM в dmesg | память закончилась | кто съел (`oom_score`), лимиты контейнера |
| `await` растёт, IOPS не растут | диск насыщен | разнести нагрузку, быстрее диск, меньше fsync |
| Периодические всплески записи на диск | сброс грязных страниц / checkpoint БД | `vm.dirty_*`, настройки БД |
| «Too many open files» | лимит FD / утечка | `ulimit -n`, `lsof`, CLOSE_WAIT |
| «Cannot assign requested address» на клиенте | исчерпаны эфемерные порты | keep-alive, `ip_local_port_range`, `tcp_tw_reuse` |
| `ListenOverflows` растёт | приложение не успевает accept | backlog, потоки accept, CPU приложения |
| «nf_conntrack: table full» | переполнена таблица conntrack | `nf_conntrack_max`, меньше коротких соединений |
| Ретрансмиссии > 1 % | потери в сети / перегруз | дропы на интерфейсах и по пути, [[02 Сеть — пропускная способность, фаерволы, узкие места]] |
| Latency хвосты в контейнере при среднем CPU 30 % | CPU throttling | `cfs_throttled`, поднять лимит / убрать CPU limit |
| Паузы latency без видимой причины | THP compaction, сброс dirty pages, steal | THP = never, dirty_bytes, steal |
