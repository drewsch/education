# Часть I. Микросервисная архитектура

## 1. Монолит vs микросервисы

| | Монолит | Микросервисы |
|---|---|---|
| Развёртывание | одно приложение целиком | каждый сервис отдельно |
| Вызов между модулями | вызов метода в памяти (наносекунды) | сетевой вызов (сотни микросекунд – миллисекунды), может упасть |
| Транзакции | одна локальная ACID-транзакция | распределённые: Saga, eventual consistency |
| Масштабирование | всё целиком | каждый сервис по своей нагрузке |
| Команды | общая кодовая база, координация релизов | независимые команды и релизы |
| Отказ | падает всё | частичная деградация (если спроектировано) |
| Наблюдаемость | стектрейс | распределённая трассировка, корреляция логов |
| Сложность | в коде | в инфраструктуре и взаимодействии |

**Модульный монолит** — компромисс: один деплой, но жёсткие границы модулей. Часто правильный старт; в микросервисы выделяют то, что действительно нужно масштабировать или релизить независимо.

**Границы сервисов** — по бизнес-возможностям (Bounded Context из DDD: «Заказы», «Платежи», «Склад»), а не по техническим слоям («сервис БД», «сервис валидации»). Плохие границы = «распределённый монолит»: сервисы деплоятся только вместе и вызывают друг друга на каждый запрос синхронно.

## 2. API Gateway

**Единая точка входа** для всех внешних запросов.

```
                   ┌─────────────────────────────────────┐
Web ──┐            │            API Gateway              │      ┌──> Orders
Mobile┼──HTTPS──>  │ TLS · аутентификация · rate limit · │ ─────┼──> Payments
Партнёр┘           │ маршрутизация · кэш · агрегация ·   │      └──> Users
                   │ логирование · трассировка           │
                   └─────────────────────────────────────┘
```

**Отвечает за:**

- **маршрутизацию**: `/api/orders/**` → Orders, `/api/payments/**` → Payments;
- **завершение TLS** ([[03 Протоколы взаимодействия]], раздел 5.4);
- **аутентификацию**: проверка JWT/introspection один раз на входе ([[04 Аутентификация и токены]], раздел 12);
- **rate limiting и квоты** по клиенту/ключу;
- **кэширование** ответов;
- **агрегацию**: один внешний запрос → несколько внутренних вызовов (API composition);
- трансформацию протоколов (REST снаружи → gRPC внутри), версионирование, CORS;
- сквозные заголовки: `traceparent`, `X-Request-Id`.

**Продукты:** Kong, NGINX, Envoy, Spring Cloud Gateway, KrakenD, облачные API Gateway; в Kubernetes — Ingress-контроллеры и Gateway API.

| Плюсы | Минусы |
|-------|--------|
| сквозные функции в одном месте | **единая точка отказа** → нужна отказоустойчивость (несколько реплик) |
| клиенты не знают внутренней топологии | **дополнительный сетевой хоп** и обработка: +0,5–5 мс |
| безопасность периметра | может стать **узким местом** по CPU (TLS, JWT, логирование) и соединениям |
| | соблазн поместить туда бизнес-логику («толстый gateway») |

**Что проверять на НТ:**

- latency, которую добавляет gateway (сравнить время на gateway и время сервиса — в трейсе или логах);
- CPU gateway при целевом RPS (TLS-рукопожатия, проверка JWT, логирование каждого запроса);
- пулы соединений gateway → бэкенды (не стали ли узким местом);
- rate limit — согласовать или отключить для IP генераторов;
- поведение при падении одного бэкенда: не забираются ли все рабочие потоки/соединения gateway ожиданием (нужны таймауты и circuit breaker на маршрут).

## 3. Service Registry и Service Discovery

**Задача:** сервисы динамически появляются и исчезают (автомасштабирование, перезапуск подов, деплой), их IP меняются. Нужен механизм, по которому сервис находит **актуальные адреса** других без жёстко прописанных IP.

**Реестр (registry)** — база «имя сервиса → список живых экземпляров (IP:порт) + метаданные». Экземпляр **регистрируется** при старте, подтверждает жизнь **heartbeat**-ами или проверками здоровья, удаляется при остановке или пропуске heartbeat.

### 3.1 Два способа обнаружения

**Client-side discovery** — клиент сам спрашивает реестр и сам балансирует:

```
Сервис A ──(1) где Orders?──> Реестр (Eureka, Consul)
         <──(2) [10.0.1.5, 10.0.1.6, 10.0.1.7]──
         ──(3) запрос напрямую на 10.0.1.6 (клиент выбрал сам: round robin, least requests)
```

- плюсы: нет лишнего хопа, умная балансировка по запросам (важно для gRPC/HTTP/2);
- минусы: логика в каждом клиенте/языке (библиотеки), клиент кэширует список → может ходить на уже мёртвые экземпляры.

**Server-side discovery** — клиент обращается к стабильному адресу, балансировщик сам знает экземпляры:

```
Сервис A ──> orders.svc (стабильное имя/VIP) ──> балансировщик/kube-proxy ──> один из подов
```

- плюсы: клиент простой, работает для любого языка;
- минусы: лишний компонент; L4-балансировка соединений вместо запросов ([[02 Сеть — пропускная способность, фаерволы, узкие места]], раздел 11).

### 3.2 Реализации

| Реализация | Как |
|------------|-----|
| **Kubernetes Service + DNS** | Service имеет стабильное имя `orders.ns.svc.cluster.local` и ClusterIP; kube-proxy (iptables/IPVS/eBPF) направляет на поды из Endpoints/EndpointSlices; в список попадают только поды, прошедшие **readinessProbe**. **Headless Service** (`clusterIP: None`) — DNS возвращает IP всех подов → для клиентской балансировки |
| Consul | реестр + health checks + DNS-интерфейс + KV |
| Eureka (Netflix, Spring Cloud) | клиентская регистрация и обнаружение |
| etcd / ZooKeeper | хранилище, на котором строят реестр |
| Service mesh (Istio, Linkerd) | sidecar-прокси получает список экземпляров от control plane |

### 3.3 Проблемы, видимые на НТ

- **Задержка распространения:** под умер, а клиенты ещё N секунд шлют на него запросы (кэш реестра, DNS TTL, обновление правил kube-proxy) → всплеск ошибок при каждом рестарте/деплое.
- **Graceful shutdown:** при остановке под должен сначала перестать получать трафик (readiness → false, `preStop`-задержка 5–10 с), потом дождаться завершения текущих запросов, потом выйти. Иначе каждый деплой под нагрузкой = 502/обрывы.
- **Неравномерность:** долгоживущие соединения + L4 → новые поды после масштабирования не получают нагрузку.
- **Нагрузка на DNS/реестр** при частом разрешении имён.

## 4. Backends for Frontends (BFF)

**Отдельный бэкенд под каждый тип клиента**: Web, Mobile, партнёрский API. Каждый клиент получает ровно те данные и в том виде, который ему нужен.

```
Web-приложение  ──> Web BFF    ─┐
iOS / Android   ──> Mobile BFF ─┼──> Orders, Users, Payments, Catalog (общие доменные сервисы)
Партнёры        ──> Partner API ┘
```

**Зачем:**

- мобильному клиенту нужны компактные ответы (медленная сеть, батарея), один запрос на экран вместо десяти;
- веб-клиенту — больше данных, другие поля, другая агрегация;
- разные циклы релизов: команда мобильного приложения сама меняет свой BFF;
- разная аутентификация (cookie для веба, токены для мобильных).

| Плюсы | Минусы |
|-------|--------|
| каждый клиент оптимизирован (меньше запросов, меньше байт) | дублирование кода между BFF |
| меньше RTT для мобильных (агрегация на сервере, где сеть быстрая) | ещё один слой и хоп |
| независимость команд фронтенда | соблазн дублировать бизнес-логику в BFF |

**Связь с производительностью:** BFF переносит «N запросов по медленной мобильной сети (RTT 50–150 мс)» на «N запросов по быстрой сети ЦОДа (RTT 0,5 мс) + 1 по мобильной». Экран из 8 запросов: 8 × 100 мс = 800 мс → 1 × 100 мс + 8 × 1 мс (параллельно) ≈ 105 мс. Но **внутри** BFF fan-out к сервисам — и тогда важна хвостовая задержка (раздел 27).

GraphQL часто используют как универсальный BFF.

## 5. Event-Driven Architecture

**Сервисы обмениваются не прямыми вызовами, а событиями через брокер**: один сервис публикует факт («Заказ создан»), все заинтересованные подписчики асинхронно получают и обрабатывают.

```
Orders ──publish "OrderCreated"──> Kafka topic orders.events
                                        │
                     ┌──────────────────┼──────────────────┐
                     ▼                  ▼                  ▼
              Payments (списать)   Warehouse (резерв)   Notifications (письмо)
```

### 5.1 Команда vs событие

| | Команда (command) | Событие (event) |
|---|---|---|
| Смысл | «сделай X» | «случилось X» (прошедшее время) |
| Получатель | конкретный | любой подписчик, отправитель не знает кто |
| Пример | `ReserveStock(orderId)` | `OrderCreated(orderId, items)` |
| Связанность | отправитель знает получателя | слабая |

### 5.2 Виды событий

- **Event notification** — «заказ 42 изменился» (только ID); подписчик сам идёт за деталями (синхронный вызов → нагрузка на источник!).
- **Event-carried state transfer** — событие несёт все нужные данные; подписчик хранит свою копию → не нужен обратный вызов, но данные дублируются.
- **Event sourcing** — состояние сущности хранится **как последовательность событий**, текущее состояние = свёртка событий; снапшоты для скорости. Полный аудит, но сложные запросы и миграции схем событий.

### 5.3 Плюсы и минусы

| Плюсы | Минусы |
|-------|--------|
| слабая связанность: новые подписчики без изменения источника | **eventual consistency**: данные согласуются не сразу |
| брокер **буферизует пики**: источник не зависит от скорости потребителей | сложнее отладка: «где застряло событие?» |
| отказ потребителя не роняет источник | порядок событий, дубли, повторы → идемпотентность потребителей |
| естественная аудиторская история | эволюция схем событий |
| | брокер — критичная инфраструктура |

### 5.4 На что смотреть на НТ

- **consumer lag** — отставание потребителей ([[08 Kafka]], раздел 15): растёт = потребители не успевают;
- **end-to-end latency**: время от публикации до обработки последним потребителем (отметка времени в событии + метрика при обработке);
- поведение при **всплеске**: брокер принял пик, а потребители разгребают его минуты — допустимо ли это по SLA;
- дубли и порядок при перебалансировке потребителей.

## 6. CQRS (Command Query Responsibility Segregation)

**Разделение операций записи (Commands) и чтения (Queries)** на разные модели, а часто и разные хранилища.

```
                Команды (запись)                    Запросы (чтение)
Клиент ──> Command API ──> валидация ──>      Клиент ──> Query API ──> Read-модель
                          бизнес-правила                               (денормализованная,
                          ──> Write-модель                              под конкретные экраны:
                              (нормализованная,                         Elasticsearch, ClickHouse,
                               PostgreSQL)                              Redis, materialized view)
                                   │                                         ▲
                                   └── события / CDC / outbox ───────────────┘
```

- **Commands** — изменяют состояние, проходят валидацию и бизнес-правила, работают с нормализованной моделью, транзакционно.
- **Queries** — только читают, оптимизированы под быстрое получение, агрегации, отчёты, полнотекстовый поиск.

**Зачем:**

- нагрузка чтения и записи часто различается на порядки (1 запись на 100 чтений) — масштабировать отдельно;
- оптимальная схема для записи (нормализация, ограничения) плохо подходит для сложного чтения (JOIN-ы на 8 таблиц, агрегации);
- разные хранилища под разные запросы: поиск — Elasticsearch, аналитика — ClickHouse ([[06 ClickHouse]]).

| Плюсы | Минусы |
|-------|--------|
| чтение и запись масштабируются независимо | **задержка согласования** read-модели (пользователь сохранил и не видит изменения) |
| read-модели под конкретные запросы — быстро | больше компонентов, синхронизация, дубли данных |
| упрощение каждой модели | восстановление read-модели при ошибке (перепроигрывание событий) |

**Простейший CQRS без отдельной БД:** запись в мастер PostgreSQL, чтение с реплик + materialized views ([[05 PostgreSQL]], разделы 18, 19.2).

**На НТ:** мерить **лаг проекции** (сколько секунд от команды до появления в read-модели) при целевой нагрузке записи; проверить, что под пиком записи лаг не растёт бесконечно.

## 7. Database-per-Service

**Каждый сервис владеет своими данными** в своей БД (или схеме) и никто больше не ходит в неё напрямую — только через API или события сервиса.

```
Orders  ──> orders_db  (PostgreSQL)
Payments ──> payments_db (PostgreSQL)
Catalog ──> catalog_db (MongoDB / Elasticsearch)
Sessions ──> Redis
```

**Зачем:**

- **минимальная связанность**: можно менять схему, не согласуя с другими командами;
- выбор хранилища под задачу (polyglot persistence);
- изоляция нагрузки: тяжёлый отчёт одного сервиса не тормозит другой;
- независимое масштабирование.

**Антипаттерн — общая БД:** несколько сервисов читают и пишут одни таблицы → изменение схемы ломает чужие сервисы, блокировки и нагрузка одного влияют на всех, это распределённый монолит.

**Главная проблема — синхронизация данных и запросы через границы:**

| Задача | Как решают |
|--------|-----------|
| Транзакция, затрагивающая несколько сервисов | Saga (разделы 8–10) |
| Сервису нужны чужие данные | синхронный вызов API (задержка + зависимость), **локальная копия** через события (eventual consistency), API Composition |
| Отчёт по данным нескольких сервисов | CQRS/отдельное аналитическое хранилище (CDC → Kafka → ClickHouse) |
| Ссылочная целостность (FK между сервисами) | невозможна на уровне БД → проверки в коде, события об удалении |
| Атомарно «изменить свои данные + сообщить другим» | Transactional Outbox (раздел 11) |

**На НТ:** у каждого сервиса свой профиль нагрузки на свою БД; узкое место ищется в конкретной БД. Количество БД-соединений = сумма пулов всех экземпляров каждого сервиса.

## 8. Распределённые транзакции: 2PC и Saga

### 8.1 Two-Phase Commit (2PC)

```
Координатор: «готовы?» (PREPARE) → все участники блокируют ресурсы, отвечают «да»
Координатор: «фиксируем» (COMMIT) → все фиксируют
```

- строгая согласованность (атомарность через несколько ресурсов);
- **блокирующий**: участники держат блокировки до решения координатора; падение координатора между фазами — ресурсы заблокированы;
- latency = 2 RTT до самого медленного участника + fsync у всех;
- плохо масштабируется, многие системы (Kafka, большинство NoSQL, REST API) его не поддерживают;
- в PostgreSQL есть `PREPARE TRANSACTION`, в Java — XA/JTA. В микросервисах почти не используют.

### 8.2 Saga

**Saga** — последовательность **локальных** транзакций в разных сервисах. Если шаг не удался — выполняются **компенсирующие** транзакции для уже сделанных шагов.

```
Оформление заказа:
  T1: Orders    — создать заказ (PENDING)        C1: отменить заказ
  T2: Payments  — списать деньги                 C2: вернуть деньги
  T3: Warehouse — зарезервировать товар          C3: снять резерв
  T4: Orders    — подтвердить заказ (CONFIRMED)

Успех:   T1 → T2 → T3 → T4
Провал на T3 (нет товара):  T1 → T2 → T3✗ → C2 → C1
```

Свойства:

- **нет изоляции**: промежуточные состояния видны другим (заказ PENDING, деньги списаны, товара ещё нет) → «семантические блокировки» (статусы), проверка версий;
- компенсации — **бизнес-операции**, а не откат: «вернуть деньги» — это новая операция возврата, а не удаление списания;
- все шаги и компенсации должны быть **идемпотентными** (повторы при сбоях);
- некоторые шаги нельзя компенсировать (отправленное письмо) → ставить их последними («pivot transaction»).

Два способа координации саги — оркестрация и хореография.

## 9. Оркестрация

**Центральный сервис (оркестратор) управляет порядком вызовов**: знает весь процесс, отдаёт команды участникам, ждёт ответы, решает, что делать дальше, запускает компенсации.

```
                        ┌───────────────────────┐
                        │   Оркестратор саги    │  ← состояние процесса, таймеры, ретраи
                        │ (Camunda / Zeebe,     │
                        │  Temporal, свой код)  │
                        └──┬───────┬────────┬───┘
                 1.создать │ 2.списать│ 3.резерв│
                           ▼          ▼        ▼
                        Orders    Payments  Warehouse
```

**Обеспечивает:**

- последовательность выполнения алгоритмов, которые используют разные микросервисы;
- целостность и контроль: состояние каждого экземпляра процесса хранится, видно, на каком шаге он остановился;
- таймауты, ретраи, компенсации, ручную обработку инцидентов — централизованно.

**Пример оркестратора — Camunda / Zeebe**: процесс описывается в BPMN, движок хранит состояние каждого экземпляра, создаёт задачи (jobs), которые забирают воркеры сервисов. Подробно — [[09 Camunda Zeebe]].

| Плюсы | Минусы |
|-------|--------|
| логика процесса в одном месте, наглядна (BPMN-схема) | оркестратор — центральная зависимость и потенциальное узкое место |
| легко понять состояние любого экземпляра, отладка | риск «умного оркестратора и глупых сервисов» — бизнес-логика уезжает в процесс |
| сервисы-участники не знают друг о друге | дополнительная инфраструктура (кластер Zeebe, Elasticsearch) |
| простые компенсации и таймауты | дополнительная latency на каждый шаг (оркестратор ↔ воркер) |

**На НТ:** пропускная способность оркестратора (экземпляров процессов в секунду, jobs/с), backpressure, накопление незавершённых jobs, latency каждого шага, число одновременно активных экземпляров (по закону Литтла: `активные = старты/с × время жизни процесса`).

***

## 10. Хореография

**Нет центрального управляющего.** Сервисы обмениваются событиями через брокер; каждый сам знает, на какие события реагировать и какие публиковать. Порядок выполнения возникает из цепочки «событие → реакция → новое событие».

```
Orders ──OrderCreated──> [брокер] ──> Payments ──PaymentCompleted──> [брокер] ──> Warehouse
                                                                                    │
       <──────────────── OrderConfirmed ──── [брокер] <── StockReserved ────────────┘

Ошибка: Warehouse ──StockReservationFailed──> Payments (компенсирует: возврат)
                                           ──> Orders (отменяет заказ)
```

| Плюсы | Минусы |
|-------|--------|
| слабая связанность, нет центральной точки отказа | **процесс нигде не описан целиком** — размазан по сервисам |
| легко добавить нового участника-подписчика | сложно ответить «на каком шаге заказ 42?» → нужна трассировка и корреляция |
| хорошо масштабируется | риск циклических зависимостей событий |
| | сложнее компенсации и таймауты («что если ответ так и не пришёл?») |

### Оркестрация vs хореография — когда что

| Критерий | Оркестрация | Хореография |
|----------|-------------|-------------|
| Число шагов | много, сложные ветвления, таймеры | 2–4 простых шага |
| Нужна наглядность процесса и аудит | да | нет |
| Требования к связанности | допустим центральный компонент | максимальная независимость |
| Примеры | оформление кредита, налоговая проверка, onboarding клиента | обновление кэшей, уведомления, аналитика |

На практике часто **гибрид**: внутри домена — оркестрация, между доменами — события.

## 11. Transactional Outbox, Inbox, CDC

### 11.1 Проблема двойной записи

```java
@Transactional
void createOrder(Order o) {
    orderRepo.save(o);                       // 1. запись в БД
    kafka.send("orders", new OrderCreated(o)); // 2. публикация события
}
```

- БД закоммитилась, отправка в Kafka упала → заказ есть, события нет — другие сервисы не узнают.
- Отправили в Kafka, а транзакция БД откатилась → событие о несуществующем заказе.

Атомарно записать в БД и в брокер нельзя (нет общей транзакции).

### 11.2 Transactional Outbox

```sql
BEGIN;
INSERT INTO orders (...) VALUES (...);
INSERT INTO outbox (id, aggregate_id, type, payload, created_at)
       VALUES (gen_random_uuid(), 42, 'OrderCreated', '{...}', now());
COMMIT;   -- обе записи атомарно в одной локальной транзакции
```

Отдельный **релей** читает `outbox` и публикует в брокер:

- **polling publisher**: `SELECT ... FROM outbox WHERE published = false ORDER BY created_at LIMIT 100 FOR UPDATE SKIP LOCKED` → отправить → пометить/удалить ([[05 PostgreSQL]], раздел 17.3);
- **CDC (Change Data Capture)**: Debezium читает WAL PostgreSQL (логическая репликация) и превращает вставки в `outbox` в сообщения Kafka — без нагрузки опросами.

Гарантия — **at-least-once**: событие может уйти дважды (релей отправил и упал до пометки) → потребители обязаны быть идемпотентными.

**На НТ:** таблица `outbox` — горячая (INSERT + UPDATE/DELETE на каждое событие) → bloat, autovacuum; лаг релея; при CDC — слот логической репликации и удержание WAL.

### 11.3 Inbox / идемпотентный потребитель

```sql
-- В одной транзакции с бизнес-изменением
INSERT INTO inbox (message_id) VALUES ($1) ON CONFLICT DO NOTHING;
-- 0 строк вставлено → сообщение уже обработано → пропустить
```

Защищает от повторной обработки при at-least-once доставке.

### 11.4 CDC

Захват изменений из журнала БД (WAL PostgreSQL, binlog MySQL) и публикация в Kafka. Используется для outbox, для наполнения read-моделей CQRS, аналитики (ClickHouse), поиска. Не требует изменения кода сервиса, но создаёт связанность по схеме таблиц.

## 12. Паттерны устойчивости

Подробно о таймаутах, ретраях и идемпотентности — [[03 Протоколы взаимодействия]], раздел 13.

| Паттерн | Суть | Что защищает |
|---------|------|-------------|
| **Timeout** | ограничить ожидание любой зависимости | потоки/соединения не висят вечно |
| **Retry с экспонентой и джиттером** | повтор транзиентных ошибок | разовые сбои; опасен retry storm |
| **Circuit Breaker** | после порога ошибок — «разомкнуть цепь» и сразу отвечать ошибкой/фолбэком, через время пробовать снова (half-open) | не тратить ресурсы на заведомо больную зависимость, дать ей восстановиться |
| **Bulkhead** | отдельные пулы потоков/соединений на зависимости | медленная зависимость не забирает все ресурсы |
| **Rate Limiting** | ограничение запросов (token bucket) | перегрузка, справедливость между клиентами |
| **Load Shedding** | при перегрузке сразу отклонять часть запросов (503) | лучше быстро отказать части, чем медленно всем |
| **Fallback** | запасной ответ (кэш, значение по умолчанию) | деградация вместо отказа |
| **Idempotency** | повтор безопасен | дубли при ретраях |
| **Backpressure** | сигнал «сбавь темп» от перегруженного компонента | лавинообразное накопление очередей |

**Circuit breaker — состояния:**

```
CLOSED (норма) ──доля ошибок > 50 % за окно──> OPEN (сразу ошибка, без вызова)
OPEN ──через 30 с──> HALF-OPEN (пропустить несколько пробных вызовов)
HALF-OPEN ──успех──> CLOSED   ──ошибка──> OPEN
```

**Каскадный отказ — как он развивается и почему эти паттерны нужны:**

```
1. Сервис C замедлился с 50 мс до 5 с
2. У B нет таймаута/он 30 с → потоки B ждут C
3. По закону Литтла: 200 RPS × 5 с = 1000 одновременных запросов вместо 10 → пул B исчерпан
4. B перестаёт отвечать и тем запросам, которые C не трогают
5. A ретраит B ×3 → нагрузка на B растёт, когда ему уже плохо
6. Отказ поднимается до gateway → лежит всё
Защита: таймаут B→C 300 мс, circuit breaker на C, bulkhead (отдельный пул на C),
        ретраи только на одном уровне с бюджетом, load shedding на входе
```

## 13. Sidecar и Service Mesh

**Sidecar** — вспомогательный контейнер в том же поде, берёт на себя сквозные функции: прокси, логи, сертификаты.

**Service mesh** (Istio, Linkerd, Cilium) — sidecar-прокси (Envoy) у каждого сервиса + control plane:

- mTLS между всеми сервисами автоматически ([[04 Аутентификация и токены]], раздел 10);
- L7-балансировка (по запросам — решает проблему gRPC/HTTP/2), ретраи, таймауты, circuit breaking — конфигурацией;
- метрики и трассировка всех вызовов без изменения кода;
- канареечные релизы, разделение трафика.

**Цена:** каждый вызов проходит через **два** дополнительных прокси (исходящий и входящий) → +0,5–3 мс на хоп и CPU/память на каждый под (sidecar Envoy — десятки–сотни МБ). Новые режимы без sidecar (Istio ambient, eBPF) снижают накладные расходы. **На НТ** накладные расходы mesh нужно измерять: сравнить latency и CPU с mesh и без.

***

## 14. Strangler Fig, API Composition, Anti-Corruption Layer

- **Strangler Fig** — постепенная миграция монолита: перед монолитом ставится прокси/gateway, функциональность по одной выносится в новые сервисы, маршруты переключаются, монолит «усыхает».
- **API Composition** — запрос, которому нужны данные нескольких сервисов, выполняется композитором (gateway/BFF): параллельные вызовы + объединение в памяти. Простой, но latency = самый медленный вызов, и при больших объёмах — дорого (JOIN в памяти).
- **Anti-Corruption Layer** — слой-переводчик между своей моделью и чужой (легаси, внешний API), чтобы чужие понятия не «протекали» в домен.

***

## 15. Наблюдаемость в микросервисах

- **Распределённая трассировка** (OpenTelemetry → Jaeger/Tempo): каждый запрос получает trace ID, который передаётся через все вызовы (`traceparent`), в том числе через Kafka-заголовки. Позволяет увидеть, в каком сервисе и на каком хопе тратится время.
- **Корреляция логов** — trace ID в каждой строке лога.
- **Метрики RED** на каждом сервисе (Rate, Errors, Duration) и **USE** на ресурсах ([[01 Linux — ядро, ресурсы, метрики]], раздел 9).
- **Метрики зависимостей**: latency и ошибки исходящих вызовов, состояние circuit breaker-ов, занятость пулов.
- **Бизнес-метрики** — заказы/мин, процент успешных оплат.

Для НТ трассировка — главный инструмент: «у нас p99 = 2 с» превращается в «из них 1,6 с — ожидание соединения из пула в сервисе Payments перед вызовом БД».

## 17. Нефункциональные требования

### 17.1 SLI, SLO, SLA

- **SLI (Service Level Indicator)** — измеряемый показатель: доля успешных запросов, p99 latency.
- **SLO (Objective)** — целевое значение: «99,9 % запросов успешны за 30 дней», «p99 < 300 мс».
- **SLA (Agreement)** — договор с последствиями (штрафы) — обычно мягче SLO.
- **Error budget** = 100 % − SLO. При SLO 99,9 % бюджет 0,1 % — можно «потратить» на релизы и эксперименты; кончился — заморозка изменений.

### 17.2 Доступность в «девятках»

| Доступность | Простой в год | В месяц | В сутки |
|-------------|---------------|---------|---------|
| 99 % | 3,65 дня | 7,3 ч | 14,4 мин |
| 99,9 % | 8,76 ч | 43,8 мин | 1,44 мин |
| 99,95 % | 4,38 ч | 21,9 мин | 43 с |
| 99,99 % | 52,6 мин | 4,38 мин | 8,6 с |
| 99,999 % | 5,26 мин | 26 с | 0,86 с |

**Последовательные зависимости перемножаются:** сервис зависит синхронно от 5 сервисов по 99,9 % → 0,999⁵ = 99,5 %. **Резервирование складывается:** два независимых экземпляра по 99 % → 1 − 0,01² = 99,99 %.

### 17.3 Перцентили, а не средние

Среднее скрывает хвост: 99 запросов по 10 мс и 1 по 5000 мс → среднее 60 мс, p99 = 5000 мс. SLO формулируют на перцентилях (p95, p99, p99.9). Перцентили **нельзя усреднять** между инстансами — считать из гистограмм (`histogram_quantile` в PromQL).

## 18. Оценка нагрузки «на салфетке»

**Опорные числа:**

```
1 день ≈ 86 400 с ≈ 10⁵ с (для оценок)
1 млн запросов/день ≈ 12 RPS в среднем
Пик обычно = среднее × 2–5 (рабочие часы, сезонность, отчётные даты)
1 КБ × 1 млн = 1 ГБ;   1 КБ × 1 млрд = 1 ТБ
1 Гбит/с ≈ 110–120 МБ/с полезных
```

**Пример расчёта: сервис приёма событий мониторинга**

```
Дано: 50 000 источников, каждый шлёт событие раз в 10 с, событие 1 КБ, хранить 90 дней, 2 реплики

Нагрузка:
  50 000 / 10 = 5 000 событий/с в среднем; пик ×3 = 15 000/с

Входящий трафик:
  15 000 × 1 КБ = 15 МБ/с ≈ 120 Мбит/с на пике → один канал 1 Гбит/с выдерживает с запасом

Объём:
  5 000 × 86 400 = 432 млн событий/сутки × 1 КБ = 432 ГБ/сутки
  × 90 дней = 38,9 ТБ «сырых» × 2 реплики = 77,8 ТБ
  в ClickHouse сжатие ×8 → ~10 ТБ на диске — уже выбор хранилища определён расчётом

Запись в БД:
  15 000 строк/с → для ClickHouse вставлять пачками раз в 1–2 с по 15–30 тыс. строк
  ([[06 ClickHouse]], раздел 5); через Kafka как буфер

Одновременность (закон Литтла):
  если обработка события 20 мс → 15 000 × 0,02 = 300 событий в обработке одновременно
```

**Пример: сколько серверов приложения**

```
Пик 6 000 RPS, один запрос = 15 мс CPU
CPU-секунд в секунду = 6 000 × 0,015 = 90 ядер загружено
Целевая утилизация 60 % (запас на пики, GC, деградацию) → 90 / 0,6 = 150 ядер
Под по 4 ядра → 38 подов; + N+1/N+2 на отказ зоны → ~45
```

## 19. Числа задержек, которые нужно знать (порядки)

| Операция | Время |
|----------|-------|
| обращение к L1-кэшу CPU | ~1 нс |
| обращение к RAM | ~100 нс |
| сжатие 1 КБ (быстрый кодек) | ~2 мкс |
| системный вызов, context switch | ~1–5 мкс |
| чтение 4 КБ с NVMe | ~20–100 мкс |
| RTT внутри ЦОДа | ~0,2–0,5 мс |
| GET в Redis через сеть | ~0,2–0,5 мс |
| простой SELECT по индексу в PostgreSQL (включая сеть) | ~0,5–2 мс |
| fsync на хорошем SSD | ~0,1–1 мс |
| чтение 4 КБ с HDD (seek) | ~5–10 мс |
| RTT Москва — Санкт-Петербург | ~10 мс |
| TLS-рукопожатие с новым соединением | ~2–3 RTT + 1–2 мс CPU |
| RTT Москва — Владивосток | ~120 мс |

Из этой таблицы следует большинство архитектурных решений: кэш в памяти в 1000 раз быстрее сетевого запроса; каждый сетевой хоп — сотни микросекунд; межрегиональный синхронный вызов — сотни миллисекунд.

## 20. Масштабирование

- **Вертикальное (scale up)** — больше CPU/RAM на сервер. Просто, без изменений кода; потолок железа, одна точка отказа, дорого на верхних уровнях.
- **Горизонтальное (scale out)** — больше экземпляров. Требует, чтобы сервис был **stateless**: состояние (сессии, кэш, файлы) — во внешних хранилищах (Redis, БД, S3), а любой экземпляр может обработать любой запрос.
- **Что мешает горизонтальному масштабированию:** локальные сессии (sticky sessions), локальные файлы, in-memory кэши без инвалидации, единственная БД-мастер, глобальные блокировки, «синглтон»-задачи (cron в каждом экземпляре — дубли; нужен leader election или advisory lock — [[05 PostgreSQL]], раздел 17.6).
- **Закон Амдала:** если 10 % работы не параллелится, ускорение не больше чем в 10 раз при любом числе узлов. **Universal Scalability Law** добавляет накладные расходы на согласование (contention, coherency): после некоторой точки добавление узлов **уменьшает** throughput — это видно на НТ ступенчатым увеличением реплик.

## 21. Балансировка нагрузки

Уровни: DNS (GeoDNS между регионами) → L4 (IP/порт) → L7 (HTTP) → клиентская. Подробно алгоритмы, L4 vs L7, idle timeout и проблемы долгоживущих соединений — [[02 Сеть — пропускная способность, фаерволы, узкие места]], раздел 11.

Health checks: **liveness** (жив ли процесс) и **readiness** (готов ли принимать трафик: прогрет, соединения к БД есть). Ошибка — проверять в readiness внешние зависимости: упала БД → все поды не ready → полный отказ вместо частичной деградации.

## 22. Кэширование

### 22.1 Уровни

```
Браузер/клиент → CDN → API Gateway → кэш в памяти сервиса (Caffeine) → распределённый кэш (Redis) → БД (shared_buffers) → page cache ОС
```

### 22.2 Стратегии

| Стратегия | Как | Плюсы / минусы |
|-----------|-----|----------------|
| **Cache-aside** (lazy loading) | приложение: есть в кэше → вернуть; нет → прочитать из БД, положить в кэш | самая частая; первый запрос медленный, возможна несогласованность |
| **Read-through** | кэш сам загружает из БД при промахе | логика в кэш-слое |
| **Write-through** | запись в кэш и БД синхронно | кэш всегда актуален, запись медленнее |
| **Write-behind** | запись в кэш, в БД — асинхронно пачками | быстро, риск потери данных |
| **Refresh-ahead** | обновлять до истечения TTL | нет промахов для горячих ключей |

### 22.3 Проблемы кэша под нагрузкой

| Проблема | Что | Решение |
|----------|-----|---------|
| **Cache stampede** (dog-pile) | популярный ключ истёк → тысячи запросов одновременно идут в БД | блокировка на перезагрузку (single flight), refresh-ahead, вероятностное раннее обновление |
| **Cache penetration** | запросы несуществующих ключей всегда мимо кэша → в БД | кэшировать «нет данных», Bloom filter |
| **Cache avalanche** | много ключей истекает одновременно (поставлены одним TTL при старте) | джиттер TTL |
| **Холодный кэш** | после рестарта/деплоя — БД получает всю нагрузку | прогрев, постепенный ввод трафика |
| **Горячий ключ** | один ключ на одном шарде Redis | локальный кэш, реплицирование ключа |
| **Несогласованность** | данные изменили в БД, в кэше старые | инвалидация при записи, короткий TTL, события |

**На НТ:** hit rate кэша обязан соответствовать проду: тест по 100 одинаковым ID даст hit rate 100 % и нереально хорошие результаты. Тестовые данные должны иметь реалистичное распределение популярности (часто — Zipf: немного очень популярных ключей и длинный хвост).

## 23. Масштабирование хранения

| Подход | Что даёт | Цена |
|--------|---------|------|
| Индексы и оптимизация запросов | на порядки, бесплатно по инфраструктуре | — |
| Вертикальное масштабирование БД | просто | потолок |
| **Реплики чтения** | масштабирование чтения | лаг реплик, read-your-writes ([[05 PostgreSQL]], раздел 18) |
| Кэш перед БД | снижение нагрузки чтения | согласованность |
| **Партиционирование** (внутри одной БД) | управляемость больших таблиц, удаление старых данных | ключ в запросах |
| **Шардирование** (данные по разным серверам) | масштабирование записи и объёма | кросс-шардовые запросы и транзакции, перебалансировка, выбор ключа |
| CQRS + отдельные read-хранилища | разные хранилища под разные запросы | синхронизация |

**Ключ шардирования:**

- по хэшу ID (`hash(user_id) % N`) — равномерно, но диапазонные запросы идут во все шарды, а изменение N требует переноса почти всех данных → **consistent hashing** (переносится ~1/N);
- по диапазону (даты, алфавит) — диапазонные запросы локальны, но горячие шарды (все новые данные — в последнем);
- по сущности-владельцу (tenant_id, user_id) — все данные клиента на одном шарде, транзакции локальны; риск «китов» — огромных клиентов.

## 24. Очереди и асинхронная обработка

Когда использовать очередь между компонентами:

- сглаживание пиков (производитель быстрее потребителя в пике, в среднем — нет);
- долгие операции (отчёты, рассылки) не держат HTTP-запрос: `202 Accepted` + статус по ID;
- развязка сервисов и повтор при сбоях потребителя.

Что учитывать: семантика доставки (at-least-once → идемпотентность), порядок, DLQ для «ядовитых» сообщений, мониторинг lag, **backpressure** (ограничение длины очереди, иначе очередь растёт до исчерпания памяти/диска). Подробно — [[08 Kafka]].

**Закон Литтла для очереди:** если потребитель обрабатывает 1000 сообщений/с, а на вход идёт 1200/с, очередь растёт на 200/с = 720 000 в час, и время ожидания нового сообщения растёт линейно и бесконечно. Устойчивость возможна только когда **средняя** скорость обработки больше средней скорости поступления.

## 25. Согласованность

- **CAP:** при сетевом разделении выбрать согласованность (CP) или доступность (AP) — [[05 PostgreSQL]], раздел 18.6.
- **PACELC:** при разделении (P) — A или C; **иначе (E) — Latency или Consistency.** Даже без сбоев синхронная репликация (согласованность) стоит задержки. PostgreSQL с синхронной репликой — PC/EC, Cassandra — PA/EL.
- **Модели согласованности:**
  - **строгая (linearizability)** — каждое чтение видит последнюю запись;
  - **read-your-writes** — пользователь видит свои изменения;
  - **monotonic reads** — не видишь «откат во времени» при переключении между репликами;
  - **eventual consistency** — когда-нибудь все реплики сойдутся.
- **Кворумы** (Cassandra, etcd): N реплик, запись подтверждают W, чтение опрашивает R. `R + W > N` → чтение пересекается с последней записью. N=3, W=2, R=2.

## 26. Пример: проектирование системы приёма заявок

**Требования:** клиенты подают заявки через API (пик 2 000 заявок/с), каждая проходит проверки в 4 сервисах (документы, скоринг, антифрод, лимиты), ответ клиенту «принято» — < 300 мс p99, итоговый результат — в течение 5 минут, ни одна заявка не теряется, аудит всех шагов 3 года.

```
Клиент ──HTTPS──> API Gateway (аутентификация, rate limit)
              ──> Intake Service
                    1. валидация формата (синхронно, отклонить сразу с 400/422)
                    2. INSERT заявки (PENDING) + outbox в PostgreSQL одной транзакцией
                    3. ответ 202 Accepted + id заявки            ← p99 < 300 мс
              Outbox relay / Debezium ──> Kafka topic applications.created
              Оркестратор (Zeebe) стартует процесс на заявку:
                    задачи → воркеры: документы, скоринг, антифрод, лимиты (параллельно, где можно)
                    таймауты шагов, ретраи, компенсации, ручная обработка
              Результат ──> Kafka applications.decided ──> Notifications, статус в Intake
              Аудит: все события ──> ClickHouse (90 дней горячих, остальное — холодное хранилище)
              Статус для клиента: GET /applications/{id} (read-модель / кэш Redis)
```

**Оценка:**

```
Активных процессов (Литтл): 2 000/с × до 300 с = до 600 000 одновременно в оркестраторе
Jobs: 2 000 × 4 шага = 8 000 jobs/с на пике
Kafka: 2 000 событий/с × ~5 событий на заявку = 10 000 сообщений/с
PostgreSQL Intake: 2 000 INSERT/с + 2 000 outbox + обновления статусов → батчинг коммитов,
                   autovacuum на outbox, партиционирование по дате
Аудит: 10 000 событий/с × 2 КБ = 20 МБ/с ≈ 1,7 ТБ/сутки сырых → ClickHouse со сжатием
```

**Где искать узкие места на НТ:** fsync коммитов Intake; лаг outbox → Kafka; backpressure Zeebe и накопление jobs; самый медленный воркер (по закону Литтла — сколько его экземпляров нужно); пулы соединений воркеров к их БД; consumer lag на уведомлениях; рост числа частей в ClickHouse.

# Часть III. Производительность распределённых систем

## 27. Хвостовая задержка при fan-out

Если запрос пользователя параллельно вызывает N сервисов и ждёт **всех**, его latency = **максимум** из N.

```
Каждый сервис: 99 % запросов быстрее 100 мс (p99 = 100 мс), 1 % — медленные
Вероятность, что ВСЕ N ответят быстро = 0,99^N

N = 1   → 99 % запросов пользователя быстрые
N = 10  → 0,99^10 = 90,4 %   → почти 10 % запросов пользователя медленные
N = 100 → 0,99^100 = 36,6 %  → большинство медленные!
```

**Вывод:** p99 отдельного сервиса становится **медианой** для запроса с большим fan-out. Поэтому в микросервисах важны p99/p99.9 каждого компонента, а не среднее.

Методы борьбы: уменьшать fan-out, **hedged requests** (через p95 отправить дубликат запроса в другую реплику, взять первый ответ), таймауты с частичным результатом, кэширование.

## 28. Бюджет задержки и сетевые хопы

```
SLO: p99 < 300 мс
Клиент → Gateway (TLS, JWT)          10 мс
Gateway → BFF                         2 мс
BFF → 3 сервиса параллельно          120 мс (p99 самого медленного с учётом fan-out)
Каждый сервис → БД (2 запроса)        10 мс
Сериализация/десериализация на 4 хопах 8 мс
Запас на GC-паузы, ретраи, очереди    ~150 мс
```

Каждый синхронный хоп добавляет: сеть (0,2–0,5 мс), сериализацию, пул соединений, sidecar (если mesh), и **свой хвост**. Цепочка из 6 синхронных вызовов «вглубь» почти гарантированно не уложится в жёсткий SLO по p99.

## 29. Где искать узкие места в микросервисах

```
1. Трассировка: какой span занимает время на медленных запросах (не средних!)
2. Разделить: работа внутри сервиса vs ожидание (пулы, сеть, зависимость)
3. Закон Литтла на каждом пуле: concurrency = RPS × latency зависимости → хватает ли пула?
4. Ресурсы сервиса (CPU, throttling, GC) — [[10 JVM]], [[11 Go]], [[12 Python]], [[13 Kubernetes, OpenShift, Docker]]
5. Хранилища каждого сервиса — [[05 PostgreSQL]], [[07 Redis]], [[06 ClickHouse]]
6. Асинхронные части: consumer lag, backpressure оркестратора — [[08 Kafka]], [[09 Camunda Zeebe]]
7. Сеть между сервисами: ретрансмиссии, DNS, conntrack, L4-балансировка — [[02 Сеть — пропускная способность, фаерволы, узкие места]]
8. Поведение при отказе: убить под/зависимость под нагрузкой — сработали ли таймауты,
   circuit breaker, не начался ли retry storm, сколько ошибок при деплое (graceful shutdown)
```

## 30. Шпаргалка

| Паттерн | Одной строкой | Главный риск |
|---------|---------------|--------------|
| API Gateway | единая точка входа: маршрутизация, аутентификация, rate limit, кэш | единая точка отказа, лишний хоп, узкое место по CPU |
| Service Discovery | сервисы находят друг друга по имени через реестр/DNS | запаздывание обновлений, ошибки при деплое |
| BFF | отдельный бэкенд под каждый тип клиента | дублирование логики |
| Event-Driven | обмен событиями через брокер | eventual consistency, отладка, дубли |
| CQRS | раздельные модели записи и чтения | лаг read-модели |
| Database-per-Service | каждый сервис владеет своими данными | синхронизация, распределённые транзакции |
| Saga | цепочка локальных транзакций + компенсации | нет изоляции, идемпотентность |
| Оркестрация | центральный координатор процесса (Camunda) | центральная зависимость |
| Хореография | процесс из реакций на события | процесс нигде не виден целиком |
| Outbox | событие пишется в БД в той же транзакции | bloat таблицы, at-least-once |
| Circuit Breaker | не вызывать больную зависимость | неверные пороги |
| Bulkhead | отдельные пулы на зависимости | — |
| Service Mesh | прокси рядом с каждым сервисом | latency и ресурсы sidecar |

```
Доступность последовательных зависимостей перемножается: 0,999^5 = 99,5 %
Fan-out: P(все быстрые) = p^N → 0,99^100 = 37 %
Литтл: concurrency = RPS × latency
1 млн/день ≈ 12 RPS; пик = среднее × 2–5
```
