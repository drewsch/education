## 1. Три понятия

| Понятие | Вопрос | Пример |
|---------|--------|--------|
| **Аутентификация** (authentication, AuthN) | **кто** ты? | логин и пароль, сертификат, токен |
| **Авторизация** (authorization, AuthZ) | **что** тебе можно? | роль `ADMIN`, scope `orders:read`, доступ только к своим заказам |
| **Учёт** (accounting/audit) | **что** ты сделал? | журнал действий |

HTTP-коды: `401 Unauthorized` — на самом деле «не аутентифицирован» (нет или неверный токен), `403 Forbidden` — «аутентифицирован, но прав нет».

## 2. Способы аутентификации

| Способ | Как работает | Плюсы | Минусы |
|--------|-------------|-------|--------|
| Basic | `Authorization: Basic base64(login:password)` в каждом запросе | просто | пароль в каждом запросе; base64 — не шифрование, только с TLS; сервер проверяет пароль на каждый запрос (дорогой хэш!) |
| Сессия + cookie | логин → сервер создаёт сессию, отдаёт cookie с её ID | отзыв мгновенный, маленькая cookie | состояние на сервере (общее хранилище для кластера), CSRF |
| Bearer-токен (JWT) | `Authorization: Bearer <JWT>` | без состояния, проверка локально | отозвать до истечения сложно, большой размер |
| Bearer-токен (opaque) | случайная строка, данные — у сервера авторизации | легко отозвать | проверка = запрос к серверу авторизации или кэшу |
| API-ключ | `X-API-Key: ...` | просто для машин | долгоживущий секрет, обычно без пользователя |
| HMAC-подпись | подпись запроса секретом (как AWS SigV4) | секрет не передаётся, защита от изменения запроса | сложнее реализация, синхронизация времени |
| mTLS | клиентский сертификат в TLS | сильная аутентификация машин | управление сертификатами, ротация |
| Kerberos / SPNEGO | билеты от KDC (Active Directory) | SSO в корпоративной сети | сложная инфраструктура |

## 3. Сессии на сервере vs токены

```
Сессия (stateful):
  1. POST /login → сервер проверяет пароль → создаёт сессию {user: 42, roles: [...]} в памяти/Redis
  2. Ответ: Set-Cookie: SESSION=8f3a9c...; HttpOnly; Secure; SameSite=Lax
  3. Каждый запрос: браузер шлёт cookie → сервер ищет сессию по ID → знает пользователя

JWT (stateless):
  1. POST /login → сервер проверяет пароль → выпускает подписанный токен {sub: 42, roles: [...], exp: ...}
  2. Ответ: {"access_token": "eyJ..."}
  3. Каждый запрос: Authorization: Bearer eyJ... → сервер проверяет подпись → знает пользователя
     без обращения к хранилищу
```

| | Сессия | JWT |
|---|---|---|
| Где состояние | на сервере (Redis, БД) | в самом токене |
| Проверка | поиск в хранилище (сеть, ~0,2–1 мс) | криптографическая проверка подписи (CPU, десятки мкс) |
| Масштабирование | нужно общее хранилище сессий или sticky sessions | любой инстанс проверяет сам |
| Отзыв | удалить сессию — мгновенно | сложно: токен валиден до `exp` |
| Размер | ID 32–64 байта | 500 байт – несколько КБ |
| Для НТ | нагрузка на хранилище сессий | нагрузка на CPU (проверка подписи) и сеть (размер заголовка) |

## 4. JWT

### 4.1 Устройство

JWT = три части в base64url через точку: `header.payload.signature`.

```
eyJhbGciOiJSUzI1NiIsImtpZCI6ImtleS0yMDI2In0     ← header
.eyJzdWIiOiI0MiIsImlzcyI6Imh0dHBzOi8vYXV0aC...  ← payload (claims)
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c    ← подпись
```

Header:

```json
{ "alg": "RS256", "typ": "JWT", "kid": "key-2026" }
```

Payload (claims):

```json
{
  "iss": "https://auth.example.com",     // кто выпустил
  "sub": "42",                           // кто субъект (пользователь)
  "aud": "orders-api",                   // для кого предназначен
  "exp": 1792327200,                     // истекает (Unix-время)
  "iat": 1792326300,                     // выпущен
  "nbf": 1792326300,                     // не раньше
  "jti": "c1a7e2...",                    // уникальный ID токена (для отзыва/защиты от повтора)
  "scope": "orders:read orders:write",
  "roles": ["operator"]
}
```

⚠️ **Payload не зашифрован**, только закодирован base64url — любой может его прочитать. Нельзя класть туда секреты и персональные данные. (Зашифрованный вариант — JWE, используется редко.)

### 4.2 Подпись

| Алгоритм | Тип | Ключ | Кто может проверить |
|----------|-----|------|---------------------|
| `HS256` | HMAC-SHA256, симметричный | один общий секрет | только тот, у кого секрет — он же может и **выпустить** токен |
| `RS256` | RSA-SHA256, асимметричный | закрытый ключ подписывает, открытый проверяет | любой сервис с открытым ключом; выпустить может только сервер авторизации |
| `ES256` | ECDSA P-256, асимметричный | то же | то же; ключи и подписи меньше |
| `EdDSA` (Ed25519) | асимметричный | то же | быстрый, компактный |

В микросервисах — асимметричные алгоритмы: сервисы получают открытые ключи и не могут подделать токен.

### 4.3 JWKS — публикация открытых ключей

Сервер авторизации публикует открытые ключи по адресу `https://auth.example.com/.well-known/jwks.json`:

```json
{ "keys": [ { "kid": "key-2026", "kty": "RSA", "alg": "RS256", "n": "...", "e": "AQAB" } ] }
```

Сервис при проверке берёт `kid` из заголовка токена и ищет ключ в JWKS. **JWKS кэшируется** (на минуты–часы); при неизвестном `kid` (ротация ключей) — перезагружается.

### 4.4 Проверка JWT — полный список

1. Разобрать токен, проверить формат.
2. `alg` — только из **разрешённого списка** сервера (не верить заголовку токена: атака `alg: none` и подмена RS256 → HS256 с открытым ключом как секретом).
3. Найти ключ по `kid`, проверить **подпись**.
4. `exp` — не истёк (с допуском на рассинхрон часов, clock skew, обычно 30–60 с).
5. `nbf`, `iat` — не из будущего.
6. `iss` — ожидаемый издатель.
7. `aud` — токен выпущен **для этого** сервиса (иначе токен одного сервиса подходит к другому).
8. Авторизация: `scope`/`roles` позволяют операцию.
9. Опционально: `jti` не в чёрном списке (отзыв).

## 5. Access и refresh токены

```
POST /token (логин)
  → access_token  (JWT, живёт 5–15 минут)  — для вызовов API
  → refresh_token (живёт часы–недели)        — только для получения нового access_token

Через 15 минут API отвечает 401 (истёк)
  → клиент: POST /token grant_type=refresh_token → новый access_token (+ часто новый refresh_token)
```

**Зачем два токена:**

- короткий access token ограничивает ущерб при утечке и решает проблему отзыва JWT (живёт недолго);
- refresh token хранится аккуратнее, отправляется только серверу авторизации и **может быть отозван** (он проверяется по базе при каждом использовании).

**Refresh token rotation:** каждый refresh выдаёт новый refresh token, старый становится недействительным. Если старый кто-то использовал повторно — признак кражи, отзываем всю цепочку.

**Отзыв JWT до истечения:**

- короткий срок жизни (основной способ);
- чёрный список `jti` в Redis до момента `exp` (возвращает состояние — проверка на каждый запрос);
- «версия токенов» пользователя: при выходе/смене пароля увеличить `token_version` → токены со старой версией отклоняются;
- для мгновенного отзыва — opaque-токены.

## 6. Opaque-токены и introspection

**Opaque-токен** — случайная строка без смысла (`2YotnFZFEjr1zCsicMWpAA`). Чтобы понять, кто владелец, сервис спрашивает сервер авторизации (**token introspection**, RFC 7662):

```
POST /introspect  token=2YotnFZ...
→ {"active": true, "sub": "42", "scope": "orders:read", "exp": 1792327200}
```

| | JWT | Opaque + introspection |
|---|---|---|
| Проверка | локально, CPU | сетевой вызов (или кэш) |
| Отзыв | сложно | мгновенно |
| Утечка данных из токена | payload читается | ничего не видно |
| Нагрузка на сервер авторизации | только выдача | **каждый запрос** (без кэша) |

На НТ с opaque-токенами сервер авторизации часто становится узким местом: 10 000 RPS API = 10 000 RPS introspection. Решения: кэш результата introspection на время жизни токена (с учётом отзыва), или переход на JWT внутри периметра (паттерн «phantom token»: снаружи opaque, gateway обменивает на JWT).

## 7. OAuth 2.0

### 7.1 Роли

- **Resource Owner** — пользователь, владелец данных;
- **Client** — приложение, которое хочет доступ (веб, мобильное, сервис);
- **Authorization Server** — выдаёт токены (Keycloak, Okta, Auth0, ADFS);
- **Resource Server** — API, которое принимает токены.

OAuth 2.0 — протокол **авторизации** (делегирования доступа): «разрешить приложению читать мои заказы», а не «кто я». Аутентификацию добавляет OIDC (раздел 8).

### 7.2 Потоки (grant types)

**Authorization Code + PKCE** — для пользователей (веб, мобильные, SPA). Стандарт сейчас.

```
1. Клиент генерирует code_verifier (случайная строка) и code_challenge = SHA256(code_verifier)
2. Браузер → Authorization Server: /authorize?response_type=code&client_id=..&redirect_uri=..
                                   &scope=..&state=..&code_challenge=..&code_challenge_method=S256
3. Пользователь логинится, соглашается
4. Redirect → redirect_uri?code=AUTH_CODE&state=..
5. Клиент (сервер или приложение) → POST /token  code=AUTH_CODE, code_verifier=..
6. Authorization Server проверяет SHA256(code_verifier) == code_challenge → выдаёт токены
```

PKCE защищает от перехвата кода: без `code_verifier` код бесполезен.

**Client Credentials** — сервис к сервису, без пользователя:

```
POST /token
  grant_type=client_credentials&client_id=billing&client_secret=...&scope=orders:read
→ access_token
```

Сервис должен **кэшировать** токен до истечения и обновлять заранее, а не запрашивать новый на каждый вызов (частая ошибка — и источник нагрузки на сервер авторизации).

**Refresh Token** — обмен refresh на новый access (раздел 5).

**Device Code** — для устройств без браузера (ТВ, CLI): показывают код, пользователь вводит его на другом устройстве.

**Token Exchange** (RFC 8693) — сервис обменивает токен пользователя на токен для вызова следующего сервиса (с другим `aud`, урезанными правами).

**Устаревшие и не рекомендуемые:** Implicit (токен в URL — утечки через историю/referer), Resource Owner Password Credentials (приложение получает пароль пользователя). В OAuth 2.1 их убрали.

### 7.3 Scope

Scope — права, которые клиент запрашивает и пользователь одобряет: `orders:read`, `orders:write`, `profile`. Resource Server проверяет, что scope токена покрывает операцию.

## 8. OpenID Connect (OIDC)

Надстройка над OAuth 2.0 для **аутентификации**:

- scope `openid` → кроме access token выдаётся **ID Token** — JWT о пользователе (`sub`, `name`, `email`, `auth_time`, `nonce`) для **клиента**, а не для API;
- endpoint `/userinfo` — профиль пользователя;
- discovery: `/.well-known/openid-configuration` — адреса всех endpoint-ов, JWKS, поддерживаемые алгоритмы.

**Не путать:** ID Token — «кто вошёл» (для клиентского приложения); Access Token — «что можно» (для API). Отправлять ID Token в API как access token — ошибка.

## 9. API-ключи и HMAC

**API-ключ** — долгоживущий секрет приложения. Хранить на сервере не сам ключ, а его хэш (как пароль), но **быстрый** (SHA-256), а не bcrypt — ключи длинные и случайные, перебор не грозит, а проверка идёт на каждый запрос.

**HMAC-подпись запроса** (пример — AWS Signature V4):

```
строка = METHOD + "\n" + path + "\n" + query + "\n" + хэш(тело) + "\n" + timestamp
подпись = HMAC-SHA256(секрет, строка)
Заголовки: X-Timestamp, X-Signature
Сервер вычисляет так же и сравнивает; timestamp старше 5 минут — отклоняет (защита от повтора)
```

Секрет не передаётся по сети, изменение запроса по пути ломает подпись.

## 10. mTLS и привязанные токены

- **mTLS** — сервер требует клиентский сертификат; аутентифицирует **машину/сервис**. В service mesh (Istio) каждый под получает короткоживущий сертификат с идентичностью (SPIFFE ID `spiffe://cluster/ns/orders/sa/orders-api`), ротация автоматическая.
- **Certificate-bound tokens** (RFC 8705): в токен записан отпечаток сертификата клиента (`cnf.x5t#S256`) → украденный токен бесполезен без закрытого ключа.
- **DPoP** — аналог без TLS-сертификатов: клиент подписывает каждый запрос своим ключом.

Стоимость mTLS: дополнительная проверка цепочки клиентского сертификата при каждом **новом** соединении; при keep-alive — почти бесплатно.

***

## 11. Kerberos, SAML, LDAP — коротко

- **LDAP** — протокол каталога (Active Directory, OpenLDAP); часто «аутентификация через LDAP bind» — проверка пароля обращением к каталогу. На НТ: каждый логин → запрос в AD; AD может стать узким местом и блокировать учётки за множество попыток.
- **Kerberos** — билеты от KDC: пользователь получает TGT при входе в домен, потом билеты к сервисам без повторного ввода пароля. В HTTP — SPNEGO (`Authorization: Negotiate ...`). Чувствителен к рассинхрону часов (±5 мин).
- **SAML 2.0** — XML-протокол SSO для корпоративных веб-приложений; утверждения (assertions) подписаны XML-подписью; тяжёлый по CPU (разбор и проверка XML).

## 12. Токены в микросервисах

```
Клиент ──Bearer JWT──> API Gateway ──> Сервис A ──> Сервис B
```

**Где проверять:**

| Подход | Описание | Плюсы | Минусы |
|--------|----------|-------|--------|
| Только на gateway | gateway проверяет токен, внутрь передаёт заголовки `X-User-Id` | внутри дёшево | внутренние сервисы доверяют сети; любой внутри может подделать заголовок |
| Gateway + каждый сервис | токен передаётся дальше, каждый сервис проверяет подпись (JWKS кэширован) | zero trust | CPU на проверку в каждом хопе (обычно копейки) |
| Token exchange | на каждом хопе токен с нужным `aud` и урезанными правами | минимум прав | вызов сервера авторизации (кэшировать) |
| mTLS между сервисами + JWT пользователя | идентичность сервиса + пользователя | сильная модель | сложность инфраструктуры |

**Размер токена и заголовков:** JWT с десятками ролей разрастается до 4–8 КБ. Многие прокси ограничивают размер заголовков (nginx `large_client_header_buffers` по умолчанию 8 КБ на строку → `400 Request Header Or Cookie Too Large`; Tomcat `maxHttpHeaderSize` 8 КБ). Плюс каждый запрос несёт эти килобайты по сети — при HTTP/1.1 без сжатия заголовков это заметный трафик.

## 13. Производительность: сколько стоит аутентификация

### 13.1 Порядки величин (одно ядро, ориентировочно)

| Операция | Время | Операций/с на ядро |
|----------|-------|-------------------|
| Проверка JWT HS256 | ~2–5 мкс | сотни тысяч |
| Проверка JWT RS256 (RSA-2048, проверка подписи дешёвая) | ~20–50 мкс | 20–50 тысяч |
| **Подпись** RS256 (выдача токена) | ~1–2 мс | ~500–1000 |
| Проверка ES256 | ~50–100 мкс | 10–20 тысяч |
| Подпись ES256 | ~20–50 мкс | десятки тысяч |
| Проверка пароля bcrypt cost=10 | **~50–100 мс** | **10–20** |
| Проверка пароля Argon2id (рекомендуемые параметры) | ~50–500 мс, + память | единицы–десятки |
| Introspection / поиск сессии в Redis | ~0,2–1 мс (сеть) | ограничено сервером авторизации/Redis |

### 13.2 Выводы

- **Логин дорогой намеренно**: хэш пароля (bcrypt/argon2/PBKDF2) специально медленный, чтобы затруднить перебор. 8 ядер × 15 bcrypt-проверок/с = **~120 логинов в секунду** на весь сервер аутентификации. Сценарий НТ «каждый виртуальный пользователь логинится перед каждым запросом» положит сервер аутентификации и покажет нереалистичную картину.
- **Выдача RS256-токенов** — тоже CPU-ёмкая (подпись RSA). Сервер авторизации при массовом логине/refresh упирается в CPU.
- **Проверка JWT** — дёшево, если JWKS **кэширован**. Ошибка: загружать JWKS при каждой проверке → каждый запрос API = HTTP-вызов к серверу авторизации.
- **Introspection без кэша** = сервер авторизации на пути каждого запроса.
- **Сессии в Redis** — каждый запрос = обращение к Redis; при 50 000 RPS это 50 000 оп/с на Redis и RTT в latency.

### 13.3 Метрики, которые стоит смотреть

- RPS и latency endpoint-ов `/token`, `/introspect`, `/userinfo`, `/.well-known/jwks.json` сервера авторизации;
- CPU сервера авторизации (Keycloak — Java: профиль покажет bcrypt/PBKDF2 и RSA);
- доля ответов `401` на API под нагрузкой (истекающие токены в скрипте НТ);
- частота обновления JWKS;
- у Keycloak: число активных сессий (хранятся в Infinispan-кэше — память, репликация между узлами).

## 14. Токены в нагрузочном тестировании

1. **Не логиниться на каждый запрос.** Получить токены заранее (setup/`on_start` в Locust) или пулом, переиспользовать до истечения.
2. **Обновлять до истечения.** Тест длиной 2 часа, токен живёт 15 минут → без refresh через 15 минут все запросы получат `401`, и тест «станет быстрее» (отказ дешевле работы). Проверять долю `401`.
3. **Реалистичное число пользователей.** Если в проде 10 000 разных пользователей, а в тесте один токен на всех — кэши по пользователю (права, профиль) всегда горячие, а rate limit по пользователю сработает. Готовить пул тестовых учёток.
4. **Отдельный сценарий на сам сервер авторизации:** логины, refresh, introspection — с реальной долей от общей нагрузки (например, 1 логин на 200 запросов API).
5. **Срок жизни и смещение часов:** генератор и сервер с разным временем → токены «из будущего» (`nbf`/`iat`) отклоняются.
6. **Не хранить реальные секреты в репозитории скриптов НТ** — переменные CI, хранилище секретов.

```python
# Locust: токен на пользователя, обновление заранее
import time
from locust import FastHttpUser, task, between

class ApiUser(FastHttpUser):
    wait_time = between(0.5, 1.5)

    def on_start(self):
        self.creds = next_test_account()   # пул тестовых учёток
        self._login()

    def _login(self):
        r = self.client.post("/auth/token", json=self.creds, name="auth:token")
        body = r.json()
        self.token = body["access_token"]
        self.refresh = body["refresh_token"]
        self.expires_at = time.time() + body["expires_in"] - 60   # обновить за минуту до истечения

    def _ensure_token(self):
        if time.time() >= self.expires_at:
            r = self.client.post("/auth/refresh", json={"refresh_token": self.refresh}, name="auth:refresh")
            if r.status_code == 200:
                body = r.json()
                self.token, self.refresh = body["access_token"], body.get("refresh_token", self.refresh)
                self.expires_at = time.time() + body["expires_in"] - 60
            else:
                self._login()

    @task
    def get_orders(self):
        self._ensure_token()
        self.client.get("/api/orders", headers={"Authorization": f"Bearer {self.token}"}, name="orders:list")
```

## 15. Типичные уязвимости и ошибки

| Ошибка | Чем опасна |
|--------|-----------|
| Принимать `alg` из заголовка токена (`none`, HS256 вместо RS256) | подделка токенов |
| Не проверять `aud` | токен одного сервиса принимается другим |
| Не проверять `exp`/`iss` | вечные или чужие токены |
| Секреты/персональные данные в payload JWT | утечка — payload читается кем угодно |
| JWT в `localStorage` браузера | кража через XSS; безопаснее HttpOnly-cookie + защита от CSRF |
| Токены в URL (`?access_token=`) | попадают в логи, историю, referer |
| Долгоживущие access-токены без отзыва | утечка = долгий доступ |
| Логирование заголовка `Authorization` | токены в логах и системах сбора логов |
| Слабый `HS256`-секрет | перебор офлайн |
| Нет rate limit на `/login` | перебор паролей; с другой стороны — DoS дорогим bcrypt |

## 16. Шпаргалка

```
401 — не аутентифицирован; 403 — нет прав
JWT = header.payload.signature (base64url), payload НЕ зашифрован
RS256/ES256 — асимметрично: сервер авторизации подписывает, сервисы проверяют по JWKS
Проверять: alg (whitelist), подпись (kid → JWKS), exp/nbf, iss, aud, scope
Access 5–15 мин + refresh (rotation); отзыв JWT — короткий срок, blacklist jti, версия токенов
Opaque → introspection → нагрузка на сервер авторизации (кэшировать)
OAuth 2.0: Authorization Code + PKCE (пользователи), Client Credentials (сервисы)
OIDC: ID Token — для клиента, Access Token — для API
Логин дорогой (bcrypt ~50–100 мс CPU) → не логиниться на каждый запрос в НТ
Проверка JWT дешёвая, если JWKS кэширован
```
